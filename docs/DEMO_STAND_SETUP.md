## Репетиция основных разделов до передачи в банк — 23.11.2026

Для показа Бэклога без ИИ предусмотрен отдельный изолированный профиль
[compose.demo-core.yaml](../compose.demo-core.yaml) и
[rehearse-demo-core.py](../scripts/rehearse-demo-core.py). Это проверочный стенд:
собственные PostgreSQL/Redis/тома, синтетические записи, два backend с
`DEBUG=false`, настоящий lifespan, Nginx HTTPS, Collector и ClamAV. Рабочие
БД и тома к нему не подключаются. Требуются Docker Compose, Python-окружение
проекта и установленные Playwright/Chromium из `dmb-backlog`.

```powershell
.\.venv\Scripts\python.exe scripts/rehearse-demo-core.py
```

Проверка создаёт временный CA только для своего адреса `https://127.0.0.1:8443`;
системное доверие сертификатам не меняется. Она включает bootstrap/активацию,
вход и refresh, браузерные действия со справочником и задачей, две вкладки,
проверку вложений настоящим ClamAV, запрет действий наблюдателю, два естественных
истечения access, перезапуск, обновление заполненной старой схемы и восстановление
backup в другую БД. Первый запуск ClamAV требует загрузки сигнатур и может быть
долгим. Для закрытого контура образы и актуальные сигнатуры нужно доставить заранее.

Безопасный отчёт с результатами и ID образа находится в игнорируемом
`.test-rehearsal-*/report.json`. В том же каталоге есть тестовые секреты и
закрытый TLS-ключ: каталог целиком не переносить, не публиковать и не добавлять
в Git. По умолчанию свои контейнеры и тома удаляются даже при ошибке. `--keep`
оставляет только этот стенд для диагностики. `--skip-natural-expiry` даёт
диагностический прогон, который не подтверждает естественное обновление токена.

Новый `AGENT_READINESS_REQUIRED=false` отключает только обязательность readiness
ИИ-агента. По умолчанию он `true`; полный production-профиль сохраняет прежнее
поведение. В профиле репетиции также выключены Prioritiser, V2, scheduler и
обработка встреч; сервис авторизации и проверки полномочий работают штатно.

Dockerfile использует отдельный хэшированный `backend/requirements-linux.lock`:
Windows lock не содержит обязательный для `uvicorn[standard]` Linux-пакет
`uvloop`. Общие версии двух lock-файлов сохранены. Linux lock генерируется
`pip-tools==7.5.2` в Python 3.12 Linux из `requirements.txt` с ограничениями
`--constraint=requirements.lock --generate-hashes`; менять его нужно в Linux
и затем проверять настоящей сборкой и `python -m pip check` внутри образа.

## Адрес и конфигурация

Браузер должен получать интерфейс и API с одного внешнего HTTPS origin:
например, `https://dmb.example.internal`, `/static/...` и `/api/v1/...`.
Внутренний Nginx также сохраняет внешний `Host` вместе с портом и доверенный
`X-Forwarded-Proto`: иначе slash-redirect API выдаёт HTTP/неверный порт за HTTPS
ingress. Внешний ingress должен сам перезаписывать `X-Forwarded-Proto` клиента;
HTTP listener приложения доступен только ему/loopback. При приёмке проверить
`Location` перенаправления `/api/v1/timeline?year=2026`: origin должен совпадать
с внешним HTTPS origin стенда. Конфигурация проверена 23.11.2026.

Прокси сохраняет `Authorization`, `Origin`, `Cookie` и `Set-Cookie`, не меняет
префикс `/api/v1/auth`. Cookie `dmb_refresh`: HttpOnly, Secure, SameSite=Strict,
path `/api/v1/auth`. Сам access JWT передаётся в заголовке Bearer и живёт 5 минут.
Один начальный 401 при истёкшем access допустим, если refresh и повтор дают 200.

В защищённом env-файле для [production Compose](../compose.production.yaml)
наряду с БД, Redis и остальными полями
[шаблона](../.env.production.example) задать:

```dotenv
DMB_CORS_ORIGINS=["https://dmb.example.internal"]
DMB_AUTH_ORIGINS=["https://dmb.example.internal"]
DMB_AUTH_ALLOWED_HOSTS=["dmb.example.internal","localhost","127.0.0.1","backend"]
DMB_AUTH_RATE_HMAC_KEY=<отдельный секрет длиной не менее 32 символов>
```

В `AUTH_ORIGINS` указывается точный внешний origin, включая нестандартный порт,
без завершающего `/`. В `AUTH_ALLOWED_HOSTS` — имена хостов без схемы и порта.
При запуске без Compose используются имена переменных без префикса `DMB_`.
У всех backend-реплик одинаковые `SECRET_KEY`, `AUTH_ISSUER`, `AUTH_AUDIENCE`,
БД и Redis. `AUTH_RATE_HMAC_KEY` отличается от `SECRET_KEY`. В Redis должен
работать атомарный limiter: при его недоступности вход возвращает 503.

Обычный запуск не создаёт учётки/команды/справочники. Не запускать `seed.py`
и не включать `RUN_STARTUP_SEED`/`RUN_STARTUP_MAINTENANCE`.
Полная существующая топология с агентами описана в
[production runbook](PRODUCTION_RUNBOOK.md); этот документ не меняет состав
агентов и внешние зависимости readiness полного production-профиля.

## Обновление кода и схемы

Перед обновлением сохранить согласованный backup БД и вложений; остановить
изменяющие запросы на время миграции и согласования справочников. Не заменять
рабочую БД пустой и не перезаписывать её демонстрационным набором.

Из каталога `dmb-backlog/backend`, в окружении именно целевого backend:

```sh
python -m alembic upgrade head
python -m alembic current
python account_operator.py reference-report
```

Новая ревизия — `d352a19c40e8`. Она добавляет nullable `reference_id` и уникальность
пары `(dict_type, reference_id)` в `dictionary_items`; сама миграция не меняет
защищённые записи. Alembic-конфигурация теперь разрешается относительно своего
файла и поддерживает запуск из другого каталога с `-c`.

Для Compose команды ниже можно выполнять в интерактивном одноразовом backend:

```sh
docker compose --env-file /secure/dmb-production.env -f compose.production.yaml run --rm --no-deps backend python account_operator.py reference-report
```

Рабочий env-файл хранится вне Git. Команды `account_operator.py` с `--apply`
требуют интерактивную защищённую консоль и непустой `--reason`.
Не использовать `-T`, pipeline или запись терминала при выдаче приглашения.

## Уже заполненный стенд

После просмотра `reference-report` явно согласовать связывание справочников:

```sh
python account_operator.py reconcile-references --reason DEMO-DEPLOY-001 --apply
python account_operator.py reference-report
```

Команда связывает административные значения с типизированными таблицами
`priorities`, `statuses`, `task_types`, `channels`, `deadlines`, `team_types`,
`project_statuses`. Существующие ID и ссылки задач/команд/проектов сохраняются.
Для значений только в типизированных таблицах добавляется административное
представление. Для значений только в редакторе создаётся типизированная запись.
Повторный запуск не создаёт копии. При неоднозначном совпадении кода/названия
команда возвращает 409, вся транзакция откатывается; автоматически выбирать
один из дубликатов нельзя. Устранить неоднозначность по согласованным данным
и повторить. Нулевое число `unbound_rows` — необходимая проверка после операции.

Для исправления прав **одной согласованной существующей учётки**:

```sh
python account_operator.py configure-admin-access --user-id 123 --reason DEMO-ADMIN-001 --apply
```

Вместо `123` указать проверенный ID. Команда назначает этому пользователю
отдельную роль с полным административным и рабочим доступом. Общая прежняя
роль и другие пользователи не меняются; логин, пароль и команда сохраняются.
Сессии и текущие подтверждения выбранной учётки отзываются: после операции
нужно войти заново. Неактивная/неизвестная учётка отклоняется. Это явная выдача
полномочий оператором, а не автоматическая починка при входе.

Если существующая учётка ещё не готова ко входу, после проверки назначения
доступна прежняя операция `recover-admin --user-id ID --reason CHANGE-ID --apply`:
она выдаёт новое приглашение и сбрасывает прежний пароль. Использовать её
только при отдельной необходимости восстановления, не вместо сохранения
работающего пароля.

## Новый пустой стенд

Создать первого администратора без правки SQL:

```sh
python account_operator.py bootstrap-admin --login demo.admin --name "Администратор демонстрации" --reason DEMO-FIRST-001 --apply
```

Для **новой отдельной демонстрационной БД** можно добавить `--demo-data`:

```sh
python account_operator.py bootstrap-admin --login demo.admin --name "Администратор демонстрации" --demo-data --reason DEMO-FIRST-001 --apply
```

Первый вариант создаёт только администратора, отдельную полную роль и одноразовое
приглашение. Второй дополнительно создаёт небольшой синтетический набор:
приоритеты, статусы, типы задач, каналы, срок «БЕЗ СРОКА», тип команды, статус
проекта, одну команду, проект и пример задачи. У администратора назначена эта
демонстрационная команда. Пользовательские/банковские снимки не используются.

При наличии любого пользователя или резервирования логина bootstrap отклоняется.
Режим `--demo-data` также отклоняется при заполненных рабочих таблицах или
справочниках. Повторный запуск ничего не перезаписывает. Пароля по умолчанию нет.

Одноразовый код выводится только после успешного commit. В браузере открыть
`https://dmb.example.internal/#/activate`, ввести код и самостоятельно задать
пароль по действующей политике. Затем выполнить обычный вход. Код не включать
в лог, Git, протокол или снимок экрана; при потере использовать операторское
восстановление уже созданного администратора.

## Проверка внутри банковского контура

Скрипт [stand_smoke.py](../dmb-backlog/backend/stand_smoke.py) использует только
стандартную библиотеку Python. Запускается на компьютере, которому доступны
внешний HTTPS URL и доверенный сертификат банка:

```sh
python stand_smoke.py --base-url https://dmb.example.internal --login demo.admin --expect-admin --output demo-smoke.json
```

Если CA банка не установлен в системное хранилище Python, добавить
`--ca-file /secure/bank-ca.pem`. Проверку TLS отключить нельзя. Пароль вводится
скрыто и не передаётся в аргументах. Скрипт не следует редиректам.

Для проверки действительного истечения access добавить `--wait-access-expiry`:
скрипт подождёт один срок access (обычно пять минут), проверит 401 старого токена,
обновит сессию по реальной cookie и повторит чтение.

Отчёт содержит только пути, HTTP-статусы, количества справочников и результат.
Пароли, access/refresh, cookie и содержимое профилей в него не попадают.
Скрипт создаёт/завершает свою сессию, но не меняет рабочие записи, пользователей,
роли, назначения и справочники. Проверяет `/auth/me`, административные списки,
справочники, атрибуты cookie, refresh и logout. Это API-проверка: для браузера
дополнительно пройти следующие действия.

1. Войти и открыть все административные вкладки нужного профиля.
2. Добавить согласованное значение справочника, открыть форму новой задачи и
   убедиться, что значение выбирается. Сохранить задачу и открыть её повторно.
3. Переименовать значение: существующая задача сохраняет связь и новое название.
   Архивировать значение: оно исчезает из новых вариантов выбора, прежние связи
   остаются. Восстановить значение при необходимости.
4. Перезагрузить страницу, затем повторить действия после пяти минут.
   В Network проверить конечный ответ запроса после возможного refresh/retry.

При 500 `/auth/me` сохранить серверный traceback и request ID без секретов.
При 401 различать отсутствие Bearer, недействительный access/серверную сессию и
отсутствие refresh-cookie. При 403 проверить точный Origin и поля полномочий,
а не только название роли. Не прикладывать необработанный HAR с credentials.
