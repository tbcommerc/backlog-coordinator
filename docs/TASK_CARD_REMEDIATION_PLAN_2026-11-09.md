# План устранения замечаний карточки задачи

Дата плана: 09.11.2026. Проверено: 11.11.2026. Статус: **после отклонения первого внедрения карточка повторно реализована по разработанным референсам**. Подтверждённые проверки и открытые границы приёмки перечислены в [актуальном отчёте внедрения](dev-testing/TASK_CARD_PROPOSAL_IMPLEMENTATION_2026-11-09.md); историческая отмена не описывает текущий код.

Область: действующая карточка обычной задачи бэклога и её переходы к рабочим задачам. План не означает переработку всего реестра или внедрение новых бизнес-возможностей. Источник замечаний — [сводное ревью](../artifacts/task-card-review-2026-11-09/review.md), [независимая оценка A](../artifacts/task-card-review-2026-11-09/assessment-a.md), [независимая оценка B](../artifacts/task-card-review-2026-11-09/b/assessment-b.md).

Контракты: [DESIGN.md](../dmb-backlog/DESIGN.md), [UI Kit](../dmb-backlog/docs/UI_KIT_CONTRACTS.md), [композиции](../dmb-backlog/docs/UI_PAGE_COMPOSITIONS.md), [протокол приёмки](../dmb-backlog/docs/UI_KIT_REVIEW_PROTOCOL.md). Источником AS-IS остаётся актуальный код; перед каждым этапом необходимо сверить изменившиеся после ревью участки.

## 1. Результат, который должен получить пользователь

1. После открытия сразу понятны название, статус, исполнитель, срок и следующее доступное действие.
2. Пользователь заранее понимает, когда данные будут сохранены и как отменить изменение.
3. Ошибка не выдаётся за отсутствие данных; восстановление выполняется на месте.
4. Вложенные окна закрываются по одному, не теряя контекст и фокус.
5. Карточка использует действующие варианты UI Kit во всех состояниях, темах и размерах.
6. Все замечания имеют результат: исправлено с доказательством, снято после проверки либо остаётся открытым с конкретной причиной. Непроверенный сценарий не становится PASS.

## 2. Решения, принятые для планирования

Это рекомендуемый целевой контракт; он должен быть зафиксирован в документации при реализации, а не незаметно изменён в процессе.

- **Композиция «карточка».** Один заголовок, рабочая сводка, описание, дополнительные атрибуты, расчёты. Части одной сущности — `SectionCard` с вариантом `plain`; рамки остаются у самостоятельных объектов, например отчётного статуса отдельной встречи.
- **Явное сохранение полей карточки.** Inline-изменение любого поля, включая приоритет и срок, остаётся черновиком до «Сохранить». Полный редактор использует тот же контракт. Отчёты, комментарии и файлы сохраняют самостоятельные предметные действия с ясными подписями.
- **Шесть вкладок сохраняются на первом этапе.** Само количество не признано дефектом. Сначала исправляются первый экран, названия и контекстные действия; слияние вкладок возможно только после отдельного обоснования.
- **Общие компоненты важнее локальной заплаты.** Если существующего варианта недостаточно, добавить именованный вариант UI Kit и пример в каталоге. Не наращивать специфичность CSS карточки.
- **Наблюдение не равно дефекту.** Гипотезы про полное имя, footer и разделение внешних ссылок сначала проверяются. Наличие legacy-adapter не требует его автоматического удаления.
- **Нет автоматического расширения продукта.** Редактирование/удаление опубликованных комментариев, новая модель ACL и запуск AI-сервиса не входят в исправления по умолчанию.

## 3. Порядок поставок и зависимости

| Этап | Содержание | Зависимости | Условие выхода |
|---|---|---|---|
| E0 | Актуализировать доказательства, воспроизвести исходниковые находки, зафиксировать сценарии | Нет | Исходный полный экран, ожидаемое поведение и набор данных для каждого пункта |
| E1 | Честные состояния данных и корректный стек диалогов | E0 | Ошибки не маскируются пустотой; Escape закрывает один слой |
| E2 | Единый контракт редактирования, отмены и восстановления | E0; общая оболочка E1 | Приоритет/срок/остальные поля ведут себя одинаково |
| E3 | Композиция основного экрана и соответствие UI Kit | E1–E2 | Рабочая сводка доступна сразу; полный экран принят визуально |
| E4 | Отчётные статусы, ссылки, рабочие задачи и тексты | E3; часть локальных пунктов можно подготовить раньше | Вторичные поверхности ясны и согласованы |
| E5 | Доступность, числовые значения и крайние данные | Начать на E0, завершить после E3–E4 | Клавиатура, семантика, контраст и данные проверены |
| E6 | Сквозные пути, роли и отказы на живом приложении | E1–E5 | Обязательная матрица имеет отдельные результаты fixture/live |
| E7 | Независимая повторная визуальная оценка и документация | E6 | Нет открытых подтверждённых дефектов в заявленной области; остаток перечислен |

Работы группировать в небольшие изменения по этим этапам, а не в одну переработку `modal.js`. Для каждой поставки отдельно фиксировать изменённые общие компоненты и затронутых потребителей. Изменение поведения должно сопровождаться профильной документацией и датой проверки.

## 4. Реестр работ: каждое замечание имеет пункт

Исходный статус пунктов при создании плана — **запланировано**.
Актуальные статусы и доказательства находятся в отчёте реализации выше.

### E0. Подготовка и воспроизведение

**TC-00 — исходная точка и область изменений.**

- Снять актуальный полный экран и открытые состояния карточки; сопоставить с доказательствами от 09.11.2026. Не использовать размытые снимки 01–10, ошибочно названный dark-снимок 34 и пустые текстовые sidecar как доказательство.
- Проверить рабочее дерево и сохранить чужие незавершённые изменения. Не делать сопутствующую очистку большого файла `modal.js`.
- Зафиксировать активные render/open entry points, общие модальные обработчики, текущие adapters и реальных потребителей UI Kit. Исторические функции не использовать как доказательство поведения.
- Подготовить воспроизводимые наборы: пустая задача; реалистичная заполненная; длинные строки; нулевые/отсутствующие значения; четыре встречи; история с несколькими изменениями; задача чужой команды.
- Для каждого исходникового замечания сначала создать минимальное воспроизведение на настоящем компоненте с изолированными ответами API. Если текущая реализация уже исправлена — записать факт и не вносить лишнее изменение.

**Приёмка:** карта «пункт → актуальная реализация → сценарий → доказательство». Все дальнейшие сравнения используют одинаковые данные, тему и размер.

### E1. Надёжность состояний и диалогов

**TC-01 · P1 — файлы и история: ошибка не должна становиться пустотой.** Источник: R1/A3.

- Затронуты загрузчики вложений и истории в `modal.js`, вывод вложений в `taskAttachments.js`, общие состояния UI Kit.
- Разделить первоначальную загрузку, успешную пустоту, данные, ошибку без данных и устаревшие данные с ошибкой обновления.
- При неуспешном обновлении сохранять уже полученные строки; показывать понятную причину и «Повторить» на этой же вкладке.
- Счётчик вкладки не обнулять из-за ошибки. Не показывать ошибку для отменённого запроса после закрытия/смены задачи.
- Сохранить защиту от устаревшего ответа: данные задачи A не попадают в задачу B.

**Приёмка:**500, timeout, offline, повторный успех, первоначальная пустота и ошибка после непустого ответа. Проверить и визуальный смысл, и фактическую принадлежность данных.

**TC-02 · P2 — отчётные статусы: восстановление и загрузка на месте.** Источник: A minor/B05.

- Заменить инструкцию «переключитесь на вкладку ещё раз» непосредственным повтором запроса.
- Выбранная вкладка должна сразу становиться активной и показывать загрузку; для истории проверить тот же порядок относительно `await`.
- Повторное получение данных не стирает несохранённые статусы разных встреч. Сообщение различает ошибку чтения и ошибку записи.

**Приёмка:** переключение во время медленной загрузки, повтор после ошибки, два заполненных черновика, повторное открытие. Нет зависшего прежнего содержимого под новым названием вкладки.

**TC-03 · P2 — стек вложенных окон.** Источник: R4/A4.

- Перевести окно требований AI на общую регистрацию и закрытие диалогов.
- Обработчик Escape действует только на верхний слой; закрытие мышью и клавиатурой дают одинаковый результат.
- После закрытия фокус возвращается на соответствующую AI-кнопку; при закрытии карточки — на исходный элемент реестра либо предсказуемый запасной элемент, если строка исчезла.
- Сохранить работающий Tab-trap. Утечка Tab в предыдущем ревью не подтвердилась и не должна фигурировать как исправленный дефект.

**Приёмка:** открыть карточку → требования AI → Tab/Shift+Tab → Escape: остаётся карточка, фокус на инициаторе. Второй Escape закрывает карточку. Повторить для других вложенных подтверждений, включая несохранённый ввод.

**TC-04 · P2 — геометрия диалога AI.** Источник: R4/B06.

- Устранить попадание общей оболочки под широкий reset `#task-detail-overlay *`.
- Использовать общие отступы header/body/footer, ширину, заголовок, прокрутку и кнопку закрытия. Не исправлять через более специфичный selector.
- Проверить другие окна внутри карточки, чтобы удаление reset не раскрыло скрытые зависимости.

**Приёмка:** полный экран диалога в обеих темах, на 320/390/1366/1440, с длинным списком требований и увеличением 200%; действия и заголовок доступны, отступы соответствуют каталогу.

### E2. Редактирование и сохранение

**TC-05 · P2 — единое явное сохранение.** Источник: R3/A2.

- Убрать скрытое автосохранение priority/deadline при inline-изменении; синхронизировать подсказки и документацию.
- Использовать общий набор состояний: без изменений → изменено → сохраняется → сохранено либо ошибка. Количество изменений отражает фактический diff.
- Escape/«Отменить изменения» до сохранения не отправляют запись. Переход/закрытие с изменениями предлагает сохранить, продолжить редактирование либо отказаться.
- Сохранить явный результат операции и undo. Undo не должен перезаписывать чужое более новое изменение без проверки версии.
- Не менять самостоятельную транзакционную модель загрузки файлов, публикации комментария и статуса встречи; сделать её явной в подписях.

**Приёмка:** priority, deadline, status, progress, title, description, internal comment и доступные ссылки — одинаковый момент записи; сохранение мышью и существующими shortcuts; no-op, двойной submit, ошибка, повтор, конфликт, отмена, undo. При conflict ввод не теряется и не происходит молчаливого перезаписывания.

**TC-06 · проверка UX — контекст нижней панели на вкладках.** Источник: наблюдение A.

- Проверить назначение общей кнопки на «Комментариях», «Ссылках и файлах», «Рабочих задачах» и «Логе».
- Для самостоятельных операций оставить предметные действия у соответствующего объекта. Общий переход в редактор, если он нужен, подписать «Редактировать задачу» и не представлять как редактирование комментария/рабочей задачи.
- На ссылках сохранить очевидный путь редактирования самих ссылок. В режиме только чтения объяснение прав должно быть доступно и с клавиатуры, не только через tooltip disabled-кнопки.

**Приёмка:** пользователь по подписи предсказывает изменяемую сущность; основной action соответствует вкладке; readonly объясняется без попытки выполнить недоступную операцию. Если текущий вариант подтверждён как достаточный — документировать решение вместо лишнего редизайна.

- Проверить одно/два/три слова, двойную фамилию, латиницу, длинную строку и отсутствующее имя. Пользователей и их данные для этого не изменять: использовать fixture.

**Приёмка:** человек однозначно узнаваем, полное имя доступно assistive technology, длинное значение не ломает сводку.

**TC-15 · проверка IA — ссылки на материалы и внешнее исполнение.** Источник: наблюдение A.

- Явно разделить назначение: «Материалы и требования» и «Внешнее исполнение». Проверить актуальную терминологию перед переименованием.
- У каждого типа ссылки объяснить, что пользователь добавляет и где затем найдёт запись. Не переносить существующие данные между моделями автоматически.
- Уточнить validation недопустимого URL, пустого/повторного адреса, безопасное открытие и сохранение ввода при ошибке.

**Приёмка:** из подписи понятна сущность; валидная ссылка создаётся в ожидаемом месте; неверная не сохраняется; внешние переходы не теряют черновик карточки.

### E5. Доступность и корректность значений

**TC-16 · P2 — семантика выбора и восстановление фокуса.** Источник: B01.

- Для независимого выбора команд/меток использовать общий multi-select/checkbox либо корректный toggle с `aria-pressed`.
- Состояние не должно передаваться только классом `.on` и иконкой. После перерендера возвращать фокус на тот же логический элемент либо ближайший допустимый.
- Проверить списки выбора исполнителя/проекта/заказчика: доступные имена, поиск, empty/error/loading, длинные значения и закрытие.
- Семантику защищённых справочников и команд проверять в изолированных данных или чтением готовых значений; не менять защищённые записи.

**Приёмка:** выбор и снятие понятны скринридеру; Tab/Shift+Tab и Space/Enter не теряют позицию; состояние соответствует фактическому черновику.

**TC-17 · P2 — различить ноль и отсутствие стоимости.** Источник: A minor/B03.

- Заменить truthy-проверки трудозатрат/стоимости на явное различение0, null, undefined и пустого значения.
- Выводить0 ₽ только если нулевой результат определён предметной формулой; отсутствие ставки не превращать в достоверный ноль.
- Проверить plan/fact, итоги, единицы, округление, большие значения и C/V при нулевом знаменателе. Не менять предметную формулу без отдельного основания.

**Приёмка:** числовые fixture-примеры с ожидаемым результатом; 0 визуально отличается от отсутствия данных; нет NaN/Infinity и ложной достоверности.

**TC-18 · обязательная приёмка — общая доступность и адаптивность.** Источник: открытое покрытие A/B.

- Проверить именованные вкладки и panel-связи, стрелки/Home/End/Enter, порядок Tab, видимый focus, ошибки и live announcements.
- Измерить контраст текста, контролов и фокуса в обеих темах. Проверить forced colors, reduced motion, 200% zoom и touch targets по контрактам UI Kit.
- Проверить закрытые/открытые dropdown, popover, tooltip, даты и подтверждения у краёв экрана, не только основной закрытый вид.
- Прогнать NVDA или другой доступный экранный диктор; если инструмент недоступен, оставить эту строку открытой, не заменять её только DOM-проверкой.

**Приёмка:** основной путь выполняется только клавиатурой; нет потери контекста, неименованных интерактивных элементов и перекрытых действий. Отсутствие overflow само по себе не закрывает визуальную часть.

### Ролевое покрытие

- Использовать только готовые разрешённые QA-профили из паспорта; авторизация не даёт права менять пользователей, роли, справочники или состав команд.
- Сначала составить expected-матрицу из актуального backend и предметных контрактов. Наблюдение «staff200/customer403» из предыдущего прогона не является автоматически дефектом ACL.
- Отдельно проверить клиентский маршрут customer. Известное отсутствие customer binding в `auth/me` сверить с паспортом и текущим кодом; если оно блокирует путь, связать с отдельным дефектом и оставить строку открытой. Не менять модель авторизации под дизайн-ревью без основания.
- Повторять одинаковую визуальную геометрию для каждого пользователя не требуется. Все различающиеся права, действия и переходы проверить на соответствующем профиле; сокращения матрицы обосновать.

### Неподдерживаемые и ограниченные операции

- Редактирование/удаление опубликованных комментариев не добавлять автоматически: сначала подтвердить продуктовую необходимость. Если функция отсутствует по контракту, отметить как неприменимую, а не «исправленную».

- Task Prioritiser не запускать без прямого указания пользователя. Полный live AI-путь останется открытым, если сервис недоступен; fixture-ответы не выдавать за расчёт реальным агентом.
- Необратимое удаление live-файла требует отдельного подтверждения в момент действия. До него можно проверить диалог и отмену, а финальную ветку — на изолированном стенде.

## 9. Критерий завершения

План исполнен только когда:

- все подтверждённые замечания TC исправлены либо мотивированно сняты после повторного воспроизведения;
- все обязательные применимые пути J имеют результаты, а недоступные проверки перечислены без заявления полной приёмки;
- основной и вторичные экраны отдельно приняты визуально в обеих темах и согласованных размерах;
- нет нового расхождения с UI Kit и регрессии его затронутых потребителей;
- сохранение, отмена, права и восстановление после ошибок подтверждены на требуемом уровне;
- документация соответствует реализации, QA-изменения и ограничения среды учтены.

Ни число пройденных тестов, ни более высокий эвристический балл, ни улучшение относительно исходного снимка сами по себе не закрывают план.
