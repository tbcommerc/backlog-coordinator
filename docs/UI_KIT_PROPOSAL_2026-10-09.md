# Предложение по единому UI kit системы

Дата анализа: **09.10.2026**. Статус: **план принят, внедрение поэтапно**.
Ниже сохранён анализ состояния до начала изменений. На 09.10.2026 внедрены ядро,
общий визуальный слой, пилот реестров и базовые элементы карточки/создания задачи; фактический охват и оставшиеся этапы
описаны в [UI kit v1](../dmb-backlog/docs/UI_KIT.md). Остальные целевые решения
этого предложения не следует считать внедрёнными.

Рекомендация — развить существующую дизайн-систему Backlog Coordinator в единый
UI kit: общие токены, компоненты с одинаковым поведением, шаблоны страниц и живой
каталог с проверками. Основа уже существует, но страницы применяют её неравномерно.
Приоритет — устранить расхождения в базовых элементах и закрепить правила,
по которым будут создаваться следующие экраны.

## Область анализа

Основной пользовательский интерфейс находится в `dmb-backlog/frontend`:
SPA на JavaScript с ES-модулями, HTML-шаблонами и CSS. В этой же оболочке находятся
интерфейсы AI-ассистентов и взаимодействие с приоритизатором.

| Поверхность | Текущее устройство | Предлагаемый охват |
|---|---|---|
| Backlog Coordinator | Общие CSS, router, страницы в `js/components` | Все пользовательские страницы, вход, навигация, диалоги и уведомления |
| AI-ассистент | Страница `#/customer/create`, модуль `agentChat.js` | Общие элементы и отдельный шаблон рабочей области ассистента |
| Assistant V2 | `#/agent-v2`, собственные CSS и `js/agent-v2`; доступ API зависит от конфигурации | Включить в общий визуальный контракт; учитывать состояния недоступности сервиса |
| Legacy Assistant V2 | Сохранённые `js/assistant-v2` и отдельный backend-прототип; старый маршрут перенаправляется на `#/agent-v2` | Не использовать как визуальный эталон действующей системы |
| Standalone UI приоритизатора | Отдельный Streamlit-интерфейс с пятью вкладками, запускается отдельно; код напрямую работает с БД | Отдельное решение о его дальнейшем назначении; см. ниже |

Источники: [оболочка SPA](../dmb-backlog/frontend/index.html),
[маршруты](../dmb-backlog/frontend/js/router.js),
[Assistant V2](../dmb-backlog/frontend/js/agent-v2/workspace.js),
[Streamlit UI](../agents/value-priority-assessor/value_priority_assessor/ui/streamlit_app.py),
[запуск standalone UI](../agents/value-priority-assessor/README.md).

Для приоритизатора предлагаю единый пользовательский опыт обеспечивать через
основной frontend. Если отдельный Streamlit UI используется как рабочий продукт,
его сценарии нужно включить в самостоятельную волну переноса в общую оболочку
через API. Если он остаётся диагностическим инструментом, явно закрепить это
назначение и согласовать минимальное совпадение темы и терминологии. Простая
подмена CSS в Streamlit не даст тот же компонентный контракт.

В браузере проверены доступность приложения, экран входа и автономный каталог
диалогов с текущими стилями. Авторизованные страницы и все их состояния в рамках
этого анализа визуально не проходились. Каталог содержит демонстрационные данные
и отдельные шаблоны: он показывает стили, но не доказывает полноту поведения
реальных форм. Исторические снимки и `graphify-out` использовались только для
ориентации, не как подтверждение текущего интерфейса.

## Подтверждённые расхождения

### Объём и распределение оформления

В 13 файлах `frontend/css/*.css` — **19 009 строк** и **296 вхождений
`!important`**. На `components.css` и `pages.css` приходится 16 241 строка,
около 85% CSS. В 67 JS-файлах под `frontend/js`, без `lib`, найдено
**1 128 вхождений `style=`**.

Это лексические показатели, а не количество дефектов или независимых
компонентов. Строки включают комментарии; набор JS включает сохранённые legacy
модули. Динамическая ширина прогресса, размеры колонок и цвета данных могут
обоснованно задаваться из JS. Сначала следует извлекать статическое оформление.

Наиболее крупные модули: `modal.js` — 8 092 строки и 268 вхождений `style=`,
`admin.js` — 3 528 и 243, `reports.js` — 2 495 и 90,
`expressEstimate.js` — 2 057 и 124. Это кандидаты на постепенное выделение
компонентов по сценариям; механическое дробление файлов само по себе
единообразия не создаст.

### Конкретные проблемы и последствия

| Наблюдение | Подтверждение | Последствие | Предлагаемое решение |
|---|---|---|---|
| У кнопок нет отдельного цвета текста поверх акцента | `components.css`, строки 684–687: фон `--accent`, текст white | Не все акценты обеспечивают читаемую пару | `action-primary-bg`, `action-primary-text`, hover/active/focus как проверенный набор |
| Производные акцента обновляются не полностью | `tokens.css`: десять вариантов меняют accent, hover и light, но `accent-medium` определён только для indigo | Кольцо фокуса или подсветка могут сохранить индиго после выбора другого акцента | Полный набор производных для каждого акцента |
| V2 использует несовместимые имена токенов | `agent-v2.css`: `--text-color` не объявлен в CSS; `--surface` определён только внутри task overlay, вне дерева V2 | Срабатывают локальные тёмный текст и белая поверхность; общей темы недостаточно | Перевести V2 на общие семантические токены |
| В V2 много фиксированных цветов | 103 hex-вхождения в `agent-v2.css`, включая фон редактора и градиент шапки; theme overrides в этом файле отсутствуют | Отдельный визуальный характер и неполное наследование тем | Общие поверхности и типографика, умеренный акцент AI |
| Карточка задачи имеет свой словарь компонентов | `components.css`, начиная со строки 5044: scoped aliases, `.btn.primary`, `.btn.ghost`, собственные вкладки и поля | Изменения общих кнопок не полностью определяют вид кнопок карточки | Общие примитивы внутри отдельного шаблона TaskWorkspace |
| Размер small зависит от контекста | Общая `.btn-sm` задаёт padding; toolbar добавляет min-height 32 px. В каталоге измерены кнопки «Сохранить» высотой 26 и 27,33 px при шрифте 12 px | Один вариант не гарантирует одинаковую геометрию | Явные размеры контролов и правила плотности |
| Унификация диалогов работает поверх нескольких структур | `modal-system.css` перечисляет семейства overlay; task/create намеренно исключены | Накладно поддерживать одинаковые состояния закрытия и сохранения | Общие Dialog и FormDialog, отдельный WorkspaceDialog |
| Цвета графиков задаются отдельно | `analytics.js`: `LT_TYPE_COLORS`, `LT_MAP_COLORS`, `chartTextColor`; в оболочке подключены ECharts и Chart.js | Тема и семантика графиков развиваются отдельно от UI | Общие токены визуализации данных и адаптеры используемых библиотек |

Scoped CSS карточки задачи не распространяется автоматически на всю страницу:
это намеренная изоляция, а не доказательство глобального конфликта селекторов.
Сохранить её границу полезно, но базовые элементы внутри должны стать общими.

### Контраст требует отдельного исправления

В живом каталоге для обычной кнопки «Сохранить» получены фон `rgb(99,102,241)`,
белый текст и размер шрифта 12 px. Расчёт контраста даёт **4,467:1**.
Для остальных accent-значений из токенов пара с белым текстом даёт, например,
**2,148:1** для amber и **2,537:1** для emerald. Все десять базовых accent-пар
с белым текстом ниже 4,5:1; для девяти дополнительных вариантов это расчёт по
CSS, а не проверка всех страниц в браузере.

Порог обычного текста — 4,5:1; округлять результат до порога нельзя.
[Пояснение W3C к контрасту](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
Предлагаю отделить декоративный акцент от фона основной кнопки и проверять
контраст всех разрешённых сочетаний автоматически.

У статуса запроса и статуса задачи может быть общий Badge, но сохраняются

примитивов без встраивания новой модели данных в UI kit.

### Предлагаемые визуальные правила

Сохранить Inter и Lucide, нейтральные поверхности и текущий индиго как
отправную точку. Основная рабочая тема — светлая, с полноценной тёмной и
режимом system, которые уже доступны в настройках. Существующие десять
акцентов сохранить через полные проверенные палитры; сокращение выбора —
отдельное продуктовое решение.

| Параметр | Предложение для первого визуального эталона |
|---|---|
| Текст | Основной 14 px, плотные таблицы 13 px, метаданные 12 px; важные подписи не уменьшать до 9–11 px |
| Заголовки | Страница 24 px, секция 18 px, группа 14 px semibold |
| Отступы | Базовый шаг 4 px; типовые значения 4, 8, 12, 16, 24, 32 |
| Контролы | Compact 32 px, default 36 px, крупное основное действие 40 px |
| Touch | Интерактивная область основных контролов не меньше 44×44 px как внутренний стандарт продукта |
| Радиусы | Контролы 8 px, панели 12 px, диалоги 16 px; pill для меток и фильтров |
| Плотность | Два явных режима: comfortable и compact; менять высоты строк и отступы, сохранять читаемость |
| Цвет | Отдельные роли для основного действия, выделения, текста, состояния, категории и команды |
| Состояния | Default, hover, active, focus, disabled, loading, invalid и read-only там, где они применимы |
| Анимация | Короткие функциональные переходы; уважать prefers-reduced-motion |

Размер 44×44 — предложенное продуктовое правило. Минимум WCAG 2.2 AA для
цели указателя — 24×24 CSS px с оговорёнными исключениями; маленькая высота
кнопки сама по себе ещё не доказывает нарушение критерия.
[Пояснение W3C к размеру цели](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Значения таблицы — материал для пилота. Проверить их на плотном бэклоге,
длинных русских подписях и карточке задачи перед распространением.

### Общие правила поведения

- Основное действие находится в предсказуемом месте и обозначает результат:
  «Сохранить», «Отправить на ревью», «Применить к 12 задачам». В одной области
  решения обычно одно визуально главное действие.
- Поле объединяет подпись, обязательность, подсказку, ошибку и счётчик.
  Ошибка сохранения оставляет введённые данные. Read-only и disabled различаются.
- Single-select, multi-select и переключатель режима имеют разные контракты.
  Панель фильтров показывает активные ограничения, количество результатов,
  понятный сброс и состояние «Ничего не найдено».
- Toast подтверждает короткую операцию; ошибка поля остаётся у поля,
  ошибка формы — в форме. Центр уведомлений остаётся отдельным устойчивым
  списком событий с собственными правилами прочтения.
- Диалог управляет начальным фокусом, Escape, возвратом фокуса и закрытием.
  Сохранение, несохранённые данные и конфликт версии представлены явными
  состояниями. Не добавлять второй конкурирующий обработчик клавиатуры.
- Для каждой страницы определить владельца прокрутки. Таблицы могут иметь
  локальную горизонтальную прокрутку; закреплённые панели не перекрывают
  сфокусированный элемент. Карточки и формы читаются последовательно на mobile.
- Ассистент сохраняет ввод, показывает ожидание и ошибку рядом с работой,
  различает черновик и отправленный документ. История и длинные документы
  используют специализированную компоновку при общих кнопках и полях.

## Техническое устройство

На первом этапе достаточно библиотеки внутри текущего frontend. Предлагаемые
каталоги, которых пока нет как готового UI kit:

```text
frontend/css/ui/        # tokens, themes, базовые и составные компоненты
frontend/js/ui/         # render/mount/destroy и доступное поведение
frontend/js/patterns/   # общие композиции экранов
frontend/ui-catalog/    # примеры из реальных компонентов
```

Существующие `viewState.js`, `uiFeedback.js`, `modalAccessibility.js` и общие
фильтры становятся исходным материалом. В переходный период сохранить
совместимые импорты или адаптеры. Страницы отвечают за данные, права и сценарии;
компоненты принимают параметры и события, не обращаются сами к `window.app`,
хранилищу задач и API.

Динамическому компоненту нужен жизненный цикл с освобождением обработчиков
и observer при смене маршрута. Текст экранируется существующими HTML helpers;
обработку Markdown и безопасных URL сохранить при переносе. В UI kit не должны
появляться бизнес-решения о правах или допустимости изменения данных.

CSS сначала переносить небольшими блоками с контролем вычисленных стилей.
Статические inline styles заменять классами; динамические размеры передавать
через документированные CSS-переменные. Не вводить глобальные селекторы
`.tab`, `.btn.primary` и подобные вне явно ограниченной области.

Cascade layers можно использовать после проектирования порядка legacy и новых
стилей. Обычные правила без слоя имеют приоритет над обычными правилами в слоях;
поэтому простое добавление нового kit в `@layer` не гарантирует, что он
перекроет существующие стили.
[Документация MDN по слоям CSS](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer).

Выделение npm-пакета, смену frontend-фреймворка и выбор внешней библиотеки
имеет смысл оценивать по отдельным потребностям. Для текущей консолидации они
не являются предварительными условиями. Если у банка есть обязательная
дизайн-система, её требования нужно сопоставить с этим предложением до фиксации
визуального эталона.

Крупные переплетённые модули карточки и оценки переносить после пилота.
Проблемы контраста и theme-токенов V2 исправлять уже в ядре, не откладывая
до полного переноса рабочих областей.

Оценку полной трудоёмкости уточнить по пилоту: число строк не отражает
количество интерактивных состояний. Для планирования нужны доступность дизайнера,
frontend-разработчика и QA, браузеры целевого стенда, а также решение о standalone
UI. Первый самостоятельный результат — работающий каталог ядра и две принятые
страницы, а не глобальная смена оформления за один релиз.

С [планом серверной миграции](JAVA_JS_MICROSERVICES_MIGRATION_PLAN.md), который
предлагает сохранять визуальный эталон, этот переход следует вести отдельным
набором изменений. Визуальные изменения UI kit получают собственный принятый
эталон и не маскируются обновлением снимков тестов серверной эквивалентности.

## Условия готовности

1. Все пользовательские поверхности из согласованного охвата внесены в матрицу;
   ни один активный экран не остаётся без решения о миграции или исключении.
2. У каждого компонента есть API, примеры и применимые состояния, включая
   длинные подписи, отсутствие данных, ошибки и отсутствие прав.
3. Проверены светлая и тёмная темы, обе плотности, все разрешённые акцентные
   палитры для базовых контролов. Контраст текстовых пар проходит порог;
   приоритет и статус не передаются только цветом.
4. Представительные страницы проверены на 390, 768, 1280 и 1440 px и при
   увеличении масштаба. Таблица допускает внутреннюю прокрутку, страница —
   отсутствие непреднамеренного горизонтального переполнения.
5. Клавиатурой доступны фильтры, вкладки и диалоги; фокус виден, возвращается
   после закрытия и не скрывается под закреплёнными панелями.
6. Сохранились черновики, сортировки, выбор строк, состояние фильтров,
   deep links, контекст возврата и обработка конфликтов. Различия доступа
   проверяются на изолированных fixtures без изменения защищённых записей БД.
7. В мигрированных компонентах нет необоснованных фиксированных цветов,
   статических inline styles и новых `!important`. Динамическая геометрия,
   цвета данных и специальные accessibility overrides документированы.
8. Каталог использует реальные render/mount-компоненты. Визуальные снимки
   дополняются проверками поведения; одних regex-проверок текста исходников
   недостаточно для приёмки.

Для дальнейшей поддержки нужен назначенный владелец UI kit, журнал изменений
контрактов и правило: новый визуальный вариант сначала появляется в каталоге,
затем на странице. Роль владельца предлагается назначить; конкретный сотрудник
в рамках анализа не определялся.
