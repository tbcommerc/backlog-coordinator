# Техническое задание на объединение страниц бэклога

Агенту разработки требуется объединить «Бэклог DMB» и «Бэклог команды» в одну страницу «Бэклог». Страница предоставляет две явно обозначенные области: «Моя команда» и «Все доступные». Сохраняются задачи, их карточки, доступные операции, персональные настройки и работоспособность прежних ссылок.

Документ задаёт целевое решение для реализации. Он не является отчётом о внедрении. Проверка исходного состояния выполнена по рабочему дереву 03.11.2026; при реализации агент повторно сверяет перечисленные точки входа. Программа приёмки находится в [отдельном приложении](backlog-unification-test-plan.md). Оба документа обязательны; номера разделов ниже используются в приложении для трассировки.

## 1. Результат и границы работы

### 1.1. Обязательный результат

1. Один пункт бокового меню «Бэклог», один основной контроллер страницы и единая реализация таблицы/карточного представления.
2. Две области данных с независимыми персональными настройками и состоянием просмотра.
3. Доступные действия определяются правами пользователя и конкретной задачей; выбор области не выдаёт и не отнимает объектное право.
4. Рабочие старые адреса, закладки, ссылки на задачу, вкладку и комментарий.
5. Перенос существующих настроек без удаления исходных ключей браузера.
6. Отсутствие регрессий поиска, фильтров, сортировки, пагинации, экспорта, импорта, быстрого редактора, массовых операций, карточки, отчётных переходов и обновлений.
7. Обновлённая профильная документация, тесты, матрица критериев приёмки и отчёт с доказательствами.

### 1.2. Входит в поставку

Общая страница, контекст области, маршрутизация и история браузера, состояние и перенос настроек, унификация проверки прав в таблице с карточкой, жизненный цикл загрузки и обновлений, адаптация входящих/исходящих ссылок, регрессия затронутых сценариев. Изменения административных подписей допускаются как изменения интерфейсного текста по §4.5.

### 1.3. За пределами поставки

- Объединение Task с WorkTask, запросами заказчиков, проектами, метриками или поручениями встреч. Их сущности, страницы и жизненные циклы сохраняются.
- Изменение статусов, приоритетов, расчётов C/V, финансового эффекта, правил кварталов, решений ПИП, модели команд и состава ролей.
- Включение канбана в новую страницу. Существующий `#/kanban` остаётся самостоятельным потребителем и проходит регрессию общих модулей.
- Перенос всех фильтров, экспорта и пагинации на сервер; это самостоятельное изменение контракта. В этой поставке сохраняется полная загрузка выбранной области и клиентский отбор по §12.
- Новые сущности БД, Alembic-миграции, обязательные переменные окружения, новый AI-сервис и изменение настроек запуска.
- Изменения защищённых данных, перечисленных в корневом [AGENTS.md](../AGENTS.md). В частности, нельзя исправлять доступ изменением роли или назначением команды.

## 3. Область данных и начальный контекст

### 3.1. Определения

- `scope=team` — только Task, у которых ответственная `team_id` равна актуальной команде пользователя. Отображаемое имя — «Моя команда», рядом название команды.
- `scope=all` — все Task, которые разрешает текущая серверная policy чтения. Отображаемое имя — «Все доступные».
- Область — обязательная граница выборки. Обычные фильтры дополнительно сужают её.
- `involved_teams` не заменяет ответственную команду и не включает задачу в «Мою команду». Вовлечённые команды остаются отдельным атрибутом/фильтром.
- Task без ответственной команды входит только в `all`, если его разрешает сервер. Он не назначается команде автоматически.
- Записи с `metric_id` не возвращаются в реестр задач: сохраняется исключение из `task_read_scope_clause`.

### 3.2. Доступность областей

| Условия после загрузки текущего пользователя | Поведение |
|---|---|
| Есть доступ к DMB и командному разделу, назначена команда | Доступны обе области |
| Есть только DMB | Доступна `all`; наличие команды само по себе не выдаёт доступ к командному разделу |
| Есть только командный раздел и команда | Единственная область `team`; без бессмысленного переключателя на ту же выдачу |
| Командный раздел разрешён, команды нет | Командная область показывает специальное состояние; API общего списка не вызывается |
| Нет обоих доступов | Пункт меню скрыт; прямой вход показывает отказ, запрос списка не выполняется |
| Пользователь ограничен customer portal | Сохраняются ограничения клиентского портала; общий бэклог недоступен |
| Пользователь ещё не загружен/ошибка `/auth/me` | Загрузка/ошибка авторизации; нельзя временно считать все области разрешёнными |

Под «доступом к DMB» понимается существующее разрешение `backlog_dmb` на чтение; под командным — ненулевое `backlog_team` с сохранением серверного ограничения. Значения `read_all`/`write_all` командного разрешения не являются основанием самостоятельно расширять серверную область чтения: текущая policy глобального чтения проверяет `backlog_dmb`.

### 3.3. Выбор при входе через меню

1. Восстановить последнюю доступную область текущего пользователя; командная сохранённая область должна относиться к его актуальной команде.
2. При отсутствии истории выбрать `team`, если есть командный доступ, команда и `task_edit=team` либо отсутствует DMB-доступ.
3. Иначе выбрать доступную `all`; если её нет — доступную `team`.
4. При отсутствии работоспособной области показать соответствующее состояние из §3.2.

Ссылки с явной областью имеют приоритет над этой логикой. Серверная роль или `admin=full` сами по себе не обходят объектную policy. Повторный обычный вход не требует заново выбирать команду.

### 3.4. Переключение областей

Переключение сначала проходит защиту несохранённого ввода (§11), затем сохраняет состояние источника, отменяет его запросы, очищает выделение, активирует состояние назначения и загружает его данные. До ответа данные предыдущей области не показываются под новым заголовком. Последний контекст записывается только после принятого перехода.

Состояние назначения восстанавливается независимо: поиск и фильтр нескольких команд из `all` не переносятся в `team`. При первом входе в область применяются её значения по умолчанию. Возврат в уже открытую область восстанавливает её страницу/прокрутку, если пользователь явно не изменил условия выборки.

## 4. Права и безопасные действия

### 4.1. Единое правило

Чтение и запись всегда окончательно проверяет сервер. UI использует полученные из `/auth/me` явные `task_edit`, `task_comment`, `task_delete` и принадлежность конкретной задачи. Для редактирования и комментариев переиспользовать `taskCardPermissions.js`; не создавать третью таблицу имён ролей. Отсутствие явного поля обрабатывается существующим legacy-fallback этого модуля; неизвестное явное значение означает отказ. Состояние до загрузки пользователя не является legacy-fallback.

Это выравнивание интерфейсов: действие, уже разрешённое сервером и карточкой, становится одинаково доступным в строке и quick edit независимо от области. Например, `task_edit=team` позволяет менять свою задачу и в `all`, а чужую не позволяет ни в одной области. Если сервер разрешает чтение, право записи не делает невидимую задачу видимой само по себе.

### 4.2. Матрица объектных действий

| Явная область действия | Своя задача | Чужая задача | Задача без команды |
|---|---|---|---|
| `none` | Запрещено | Запрещено | Запрещено |
| `team`, у пользователя есть команда | Разрешено | Запрещено | Запрещено |
| `team`, команды нет | Запрещено | Запрещено | Запрещено |
| `all` | Разрешено | Разрешено | Разрешено |

Матрица применяется отдельно к edit/comment/delete и только к читаемым объектам. Метрическая legacy-запись не становится редактируемой Task. Перенос задачи другой команде запрещён командному редактору по существующему `can_edit_task`; глобальный редактор действует в существующих пределах API.

### 4.3. Специальные операции

Создание и импорт сохраняют собственные серверные проверки, включая `backlog_team` и task-policy. Видимость кнопки не рассчитывается только по наличию редактируемой строки: пустая команда может создавать задачи. Экспорт требует чтения и полной успешной загрузки. Удаление, комментарий, решения ПИП, отчётные статусы и квартальное обновление сохраняют свои отдельные разрешения и проверки.

403 при записи не превращается в успешный toast: сохраняется введённое, объясняется отказ, перечитываются права. После отзыва чтения содержимое и кеш недоступных задач удаляются немедленно. Возможность сохранить черновик не даёт права снова показывать отозванное содержимое.

### 4.4. Защищённые данные

Запрещены изменения справочников, пользователей, паролей, ролей, назначений ролей, состава команд, привязки пользователя к команде, PO/PL/CL и других атрибутов команд. Запрет действует при миграции, тестировании, SQL и API. Не запускать seed и не обходить ограничения обновлением роли. Ссылки `team_id`/`owner_id` самой рабочей задачи можно менять только в разрешённом штатном сценарии задачи, используя готовые справочники; это не разрешает менять связанные сущности.

### 4.5. Администрирование

Сохраняются поля API/БД `backlog_dmb_access`, `backlog_team_access`, `task_*_scope` и значения всех ролей. В интерфейсных подписях допускается «Бэклог — общая область» и «Бэклог — моя команда». Подсказки объясняют сохранённые ограничения; нельзя обещать `read_all` больше, чем реально допускает сервер. Канбан и экспресс-оценка продолжают использовать прежние разрешения. Нельзя заменить оба permission-key одним или менять payload сохранения роли ради новой навигации.

## 5. Композиция страницы

Порядок сверху вниз:

```text
Бэклог                                  [Поиск] [Представления] [Действия]
[Моя команда · название] [Все доступные]  [Таблица / Карточки]
Закреплённые фильтры                     [Все фильтры] [Колонки]
Быстрые выборки с числами                Активные условия / Сбросить
Состояние выделения или быстрого редактирования
Таблица либо карточки
Найдено N задач                          Пагинация
```

Это структура, а не новая фиксированная геометрия. Использовать существующий UI kit и общую раскладку toolbar; на широком экране совместимые элементы объединяются в строки, на узком переносятся без наложений.

- Заголовок и breadcrumb — «Бэклог». Команда/область не скрыта внутри каталога фильтров.
- При двух областях использовать SegmentedControl/группу с доступным состоянием, не ARIA tabs без tabpanel. При одной области показывать её подпись.
- Сегменты не содержат глобальных счётчиков, ради которых потребовалась бы загрузка второй области.
- Общие действия: создание, обновление, импорт, экспорт, quick edit, операции — по своим условиям доступа.
- «Операции» объединяет существующий конструктор массовых изменений, статусы к встречам и обновление прогресса/статусов; независимые действия остаются доступны, если массовое редактирование запрещено.
- Область списка не меняет автоматически собственный охват отчётного рабочего места. Подпись и права этого рабочего места объясняют его охват.
- Предупреждение о несохранённых/скрытых правках, неполной загрузке или устаревших данных не должно исчезать за меню.

## 6. Адреса и история браузера

### 6.1. Канонический контракт

Путь — `#/backlog`. Новые ссылки всегда явно задают `scope=team|all` и `bv=2`. Это версия сериализации UI, не версия API или данных задачи.

| Параметр | Значение и правило |
|---|---|
| `bv` | `2`; определяет полный снимок query-состояния |
| `scope` | `team` или `all` |
| `q` | Поиск; Unicode, кодирование через URLSearchParams |
| `filters` | JSON-объект: допустимый ключ фильтра → массив строк; включая существующие range/text/empty-токены и quick-key |
| `sort` | Один существующий код сортировки toolbar; default `id-desc` |
| `cs`, `cd` | Ключ сортировки колонки и `asc|desc`; допустимы только ключи каталога |
| `view` | `table|cards`; default `table` |
| `page` | Положительное целое; default 1, корректируется после получения полной выборки |
| `task` | Внутренний положительный integer Task.id, как в действующих deep links; не публичный ID |
| `tab`, `comment` | Действующие значения и нормализация карточки из router.js |

Пустые `q`/`filters`, `sort=id-desc`, `view=table`, `page=1` можно не писать; при `bv=2` их отсутствие означает указанные defaults, а не подмешивание старого поиска из браузера. Параметры колонок, ширины, закрепления и ID локального представления в ссылку не входят. Ссылка воспроизводит выборку и вид, а колонки использует из профиля получателя. `scope=team` означает команду получателя ссылки, а не автора; в URL не добавляется скрытая привязка к команде отправителя.

Декодирование выполняется один раз. Фильтры валидируются по каталогу; JSON не выполняется как код, опасные prototype-key не участвуют в merge. Снять дубликаты значений набора, сохранить все корректные элементы, нормализовать порядок сериализации. Повторяющиеся одиночные параметры (`scope`, `bv`, `task` и остальные scalar-поля) считаются ошибкой, а не выбором первого/последнего по случайному правилу. Неизвестные параметры не влияют на права/выборку; неподдерживаемые ключи/неверный JSON дают понятное сообщение и явное действие сброса только ошибочной части. Нельзя незаметно превратить повреждённый ограничивающий фильтр в широкую выдачу. Предельные размеры: q — 2000 символов, filters — 16 КиБ UTF-8, не более 100 значений одного ключа. Превышение показывает ошибку, не обрезает выборку. Более новая `bv` не интерпретируется как v2: показать несовместимость и предложить открыть область с defaults.

### 6.2. Совместимость

| Входящий адрес | Результат |
|---|---|
| `#/team-backlog` с прежними task/tab/comment | `#/backlog?bv=2&scope=team` с сохранением параметров карточки |
| `#/backlog` без scope и без bv | Legacy-вход в `all`, если DMB разрешён; иначе в доступную `team` с пояснением ограниченной области |
| `#/backlog?task=…` без scope | Тот же legacy-контекст плюс открытие задачи по серверному доступу |
| Явный `scope=team` без команды | «Команда не назначена»; без фонового перехода в `all` |
| Явная недоступная область | Отказ в этой области и ссылка в доступную, если она есть; без тихого расширения |
| Неизвестный scope | Ошибка параметра и выбор доступной области пользователем; не считать `all` |

У bare `#/backlog` сохраняется исторический смысл области. Если legacy-вход не содержит условий списка, адаптер сначала восстанавливает состояние этой области по §7.2, затем сериализует его в полный URL v2; он не должен преждевременно добавлять `bv=2` и тем самым стирать default-view/восстановленный поиск. Поэтому новый пункт меню вычисляет и выдаёт явную каноническую ссылку по §3.3; он не полагается на bare-path для персонального входа. Ссылка меню/переключателя также строится после разрешения состояния назначения, а не только добавлением scope к пустому запросу. Переадресация и канонизация выполняются через replace, без лишнего шага в Back и без циклов. Поддержку `/team-backlog` не удалять после перевода внутренних ссылок.

### 6.3. Изменение состояния

- Смена области, вида и страницы, применение набора фильтров/представления создают одну запись history на завершённое действие.
- Ввод поиска обновляет текущую запись через replace с debounce 250 мс; экспорт/сохранение представления читают введённое значение сразу, до debounce.
- Исправление URL, загрузка данных, тики обновления и перерасчёт числа страниц используют replace и не засоряют history.
- Back/Forward восстанавливают область, фильтры, вид, страницу и карточку без двойного открытия. Защита dirty действует также для history-переходов; отмена полностью сохраняет исходный адрес и экран.
- `task/tab/comment` обновляются существующим механизмом карточки, сохраняя все параметры списка. Закрытие карточки удаляет только параметры карточки.

### 6.4. Карточка вне выборки

Разрешённую сервером задачу открыть даже вне текущего фильтра/страницы; пометить «Задача вне текущей выборки». Область и фильтры списка не расширяются. Для 403/404 использовать существующее обобщённое сообщение о недоступной/удалённой задаче, не раскрывая её атрибутов; убрать ошибочные параметры карточки, сохранить список. Невалидные task/comment/tab нормализуются действующими функциями router.js. Несколько быстрых deep links открывают только последнюю актуальную карточку.

## 7. Состояние и персональные настройки

### 7.1. Разделение состояния

| Где | Что хранится |
|---|---|
| URL | Область, поиск, фильтры, сортировка, вид, страница, открытая задача/вкладка/комментарий |
| localStorage пользователя | Версия схемы, последняя область, колонки/порядок/ширины/закрепления, закреплённые фильтры, сохранённые представления по областям |
| sessionStorage пользователя | Последнее состояние списка и прокрутки каждой области в этой вкладке, валидируемый контекст возврата |
| Память экземпляра страницы | Кеш Task, загрузка, AbortController, выделение, быстрые правки, подписки, фокус |
| Существующее хранилище карточки | Её штатные черновики создания/редактирования/комментария; не копировать их в новый workspace-key |

Новые ключи: `dmb_backlog_workspace_v2:<userId>` и `dmb_backlog_session_v2:<userId>`. Общий локальный marker владения импортом — `dmb_backlog_legacy_claim_v2`, содержащий только userId и идентификаторы/отпечатки импортированных источников. Он не даёт права читать данные сервера и не переносится в профиль другого пользователя. Ключ userId строится только после установленной сессии. У `team` хранится teamId привязки; при смене команды нельзя применять прежние фильтры исполнителей/команд и кеш как состояние новой команды.

Целевой объект настроек:

```json
{
  "schemaVersion": 2,
  "userId": 123,
  "revision": 0,
  "updatedAt": null,
  "lastScope": "team",
  "contexts": {
    "all": {
      "columns": {"settings": {}, "order": [], "widths": {}, "fixed": {}},
      "pinnedFilters": [],
      "views": {"items": [], "defaultId": null}
    },
    "team": {
      "teamId": 7,
      "columns": {"settings": {}, "order": [], "widths": {}, "fixed": {}},
      "pinnedFilters": [],
      "views": {"items": [], "defaultId": null}
    }
  },
  "migration": {"legacyImported": false, "importedAt": null}
}
```

Фрагмент задаёт оболочку, а не пустые defaults. Представление содержит id/name/state и штатные метаданные. Сортировка колонки, присутствующая в legacy column-state, переносится в начальное состояние соответствующего списка/представления; не теряется из-за другого места в v2.

### 7.2. Приоритет восстановления

1. Явный полный URL v2 либо Back/Forward-снимок.
2. Для перехода через меню/переключатель — сохранённое в текущей вкладке состояние целевой области.
3. Представление по умолчанию этой области, если нет состояния из пунктов 1–2.
4. Персональные настройки колонок/фильтр-панели, затем shared display settings, затем defaults §9.

URL управляет выборкой; локальные колонки дополняют его, а не заменяют. Восстановление не требует повторного применения default-view на каждом обновлении данных. Не смешивать часть состояния одной области с частью другой.

### 7.3. Сохранённые представления

Сохраняются поиск, все фильтры и quick-флаги, обе сортировки, table/cards, видимость/порядок/ширины/закрепление колонок. Страница при применении сбрасывается в 1. Выделение, правки, task/comment, прокрутка и data-cache в представление не входят. Закреплённые фильтры — отдельная настройка, как сейчас.

Каталоги представлений независимы для `team` и `all`. Сохранить создание, применение, переименование, удаление с подтверждением, обновление текущими настройками, назначение/снятие default и индикатор изменений. Применение не переключает область скрытно. Одинаковые имена и id в разных областях допустимы. Адаптированное представление после применения считается чистым; новые колонки и нормализация не создают ложный dirty-индикатор. Имя ограничивается действующими 80 символами и экранируется.

### 7.4. Несколько пользователей и вкладок

Выход, вход под другой учёткой, отзыв сессии и смена команды очищают память страницы, выделение, callbacks и незавершённые запросы. Нельзя показывать даже на один кадр предыдущую выборку. Персональные настройки прежнего userId не переименовываются под нового.

Разные вкладки разделяют localStorage, но имеют независимые session-state/выделение/правки. `storage`-событие обновляет доступный каталог настроек без автоматического применения к активному вводу. Записи одного user-key сериализуются через Web Locks с общим именем `dmb-backlog-preferences-v2:<userId>` либо эквивалентный механизм с той же гарантией. Внутри блокировки перечитать объект, проверить revision, применить изменение и увеличить revision/updatedAt; одиночные read-modify-write без блокировки недостаточны. Самостоятельные view имеют revision для обнаружения редактирования одной записи. При конфликте обновления одного представления показать выбор «Перечитать»/«Сохранить как новое», не молча перезаписывать более новую редакцию. Если сериализация или storage недоступны, настройки текущей сессии работают в памяти с предупреждением о невозможности надёжно сохранить их; нельзя выдавать небезопасный fallback за успешную конкурентную запись. Эта гарантия относится также к импорту и записи lastScope/колонок, чтобы они не затирали каталог видов.

## 8. Перенос legacy-настроек

### 8.1. Карта переноса

| Источник | Назначение |
|---|---|
| `dmb_backlog_columns_v1` | `contexts.all.columns` плюс прежняя column-sort в начальное состояние |
| `dmb_team_columns_v1` | `contexts.team.columns` плюс column-sort |
| `dmb_saved_views_v1_backlog` | `contexts.all.views` |
| `dmb_saved_views_v1_team` | `contexts.team.views` |
| `dmb_pinned_filters_v1_backlog` | `contexts.all.pinnedFilters` |
| `dmb_pinned_filters_v1_team` | `contexts.team.pinnedFilters` |

Уточнение 04.11.2026 по прямому указанию пользователя: баннер переноса полностью удалён. Старые настройки привязаны к браузеру и области без подтверждённого владельца; автоматически переносить их или показывать предложение при входе нельзя. При необходимости пользователь сам выбирает «Перенести прежние настройки» в меню «Операции» и подтверждает принадлежность. Marker с userId, предупреждение о другом владельце, сохранение исходных ключей и идемпотентность ручного переноса остаются обязательными.

### 8.2. Алгоритм

1. Прочитать исходные ключи без их изменения. Каждый блок разобрать независимо; один повреждённый JSON не отменяет остальные.
2. Валидировать по allowlist каталога. Удалить дубликаты ключей, неизвестные поля и некорректные ширины; дописать новые известные колонки один раз в порядке каталога. Обязательный ID восстановить первым и видимым. Пользовательское `false` и пустой список закреплённых фильтров сохранить как явный выбор.
3. Сопоставить legacy `settings/order/widths/fixed/sort` и `view.state.toolbar/page`; сохранить имена, defaultId, поиск, token-наборы, table/cards и quick-флаги. ID представлений детерминированно снабдить namespace источника и перепривязать defaultId. Несуществующий defaultId сбросить без удаления списка.
4. Построить v2-объект в памяти. Если v2 уже содержит пользовательские изменения, не заменять их: импорт добавляет отсутствующее, совпадение предлагает сохранить отдельной копией. Повторный импорт того же исходного id не создаёт дубликат.
5. Под блокировкой из §7.4 одним `setItem` записать весь workspace-key с provenance источников и результатом миграции, перечитать и проверить schema/userId/полноту блоков. Только после успешного read-back записать marker владения и показать успех. Marker и workspace не являются общей транзакцией: при сбое marker повторный запуск сверяет provenance workspace и восстанавливает marker без повторного копирования. Claim legacy-набора между разными userId сериализуется отдельной общей блокировкой `dmb-backlog-legacy-claim-v2`; перед показом результата владелец перечитывается. При сбое не показывать полный успех.
6. Показать краткий итог: что перенесено, что потребовало defaults и что осталось недоступно по правам. Отсутствие доступа к области не удаляет её настройки.

Если для импорта нужны обе блокировки, порядок единый: общая legacy-claim, затем preference-lock пользователя; освобождение в обратном порядке после фиксации результата. Пользовательские подтверждения получают до взятия блокировок. Это исключает взаимное ожидание и удержание блокировки во время диалога.

Исходные ключи не удаляются и не перезаписываются. Миграция не отправляет запросы записи на сервер, не читает секреты и не создаёт файлы с настройками. Откат описан в §19. Поведение при команде, сменившейся после импорта, определяется §7.1: пользовательские колонки/виды сохраняются, привязанные к старой команде условия не активируются автоматически.

## 10. Поиск, фильтры, сортировка и счётчики

### 10.1. Поиск и условия

Поиск сохраняет совпадения по внутреннему ID, публичному ID, названию и описанию без учёта регистра; сохраняются подсветка и безопасное экранирование. Ввод до окончания загрузки не теряется. Формат публичного ID не меняется.

Категории допускают несколько значений: ИЛИ внутри одного поля, И между полями. Сохраняются пустые значения `__EMPTY__`, text/range/date-токены, boolean Да/Нет, независимые от показа колонок фильтры, поиск в справочном списке, черновик фильтра с «Применить» и отменой по Escape/клику снаружи. Числовые и календарные диапазоны проходят общую проверку порядка границ. Нулевое значение отличается от отсутствия.

В `team` фильтр ответственной команды показывает фиксированное значение текущей команды и пояснение области; удалить его сбросом или сохранить противоречащую команду нельзя. Legacy team-name-фильтр с другой командой импортируется в представление как требующий исправления, не отбрасывается молча. В `all` команда — обычный множественный фильтр. Поиск/справочники и их ответы не должны давать новые сведения вне уже разрешённых API.

Можно закрепить от 0 до 5 допустимых фильтров, менять их порядок и восстановить начальный набор отдельно для каждой области. Фильтры незакреплённого поля продолжают действовать и отображаются в активных условиях.

### 10.2. Быстрые выборки

Сохранить восемь существующих ключей и вычислений:

| Ключ | Подпись | Условие baseline |
|---|---|---|
| `_overdue` | Просрочено | Задан срок, он в прошлом, статус не терминальный |
| `_urgent` | Важные задачи | Приоритет «ВЫСОКИЙ» |
| `_active` | В работе | Статус задан, не терминальный и не «ХОЛД» |
| `_hold` | Холд | Статус «ХОЛД» |
| `_rejected` | Отклонённые | Статус «ОТКЛОНЕНА» |
| `_current` | Текущие задачи | Существующая функция isCurrentTask |
| `_last_quarter` | Прошлый квартал | Существующая функция isLastQuarterTask |
| `_high_cv` | Проблемный C/V | C/V неизвестен либо >1 |

Терминальные имена baseline: «ВЫПОЛНЕНА», «ОТКЛОНЕНА», «НЕ АКТУАЛЬНА». Не переписывать квартальные и C/V-формулы при объединении. Несколько включённых quick-флагов объединяются через И, как сейчас: каждый является самостоятельным условием. Это явно объяснить в панели; не переносить сюда ИЛИ из других реестров.

### 10.3. Счётчики

Каждый quick-счётчик равен числу совпадений в полной загруженной области до поиска/остальных фильтров, как в исходной реализации. Показать доступное пояснение «В выбранной области, до остальных фильтров». Число «Найдено N задач» учитывает все активные условия до клиентской пагинации. Сумма quick-счётчиков не является итогом и не показывается как итог.

После изменения Task пересчитать оба вида чисел по актуальному снимку. Во время неполной загрузки число неизвестно, а не равно нулю; частичный набор не выдаётся за полную выборку. Сохраняется склонение 1/2/5/11/21 и доступное полное число.

### 10.4. Сортировка и пагинация

Сохранить сортировку toolbar и заголовков, логический порядок справочников, направление, обработку неизвестных/пустых значений и устойчивый дополнительный порядок по внутреннему id. Активная column-sort имеет приоритет над toolbar-sort; её сброс возвращает выбранную toolbar-sort. Перенос старого состояния не превращает отсутствие column-sort в случайную сортировку.

100 записей на клиентской странице. Поиск, изменение фильтра и применение представления переводят на первую страницу; обычное обновление сохраняет страницу и корректирует её вниз, если данных стало меньше. Пустой результат имеет page=1. Смена страницы возвращает к началу таблицы/карточек, сохраняя горизонтальную позицию; обычное обновление не сбрасывает ни одну прокрутку. Навигация страниц доступна с клавиатуры и объявляет текущую страницу.

«Сбросить фильтры» очищает поиск, обычные и быстрые условия, обе сортировки до `id-desc`, выставляет page=1; сохраняет область, колонки, закреплённые фильтры и сохранённые представления. «Восстановить набор фильтров» меняет только состав панели. «Сбросить колонки» меняет только колонки/ширины/закрепления в текущей области. Эти действия должны иметь разные подписи и тесты.

## 11. Таблица, карточки и операции

### 11.1. Таблица и карточный вид

Один renderer обслуживает обе области через конфигурацию. Сохраняются настройки порядка/ширины/закрепления колонок, resize, auto-size, сортировка заголовков, горизонтальная прокрутка и sticky-панели. ID вместе с выбором строк закреплён слева. Заголовки и каркас таблицы остаются при loading/empty/error; состояние внутри tbody центрируется в видимой части горизонтально прокручиваемого контейнера. У пользователя нет двух таблиц с одинаковыми DOM-id.

Карточки используют тот же отфильтрованный и отсортированный набор, ту же страницу и право открытия. Table/cards не меняет область. Quick edit и табличное выделение недоступны в карточном виде; перед уходом из редактора действует §11.3. Сохраняются публичный ID, название, описание, даты, теги, ссылки, статусы, приоритет, исполнители, C/V и прочие реально показанные текущими карточками значения.

Узкие ячейки не меняют данные: truncation имеет доступное полное значение. Jira поддерживает несколько ссылок из массива, JSON-массива и строки через запятую; все ссылки проходят `safeExternalUrl`, строки/атрибуты экранируются. Ссылки на макеты и прочие внешние ресурсы сохраняют защиту внешнего открытия. Вовлечённые команды показываются с существующим преобразованием id/имён. Даты используют общий формат; неизвестное значение отличается от ошибки, ноль — от отсутствия, дата создания не подменяется датой поступления.

### 11.2. Выделение строк

Выбирать можно только доступные для требуемого изменения задачи. Нередактируемые строки не получают действующий checkbox. Header-checkbox означает весь отфильтрованный набор доступных для изменения задач, включая другие клиентские страницы, как в существующем `setAllSelection`. Доступное имя и подпись явно показывают «Выбрать все N доступных для изменения задач в выборке»; предусмотреть indeterminate и «Снять выделение».

Перелистывание сохраняет выделение. Изменение фильтра сверяет его с новой выдачей и правами, исключая больше не видимые/разрешённые ID; отображается новое фактическое число. Смена области/пользователя очищает выделение. Удаление/отзыв доступа убирает соответствующий ID. Выделение не хранится в URL, localStorage или saved-view. Нельзя ошибочно считать выбором только DOM текущей страницы.

### 11.3. Быстрое редактирование и несохранённый ввод

Сохранить текущий перечень редактируемых типов полей, проверки значений и правила согласования статуса/прогресса. Черновики привязаны к внутреннему Task.id и полю, а не к номеру строки. Изменение колонки/сортировки/страницы и фильтра внутри области не теряет введённое. Панель показывает число всех правок и число правок вне текущего видимого набора; сохранение явно охватывает все эти правки. Кеш исходных редактируемых задач не выбрасывается до решения пользователя.

Смена области, режима table/cards, применение сохранённого представления, открытие импорта/массового редактора и уход со страницы при dirty требуют существующего выбора: «Сохранить и выйти», «Выйти без сохранения», «Продолжить редактирование». Сохранение с ошибкой или конфликтом не выполняет запрошенный переход. Отмена оставляет URL, выбранный сегмент, введённое и фокус прежними. Без правок лишнего подтверждения нет. Один жест не создаёт два диалога от router и quickEdit.

Сохранение передаёт только изменённые поля и действующую version каждого Task. Не передавать пустые справочные поля, которые пользователь не менял; не назначать первый элемент справочника. Существующий запрет очистки заполненного типа и возможность сохранить другие поля задачи с прежним пустым типом сохраняются.

При частичном успехе убрать из dirty только подтверждённые сервером поля/задачи; показать конкретные ошибки оставшихся. 409 сохраняет локальные значения и запускает штатное согласование конфликта, а не безусловный повтор поверх чужой версии. 401 проходит обычное восстановление/вход; запрос записи не повторяется вслепую. Во время отправки повторное сохранение блокируется; его результат не применяется в другую пользовательскую сессию.

### 11.4. Создание задачи

Одна общая форма через существующий `openCreateTaskModal`, без дублирующей формы внутри backlogPage. Сохранить обязательность полей, доступные справочники, проверку дублей, штатный request-id/idempotency-контракт и черновик. В `team` передать разрешённую текущую команду как начальный контекст через явный параметр формы. В `all` выбрать единственную отфильтрованную команду только если такая одна и она разрешена для создания; иначе оставить штатный безопасный default. Нельзя автоматически брать первый элемент списка или создавать команду.

Командному редактору нельзя выбрать чужую команду; глобальному — только в пределах прежней серверной policy. Открытие формы и выбор области сами не создают/не меняют записи. После успешного сохранения закрытие/продолжение формы следует действующему контракту; текущая область, фильтры и настройки сохраняются. Если созданная задача не попала в выборку, показать успех и «Открыть задачу», не сбрасывать фильтры. Callback обновляет только действующий контроллер.

### 11.5. Массовые операции

Сохранить существующие типы операций, конструктор отбора, предпросмотр, версии, атомарные проверки разрешений и результат с группами «Изменено», «Без изменений», «Ошибка»/другими фактическими группами сервера. Общий modal не получает задачи вне выбранной области.

Если выделены строки — исходная цель операции только они. Если выделения нет — можно открыть конструктор по текущей отфильтрованной доступной для изменения выборке; до отправки явно показать охват и число задач. Выбранный/отфильтрованный набор нельзя незаметно заменить всей базой. Конструктор сохраняет свои exclude и проверки значений; пустое значение поля не означает изменение без явного выбора этого поля.

Предпросмотр и подтверждение показывают фактические ID/количество. Изменившиеся права/версии между ними обрабатываются существующим серверным ответом. Не ослаблять атомарность API ради частичного успеха UI. Повтор после сетевой неопределённости следует действующему operation-id/idempotency-контракту; автоматический повтор изменяющего запроса запрещён. После результата обновить список и числа, сохранить условия, согласовать оставшееся выделение.

### 11.6. Импорт

Одна текущая форма `importTasksFromExcel`: сохранить поддерживаемые CSV/XLS/XLSX, действующие лимиты/валидацию, декодирование, сопоставление заголовков, просмотр и отчёт по строкам. Для Excel сохранить правило первого листа и первой строки заголовков. Справочные сущности не создаются и не исправляются импортом; неизвестные ссылки объясняются в отчёте.

Импорт использует серверные права каждой операции, а не сегмент. Перед отправкой видны команда/команды и охват фактических данных файла. Нельзя незаметно переписать team_id всех строк на выбранную область. Права командного редактора ограничивают допустимые строки штатными проверками. Пока идёт запись, закрытие/повтор отправки блокируются по текущему контракту. Частичный успех сохраняет отчёт и обновляет реестр при штатном завершении; retry не создаёт дубликаты.

### 11.7. Экспорт

Экспортирует весь текущий отфильтрованный/отсортированный набор до пагинации, в порядке видимых колонок с действующими fieldLabels. Выделение строк само по себе не меняет выгрузку: подпись — «Экспорт текущей выборки». CSV остаётся CSV, даже если иконка/исторический обработчик называются Excel: не обещать XLSX без фактического файла.

Сохранить UTF-8 BOM, `;`, CRLF, экранирование кавычек/переносов и защиту spreadsheet formula injection из taskCsv.js. Ссылочные поля выгружаются читаемыми значениями, публичный ID не заменяется внутренним, C/V — по общей функции. Выгрузка использует сохранённые серверные данные; при dirty явно указать, что несохранённые правки не включены. Пока загрузка неполна/неуспешна, экспорт недоступен с причиной. При пустой выборке показать пояснение без пустого ложного отчёта. Имя файла содержит `backlog`, область и дату; только безопасные символы, без персональных реквизитов.

### 11.8. Общая карточка

Сохранить весь существующий `CARD_TABS` и вход по main/tab/comment, просмотр/редактирование, KPI, сроки и оценки, рабочие задачи и зависимости, статусы встреч, комментарии/упоминания/черновики, ссылки/вложения/скачивание, историю/таймлайн/версии, решения ПИП и штатное восстановление после ошибки. Этот проект не упрощает содержимое карточки и не строит её копию.

Открытие из строки, карточного вида, клавиатуры, публичной ссылки и события `open-task` ведёт в один механизм. Кнопка копирования ссылки сохраняет canonical scope и валидные task/tab/comment, не уничтожая параметры списка в текущем адресе. Для ссылки, предназначенной другому пользователю, получатель использует собственные права и собственные колонки; закрытые атрибуты не кодируются в URL.

После сохранения задача обновляется в списке; если перестала соответствовать фильтру — исчезает из списка после успешной записи с понятным сообщением. Открытая карточка сохраняет своё штатное поведение. Закрытие возвращает фокус к строке/карточке, если она ещё есть, иначе к контейнеру результатов. Несохранённый ввод карточки и комментария защищает её штатный guard; scope-переход не обходит его.

## 12. API, полнота и производительность

### 12.1. Сохраняемый серверный контракт

Переиспользовать `GET /api/v1/tasks/` с существующими page/per_page и одиночным team_id. `team` запрашивает свою команду на сервере; нельзя загрузить весь DMB и только затем скрыть чужие записи. `all` получает разрешённую server-policy область. Обычные множественные фильтры и поиск применяются клиентом ко всему успешно загруженному снимку. Не ограничивать обработку первой API-страницей и не выдавать per_page=1000 за общий максимум задач.

Нет основания менять модели Task, TaskResponse, таблицу tasks или роли. Если реализация требует вспомогательного capability-поля API, оно должно быть производным от существующей policy, обратносовместимым и покрытым контрактными тестами; это не разрешение вводить новые права. Предпочтительно обойтись уже выдаваемыми `task_*`.

### 12.2. Загрузка полного снимка

- Переиспользовать `loadBacklogTaskPages`, расширив его вход внешним signal/идентификатором контекста и контролируемой отменой по §13.
- Не более двух одновременно активных запросов страниц одного снимка; при замене поколения старые запросы отменяются до запуска новой очереди. Общий лимит загрузчика не увеличивается.
- Порядок объединения определяется номером страницы, не временем ответа. Дубликаты Task.id удаляются; нельзя терять записи на границах страниц.
- Загрузка завершена только после всех необходимых страниц. Отказ страницы 2+ означает ошибку полного снимка; частичный список не используется для «полного» счётчика, select-all или экспорта.
- При обновлении можно сохранить последний полный снимок той же области с явной отметкой устаревания; при смене пользователя/области такой fallback запрещён. Неудачное обновление не затирает его пустым массивом.
- Если total/pages противоречат полученным уникальным ID из-за параллельных изменений, один раз перечитать снимок. При повторном расхождении показать неполноту и повтор; нельзя бесконечно перезапускать запросы или молча обрезать.
- Поиск, фильтры и обычная клиентская пагинация не вызывают повторную загрузку уже полного снимка; explicit Refresh и invalidation вызывают.

### 12.3. Контроль регрессии

До рефакторинга зафиксировать на одинаковых fixtures 0/1/100/101/1000/2501 Task: число запросов, peak concurrency, длительность до полного снимка и до интерактивной выдачи, число экземпляров listeners/timers после повторных входов. После сравнить на том же браузере/машине и режиме mock-задержек. При детерминированных данных число запросов ровно `ceil(N/1000)` для N>0 и один для пустой выдачи; team не делает запрос all.

Предлагаемый бюджет приёмки производительности: медиана пяти повторов общего времени не хуже baseline более чем на 20% при тех же данных/задержках; при превышении приложить профиль и устранить причину до полной приёмки. Это сравнительный тест поставки, не производственный SLA. Для проверки полноты фильтр/экспорт должен находить и последнюю запись набора 2501. Не вводить фиксированный скрытый лимит, debounce на минуты или дополнительную фоновую загрузку второй области ради визуального счётчика.

## 13. Жизненный цикл, гонки и realtime

### 13.1. Контекст запроса

Каждая загрузка привязана к `{userId, permissionRevision, scope, teamId, generation}`. Перед применением ответа проверить все части. Необходима отмена при scope-переходе внутри `#/backlog`, уходе, logout, смене команды и повторной загрузке. AbortError не показывается пользователю как сбой. Одной проверки пути из текущего loader недостаточно.

Сценарий A(team) → B(all) → A(team): поздние ответы первых A и B не могут заменить текущие данные, числа, loading или обработчики последней A. Список и карточка имеют независимые request gates, но один и тот же установленный пользовательский контекст. Поздний результат записи нельзя применять к другому userId; повторять запись из-за устаревшего UI нельзя.

### 13.2. Освобождение ресурсов

Контроллер возвращает/предоставляет idempotent `dispose`. При каждом завершении/переходе освобождаются timer автообновления, hash/key/resize/scroll handlers, toolbar/popover/tooltip/selection subscriptions, pending debounce, запросы и callback `setOnTaskSaved`. Общая карточка не должна остаться с callback уже уничтоженной страницы. Освобождение callback проверяет владение/токен регистрации: поздний dispose старого экземпляра не очищает callback нового. Не удалять глобальные listeners других экранов. Повторные переходы между областями не вызывают двойного сохранения и не наращивают число запросов за тик.

### 13.3. Обновления

Сохранить периодический интервал 60 секунд, ручное обновление и invalidation/SSE из app.js. Эти источники сводятся к одному планировщику: одновременно не более одной полной загрузки и одного признака «повторить после завершения». Смена списка не выполняется через полный remount router, если это уничтожит локальное состояние.

При dirty, активной форме, массовой операции, выделении или открытом меню, где обновление нарушит действие, пометить список устаревшим и отложить замену. Показать «Данные изменились — обновить после завершения». После безопасного завершения выполнить одно обновление. Штатные события успешного сохранения обновляют нужную задачу/снимок без потери черновиков других задач. `task.activity.changed` не запускает лишнюю полную загрузку, если текущий app-контракт его исключает.

В скрытой вкладке не перерисовывать фон регулярно; при возврате выполнить одно актуальное обновление, если оно требуется. Долгая загрузка не блокирует переход к другой странице и работу оболочки. Ошибка reconnect не размножает подписки. Отзыв доступа обрабатывается сразу, даже при dirty, с выполнением §4.3.

Контекст возврата передаётся как URL-кодированное `return_to`, содержащее только локальный hash `#/backlog?...`, построенный общим builder. Внешние URL, protocol-relative, javascript/data-схемы и другие пути отклоняются; fallback определяется штатным source. Не расширять существующие уведомительные return-механизмы и не перезаписывать их общей переменной. Полный адрес возврата восстанавливает область, поиск, фильтры, вид, страницу; прокрутка/фокус восстанавливаются из session-state своей вкладки. Временное посещение формы не меняет default-view.

Агент до изменений выполняет поиск всех `#/backlog`, `/team-backlog`, имён компонентов и permission-key в активном коде/тестах/документации и сохраняет реестр мест. Приведённая таблица не заменяет поиск новых потребителей, появившихся после baseline. Исторические отчёты/архивы массово не переименовываются.

## 15. Состояния интерфейса и ошибки

| Состояние | Требуемое поведение |
|---|---|
| Первая загрузка | Каркас активной области, loading, неизвестные числа, повтор записи недоступен |
| В области нет задач | «В этой области пока нет задач»; создание только при разрешении |
| Отбор дал 0 при непустой области | «По выбранным условиям ничего не найдено» и сброс обычных фильтров, без сброса scope |
| Команда не назначена | Специальное объяснение и ссылка в разрешённую all; нет скрытого назначения команды |
| Отказ чтения | Отказ/доступная альтернатива; ни названия, ни счётчики запрещённых объектов не показываются |
| Сбой первого/продолжающего запроса | Ошибка полного снимка и «Повторить»; нет ложного нуля/успеха |
| Сбой обновления полного снимка | Старый снимок той же области с отметкой устаревания; один явный retry |
| Сетевой offline | Состояние сети, сохранённый ввод; отсутствие автоматического повтора записи |
| 409 | Локальные значения и штатное согласование версий |
| Ошибка справочника | Частичное объяснение рядом с зависимым контролом, повтор; не подменять невалидные id первым вариантом |
| Повреждённый URL | Ошибка параметра с адресным восстановлением; без расширения выборки |
| Недоступный storage | Память текущей сессии и предупреждение о несохранении настроек |
| Не найдена задача deep link | Обобщённое сообщение и восстановленный список, без утечки |

Ошибки имеют понятное сообщение, фокус/aria-связь и действие восстановления. Ввод сохраняется, если пользователь не отказался от него или доступ не отозван. Toast не заменяет устойчивое сообщение об ошибке загрузки/валидации. В логах и доказательствах нет паролей, cookies, bearer-токенов и полного содержимого секретных файлов.

## 16. UI kit, адаптивность и доступность

Использовать актуальные [UI_KIT.md](../dmb-backlog/docs/UI_KIT.md), [контракты семейств](../dmb-backlog/docs/UI_KIT_CONTRACTS.md), [протокол ревью](../dmb-backlog/docs/UI_KIT_REVIEW_PROTOCOL.md) и [правила sticky-таблиц](../dmb-backlog/docs/STICKY_BACKLOG_TABLES.md). Новые локальные размеры/цвета кнопок и дубли семейств не вводить. FilterChip, InfoChip, Counter и сегменты имеют разные роли; число 0 не маскируется прочерком. Типографика, темы, focus-ring и слои overlay сохраняются.

Обязательные размеры окна: 320×780, 390×844, 768×1024, 1024×768, 1440×900, 1920×1080; отдельно высота ≤600 px и zoom 200%. Проверять полную оболочку с раскрытой/свёрнутой sidebar, длинными русскими названиями и обеими темами. Таблица может прокручиваться внутри контейнера; горизонтальная прокрутка всей страницы и перекрытие действий недопустимы. При ширине ≤480 px сохраняется существующая компактная раскладка; скрытые с основной панели команды доступны из меню, если действие поддерживается в данном режиме.

Переключатель области и имя команды видны без открытия «Все фильтры». На узком экране допускаются перенос/компактные подписи с доступным полным именем, но не потеря выбранности. Строка поиска не схлопывается до непригодной ширины. Пагинация, меню и пустое состояние не уезжают за видимый контейнер.

Все действия доступны Tab/Shift+Tab/Enter/Space. Сегменты, меню, popover и диалоги следуют своим UI-kit keyboard-контрактам; focus trap и возврат фокуса сохраняются. `/` фокусирует поиск и `R` обновляет только при отсутствии ввода в input/textarea/select/contenteditable и конфликтующих модальных окон; комбинации браузера не перехватываются. Escape сначала закрывает верхний слой и не теряет dirty. `aria-pressed`, `aria-current`, disabled/reason и label действительны после каждого render. Изменение результата объявляется одной умеренной live-region, а не каждой ячейкой. Сенсорные цели — по общему контракту, минимум 44 px для соответствующих действий. Контраст измеряется по фактическим цветам; screenshot сам по себе его не доказывает.

## 17. Рекомендуемая структура реализации

Названия новых файлов ниже — проектные, их можно уточнить при сохранении ответственности. Не создавать монолит из механического склеивания двух старых файлов.

UI-scope, permission-scope и preference-key — разные сущности. Не подставлять строку `all` в старый `hasWritePermission('backlog')` и считать это готовой авторизацией. Отвязать общие UI-адаптеры от предположения, что существуют ровно два DOM-дерева backlog/team. Смена preference-context не создаёт второй скрытый экземпляр страницы.

Старые `renderTasksPage/initTasksPage`, `renderTeamBacklog/initTeamBacklog` допустимы как временные тонкие адаптеры на этапе переноса. К завершению нет двух самостоятельных кешей, таймеров, renderer и наборов правил; alias ведёт в общий контроллер. Если экспорты временно нужны внешним потребителям, оставить только документированную оболочку без логики. Общие компоненты, используемые канбаном/отчётами, меняются обратносовместимо либо все их потребители переводятся в этой же поставке.

## 19. Ввод в работу и откат

Поставка frontend-модулей и их import/cache-version выполняется согласованно. Новые query-state и preference-schema имеют версию; устаревшая вкладка не должна перезаписать v2-объект legacy-форматом. Обязательный серверный feature-flag и новая env-переменная не требуются. Если инфраструктура уже имеет механизм staged rollout, использовать его без изменения прав/данных.

Перед включением сохранить возможность вернуть предыдущую сборку frontend. Откат возвращает старые два экрана и их ключи; v2-key остаётся нетронутым для повторного ввода, а legacy-key не обновляется из v2 автоматически. Пользователю объясняется, что настройки, изменённые только в новой версии, сохранятся в v2 и не появятся в старой. Данные задач не откатываются: изменения, сделанные штатными операциями, остаются серверными бизнес-данными. SQL restore, удаление Task, изменение ролей и справочников для отката запрещены.

Основания для остановки ввода: утечка/расширение доступа, потеря dirty/настроек, неполный экспорт без предупреждения, поломка старых deep links, появление чужой области при гонке или невоспроизводимый повтор записи. При проблеме сохранить обезличенные доказательства и конкретную точку отказа, вернуть предыдущий UI при необходимости; нельзя объявлять весь проект неработоспособным без проверки остальных поверхностей.
