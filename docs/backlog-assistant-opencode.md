# Серверный OpenCode и границы интеграции помощника по бэклогу

Помощник поставляется как самостоятельный сервис. Его можно разрабатывать, тестировать, размещать и обновлять независимо от DMB. Целевой runtime — серверный `opencode serve`, подключаемый через адаптер. Пользовательский интерфейс и API данных не зависят от типов SDK, файлов истории и идентификаторов OpenCode.

Это техническое уточнение [проекта помощника](backlog-assistant-design.md) по требованию пользователя от 14.10.2026 о максимальной обособленности. Контракты проектные; сервер OpenCode и интеграция в этом чате не запускались. Сценарии, правила ответа и права из основного проекта сохраняются.

## 1. Что входит в самостоятельный пакет

| Часть | Владелец |
|---|---|
| Диалоги, пользовательский контекст и выбранные объекты | Backlog Assistant Service |
| Очередь вопросов, идемпотентность и управление запуском | Backlog Assistant Service |
| Prompts, формат ответа, оценочный набор | Пакет агента |
| Agent API, RuntimePort, OpenCode Adapter и MCP Tool Bridge | Пакет агента |
| Собственная БД, миграции, deployment, health-check и метрики | Пакет агента |
| Вход пользователя, связь с AuthSession, разрешённые данные | DMB |
| QuerySpec, доменный поиск, формулы, проекции полей, источники | DMB Data API |
| Панель, контекст страницы и переход к карточкам | UI DMB через Integration Gateway |

Агент не импортирует Python-модули DMB, не читает его файлы, не имеет DB credentials и не хранит копию пользователей, ролей, команд или бизнес-справочников. Ссылки `subject_ref`, `object_ref`, `receipt_ref` непрозрачны для его хранилища. Он понимает опубликованную схему данных, но не таблицы и связи ORM.

Единица поставки — каталог `agents/backlog-assistant/`, допускающий перенос в отдельный репозиторий. Собственный lockfile, контейнеры, конфигурация, миграции и тесты не используют окружение соседних агентов. В production — отдельная БД; общий PostgreSQL instance возможен при разных databases, ролях и запрете взаимного доступа.

Для автономной разработки нужен только Fake Data API с синтетическими ответами и FakeRuntime. Для проверки OpenCode fake runtime заменяется реальным изолированным runtime, а DMB ещё может оставаться имитатором. Затем подключается DMB Data API без изменения диалогового кода.

## 2. Три внешних контракта

### 2.1. Публичный API продукта

Браузер обращается к `/api/v1/backlog-assistant/*` в DMB. Gateway аутентифицирует пользователя, проверяет пилот и принадлежность контекста, затем вызывает внутренний Agent API. Он не исполняет агентный цикл и не содержит конфигурацию модели.

Внутренний Agent API `/v1/*` предоставляет sessions, messages, runs, cancel, results и feedback из основного проекта. Входящая идентичность — короткоживущее подписанное gateway-подтверждение `issuer`, `audience`, `subject_ref`, `issued_at`, `expires_at`, `request_digest`, `nonce`. Подпись и mTLS проверяются сервисом, запрос привязывается к методу/пути/телу. Браузер не может сформировать это подтверждение или передать ему свою роль.

Диалог принадлежит `(issuer, subject_ref)`; другой пользователь, даже зная его UUID, не может его читать. DMB gateway не является произвольным reverse proxy к сервису: опубликован только allowlist путей и методов. Ответ проходит проверку источников в DMB перед выдачей пользователю.

### 2.2. API предметных данных

Внутренний prefix DMB: `/internal/backlog-assistant/v1`. Этот API обслуживает разрешённые чтения, квитанции источников и управление делегированием. Он не публикуется в браузер или напрямую в сеть runtime.

| Операция | Кто вызывает и что делает |
|---|---|
| Регистрация `execution_ref` | Только доверенный код gateway DMB после пользовательской авторизации; фиксирует subject, AuthSession, контекст, срок и назначенный agent-service |
| `POST /executions/{id}/activate` | Аутентифицированный worker активирует уже зарегистрированное исполнение и получает краткоживущий grant; не может зарегистрировать произвольного пользователя |
| `POST /executions/{id}/check` | Bridge или контроллер модельных вызовов проверяет актуальность исполнения, срок и lease |
| `GET /executions/{id}/tools` | Bridge получает разрешённый каталог tools с JSON Schema и версией |
| `POST /executions/{id}/tools/{name}` | Bridge передаёт аргументы инструмента и tool_call_id; DMB выполняет чтение в текущей области доступа |
| `POST /sources/validate` | Проверка квитанций и всех зависимостей перед использованием истории или отправкой следующего контекста модели |
| `POST /answers/verify` | Проверка кандидата: схема, фактические значения, ссылки, все использованные источники и текущие права; выдача проверенного результата |
| `POST /executions/{id}/revoke` | Gateway/управление DMB отзывает исполнение; worker может завершить только собственное исполнение, не продлить или расширить его |
| `POST /receipts/purge` | Сервис удаляет квитанции только своих удаляемых разговоров; без удаления рабочих объектов |

Это проектный контракт DMB, а не существующие endpoints OpenCode. Конкретное транспортное представление служебных операций закрепляется OpenAPI до реализации. POST чтения допустим для сложного QuerySpec; обработчик не получает права на изменение предметных таблиц.

API не принимает raw SQL, имя таблицы, произвольный URL, `user_id`, роль или AuthSession из аргументов модели. Личность берётся из исполнения, а разрешение вычисляется как первоначально делегированная область ∩ текущие права ∩ фильтры вопроса. Повышение роли во время запуска не расширяет уже выданное делегирование.

Чтение старой истории не оживляет истёкший grant. Для `/sources/validate` и проверки сохранённого ответа gateway выдаёт отдельное краткоживущее подтверждение текущего пользовательского чтения, привязанное к subject и конкретным receipt refs. Оно разрешает только проверку/выдачу этих ранее сохранённых источников и не разрешает запуск новых tools. Во время активного вопроса аналогичная проверка привязана к действующему execution. Service-auth без одного из этих контекстов не раскрывает источники.

### 2.3. Контракт инструментов

Имена и схемы инструментов из основного проекта доступны через `DataPort`, одинаковый для DMB и Fake Data API. MCP bridge отображает их в инструменты runtime; он не выполняет доменные вычисления и не читает БД.

Минимальный конверт результата:

```text
ToolResult
  contract_version
  tool_call_id
  execution_ref
  tool_name
  status: ok | partial | unavailable
  data: результат по схеме конкретного инструмента
  snapshot_ref
  observed_at
  coverage
  sources[]: source_id, receipt_ref, kind, version, fields
  limitations[]
```

`receipt_ref` создан DMB и связан с конкретными execution, subject, tool_call, результатом и его хешем. Полный манифест участников агрегата остаётся в DMB. Агент не может сам изготовить квитанцию, заменить значения таблицы или получить доступ через чужой receipt ID. Перед публикацией проверяются все источники, переданные модели, включая не процитированные в финальном ответе. Если часть стала недоступной, кандидат не публикуется.

Типы предметных ссылок и действий стабильны, URL UI добавляет DMB. Внутренние имена столбцов не являются публичными полями контракта. JSON Schema и OpenAPI выпускаются с версиями; несовместимая major-версия закрывает функцию с понятной ошибкой. Минорные изменения проходят consumer/provider contract tests. Хеш каталога tools фиксируется в запуске.

## 3. Делегирование и изоляция пользователей

Последовательность одного вопроса:

1. Gateway проверяет пользовательскую сессию, создаёт стабильный `execution_ref` по ключу идемпотентности и регистрирует его в DMB. Сохраняются разрешённый контекст и предельное время исполнения.
2. Сервис агента принимает команду с execution_ref, проверяет владельца разговора, сохраняет run и помещает его в собственную очередь. Повтор команды возвращает тот же run.
3. Worker получает lease и активирует исполнение в DMB по своей service identity. DMB ещё раз проверяет AuthSession и выдаёт непрозрачный grant с TTL не более 120 секунд и не позже предельного времени исполнения. При замене lease предыдущий grant отзывается.
4. Grant хранится в памяти доверенного bridge/broker. В DMB хранится его хеш и привязка. Он не попадает в текст вопроса, tool schema, аргументы модели, историю OpenCode, UI или обычные логи.
5. OpenCode обращается только к bridge. Bridge привязан к одному execution и добавляет нужные credentials сам. Перед каждым чтением DMB повторно проверяет живые права, срок и отзыв. Service credential без активного grant недостаточен для чтения рабочих объектов.
6. Перед следующим модельным вызовом доверенный контроллер проверяет `/check`; перед выдачей ответа DMB выполняет `/answers/verify`. При невозможности проверки действует отказ, без выдачи старых данных.
7. Завершение/отмена отзывает grant, завершает runtime и очищает временное состояние. При сбое очистку повторяет janitor; слот пула освобождается после подтверждённого уничтожения экземпляра и его state, для следующего вопроса создаётся чистый экземпляр.

Доступ не продлевается просто потому, что runtime продолжает работать. Истёкший или отозванный запуск требует нового вопроса с новой пользовательской авторизацией. Межсервисный mTLS, делегирование конкретного пользователя и Basic auth OpenCode решают разные задачи и не подменяют друг друга.

Сервис агента и bridge являются доверенными компонентами, обрабатывающими разрешённые факты; изоляция защищает пользователей от смешивания контекста моделью и ошибочных межзапусковых credentials. Она не объявляет скомпрометированный управляющий сервис безопасным.

## 4. RuntimePort

Доменный код использует собственные типы:

```text
RuntimePort
  prepare(RunContext, ToolCatalog, AnswerSchema) -> RuntimeHandle
  submit(RuntimeHandle, InputEnvelope, dispatch_ref) -> DispatchReceipt
  observe(RuntimeHandle, cursor) -> RuntimeEvent[]
  inspect(RuntimeHandle) -> RuntimeState
  collect(RuntimeHandle) -> AnswerCandidate
  cancel(RuntimeHandle) -> CancellationReceipt
  dispose(RuntimeHandle) -> CleanupReceipt
```

`RunContext` включает execution_ref, модельный профиль, версии prompts/tools, разрешённый контекст и бюджеты. Он не содержит ORM, браузерный JWT и DB credentials. `RuntimeHandle` доступен только worker/adapter; UI видит исключительно application run_id.

События adapter: started, progress, tool_started, tool_finished, usage, candidate_ready, failed, cancelled. Сырые OpenCode Parts, сообщения SSE и текст внутреннего рассуждения не становятся публичными событиями продукта. Adapter проверяет соответствие экземпляра, session_id и message_id текущему запуску.

Цикл планирования и вызовов модели выполняет OpenCode. Сервис управляет жизненным циклом, бюджетом, авторизацией и результатом; не создаётся второй конкурирующий агентный планировщик. FakeRuntime воспроизводит те же события для тестов. Смена runtime не требует менять tools, Data API, UI и таблицы диалогов.

## 5. Подтверждённые точки подключения OpenCode

Официальная документация на 14.10.2026 описывает headless HTTP-сервер, `/doc`, проверку `/global/health`, создание сессии, отправку `prompt_async`, чтение сообщений, abort и удаление сессии. Server API защищается настроенными username/password. Это основа адаптера; пользовательская авторизация DMB реализуется отдельно. [OpenCode Server](https://opencode.ai/docs/server/)

| RuntimePort | Отображение на OpenCode |
|---|---|
| prepare | Проверить версию/готовность экземпляра и создать `/session` |
| submit | Передать prompt в `/session/{id}/prompt_async` с известным messageID |
| observe / inspect | Частный поток событий и сверка статуса/сообщений нужной сессии |
| collect | Прочитать завершённый ответ и преобразовать его в AnswerCandidate |
| cancel | `/session/{id}/abort` |
| dispose | Удалить сессию, завершить экземпляр и очистить его отдельный state |

SDK позволяет подключиться к существующему серверу и запрашивать JSON по схеме через structured output. Adapter должен ограничить `retryCount`, учитывать внутренний инструмент `StructuredOutput` и самостоятельно проверить итоговый JSON. Совпадение схемы не заменяет проверку фактов. [OpenCode SDK](https://opencode.ai/docs/sdk/)

MCP поддерживает локальные процессы и remote-подключение с headers; для явно выданного service token можно отключить интерактивный OAuth. Для нашего агента выбирается приватный remote bridge с отдельным токеном конкретного запуска. Токен bridge позволяет связаться только с ним; DMB grant остаётся в доверенном broker. [OpenCode MCP](https://opencode.ai/docs/mcp-servers/)

В репозитории [приоритизатора](../agents/value-priority-assessor/package.json) закреплена версия `1.17.13`. Она является локальным примером, а не автоматически выбранной версией нового сервиса. Перед реализацией закрепляются проверенные OpenCode binary, SDK, image digest и snapshot API-схемы. Документация может описывать более новую сборку, поэтому перечисленные возможности подтверждаются probes выбранной версии.

## 6. Изоляция runtime

Базовая топология — отдельный OpenCode instance на один вопрос, одна session и один bridge-контекст. Рабочий каталог, home/XDG-каталоги, конфигурация, локальная БД OpenCode, кеши и временные файлы не разделяются между активными запусками. Общим может быть только неизменяемый образ с заранее установленными зависимостями.

Разговор пользователя сохраняется в сервисе агента. Перед следующим вопросом DMB проверяет источники истории, после чего сервис собирает минимальный разрешённый контекст и передаёт его новому runtime. Долгая сессия OpenCode не является хранилищем продукта. Это исключает зависимость от его compaction и скрытой истории при отзыве доступа.

Тёплый пул допускается для чистых, ещё не привязанных экземпляров. После работы экземпляр уничтожается; повторное использование диска между пользователями не допускается. Пул «один общий OpenCode сервер, разным пользователям только разные session_id» не является принятой изоляцией. Переход к нему потребовал бы отдельно доказанной изоляции конфигурации, MCP, событий и всех хранилищ.

OpenCode слушает loopback внутри контейнера/закрытого узла, управляющий порт доступен только adapter. Нет публикации raw API в UI, автоматического mDNS, произвольного proxy и общих credentials с рабочим компьютером разработчика. Сетевая политика разрешает runtime только свой bridge и контролируемый endpoint модели. Код и БД DMB не монтируются в workspace; Docker socket также не выдаётся процессу модели.

Сетевой сбой abort не означает подтверждённую остановку: launcher ограничивает процесс/контейнер по времени и уничтожает его, grant уже отозван. Проверяется удаление записей runtime и логов, а не только исчезновение session из списка.

## 7. Конфигурация агента и ограничения OpenCode

Поставляется собственный primary agent `backlog_assistant` с системной инструкцией из основного проекта. Adapter явно указывает его при создании prompt и проверяет существование до старта. Модель, язык, схема ответа и разрешённые инструменты определены пакетом, а не пользовательским сообщением.

OpenCode имеет конфигурируемые permissions; многие действия по умолчанию разрешены. Поэтому пакет задаёт запрет по умолчанию и точный allowlist обнаруженных предметных MCP-tools. Shell, файловые операции, webfetch/websearch, подагенты, загрузка произвольных skills и интерактивный question не входят в профиль. Неожиданный permission request отклоняется, а запуск завершается определённой ошибкой. [OpenCode Permissions](https://opencode.ai/docs/permissions/)

Общие настройки OpenCode сливаются из нескольких источников; один файл не гарантирует чистое окружение. Runtime стартует с изолированной конфигурацией, отключёнными sharing, autoupdate и snapshots, а preflight проверяет итоговый набор agents/tools/plugins/providers. Отсутствие нашего primary agent не должно приводить к незаметному использованию build-agent. [OpenCode Config](https://opencode.ai/docs/config/)

Политика формируется из точных ID tools после сверки с подписанным/версионированным каталогом. Широкий allow по префиксу не должен автоматически разрешать новый инструмент после обновления bridge. Служебный StructuredOutput допускается отдельно только если он требуется выбранной версией. Результат `clarification` возвращается в UI как обычный ответ; консольные вопросы не используются.

Настройка `steps` ограничивает агентные итерации, но не заменяет наш бюджет сетевых обращений, retries и токенов. [OpenCode Agents](https://opencode.ai/docs/agents/)

Для принудительного бюджета каждый runtime обращается к модели через доверенный контроллер/прокси разрешённого провайдера с контекстом запуска. Он проверяет статус исполнения, учитывает реальные запросы и ограничивает токены по возможностям provider protocol; time/tool quotas дополнительно обеспечиваются worker/bridge. Если выбранный провайдер или сборка OpenCode не позволяют проверить необходимые ограничения, это конкретная причина не принимать такой профиль для пилота. Данные usage после завершения сами по себе не являются жёстким ограничителем расходов.

## 8. Доставка prompt и завершение

Наш API гарантирует идемпотентность создания run, а не недоказанное exactly-once исполнение LLM. До отправки worker сохраняет dispatch_ref, instance/session/message refs и состояние `dispatching`. После подтверждённого ответа фиксирует `accepted`. messageID используется для сверки и корреляции; его наличие не объявляется доказательством дедупликации OpenCode.

При timeout или разрыве соединения после отправки adapter сначала читает сообщения/статус того же экземпляра. Он не повторяет prompt автоматически. Если нельзя установить доставку, ожидает до предельного срока, затем отзывает grant, останавливает runtime и помечает run `interrupted`. Повтор пользователем создаёт новый execution, сохраняя связь с предыдущей попыткой.

SSE помогает показывать этапы, но не является единственным источником истины. Пропуск события и reconnect компенсируются чтением статуса и сообщений. `completed` ставится только после получения финального кандидата, проверки схемы и положительной проверки источников в DMB. Повторное открытие completed-ответа заново проверяет актуальные права.

Потеря DMB Data API блокирует новые tool calls, контекст и итоговую выдачу. Потеря сервиса агента не затрагивает обычные операции бэклога. Потеря runtime сохраняет канонический разговор в БД агента, но не разрешает выдавать незавершённый текст как ответ.

## 9. Контрольные проверки перед интеграцией

| Проверка | Ожидаемый результат |
|---|---|
| Чистая поставка | Агент и Fake Data API запускаются без checkout DMB и соседних агентов |
| Версия OpenCode | Записаны binary/SDK/image версии; создание, prompt_async, события, structured output, abort и delete подтверждены выбранной сборкой |
| MCP | Видны только tools из контрактного каталога, аргументы/выход валидируются; discovery не даёт модельных прав на регистрацию сервера |
| Два пользователя | Разные instances, bridge-контексты и хранилища; перекрёстные session/execution/receipt IDs не дают доступа |
| Передача credentials | Нет пользовательского JWT и DMB grant в prompt, tool args, transcript, клиентском ответе и логах |
| Смена прав | Отзыв во время чтения/LLM/выдачи и повторного открытия истории закрывает доступ, включая непроцитированные источники |
| Runtime privileges | Нет shell/files/web/skills/subagents; нет перехода к build-agent; permissions не требуют участия оператора |
| Конфигурация | Чужие глобальные настройки, plugins и MCP не попадают в effective config |
| Повтор доставки | Timeout submit не создаёт второй prompt; lease сменяется без второго активного исполнителя |
| Ограничения | Учитываются реальные provider requests, retries, токены и tools; превышение вызывает остановку |
| Очистка | После успеха, отмены и падения удалены state/logs/сессия runtime; dirty instance не возвращается в пул |
| Подмена runtime | FakeRuntime и OpenCodeRuntime возвращают один контракт ответа без изменений UI/Data API |
| Независимое обновление | Старый совместимый Agent API работает с новым DMB и наоборот; несовместимость закрывается явно |

Заглушки пользователей и прав строятся в памяти; изменения защищённых данных БД возможны только по прямому указанию пользователя. OpenCode-пробы используют синтетический API данных и разрешённую тестовую модель. Успех чтения документации не заменяет результаты этих проверок.

## 10. Порядок реализации

1. Выпустить схемы Agent API, Data API, tools и AssistantAnswer, подготовить автономные имитаторы.
2. Создать сервис разговоров и RuntimePort, проверить сквозной запрос на FakeRuntime.
3. Подключить OpenCode Adapter и MCP bridge к имитатору данных, пройти проверки изоляции и жизненного цикла.
4. Реализовать в DMB только gateway, Data API, grants и receipts с существующими ACL.
5. Подключить панель и провести сквозную приёмку на разрешённом наборе данных.

Начало с контрактов и отдельного runtime позволяет реализовать серверный OpenCode сразу, без последующего извлечения агента из монолита. Дополнительные процессы и хранилище увеличивают эксплуатационную стоимость; эта цена принята в проекте ради требуемой обособленности. Масштабирование и изменение модели выполняются внутри пакета агента, сохраняя DMB-контракт.
