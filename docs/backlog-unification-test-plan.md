# Программа приёмки объединённого бэклога

Приложение к [ТЗ на объединение страниц](backlog-unification-spec.md). Все приведённые критерии обязательны для полной приёмки. Таблицы задают будущие проверки, а не выполненные тесты. Один параметризованный тест может подтверждать несколько критериев, если отчёт содержит отдельный результат каждого из них.

## 1. Безопасная среда и данные

Для unit/browser-тестов использовать синтетические JS/Python-объекты и подменённый API. Они описывают права/команды/пользователей без создания этих сущностей в БД. Для живой проверки использовать только готовые профили из паспорта тестовых данных и уже существующие справочники/команды. Запрещено создавать или менять защищённые сущности даже ради тестовой подготовки; общие setup/seed существующих suites сначала проверить на соблюдение этого условия. Наличие изолированной БД само по себе не отменяет запрет AGENTS.md.

При запрошенной будущей реализации штатные операции с обычными Task допустимы в необходимых для её проверки пределах. Отмечать созданные обычные рабочие записи и очищать только их разрешёнными средствами, без каскадного удаления защищённых данных. Не запускать реальный импорт без заранее проверенного файла и понимания его целей.

Живой вход — только `http://127.0.0.1:8000`, сначала действующая сессия, затем готовые QA-профили с минимальной ролью. Реквизиты читаются программно без печати и передаются только форме проверенного origin; не сохраняются в менеджере паролей/отчёте/скриншоте. Не подменять отсутствующий PostgreSQL SQLite и не включать seed. Если среды или готового профиля нет, соответствующий live-критерий остаётся BLOCKED, а синтетические проверки продолжаются.

### 1.1. Минимальные синтетические профили

| Профиль | Настройки |
|---|---|
| P1 | Чтение DMB, командный доступ, команда 7, явный edit=team/comment=team/delete=none |
| P2 | Чтение DMB, явные edit/comment/delete=none, обе области доступны |
| P3 | Только командный доступ, команда 7, edit=team |
| P4 | Глобальный редактор с явными действиями all и действующими правами создания/импорта |
| P5 | DMB-доступ без команды |
| P6 | Только командный доступ без команды |
| P7 | Нет обоих разделов при обычной внутренней учётке |
| P8 | Customer portal с запрещённым общим бэклогом |
| P9 | Валидные legacy-права без task_* для проверки штатного fallback |
| P10 | Явный task_edit=none при внешне разрешающем имени роли/legacy-permission |
| P11 | Неизвестное явное task_edit либо незагруженный currentUser |
| P12 | Командное read_all/write_all без DMB-чтения: глобальный доступ самостоятельно не выводится |

Это тестовые формы capabilities, не новые роли продукта и не задание их создать. Каждое edit/comment/delete-поле проверяется независимо. Профили с исключёнными комбинациями существующих настроек допускаются в mock-тестах для доказательства fail-closed; их не требуется создавать на стенде.

### 1.2. Наборы Task и состояний

- Своя команда 7, чужая 8, без команды; отдельная задача с team_id=8 и involved_teams=[7]; запрещённая, удалённая и legacy metric_id-запись.
- 0, 1, 100, 101, 1000, 2501 уникальная Task; совпадение поиска и фильтра только в последней записи; страницы с изменённым порядком ответов и дублированием id.
- Длинные русские/латинские названия и имена, кавычки, `<script>` как текст, много ссылок Jira, пустые/null/0/false, неизвестные справочные значения.
- Все 41 baseline-ключа TASK_COLUMNS с различимыми значениями. Для quick-edit — каждый реально разрешённый тип поля; запрещённые поля отдельно.
- Все восемь quick-условий и их пересечения; даты на границах квартала/года с фиксированными часами теста, C/V неизвестен/0/1/>1.
- Валидные, пустые и повреждённые legacy-настройки, одинаковые view-id/name в разных областях, новый столбец, отсутствующий defaultId, width=NaN/negative/чрезмерное число, частичный v2, storage exception и другая учётка.
- Медленные A/B-загрузки, 403/404/409/401/422/500, offline, отказ второй страницы, SSE во время dirty/массовой операции, logout и смена команды во время запроса.

## 14. Уровни проверки и команды

### 14.1. Новые целевые наборы

Рекомендуемые новые имена, которые агент создаёт при реализации: `unifiedBacklogContext.test.mjs`, `unifiedBacklogRouteState.test.mjs`, `unifiedBacklogPreferences.test.mjs`, `unifiedBacklogMigration.test.mjs`; browser suites `unifiedBacklogNavigation.spec.mjs`, `unifiedBacklogOperations.spec.mjs`, `unifiedBacklogLifecycle.spec.mjs`, `unifiedBacklogVisual.spec.mjs`. Можно объединить файлы без потери покрытия и трассировки. Эти названия не являются уже существующими тестами.

Unit проверяет нормализацию/приоритеты/context/миграцию и предикаты. Browser с mock API подтверждает DOM/history/guard/запросы и визуальную геометрию. Backend-policy проверяется отдельно, включая чтение и версии. Живая проверка подтверждает реальный путь сессии/БД/событий и отчётных переходов; mock не заменяет её.

### 14.2. Существующие регрессии

В каталоге `dmb-backlog` уже есть scripts `test:unit`, `test:e2e`, `verify:ui-kit`, `check:ui-evidence`, `check:ui-review`, `check:ui-acceptance`. Проверка UI-evidence может показывать существующие открытые пробелы; агент отделяет baseline от внесённых регрессий и не подделывает их закрытие.

Ключевые frontend-наборы: `backlogPermissions.test.mjs`, `taskCardPermissions.test.mjs`, `backlogTaskLoader.test.mjs`, `backlogFilterCoverage.test.mjs`, `backlogSorting.test.mjs`, `tableSelection.test.mjs`, `taskCsv.test.mjs`; browser `backlogAuditState`, `backlogAuditRemaining`, `backlogAuditClosure`, `backlogFieldParity`, `backlogEmptyValues`, `backlogFilterAlignment`, `backlogKeyboardEditor`, `taskRouteMessages`, `historyConflict`, `taskCardIncrement`, `importGuards`, `importFeedback`, `importAudit` и затронутые reporting/quarterly/UI-kit suites. Точные актуальные пути агент сверяет до запуска. Тесты двух прежних экранов переводятся на два контекста новой страницы, а приём старого alias проверяется отдельно.

Backend-наборы для адресной сверки: `test_task_edit_access.py`, `test_customer_task_scope.py`, `test_task_concurrency.py`, `test_bulk_task_operations.py`, `test_tasks.py`. До запуска проверить fixtures/setup на запись защищённых сущностей и влияние окружения. Если они нарушают AGENTS.md, выполнить безопасные эквиваленты с mock-объектами/готовой разрешённой средой; не запускать автоматическую подготовку пользователей/ролей/команд. В отчёте сохраняется ограничение исходного набора.

Пример команд из `D:\Проект\dmb-backlog` после сверки окружения и наличия новых файлов:

```powershell
npm run test:unit
npm run test:e2e -- frontend/e2e/unifiedBacklogNavigation.spec.mjs frontend/e2e/unifiedBacklogOperations.spec.mjs frontend/e2e/unifiedBacklogLifecycle.spec.mjs frontend/e2e/unifiedBacklogVisual.spec.mjs
npm run verify:ui-kit
npm run check:ui-evidence
npm run check:ui-review
```

Запуск локального приложения для будущей живой приёмки — только штатным корневым `scripts/start-project.ps1` с health-check. Value Priority Assessor не включается без прямого запроса и для объединения не требуется. Доступность памяти/портов не исправлять удалением данных и отключением авторизации. Для этой разработки не требуется публикация на внешнем стенде или отправка сообщений другим людям.

### 14.3. Формат доказательств

В отчёте для каждого ID: статус PASS/FAIL/BLOCKED/NOT RUN, имя теста/точные шаги, среда mock/isolated/live, роль/capabilities без реквизитов, viewport/theme, результат и ссылка на обезличенное доказательство. Для backend/навигации — значимые request/payload assertions; для визуальных критериев — screenshot плюс фактические измерения; для производительности — исходные пять замеров, медиана и baseline. Одна картинка не доказывает все размеры и права.

Групповой PASS допустим только при раскрытии всех параметров. Отсутствующий аккаунт или настоящий zoom200 не заменяются CSS-имитацией с заявлением полной живой приёмки. Полный статус нельзя объявить, пока хотя бы один обязательный ID остаётся FAIL/BLOCKED/NOT RUN. Причины существующих дефектов, конфликтов требований и новых находок сохраняются отдельно от успешно завершённых проверок.
