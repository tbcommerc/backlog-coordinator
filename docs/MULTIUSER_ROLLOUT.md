# Чек-лист многопользовательского развёртывания

> Актуализировано по текущему multi-worker baseline 01.09.2026.

## Реализованные гарантии

- Все изменения задачи требуют `version`; конкурентное сохранение возвращает
  структурированный `409`, а не перезаписывает чужие данные.
- Edit lock является атомарной lease-блокировкой с heartbeat, presence имеет
  уникальность `(task_id, user_id)`.
- Изменение задачи/комментария/вложения/уведомления и запись `event_outbox`
  входят в одну DB-транзакцию.
- Каждый backend worker может запускать outbox dispatcher: строки разбираются
  через `FOR UPDATE SKIP LOCKED`, доставляются в Redis Stream и помечаются
  обработанными. Повторная доставка безопасна для UI, курсор хранится клиентом.
- `GET /api/v1/events/stream` отдаёт авторизованный SSE без удержания DB-сессии;
  task-события фильтруются по области доступа пользователя.
- При внешнем изменении открытая карточка предлагает загрузить свежую версию, а
  при наличии локального черновика предупреждает о предстоящем сравнении версий.
- Notification scheduler защищён PostgreSQL advisory lock. Резервный процесс
  периодически пытается получить lock и подхватывает работу после отказа лидера.
- Refresh rotation и AI-session mutations сериализованы и идемпотентны.
- `client_request_id` задач, комментариев, вложений и сохранённых отчётов
  резервируется в PostgreSQL (`idempotency_records`), поэтому повтор через
  другой worker не создаёт дубль.
- Сохранённые отчёты имеют optimistic-lock `version`.
- `RequirementRequest` и `Report` публикуют авторизованные live invalidations;
  активные списки и detail pages обновляются с debounce.
- ORM-аудит коммитится одной транзакцией с бизнес-записью и коррелируется через
  `X-Request-ID`; OpenTelemetry `trace_id` проходит через backend → agent,
  возвращается в `X-Trace-ID` и сохраняется в `audit_log`.
- Outbox имеет ограниченные попытки для некорректных событий и dead-letter
  наблюдаемость, а `/metrics` отдаёт HTTP/DB/outbox/SSE/agent метрики.
- `GET /api/v1/health/ready` проверяет PostgreSQL, Redis и общее хранилище.
- Dead-letter события доступны полному администратору и через безопасный CLI;
  replay защищён row lock, expected attempts, идемпотентностью и аудитом.
- `compose.production.yaml` поставляет две реплики backend/agent, отдельный
  scheduler, Nginx, Collector, Jaeger и Prometheus.
- Task Prioritiser вызывается stateless по полным атрибутам задачи; backend
  сохраняет результат с task version/lock. Сам сервис остаётся single replica
  с persistent SQLite volume и не публикуется наружу.

## Обязательные условия

- Backend использует PostgreSQL, agent использует отдельную PostgreSQL БД.
- Redis доступен всем backend-экземплярам.
- `ATTACHMENT_STORAGE_DIR` смонтирован как общий persistent volume.
- На старте один раз выполнен `alembic upgrade head`; приложение не запускается
  при ошибке миграции.
- `RUN_STARTUP_SEED=false`, `RUN_STARTUP_MAINTENANCE=false` на стенде.
- Планировщик уведомлений рекомендуется запускать отдельным процессом; advisory
  lock гарантирует единственного активного исполнителя и failover.
- Установлены уникальные `SECRET_KEY` и общий для backend/agent `AGENT_SECRET`.
- Prometheus скрейпит `/metrics` напрямую с каждого instance; подключены правила
  `infrastructure/observability/dmb-alerts.yml`.

## Проверка перед допуском пользователей

1. Создать резервную копию PostgreSQL и проверить восстановление на отдельной БД.
2. Проверить два backend-воркера: чтение общей задачи, конфликт двух сохранений,
   acquire/renew/release edit lock, presence, SSE-инвалидацию и отсутствие
   дублей при разборе outbox.
   Отдельно повторить с одним `client_request_id` создание комментария, загрузку
   вложения и создание/изменение/удаление сохранённого отчёта через разные
   экземпляры backend.
3. Проверить два agent-воркера: два сообщения одной сессии, повтор одного
   `message_id`, отсутствие дублей в истории.
4. Проверить одновременный refresh в нескольких вкладках и повтор старого
   refresh-токена после grace-периода.
5. Загрузить вложение через один backend-экземпляр и скачать через другой.
6. Проверить области доступа команды, Backlog coordinator, отчётов и аналитики на
   заранее подготовленных тестовых учётных записях.
7. Провести нагрузочный тест с целевой конкуренцией и контролировать pool wait,
   p95/p99, долю ожидаемых `409`, backlog/возраст outbox, reconnect SSE,
   ошибки Redis/Agent и блокировки PostgreSQL.
8. Проверить failover scheduler: остановить владеющий lock процесс и убедиться,
   что standby получил lock и выполнил следующий цикл ровно один раз.
9. Проверить `/api/v1/health/ready` через балансировщик для каждого экземпляра.
10. Проверить атомарность аудита: при успешном изменении бизнес-запись и запись
    `audit_log` имеют один `X-Request-ID`, при откате транзакции не сохраняется
    ни одна из них.
11. Создать контролируемое некорректное outbox-событие в изолированной тестовой
    БД, подтвердить переход в dead letter после лимита попыток и срабатывание
    `DmbOutboxDeadLetterPresent`.
12. Проверить оба сценария prioritiser через backend: timeout/502, `422` при
    недостаточных данных, optimistic conflict и отсутствие частичного сохранения.

Создание пользователей, ролей, назначений и состава команд выполняется отдельной
административной процедурой. Этот чек-лист не содержит автоматического изменения
таких данных.

## Критерии остановки запуска

- SQLite или process-local storage используются при `DEBUG=false`.
- Миграция не достигла актуальной Alembic revision.
- Два scheduler одновременно выполняют один цикл (нарушен advisory lock).
- Вложения недоступны между экземплярами.
- Конкурирующее сохранение молча перезаписывает данные вместо `409`.
- Outbox не уменьшается, oldest pending растёт, появились dead-letter rows или
  SSE не восстанавливается.
- Нет проверенной резервной копии и процедуры восстановления.

## Команды выпуска

Из `dmb-backlog/backend` до запуска новой версии:

```powershell
python -m alembic upgrade head
python -m alembic current
```

Актуальная ревизия этой доработки — `f8a0c3d1e942`. После запуска оба health
endpoint должны отвечать успешно, а в Redis должен появиться stream из
`EVENT_STREAM_NAME` после первого изменения обычной рабочей задачи.

Факт доступности Docker и результаты multi-worker PostgreSQL/Redis smoke, k6,
failover и restore drill фиксируются для каждого стенда отдельно. Они остаются
обязательным шлюзом и не считаются выполненными только по unit-тестам. Команды и
сценарии находятся в `PRODUCTION_RUNBOOK.md`.
