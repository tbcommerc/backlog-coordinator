# Техническое задание на редизайн рабочих задач

## 1. Назначение и статус

Переработать интерфейс рабочих задач WorkTask: список, канбан, сводку, карточку, создание, фильтры и выполнение действий. Цель — сократить визуальный шум, сделать понятными ответственность и следующий шаг, сохранить контекст при работе с несколькими задачами и обеспечить одинаковое качество на компьютере и телефоне.

Документ предназначен владельцу продукта, дизайнеру, frontend/backend-разработчикам и QA. **TO-BE DRAFT, 21.10.2026. Реализация этим документом не подтверждается.** Основание и реестр проблем — [предложение по дизайну](work-tasks-design-proposal.md). Источник текущего поведения — код; профильные документы: [WORK_TASKS](../dmb-backlog/docs/WORK_TASKS.md), [WORK_BOARD](../dmb-backlog/docs/WORK_BOARD.md), [UI_KIT](../dmb-backlog/docs/UI_KIT.md).

### 1.1. Соотношение с предыдущим ТЗ

[ТЗ на канбан](work-tasks-kanban-spec.md) продолжает задавать бизнес-правила, безопасность, переходы, курсоры и незакрытые нагрузочные критерии. При принятии настоящего ТЗ визуальные решения ниже заменяют соответствующие решения прежнего ТЗ:

| Область | Принято для этого предложения |
|---|---|
| Скрытые выполненные | Компактный переключатель в панели вида вместо пустой узкой колонки |
| Листание колонок | Управление скрыто при единственной странице; серверная пагинация сохраняется |
| Панель задачи | Режим определяется доступной шириной контейнера и минимальной шириной контента |
| Карточка приёмки | Предъявленный результат расположен выше остальных подробностей |
| Фильтры | Один редактор условий, видимые чипы, ясная область счётчиков |
| Сводка | Скрытое/неизвестное состояние не отображается числом 0 |

До согласования это предложенные изменения. Уже реализованное поведение не переписывать в AS-IS как новое.

## 2. Объём и ограничения

### 2.1. Обязательная поставка

| ID | Требование |
|---|---|
| SC-01 | Обновить рабочее место `#/work-tasks` и глубокие ссылки `#/work-tasks/{id}` |
| SC-02 | Применить единые компоненты списка, компактной карточки, фильтров, свойств и действий |
| SC-03 | Обновить существующую карточку также при открытии из проекта и крупной задачи; особенности модального контейнера допускаются |
| SC-04 | Покрыть создание, редактирование, назначение, исполнение, приёмку, возврат, отмену, переоткрытие, препятствия, чек-лист, обсуждение и материалы |
| SC-05 | Реализовать согласованные светлую/тёмную темы, клавиатуру, сенсорный ввод и адаптивность |
| SC-06 | Сохранить работающие API и расширять только явно перечисленные проекции; изменения команд и модели отдельно не требуются |
| SC-07 | Обновить документацию, каталог компонентов, адресные проверки и инструкцию отката после внедрения |

### 2.2. За пределами обязательной поставки

WIP-лимиты, метрики времени цикла и старения в статусе, ручное ранжирование, пользовательские колонки, swimlanes, массовые изменения, автоматизации, календарь/Гант, глобальный редизайн других разделов, серверная синхронизация сохранённых представлений, новый формат rich text, новая файловая модель и интеграция с внешним трекером.

Не добавлять эти элементы в макет как будто они уже поддержаны. Визуальный прототип использует вымышленные задачи и демонстрирует компоновку; он не заменяет рабочий API и критерии ниже.

### 2.3. Неприкосновенные правила

1. WorkTask остаётся отдельной от крупной Task; один уровень рабочих задач без вложенных подзадач.
2. Существующие статусы: `new`, `ready`, `in_progress`, `in_acceptance`, `done`, `cancelled`. Препятствие, просрочка и возврат не создают новые статусы.
3. Готовность, переходы, приёмка, межкомандное назначение и доступ определяются сервером. UI не получает право произвольно записывать статус.
4. Чек-лист 100% не завершает работу. Завершение WorkTask не меняет автоматически крупную Task или подтверждение результата запроса.
5. Сохраняются version, история, idempotency там, где она существует, ACL и ограничения файлов.
6. Не создавать/изменять пользователей, роли, справочники, состав/атрибуты/ответственных команд. Использовать готовые разрешённые данные для испытаний. Новые системные настройки хранить вне защищённых бизнес-справочников.

## 3. Пользователи и сценарии

Права определяются возможностями конкретной записи, а не проверкой текстового имени роли на клиенте.

| Участник | Задача пользователя | Приоритет информации | Основное действие |
|---|---|---|---|
| Исполнитель | Выбрать следующую работу и предъявить результат | Название, срок, ожидаемый результат, препятствие | Начать / передать на приёмку / завершить |
| Приёмщик | Проверить предъявленный результат | Фактический результат, ожидаемый результат, контекст, автор | Принять / вернуть с причиной |
| Постановщик | Поручить работу и понять состояние | Исполнитель/команда, срок, назначение, препятствие | Уточнить новую задачу / предложить команде |
| Редактор команды | Подготовить и распределить работы | Неназначенные, готовность, исполнитель, срок | Принять назначение / назначить / подготовить |
| Наблюдатель | Просмотреть доступные работы | Название, состояние, срок, результат | Открыть / скопировать ссылку |

Бизнес-заказчик продолжает использовать свой портал запросов. Отображение карточки WorkTask не расширяет доступ к проекту или крупной задаче.

Обязательные сквозные сценарии: открыть личную очередь; найти по номеру/названию; перейти список → доска → карточка → обратно; создать новую работу; подготовить её к исполнению; принять межкомандное назначение; обозначить и снять препятствие; предъявить результат; вернуть с причиной; повторно предъявить; принять; найти выполненную работу; открыть прямую ссылку; восстановить черновик после обновления; разрешить конфликт версий.

## 4. Информационная архитектура и состояние

### 4.1. Терминология

| Текущее/техническое | Пользовательская подпись |
|---|---|
| Раздел WorkTask | Рабочие задачи |
| `new` | Новая / Новые |
| `ready` | К исполнению |
| `in_progress` | В работе |
| `in_acceptance` | На приёмке |
| `done` | Выполнена / Выполнены |
| `cancelled` | Отменена / Отменённые |
| `blocked_reason` | Препятствие |
| Task-контекст | Крупная задача |
| `description` | Ожидаемый результат; подсказка допускает описание работы и критериев готовности |
| `result_text` | Результат работы |

«Мне выполнить», «Мне принять», «Я поручил», «Команда», «Все доступные» сохраняют действующий бизнес-смысл. «Приёмка результата» и «Принятие назначения командой» всегда называются полностью в формах; короткая кнопка должна быть однозначна в своём контексте.

### 4.2. Источники состояния

| Состояние | Где хранить | Поведение |
|---|---|---|
| Подборка, фильтры, сортировка, режим, выбранная задача, мобильный этап | URL, действующие ключи сохраняются | Прямая ссылка воспроизводит выборку с повторной проверкой доступа |
| Номер страницы списка | URL | Сбрасывается при изменении выборки, сохраняется при просмотре задачи |
| Курсоры и прокрутка колонок | sessionStorage по пользователю и нормализованной выборке | Истёкшие курсоры сбрасываются с объяснением |
| Размер панели/плотность/последний режим | Локальные UI-настройки по пользователю | Не изменяют права и бизнес-данные; URL имеет приоритет |
| Несохранённый текст | Действующий механизм черновика по пользователю и задаче | В URL и аналитику не попадает |

**ST-01.** Выбор задачи создаёт запись browser history; Back закрывает карточку и возвращает прежнюю позицию. Открытие из прямой ссылки и закрытие ведёт к соответствующей выборке, а не на неизвестную предыдущую страницу.

**ST-02.** Изменения поискового текста используют replaceState; переключение режима/подборки — понятную навигацию без десятков записей на каждый символ. Back/Forward не запускают команды записи.

**ST-03.** Смена фильтра не выбрасывает введённый текст. Если выбранная задача не входит в выборку, показать «Эта задача вне текущих условий» с действиями «Оставить открытой»/«Закрыть». Не очищать фильтры автоматически.

**ST-04.** При 403/404 скрыть данные задачи и убрать её из локально сохранённых проекций. Не продолжать показывать запрещённые данные ради сохранения контекста.

## 5. Общая компоновка

### 5.1. Широкий экран

1. Существующая глобальная оболочка и её навигация.
2. Строка раздела: заголовок, режимы, «Создать задачу»; 56–64 px.
3. Строка подборок: активное подчёркивание/мягкая подложка, счётчики; 36–40 px.
4. Панель инструментов: поиск, «Фильтры», сортировка/параметры вида; 40–48 px.
5. Чипы выбранных дополнительных условий, только при наличии; перенос на следующую строку.
6. Содержимое и, при открытии, панель задачи.

**LY-01.** При пустом наборе дополнительных условий и масштабе 100% первая строка/карточка на экране 1440×900 начинается не ниже 240 CSS px от верхнего края viewport. Это бюджет, а не требование уменьшать читаемость ради нескольких пикселей.

**LY-02.** Закреплять панель управления и заголовки в границах рабочей области. Не перекрывать фокусируемый элемент, сообщения ошибки и заголовок карточки.

**LY-03.** Список использует одну основную вертикальную прокрутку; карточка может иметь собственную. Доска использует горизонтальную прокрутку контейнера и вертикальную внутри колонок; страница целиком не получает горизонтальный скролл.

**LY-04.** Изменение размера окна вычисляет режим по ширине контейнера, учитывая открытую/свёрнутую глобальную навигацию. Не применять фиксированную сетку, минимальные ширины которой превышают контейнер.

### 5.2. Адаптивные режимы

| Доступная ширина рабочей области | Список | Доска | Карточка |
|---|---|---|---|
| От 1080 px | Полный список; с панелью компактная очередь | Читаемые колонки 260–296 px, при необходимости локальный скролл | Немодальная 520–640 px, если остаётся минимум 420 px списка либо две колонки по 260 px с промежутком |
| 640–1079 px | Колонки сокращаются до названия/участника и состояния | Читаемые колонки с локальным скроллом | Модальная панель 520–640 px, ограниченная viewport |
| До 639 px | Вертикальная очередь | Один этап, выбранный через компактный select | Полноэкранная карточка с возвратом |

Указанные значения — контракт контейнера. Вблизи порога используется более узкий режим, если все минимальные размеры не помещаются. Нельзя показывать две сдавленные области только потому, что viewport пересёк breakpoint.

## 6. Поиск и фильтры

**FL-01.** Локальный поиск: подпись «Найти рабочую задачу», пример «Название или WRK-номер». Ввод с задержкой 300 мс; Enter запускает сразу. Предыдущий запрос отменяется/помечается устаревшим. Результат старого запроса не заменяет новый.

**FL-02.** Кнопка очистки поиска имеет доступное имя. Начальная загрузка, обновление существующего результата и отсутствие совпадений визуально различаются. Не очищать список до получения нового ответа.

**FL-03.** «Фильтры» открывает popover на широком экране и sheet на телефоне: команда, исполнитель, проект, крупная задача, направление, приоритет, статус, признаки внимания. Именованный picker вместо ввода ID. Для длинных списков участников/контекстов — поиск по доступным вариантам.

**FL-04.** Внутри панели изменяется черновик условий. «Применить» применяет один набор; «Отмена»/Escape восстанавливает ранее применённый. Быстрый чип за пределами панели применяет одно действие сразу. Эти два режима не смешивать.

**FL-05.** Каждое нестандартное условие имеет видимый чип с удалением. Удаление одного чипа не сбрасывает остальные. «Сбросить фильтры» сохраняет подборку и режим, очищая поиск и дополнительные условия, возвращая активные статусы и сортировку по вниманию.

**FL-06.** Несколько признаков внимания сохраняют текущую серверную семантику пересечения: каждый выбранный признак добавляет условие AND в `Selection`. Подпись: «Все выбранные признаки». Не менять AND на OR только в клиенте. В случае отдельного продуктового решения менять семантику — версионировать контракт и проверки отдельно.

**FL-07.** «Выполненные» имеет значения «Скрыты», «7 дней», «30 дней», «Всё время». Первое включение по умолчанию — 7 календарных дней Москвы; явный предыдущий выбор пользователя сохраняется. Отдельный фильтр `done` показывает только выполненные; `active_done` — активные и выполненные. `done_period` не фильтрует активные задачи.

**FL-08.** В «Мне принять» показать, что подборка включает ожидающие приёмки работы. Несовместимые статусы не расширяют её молча; интерфейс объясняет ограничение и предлагает сменить подборку.

**FL-09.** Показать текст «N задач по текущим условиям». Счётчики подборок сохраняют действующий серверный смысл; в подсказке указать, какие общие условия они учитывают. До ответа — skeleton/«—», при ошибке — «Не удалось обновить», а не 0.

**FL-10.** Фильтры по проекту и крупной задаче не раскрывают недоступные контексты. Пустой результат и отсутствие права на параметр — разные состояния. Некорректная ссылка не должна незаметно превращаться во «Все доступные».

## 7. Список рабочих задач

### 7.1. Широкая строка

Порядок колонок: **Задача → Исполнитель → Срок → Статус → Меню**. Название занимает оставшееся пространство с минимумом 320–360 px; участник около 160–180, срок 128–144, статус 120–136, меню 36–40. При недостаточной ширине включается компактный режим, без урезания всех колонок до нечитаемости.

| ID | Требование |
|---|---|
| LS-01 | Название 14 px, вес 500, максимум две строки в обзоре; полное значение доступно в карточке и доступном tooltip |
| LS-02 | Под названием — номер и только существующий контекст; «Самостоятельная задача» не повторяется в каждой обзорной строке |
| LS-03 | Участник: инициалы в 24 px аватаре и имя; цвет аватара не кодирует роль/производительность |
| LS-04 | Срок: «Сегодня», «Завтра», «Просрочено на N д.» или «24 окт»; полная дата с годом доступна при фокусе и в карточке. Будущий/прошлый другой год показывается сразу |
| LS-05 | Приоритет «Обычный» не выводится в обзоре; «Высокий» и «Срочный» имеют и знак, и текст. Все значения доступны в свойствах |
| LS-06 | Препятствие/возврат/ожидание назначения видны без открытия. При нескольких сигналах — основной и «Ещё N» с раскрытием; ничего не теряется в карточке |
| LS-07 | Клик по названию открывает карточку; клик по пустой части строки допускается как удобство. Меню, текстовое выделение и ссылки контекста не открывают задачу повторно |
| LS-08 | Меню доступно постоянно, с клавиатуры и на touch; быстрый переход не требует открытия большой формы, если сервер не требует ввода |
| LS-09 | Hover, выбранная строка, фокус и busy различаются. Выбор задачи не делает остальные строки недоступными |
| LS-10 | Группировка не меняет глобальную серверную сортировку и пагинацию. Над группами видна подпись «Группы на текущей странице», пока сервер не возвращает полноценные группы |

Типовая строка 64–72 px. Длинное название, несколько сигналов или масштабирование могут увеличивать высоту. Фиксированная высота с обрезанием существенного текста запрещена.

### 7.2. Компактная очередь

В режиме рядом с карточкой и на телефоне: название; номер/контекст; исполнитель; одна строка срока и статуса; сигнал при наличии. Комбинировать короткие метаданные, не создавать по строке на каждое слово. «Без исполнителя» показывать явно; известное имя не заменять только аватаром.

Пагинация списка остаётся серверной. Общий итог и диапазон показаны внизу; единственная страница не требует неактивных стрелок. После возврата из карточки восстанавливаются выбранная строка, фокус и scroll anchor.

## 8. Канбан

### 8.1. Колонки

**KB-01.** По умолчанию четыре активных колонки в неизменном порядке: Новые, К исполнению, В работе, На приёмке. Включение выполненных добавляет полноценную пятую колонку с подписью периода. Это визуальное изменение; статусы и данные сохраняются.

**KB-02.** При фильтре конкретного статуса показывать только выбранные колонки, рядом видимый чип статуса. Отменённые доступны через фильтр и отдельную выборку, не смешиваются с выполненными. Не выводить ложные нули для скрытых колонок.

**KB-03.** Заголовок колонки: небольшой семантический маркер, название, серверный счётчик. Без повторения статуса на каждой карточке. Ширина 260–296 px, промежуток 12–16 px. При длинном русском заголовке разрешён перенос без уменьшения шрифта.

**KB-04.** Заголовки и локальный pager остаются доступны при прокрутке колонки. Пустая колонка сохраняет высоту и содержит короткое состояние. Различать «Задач пока нет» и «Нет задач по условиям».

**KB-05.** По 20 карточек на страницу, существующий предел 50 сохраняется. При одной странице — нет пустого footer с двумя disabled-кнопками. При нескольких — «1–20 из 83», предыдущая/следующая, явное busy, повтор ошибки текущей колонки. Не накапливать все страницы в DOM.

### 8.2. Карточка доски

Порядок:

1. Номер; высокий/срочный приоритет, если есть; меню «…» с доступным именем.
2. Название, 14/21, вес 500; до трёх строк.
3. Проект/крупная задача, только если контекст есть и разрешён; до одной строки с раскрытием полного названия.
4. Ответственный за следующий шаг с понятной ролью; срок справа или в следующем ряду при недостатке ширины.
5. Чек-лист `3/5`, если непустой; без отдельной крупной полосы прогресса.
6. Исключение: препятствие, возврат или ожидание назначения. До двух строк превью, полный текст в карточке.

**KB-06.** Типовая карточка 132–176 px при названии в две строки и одном контексте; сигналы/длинный текст могут увеличивать высоту. Все карточки одной высоты искусственно не делать.

**KB-07.** Номер вторичен, название первично. Не использовать слово «Действия» в каждой карточке при наличии доступного меню-иконки. Зоны открытия и меню не перекрываются.

**KB-08.** На приёмке показывать «Принимает: имя». При межкомандном ожидании — «Ожидает решения команды …», если название разрешено. Для обычного исполнения — исполнитель. Не выдавать одного участника за другого.

**KB-09.** У выполненной работы выводить дату завершения, а не активную просрочку. Старая причина препятствия не выделяется как текущее исключение. Результат остаётся доступен в карточке.

### 8.3. Переходы

**KB-10.** Основной доступный способ — меню команд. DnD для точного указателя использует те же transition_options, команды и формы; внутриколоночное перемещение не меняет порядок и приоритет.

**KB-11.** Начало drag только после порога перемещения 6–8 px. Клик, выделение текста, скролл и нажатие меню не начинают перенос. Touch использует меню; внедрять конфликтующее с прокруткой перетаскивание не требуется.

**KB-12.** Подсвечивать только разрешённые целевые колонки с подписью действия. Недоступная цель объясняет причину, если сервер допускает её раскрытие. Escape отменяет перенос.

**KB-13.** До ответа сервера карточка остаётся на исходном месте с busy. Целевая колонка может показывать нейтральный placeholder. Отмена формы результата/причины не меняет статус. После успеха обновляются исходная/целевая колонки, счётчики и открытая карточка.

**KB-14.** После перехода сообщение называет выполненную команду и задачу. Если запись исчезла из подборки, показать причину и ссылку «Открыть задачу». Не возвращать её в неправильную колонку ради анимации.

**KB-15.** Сохранять горизонтальную позицию, страницы и вертикальные якоря при открытии/закрытии карточки. При изменении сортировки/выборки страницы сбрасываются; истёкшая позиция объясняется.

## 9. Единая карточка задачи

### 9.1. Каркас

**DT-01.** Единый компонент данных и команд для списка, доски, сводки, проекта и крупной задачи. Контейнеры: немодальная панель / modal / полноэкранный мобильный просмотр.

**DT-02.** Верх: номер, статус, исключительный приоритет, меню, закрытие. Ниже — название до 255 символов без обрезания и контекст с разрешёнными ссылками. Кнопка закрытия имеет однозначную подпись возврата.

**DT-03.** Вкладки «Задача», «Обсуждение», «Материалы». Число комментариев/файлов — только если уже получено достоверно; неизвестное не превращается в ноль. История доступна в обсуждении переключателем «Комментарии / История / Всё».

**DT-04.** Свойства в компактной сетке: исполнитель, срок, постановщик, приёмщик, команда, направление, приоритет, контекст. На узком экране свойства переносятся. Недоступный контекст обозначается без раскрытия ID/названия.

### 9.2. Порядок содержания по состоянию

| Состояние | Первое содержание после названия | Далее | Основная команда при наличии права |
|---|---|---|---|
| Новая | Готовность: какие из результата/исполнителя/срока ещё не заданы | Ожидаемый результат, свойства, чек-лист | Передать исполнителю либо сначала заполнить недостающее |
| Назначение предложено | Ожидает решения команды; что требуется для принятия | Содержание и свойства | Принять назначение |
| К исполнению | Ожидаемый результат | Свойства, чек-лист | Начать работу |
| В работе | Препятствие/возврат, если есть; иначе ожидаемый результат | Чек-лист, результат, свойства | Передать на приёмку / завершить |
| На приёмке | Результат работы, версия результата при наличии в DTO | Ожидаемый результат, чек-лист, свойства | Принять результат |
| Выполнена | Зафиксированный результат и дата завершения | Остальное содержание и история | Переоткрыть только по доступным возможностям |
| Отменена | Отмена и причина из разрешённой истории | Содержание/история | Только разрешённые сервером команды |

**DT-05.** Причина возврата содержит автора и дату, когда они доступны. Не заменять конкретный текст возврата универсальной подсказкой.

**DT-06.** Препятствие — отдельный заметный, но компактный блок. «Указать/Изменить препятствие» и «Снять препятствие» доступны только по can_block; снятие использует существующую команду и правила. Не требовать редактирования всех свойств ради препятствия.

**DT-07.** В режиме чтения показывать текст, не набор disabled-полей. Кнопка «Редактировать» открывает редактор. Формы требований и предъявления результата не смешиваются; их черновики независимы.

**DT-08.** Нижняя панель: одно основное действие, одно вторичное при необходимости и меню дополнительных. В приёмке «Принять результат» — основное, «Вернуть на доработку» — вторичное. Отмена задачи не соседствует как равнозначная основная кнопка.

**DT-09.** Название кнопки описывает результат действия. В форме перехода вместо универсального «Подтвердить» — «Передать на приёмку», «Вернуть на доработку» и т. п. Отправка блокирует повтор, но не чтение формы.

**DT-10.** Формы результата/причины открываются внутри карточки с фокусом в первом требуемом поле. Не открывать третий вложенный диалог поверх modal. Ошибки рядом с полем и в кратком общем сообщении.

### 9.3. Обсуждение, история, материалы

**DT-11.** Комментарии: автор, время, текст; форма ответа с сохранением черновика. История: человекочитаемое действие, автор, время, разрешённые before/after. Не выводить сырой JSON.

**DT-12.** Материалы: файлы с названием, размером и состоянием загрузки/проверки; связи с типом и разрешённым названием; внешние ссылки с явной пометкой. Действующие лимиты и антивирусные ограничения сохраняются.

**DT-13.** «Переместить», «Предложить другой команде», «Отменить задачу», «Сохранить как шаблон» — в меню карточки. Причина обязательна там, где её требует сервер. Передача команде явно сообщает о снятии исполнителя и ожидании принятия.

**DT-14.** Применение шаблонов доступно в создании. На странице чтения текущей задачи не показывать постоянно раскрываемый блок «Мои шаблоны». Сохранение текущей задачи как шаблона не меняет её данные.

## 10. Создание и редактирование

**CR-01.** Создание открывается в panel/sheet шириной до 640 px. Первый экран: название, ожидаемый результат, команда, исполнитель, срок; приёмка — понятный переключатель и приёмщик. Приоритет обычный по умолчанию, компактный select.

**CR-02.** Над формой не размещать большой список шаблонов. Команда «Из шаблона» открывает выбор; перед заменой введённых значений показать, какие поля будут заменены. Применение не отправляет форму.

**CR-03.** Контекст — выбор «Самостоятельная / В проекте / В крупной задаче» с именованным picker. Два взаимоисключающих поля не выглядят как два одновременно обязательных. При создании из родителя контекст заполнен и подписан.

**CR-04.** На создание обязательны только действующие обязательные поля. Готовность к исполнению проверяется отдельно: ожидаемый результат, исполнитель, срок и условия назначения. До их заполнения новая задача может быть сохранена по существующим правилам.

**CR-05.** При межкомандном поручении исполнитель недоступен до решения команды, если так требует действующий контракт; показано объяснение. Обязательная межкомандная приёмка видима и не отключается клиентом.

**CR-06.** Недопустимые варианты не «чинить» созданием пользователей или изменением справочника. Показывать «Нет доступных вариантов» с причиной и безопасным возвратом.

**CR-07.** После успешного создания открыть новую карточку. Если задача вне текущей выборки, сообщить это; не подменять подборку и не выполнять скрытый переход статуса. При ошибке сохранять ввод и идентификатор идемпотентности для безопасного повтора поддерживаемого запроса.

**CR-08.** При редактировании явно показывать «Есть несохранённые изменения», «Сохраняем…», «Сохранено» или ошибку. Текст «Черновик сохранён в этой вкладке» не означает серверное сохранение.

**CR-09.** Закрытие с изменениями сохраняет черновик и сообщает об этом. Если локальное сохранение не удалось, закрытие требует решения «Продолжить редактирование / Закрыть без сохранения». Закрытие пустой формы не требует подтверждения.

## 11. Сводка и объяснимые числа

**SM-01.** Сводка отвечает «где требуется решение», используя текущие серверные агрегаты и attention_items. Не добавлять графики скорости и длительности без данных.

**SM-02.** Показать компактные показатели «Просрочены», «С препятствием», «На приёмке», «Без исполнителя» и короткий список ближайших действий. Числа могут пересекаться; их нельзя складывать в общий итог. Подпись области условий видна.

**SM-03.** «Выполнены» при исключённом статусе: «Не включены» и действие показа периода. При включении и нулевом серверном итоге: «0». При отсутствии значения/ошибке: «— / Не удалось загрузить». На кнопке перехода должно быть понятно, какое условие изменится.

**SM-04.** «Ближайшие действия» содержит задачу, причину её попадания, следующего участника и доступное действие. Не подписывать приёмку именем исполнителя вместо приёмщика. Если пользователь не может выполнить действие, показывать «Ожидает …», а не активную кнопку.

**SM-05.** Переход из показателя открывает список с явными чипами условий. Сохраняются подборка, контекст, поиск и прочие совместимые условия; несовместимое изменение объясняется. Карточка работает одинаково со списком и доской.

## 12. Состояния и ошибки

| Состояние | Обязательное поведение |
|---|---|
| Первичная загрузка | Skeleton соответствует будущим строкам/карточкам, без фиктивных чисел |
| Обновление | Старые данные остаются читаемыми, небольшой индикатор; устаревший ответ отбрасывается |
| Пустая система/подборка | Краткое пояснение и разрешённое создание либо смена подборки |
| Нет совпадений | Показать активные условия и «Сбросить фильтры» |
| Пустая колонка | «Задач нет»; не ошибка, не loading |
| Ошибка одной колонки | Ошибка и «Повторить» внутри неё; остальные колонки работают |
| Ошибка всего запроса | Понятный текст и повтор с теми же условиями |
| Offline | «Нет связи. Показаны ранее загруженные данные»; команды записи недоступны, черновик сохраняется локально |
| Истёк курсор | Первая страница соответствующей колонки, объяснение сброса; прочие условия сохранены |
| 422 | Поле/причина ошибки, ввод сохранён, фокус в сводке ошибки либо поле |
| 409 | Черновик сохранён; загрузка актуальной версии и сверка конфликтующих полей |
| 403/404 | Данные скрыты; «Задача недоступна», безопасный возврат |
| Истекла сессия | Штатный вход; без продления токенов/отключения защиты; восстановление безопасного контекста после входа |
| SSE во время чтения | Обновить затронутые проекции, сохранить позицию и фокус |
| SSE во время ввода | Не перезаписывать поля; баннер «Задача изменена другим участником» |

**ER-01.** При конфликте загрузить актуальную версию отдельно от черновика. Показать изменившиеся поля, исходное и новое значения; разрешённые пользовательские правки не применять автоматически. «Сохранить мои изменения» выполняет осознанный повтор с новой version и повторной проверкой прав. Для переходов заново вычислить доступность, не переотправлять старую команду вслепую.

**ER-02.** Изменения событий объединять, сохраняя действующую задержку порядка 350 мс и максимум 2 секунды ожидания. Открытое меню/форма не уничтожается перерисовкой. Возврат во вкладку, восстановление сети и смена даты обновляют сроки/выборку.

**ER-03.** Сообщения не раскрывают закрытые названия, участников или внутренние исключения. В пользовательском тексте нет «DTO», «cursor» и трассировок.

## 13. Визуальная система

### 13.1. Типографика и геометрия

| Назначение | Размер / межстрочный | Вес |
|---|---|---|
| Заголовок страницы | 24 / 32 px | 600 |
| Название в полной карточке | 20 / 28 px | 600 |
| Название строки/канбан-карточки | 14 / 20–21 px | 500 |
| Основной текст | 14 / 22 px | 400 |
| Подписи и метаданные | 12 / 18 px | 400–500 |
| Номер WorkTask | 12 / 18 px, JetBrains Mono | 400 |

Использовать установленный Inter и JetBrains Mono. Не загружать новый шрифт из сети. Мелкий текст ниже 12 px не использовать для существенной информации. Масштабирование текста не должно ломать геометрию.

Шкала отступов 4/8/12/16/24/32. Обычный control 36 px, компактный 32 px, сенсорная область 44×44 px. Радиусы 8 у контролов, 10–12 у карточек, 12–16 у панелей; значения свести к существующим токенам. Иконки одного набора 16/20 px, одинаковый stroke. Никаких эмодзи вместо системных значков.

### 13.2. Цвета для исходного макета

| Семантика | Светлая тема | Тёмная тема |
|---|---|---|
| Холст | `#F6F7FB` | `#10131B` |
| Поверхность | `#FFFFFF` | `#191E29` |
| Подложка колонки | `#EEF1F6` | `#141925` |
| Основной текст | `#182230` | `#F1F4FA` |
| Вторичный текст | `#596579` | `#AAB5C7` |
| Граница | `#DDE3EC` | `#354055` |
| Основное действие | `#4F46E5` + белый текст | `#A8A2FF` + `#17133C` |
| Просрочка/ошибка | `#B42318` | `#FDA29B` |
| Препятствие | `#854D0E` | `#F4C76B` |

Это целевая палитра для проверки контраста, не требование немедленно перекрасить всё приложение. Внедрять семантическими токенами общего UI kit либо его согласованной темой для рабочего места; не добавлять конкурирующие локальные переопределения контролов.

Обычный текст/метаданные должны давать контраст не ниже 4.5:1. Граница, необходимая для распознавания контрола, и focus ring — не ниже 3:1 относительно соседней поверхности. Статус кодируется цветом и подписью, никогда только цветом. Все фактические сочетания состояний проверяются отдельно.

### 13.3. Поведение

Hover — лёгкая заливка/граница, выбранность — мягкий акцент и маркер, focus — видимое кольцо, busy — отдельный индикатор. Тени только у плавающих слоёв. Переходы 120–180 мс; reduced motion отключает перемещения. Не анимировать первое появление всей доски каскадом.

## 14. Мобильное рабочее место и доступность

**AD-01.** На ширинах 320/390/768/1024/1280/1440/1920 CSS px проверить список, доску, карточку, создание и формы действий в обеих темах. Проверять фактический `documentElement.clientWidth`, а не только настройки инструмента.

**AD-02.** На 390×844 первая карточка канбана при закрытых дополнительных фильтрах начинается не ниже 300 px. На 320×720 — не ниже 340 px. При открытой клавиатуре допускается дополнительная прокрутка, но активное поле и основное действие остаются достижимыми.

**AD-03.** На телефоне подборка и режим занимают компактные строки; поиск раскрывается по явной кнопке, активный запрос остаётся видимым. Выбор этапа содержит название и счётчик; отдельный дублирующий заголовок не отнимает ещё одну строку. Стрелки этапов — необязательное дополнение, select достаточен.

**AD-04.** Во всём документе нет горизонтального переполнения. Исключение — локальная доска на планшете/desktop и таблица, если её выбранный режим требует скролла. Мобильный режим не требует горизонтального движения между задачами.

**AD-05.** Клавиатура: Tab по интерактивным элементам, Enter/Space для команд, стрелки по настоящим вкладкам, Escape закрывает верхний слой; фокус возвращается к исходной карточке/строке. Не перехватывать клавиши при вводе текста.

**AD-06.** Modal использует focus trap; немодальная панель его не использует. На телефоне не держать скрытый список в tab-порядке. Доступные имена меню включают номер задачи; icon-only кнопки имеют label.

**AD-07.** Для drag доступно эквивалентное меню обычными нажатиями, в том числе на touch. Реализовать не только клавиатурную альтернативу, но и альтернативу одним указателем без удержания.

**AD-08.** Ошибки связаны с полями, предупреждения объявляются через status/alert без повторного чтения всей доски. Проверить экранным диктором заголовки колонок, выбранную задачу, состояния загрузки и ошибки.

**AD-09.** При масштабе 200% сохраняются чтение и команды. На touch эффективная область цели около 44×44 px; минимум WCAG 2.5.8 — 24×24 с оговорёнными исключениями, но он не заменяет проектную цель.

Основания: [W3C Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [W3C Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

## 15. Техническая реализация

### 15.1. Frontend

Сохранить vanilla JavaScript SPA и существующие UI primitives. Разделить ответственность без введения нового фреймворка:

| Текущий модуль | Обязанность после изменения |
|---|---|
| `workTasks.js` | Маршрут, координация режима, выбранной задачи и жизненного цикла |
| `workQueue.js` | Полная/компактная строка, даты и сигналы |
| `workBoard.js` | Колонки, страницы, позиция и DnD; команды делегируются общей логике |
| `workTaskDrawer.js` | Каркас карточки и контейнеры; не содержит копию правил workflow |
| `workActions.js` | Единый запуск перехода, обработка busy, ошибки и обновления |
| `workProductivity.js` | Приоритет, чек-лист, шаблоны |
| `workPicker.js` | Доступный выбор контекста по имени |
| Новый небольшой модуль состояния/фильтров при необходимости | Нормализация URL, черновик фильтров, чипы и согласованность режимов |

Точное выделение файлов определяется реализацией. Не создавать абстракции ради переименования. Стили `work-tasks.css` и `work-board.css` очистить от конкурирующих геометрических правил после перехода; общие размеры кнопок и полей принадлежат UI kit.

Рендер обновляет затронутую область, сохраняя DOM активного редактора/меню. Обработчики, ResizeObserver, SSE и AbortController освобождаются при уходе со страницы. Загрузка карточки не должна добавлять запрос на каждого участника в списке.

### 15.2. API и вычисляемые поля

Обязательные существующие команды и read API сохраняются: `/work-tasks`, `/work-tasks/options`, `/work-tasks/board`, `/work-tasks/board/columns/{status}`, `/work-tasks/{id}`, transitions, assignment-decisions, placement, reassignment, комментарии, файлы, зависимости и шаблоны. `PATCH` не получает произвольную запись status.

Для согласованности клиентских представлений предлагаются **добавочные поля**; это TO-BE, они не объявляются присутствующими сегодня:

| Поле | Тип и смысл | Где |
|---|---|---|
| `next_step` | `{kind, label, actor_kind, actor_id?, actor_name?, action?, actionable}`; null для отсутствующего шага | Компактные DTO списка/доски, detail, attention_items |
| `summary_states` | Состояние каждой метрики `included / filtered / unavailable` и необязательная причина | Ответ списка/доски, используемый сводкой |
| `readiness` | `{missing_fields: [...], assignment_pending: boolean}`; только разрешённые сведения | Detail и при необходимости карточка новой работы |

`next_step` вычисляется из того же сервиса прав и переходов. `actionable` относится к текущему пользователю. Описание ожидаемого действия другого участника не даёт права выполнить его. Имена/ID доступны только в разрешённой проекции. Новые поля не используются как замена проверки команд сервером.

`summary_states` не меняет смысл старых чисел. Для excluded-статуса клиент показывает «Не включены»; для отсутствующего поля старого сервера — безопасное «—». На период совместимости простые состояния выводятся из нормализованных фильтров; дополнительные запросы ради косметических счётчиков не добавлять.

Первая поставка не требует новых таблиц и миграции бизнес-данных. Если при реализации обнаружится необходимость хранения новых предпочтений на сервере, вынести это в отдельное расширение; не добавлять её скрыто к редизайну.

### 15.3. Безопасность и совместимость

ACL применяется до выдачи записей, счётчиков, поисковых вариантов и действий. Доступность операции не выводится только из роли клиента. Все мутации используют версию; тексты пользователя экранируются, ссылки проверяются существующими правилами. Клиент не обращается по произвольному внешнему URL для «предпросмотра».

Старые глубокие ссылки и feature flag доски сохраняются. При отключённой доске переход на `display=board` возвращает список по действующему правилу. Старый `#/kanban` обрабатывается существующим механизмом, ID Task не превращается в ID WorkTask.

## 16. Производительность

Сохранить ограничения прежнего ТЗ: не более 15 SQL бизнес-выдачи initial board; p95 HTTP board/колонки не выше 800 мс на согласованном DEV-профиле при 10 одновременных читателях и 10 000 рабочих записей. Размер ответа, память браузера и число DOM-узлов фиксировать в отчёте. Новые computed-поля не должны создавать N+1.

Для визуального слоя: реакция на локальное переключение/открытие меню до 100 мс на согласованном эталонном компьютере; явная обратная связь о начатой загрузке/команде до 100 мс. Время загрузки по сети измеряется отдельно, не маскируется оптимистичным успехом.

В [WORK_BOARD](../dmb-backlog/docs/WORK_BOARD.md) имеется сервисный замер PostgreSQL, не включающий HTTP/авторизацию/сеть. Он не закрывает приведённый HTTP-критерий. Полная приёмка требует отдельного измерения с описанием среды. Нагрузочные записи допускаются только в разрешённой изолированной среде; защищённые данные не создаются.

## 17. Дизайнерские материалы

Перед финальной frontend-приёмкой должны быть подготовлены:

1. Рабочее место 1440×900: список, доска, список с карточкой, доска с карточкой, сводка.
2. Карточки: новая/не готова, готова, в работе, препятствие, приёмка, возврат, выполнена, отменена, read-only.
3. Создание своей команде, межкомандное поручение, редактирование, форма результата, причина возврата/отмены, конфликт.
4. Фильтры закрытые/открытые/применённые, длинные значения, нет вариантов, пустая выборка.
5. Loading, error, offline, partial error, cursor expired, доступ отозван, внешнее обновление при вводе.
6. Мобильные список/доска/карточка/создание на 390×844 и стресс-набор 320×720.
7. Светлая и тёмная темы; состояния hover/focus/selected/busy/disabled в каталоге UI kit.

Макеты используют реалистичные русские названия, длинное ФИО, несколько сигналов и разные сроки. Набор исключительно из коротких английских названий непригоден для приёмки этого интерфейса.

## 19. Проверки, внедрение и готовность

### 19.1. Порядок проверки

1. Сверить чистоту границ изменений и актуальные инструкции проекта; использовать фактическое рабочее дерево, не только последний коммит.
2. Проверить общие представления и computed-контракты unit/contract-тестами.
3. Адресные E2E существующих наборов `workWorkspace`, `workSplitWorkspace`, `workTaskDrawer`, `workBoard`, `workProductivity`, `workPagesUx`; дополнить сценариями AC без зеркалирования реализации.
4. Живой smoke на PostgreSQL готовыми профилями по [паспорту](dev-testing/TEST_DATA_PASSPORT.md): исполнитель, приёмщик, редактор, наблюдатель; отрицательный доступ заказчика.
5. Визуальная ручная проверка и клавиатура/диктор на точных размерах; нагрузка отдельно.
6. Проверить локальные Markdown-ссылки, обновить профильные документы и дату. Секреты, БД, runtime-логи, backup и graphify-out в Git не включать.

Обычные QA-рабочие записи разрешены только в объёме тестового сценария и помечены. Пользователи/роли/команды/справочники для теста не создаются. Текущий аудит является чтением, перечисленные проверки относятся к будущей реализации.

Переключение визуального слоя — отдельный обратимый feature flag, например `WORK_TASKS_REDESIGN_ENABLED` (предлагаемое имя, сейчас не объявляется существующим). Он не заменяет действующий флаг доступности канбана.

Откат возвращает предыдущую визуальную версию без удаления пользовательских данных, истории и миграций. Предпочтения нового интерфейса не ломают старую нормализацию URL. Не включать seed при запуске.

### 19.3. Пользовательский пилот

На одинаковом наборе задач сравнить старый и новый интерфейс с 5–8 участниками разных функций, по возможности меняя порядок показа. Проверить: найти срочную работу, понять препятствие, начать подготовленную работу, предъявить результат, принять/вернуть, найти выполненную, восстановить контекст после просмотра.

Цели: минимум 80% контрольных заданий поиска участника/срока/причины внимания выполнены за 5 секунд; подготовленная работа начинается не более чем за два нажатия из обзора; минимум 90% сквозных заданий завершены без подсказок. Фиксировать ошибки и медианное время, не превращать показатели в рейтинг сотрудников. Если выборка слишком мала, показывать абсолютные результаты наряду с процентами.

Оценку трудозатрат выполнять после утверждения компоновки и контракта `next_step`/метрик. Фиксированный календарный срок без оценки команды в этом ТЗ не назначается.

### 19.4. Определение готовности

Редизайн завершён, когда поставлены обязательные сценарии и состояния, пройдена AC-матрица, нет открытых блокирующих визуальных/функциональных дефектов, результаты и ограничения записаны, профильные документы обновлены, откат проверен. Незакрытый HTTP-нагрузочный критерий нельзя скрыть отметкой «дизайн готов».
