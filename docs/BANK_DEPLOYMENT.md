# Развёртывание в банке с заранее созданной БД

Проверено по коду 23.11.2026. Требование пользователя: приложение работает
с готовой структурой БД и не создаёт её самостоятельно. Порядок обновления
DBA банка пока не определён; базовый вариант — отдельные SQL-файлы для DBA.

[Результат повторной проверки: 58 тестов и 21 этап](dev-testing/BANK_DEPLOYMENT_READINESS_2026-11-23.md).
[Проверенный комплект для DBA/DevOps](../artifacts/bank-deployment-2026-11-23/bank-core-prepared-db-kit-2026-11-23.zip)
содержит SQL, банковский профиль, команду запуска и smoke; образы поставляются
отдельно по манифесту выпуска.

## Разделение ответственности

DBA создаёт БД PostgreSQL 16, рабочую схему и учётную запись приложения
по процедурам банка. Отдельно, в согласованное окно и после backup, DBA
проверяет и применяет начальную структуру либо SQL обновления. Приложение
эти SQL-файлы не читает и не выполняет.

Банковский [compose.production-core.yaml](../compose.production-core.yaml)
содержит только backend, Nginx, Redis, ClamAV и Collector. В нём нет PostgreSQL,
сервиса миграций, ИИ-агентов или seed. Он подключается к уже существующей БД.
[Старый полный production-профиль](../compose.production.yaml) с автоматическим
сервисом `migration` для банковского сценария не используется.

На старте backend выполняет только проверку подключения, версии и структуры
критических таблиц. Версия должна соответствовать образу (`d453b20d51f9` для
текущего выпуска). Пустая, старая или несовместимая схема вызывает отказ запуска,
а не автоматический repair/create/upgrade. Readiness также проверяет версию.
В PostgreSQL `init_db()` не вызывает `create_all()` или `ensure_schema()`.

## Права подключения

`DATABASE_REQUIRE_RESTRICTED_ROLE=true` обязателен в банковском профиле.
Проверка отклоняет суперпользователя, владельца объектов рабочей схемы,
наследника роли владельца, права CREATE на БД/схему и запись в `alembic_version`.
Таким образом приложение не может создавать/изменять/удалять объекты рабочей
схемы и подменять отметку версии.

DBA выдаёт DML-права на таблицы приложения, USAGE/SELECT на последовательности
и SELECT на `alembic_version`. [Шаблон выдачи прав](../infrastructure/postgres/runtime-role-grants.sql)
не создаёт роли и не содержит паролей. DBA должен учесть наследуемые права
и PUBLIC; шаблон намеренно не меняет общие права других пользователей.
После появления новых таблиц DBA повторяет согласованную выдачу прав.

После обновления существующей БД оператор отдельно выполняет read-only проверку
связей справочников. Наличие нужных таблиц само по себе не исправляет старые
назначения прав или незаполненные `dictionary_items.reference_id`:

```sh
docker compose --env-file /secure/dmb-core.env -f compose.production-core.yaml run --rm --no-deps backend python account_operator.py reference-report
```

Если отчёт показывает несвязанные/неоднозначные записи, применить порядок
согласования данных из [инструкции подготовки](DEMO_STAND_SETUP.md).
`reconcile-references --reason BANK-TICKET --apply` — отдельная явная DML-операция
после просмотра отчёта; startup/deployment её автоматически не выполняет.
Для существующего администратора аналогично доступна отдельная
`configure-admin-access --user-id ID --reason BANK-TICKET --apply`: пароль
сохраняется, прежние сессии завершаются. Такие операции выполняются только
уполномоченным оператором по согласованному основанию.

Обычные записи приложения (сессии, задачи, отчёты) сохраняются через DML.
Первый администратор, назначения прав и демонстрационные справочники — только
явные операторские действия по [инструкции подготовки](DEMO_STAND_SETUP.md).
Автоматического заполнения пользователей и справочников при старте нет.

## Подготовка SQL вне приложения

Для новой пустой БД используется проверенный `initial-schema.sql` из комплекта
выпуска: только структура и отметка версии, без пользователей и справочных данных.
Файл создаётся из отдельной пустой эталонной БД, а не из рабочей/банковской БД.
Проверяемая схема — `public`; другое размещение должен согласовать DBA.

Для существующей БД сначала DBA читает её текущую ревизию:

```sql
SELECT version_num FROM public.alembic_version;
```

SQL обновления можно подготовить **без сети и подключения к БД** из образа
того же выпуска. Пример для явно известной ревизии:

```sh
docker run --rm --network none RELEASE_IMAGE python -m schema_sql --from-revision d352a19c40e8 --output - > upgrade.sql
```

Нужно проверить код возврата, содержимое и SHA-256 файла до передачи DBA.
Скрипт не принимает неизвестный baseline и не делает `stamp head`. Если у БД
нет `alembic_version`, автоматическое присвоение версии запрещено: DBA сначала
сопоставляет реальную структуру с контрактом выпуска.

SQL обновления содержит транзакцию, общую PostgreSQL advisory-блокировку
и проверку исходной версии до DDL. Повтор на другой ревизии останавливается.
Некоторые исторические миграции могут требовать отдельного DBA-плана вместо
offline-генерации; при ошибке экспорта неполный SQL не публикуется.
Обычный Alembic также сериализован блокировкой для отдельного согласованного
DBA/job-процесса; приложение и банковский deployment его не запускают.

## Запуск приложения после подготовки БД

Загрузить согласованный образ, сверить его точный image ID с манифестом выпуска.
В закрытом контуре заранее обеспечить доступность всех закреплённых образов
из Compose (также Redis, Nginx, Collector и ClamAV) через согласованный банком
канал и подготовить актуальные базы ClamAV. До окна работ проверить, что
`docker image inspect` разрешает каждую ссылку `image` из конфигурации локально
или через внутренний registry. Само наличие TAR после переноса не подтверждает
разрешимость registry digest: это проверяет DevOps до остановки приложения.
Настоящие значения задать вне Git по
[.env.production-core.example](../.env.production-core.example): адрес уже готовой
БД, учётка DML, настройки TLS подключения по правилам банка, Redis и общие секреты
реплик. Для доверенного TLS ingress задать точные HTTPS `AUTH_ORIGINS` и
`CORS_ORIGINS`, имена хостов в `AUTH_ALLOWED_HOSTS`. Сертификаты БД при необходимости
подключаются read-only через согласованный Compose override.

Из корня проекта (Python 3.12 и Docker Compose):

```sh
python scripts/deploy-core.py --env-file /secure/dmb-core.env --report-dir /secure/deployment-evidence
```

[Команда](../scripts/deploy-core.py) блокирует параллельный выпуск на том же Docker
daemon, фиксирует image ID и проверяет готовую БД **до** остановки работающего
приложения. После этого обновляет backend, ждёт readiness и ClamAV, запускает
Nginx. Миграций, создания БД, таблиц, ролей и удаления данных в команде нет.
При ошибке запуска приложение не объявляется готовым; частично запущенные
backend/Nginx останавливаются. Lock не перехватывается автоматически после сбоя.
Отчёты и приватные диагностические файлы хранятся в защищённом каталоге оператора.

При переносе с другой Docker-топологии надо явно согласовать остановку её
пишущих сервисов. Команда отказывается использовать тома другого проекта
или молча принимать неизвестные сервисы прежней конфигурации.

## Приёмка в контуре

После согласованного первого администратора выполнить smoke с реального HTTPS
адреса и банковским CA, затем браузерный сценарий Бэклога. Пароль вводится скрыто:

```sh
python stand_smoke.py --base-url https://dmb.example.internal --login DEMO_LOGIN --expect-admin --wait-access-expiry --ca-file /secure/bank-ca.pem --output bank-smoke.json
```

Проверить вход, `/auth/me`, видимость админки, справочники, создание задачи
только с названием, повторное чтение/изменение, две вкладки и refresh.
Локальная репетиция не подтверждает банковские DNS, TLS, firewall, ресурсы
или фактическое состояние банковской БД. Доступа к ней из этого чата нет.
