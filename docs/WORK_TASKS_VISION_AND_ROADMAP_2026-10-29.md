# Рабочие задачи целевое видение и план развития

Рабочие задачи уже имеют содержательное ядро: назначение, исполнение, предъявление результата и его приёмку. Следующий этап развития должен сделать этот контур быстрым ежедневным рабочим местом: человек сразу понимает, что делать, выполняет частые операции без лишних переходов и доверяет сохранности информации. Руководитель видит ожидания, перегрузку и причины риска, а заказчик получает подтверждённый результат своего запроса.

Главные направления ближайшей доработки: единый поиск, удобная карточка, сохранённые представления, быстрые операции, личное планирование, полноценные обсуждения и согласованное отображение препятствий. Расширенное управление потоком, повторяющиеся работы и автоматизация развиваются поверх этой основы.

Документ содержит ревью текущего состояния, целевые сценарии, требования к дизайну, 72 пункта развития, порядок поставок и критерии приёмки. Приоритеты и этапы являются предложением; календарные сроки и трудозатраты требуют оценки команды.

## 1. Область и основания ревью

Срез выполнен **29 октября 2026 года по рабочему дереву**, включая незакоммиченные изменения. Проверялись модель WorkTask, контракты и сервисы команд, выборки и доски, карточка, список, продуктивность, связи, уведомления и соседние контуры проектов и поручений встреч. Исторические отчёты использовались для поиска контекста, затем существенные утверждения сверялись с реализацией.

В работающем приложении под действующей QA-сессией участника команды проверены:

- список личной очереди, состав подборок и их счётчики, открытие задачи и сохранение контекста;
- карточка WRK-27 с препятствием, вкладки «Задача», «Активность», «Материалы»;
- форма создания без сохранения;
- доска и сводка с теми же условиями;
- общий поиск известной рабочей задачи;
- каталог проектов, паспорт проекта и пустое состояние его исполнения.

Настольный CSS viewport — **1422 × 800**. Результаты живого чтения не распространяются на остальные роли, мобильные устройства и темы. Рабочие записи и защищённые данные в приложении не изменялись.

Адресный запуск существующих тестов `test_work_tasks.py`, `test_work_presentation.py`, `test_work_audit.py`: **15 PASS**, три предупреждения об устаревающих API библиотек. Проверены переходы, обязательные данные, права участников, версии, сохранение результата при приёмке и следующий шаг. Тестовые записи создавались только в изолированных таблицах рабочих задач, истории и outbox; защищённые таблицы не создавались. Это не полная регрессия и не нагрузочная приёмка PostgreSQL.

## 2. Что уже есть и должно стать основой развития

| Область | Подтверждённое текущее состояние | Что важно сохранить |
|---|---|---|
| Единица исполнения | WorkTask отдельно от задачи бэклога Task; самостоятельная работа, работа в проекте или в задаче бэклога | Одна сущность поручения; один основной контекст учёта |
| Структура | Один уровень рабочих задач; рабочих задач внутри рабочих задач нет | Чек-лист и связи покрывают детализацию без новой иерархии |

| Ответственность | Постановщик, исполнитель, приёмщик, команда выполнения; принятие межкомандного назначения | Явная ответственность и приёмка межкомандного результата |

| Управление | Четыре приоритета, срок, текст препятствия, чек-лист до 50 пунктов | Чек-лист не подменяет принятие результата |
| Рабочее место | Пять подборок; список, доска, сводка; URL-контекст, пагинация, общая карточка | Согласованность фильтров, выбранной задачи и возврата |
| Отбор | Поиск WRK-ID/названия; категории, контексты, приоритет, участник, признаки внимания, период выполненных | Множественный выбор уже предусмотрен контрактами; не планировать его заново |
| Доска | Серверные переходы, меню, дополнительный перенос указателем, отдельные страницы колонок, мобильная колонка | Меню остаётся полноценной альтернативой переносу |

| Шаблоны | Личные шаблоны содержания, направления, приоритета, приёмки и чек-листа | Назначения, даты и выполненные отметки не копируются |
| Связи | Зависимости между работами и задачами бэклога; поиск доступной цели; проверка циклов | Ссылка не даёт дополнительных прав; управление графом проверяется на PostgreSQL |
| Входящие запросы | Размещение в новую/существующую работу, разбиение, снимки требований, отдельное подтверждение покрытия и выполнения | Одобрение запроса, закрытие работы и удовлетворение потребности — разные факты |
| Проекты | Каталог, паспорт, планирование по кварталам, бэклог, исполнение, результаты | Проект — продолжающееся направление; общий процент завершения ему не обязателен |
| Отчётность | Агрегаты рабочих задач, отдельные неизменяемые снимки для встреч | Текущая выборка и исторический снимок должны различаться |
| Внешнее исполнение | URL внешних работ у задач бэклога; автоматической синхронизации нет | Ссылку нельзя показывать как подтверждённый внешний статус |

### Принципиальные границы целевого решения

1. Сохранять один уровень рабочих задач, выбранный пользователем. Если пункт требует отдельного исполнителя, срока и приёмки, создавать связанную рабочую задачу в том же контексте.
2. Использовать актуальные названия «Задача бэклога» и «Рабочая задача». «Обязательство» не вводить как новую сущность.
3. Развивать проект как направление работ с пересматриваемым бэклогом. Конечные этапы и вехи допустимы внутри отдельных инициатив, но не обязательны для каждого проекта.
4. Сохранять отдельное решение о выполнении запроса. Количество закрытых работ и процент чек-листа не доказывают бизнес-эффект.
5. Автоматическую интеграцию с IT-трекером рассматривать отдельным последующим решением: текущий выпуск остаётся со ссылками согласно принятому ограничению.
6. Развивать существующий UI kit и рабочее место последовательными поставками. Новая визуальная оболочка сама по себе не закроет перечисленные сценарии.

## 4. Целевое продуктовое видение

**Рабочие задачи — единое место ежедневного исполнения и координации:** от быстрого захвата поручения до принятого результата, с понятным следующим действием, видимыми ожиданиями и минимальными затратами на актуализацию.

### Для кого и какой результат

| Участник | Что должно получаться без дополнительной сверки |
|---|---|
| Исполнитель | Увидеть свой следующий шаг; спланировать день; быстро обновить работу, запросить помощь и предъявить результат |
| Постановщик | Зафиксировать ожидаемый результат; проверить принятие назначения; увидеть ожидание и получить итог |
| Приёмщик | Получить компактную очередь решений; сравнить ожидание и результат; принять или вернуть с конкретными замечаниями |
| Координатор/руководитель | Разобрать входящие; согласовать приоритеты; увидеть перегрузку, стареющие работы и межкомандные ожидания |
| Заказчик | Проследить покрытие своего запроса и подтверждённый итог в разрешённой проекции |
| Наблюдатель | Понять доступное состояние без недоступных команд и раскрытия закрытых материалов |

### Основные принципы

- **Следующее действие видно сразу.** Что требуется, от кого, почему и что мешает; недоступная команда имеет объяснение.
- **Быстрый захват, постепенное уточнение.** Новое поручение можно зафиксировать кратко; перед исполнением сохраняются обязательные ожидаемый результат, исполнитель и срок.
- **Один факт обновляется в одном месте.** Список, доска, проект, уведомление и агент используют одни команды и правила.
- **Личный план не меняет обещание.** «Сделаю во вторник» и «должно быть принято к пятнице» — разные данные.
- **Исключения заметнее нормы.** Причина ожидания, риск срока и необходимость решения выделяются сильнее обычных статусов.
- **Система помнит контекст.** Условия, выбранная работа, позиция, черновик и незавершённое решение восстанавливаются предсказуемо.
- **Совместная работа остаётся в задаче.** Обсуждение, решение, подтверждающие материалы и источник поручения связаны с результатом.
- **Ошибку можно исправить.** Доступны восстановление, понятная сверка конфликтов и контролируемая отмена допустимых операций.
- **Пользователь управляет вниманием.** Подписки и напоминания помогают работать; поток однотипных обновлений не превращается в обязательную очередь действий.
- **Руководитель управляет потоком.** Метрики объясняют ожидания и предсказуемость; число закрытий не становится рейтингом сотрудников.

### Целевая организация рабочего места

Основной вход — «Моя работа» внутри существующего раздела. Сначала видны «Требуют решения», «План на сегодня», «В работе», «Жду ответа/приёмки». Нынешние подборки сохраняются как быстрые переходы. «Команда» даёт обзор входящих, текущего потока и ожиданий. Именованные представления объединяют постоянные рабочие срезы.

Список — основной режим для частых операций. Доска — режим управления потоком. Календарь — дополнительный способ планирования. Сводка — короткое объяснение рисков с переходом в точную выборку. Полноэкранная карточка доступна для сложной работы; инспектор обеспечивает быстрое чтение без потери очереди.

```mermaid
flowchart LR
    I[Поручение или запрос] --> N[Входящая работа]
    N --> R[Ожидание результата и готовность]
    R --> E[Исполнение]
    E --> A[Предъявленный результат]
    A --> V[Приёмка если требуется]
    V --> D[Выполненная работа]
    V --> E
    D --> Q[Отдельное подтверждение выполнения запроса]
```

Схема показывает основной путь; самостоятельная работа может завершаться без отдельного приёмщика по действующим правилам. Отмена, восстановление и межкомандное принятие остаются явными ветками процесса.

## 5. Требования к ключевым сценариям

### Быстро зафиксировать и разобрать поручение

Открыть создание из раздела, проекта, задачи бэклога, поиска или команды клавиатуры. Сохранить краткую новую работу с понятным контекстом. Предлагать содержательные шаблоны и похожие доступные записи до создания дубля. После создания позволять сразу добавить ещё одну работу. При превращении пункта встречи в работу показывать, какая запись создана или использована.

Отдельная очередь входящих показывает работы без исполнителя/срока, ожидающие решения команды и отклонённые назначения. У каждого исключения есть ответственный за следующий шаг. Не добавлять обязательных полей ради заполненности карточки.

### Спланировать личную работу

В начале дня человек видит обязательства по сроку отдельно от выбранного плана. Может включить работу в день/неделю, вручную упорядочить личный список и поставить напоминание. Невыполненный личный план не меняет дедлайн и не переносится бесшумно бесконечно. В конце дня предлагается осознанный перенос или отказ от личного плана.

### Выполнять и устранять ожидания

В списке доступны частые поля и разрешённый переход. В карточке видны ожидаемый результат, основные свойства, чек-лист, обсуждение и нужные материалы. Причины ожидания различают внешний ответ, зависимость, решение команды и техническое препятствие. Для препятствия можно указать действие по снятию, ожидаемого участника и контрольную дату в пределах действующих прав.

### Предъявлять и принимать результат

При предъявлении доступны текст, ссылки на материалы и состояние критериев. На приёмке рядом показываются согласованная редакция ожидания, представленный результат и замечания. Принятие не переписывает результат исполнителя. Возврат содержит конкретные замечания и сохраняет прежнюю редакцию. Самоприёмка, замещение отсутствующего приёмщика и изменение условий имеют явные правила; существующие права не расширяются неявно.

Для коротких самостоятельных работ проверить в пилоте сокращённый путь «Зафиксировать результат»: одна форма собирает необходимые данные и проводит разрешённые переходы. Это возможное упрощение UI, а не снятие серверных условий или обязательной межкомандной приёмки.

### Координировать команду и межкомандную работу

Координатор видит входящую очередь, текущие работы, перегрузку и ожидающие решения. Доска поддерживает группировку по участнику/проекту, явный командный порядок и ограничения одновременной работы. Назначение конкретного исполнителя, участие нескольких команд и принятие поручения не смешиваются. Один результат учитывается один раз, даже когда он важен нескольким направлениям.

### Возвращаться к прошлой работе

Поиск охватывает доступные заголовки, содержание и результат; комментарии/файлы подключаются с отдельной политикой индексации. Можно открыть выполненную и отменённую работу, прочитать всю историю, понять причину решения, восстановить ошибочную отмену или переоткрыть результат. Архивирование управляет видимостью и не уничтожает аудит.

## 6. Целевой дизайн и удобство

### Список и верхняя панель

Заголовок, виды и основное действие занимают одну компактную область. Поиск остаётся постоянно доступным. В повседневном режиме видны выбранная подборка, активные условия и несколько нужных быстрых фильтров; полный редактор условий раскрывается по запросу. При открытой карточке панель может сворачиваться до строки, сохраняя состояние и явную кнопку возврата.

В строке прежде всего читаются название, следующий участник/шаг, срок и исключения. Поля настраиваются пользователем; компактный и обычный режимы используют токены UI kit. Название не превращается в длинную ленту разноцветных чипсов. Чекбокс массового выбора, выделение открытой строки и команда открытия визуально различимы.

Группировка должна быть серверной, если обещает общую группу выборки. Нынешнюю группировку текущей страницы можно сохранить с явным пояснением. Ручной командный порядок, автоматическая сортировка и личный порядок имеют разные подписи и не перезаписывают друг друга.

### Карточка

На настольном экране — регулируемый инспектор и доступный полноэкранный режим. При ширине 1422 × 800 целевая верхняя граница открытой карточки — не ниже 200 px; точный бюджет уточняется на макете с реальными заголовками. Результат и основные свойства должны быть читаемы без борьбы с несколькими вложенными прокрутками.

Шапка содержит ID, название, статус, контекст и одно основное действие. Исполнитель, приёмщик и срок доступны при чтении; редкие свойства раскрываются. Во время приёмки в начале находятся результат и критерии, во время исполнения — ожидаемый результат и текущая работа. Пользователь может перейти к следующей/предыдущей задаче очереди без закрытия инспектора.

Редактирование обычного свойства не требует переходить в режим огромной формы. Статус сохранения различает «сохранено на сервере», «локальный черновик» и «не удалось сохранить». Значимые переходы и приёмка выполняются явной командой.

### Доска и дополнительные виды

У карточки доски достаточный контекст, минимум повторяющейся информации и заметная причина ожидания. Видны возраст работы на этапе и превышение WIP, когда эти возможности включены. Меню и клавиатура позволяют сделать всё, что возможно переносом. Скрытые фильтром колонки не получают ложных нулей.

Календарь различает дедлайн и личный план. Перенос элемента ясно сообщает, какой именно факт меняется. Временная шкала добавляется для зависимого планирования, когда готовы даты начала/окончания и сценарий подтверждён пилотом; она не нужна каждой простой задаче.

### Мобильность и доступность

На телефоне — одна читаемая колонка списка/доски, полноэкранная карточка, закреплённое основное действие и предсказуемый возврат. Сенсорные цели проектируются от 44 × 44 CSS px без принудительного увеличения всех настольных строк. Проверяются системная клавиатура, безопасные зоны, длинные русские названия и смена ориентации.

Обязательны полный путь с клавиатуры, заметный фокус, корректные названия контролов, сообщения о сохранении/ошибках, доступность без переноса мышью, контраст в обеих темах, реальный zoom 200/400%, screen reader и reduced motion. Геометрические автотесты без ручного чтения интерфейса не закрывают визуальную приёмку.

Денежную оценку и календарь строить по оценке команды и её доступности; размер пункта здесь намеренно не угадывается.

### Существенные зависимости

- W09/W10 и W11/W12 опираются на один нормализованный серверный отбор и ACL. Сохранённый вид хранит намерение запроса, не снимок прав.
- W02 предшествует развитым обсуждениям: ответы и упоминания бесполезны, если длинный тред перестаёт показывать новые сообщения.
- W04 предшествует расширению приёмки и AI-проверке результата: нужна однозначная редакция ожиданий.
- W05/W42 предшествуют W43/W44/W48: сначала договориться о значении ожидания, затем управлять и измерять его.
- W21/W24 предшествуют W25–W27: расписания требуют устойчивого смысла даты, часового пояса и рабочего календаря.
- W14/W15 требуют server-side проверки каждого объекта, явного объёма операции и защиты от повторов.
- W51/W52 требуют устойчивой связи источника и результата; полагаться только на совпадение названий нельзя.
- W57/W58 используют те же команды, права и журнал, что и человек; отдельный обходной путь записи не вводится.

## 9. Изменения модели и API

Это направления технического проектирования, а не требование создать все таблицы сразу.

| Возможность | Предлагаемая опора |
|---|---|
| Общий поиск | ACL-aware серверный поиск по типам; полная пагинация, актуализация индекса и отзыв видимости |
| Длинная активность | Стабильные курсоры комментариев/истории; привязка к событию/комментарию; единый порядок и загрузка соседнего контекста |
| Личный план/порядок | Отдельные пользовательские данные планирования, не перегрузка `due_date` или командного приоритета |
| Именованные виды | Владелец, область видимости, version, нормализованный query, схема представления и политика удаления |
| Массовые операции | Зафиксированный набор целей либо подтверждённый query-снимок, версии, лимиты, результат по объектам, ключ повтора |
| Редакции ожиданий | Номер редакции, согласованное содержание, предъявленный результат и решение по конкретной редакции |
| Упоминания/подписки | Участник, объект/сообщение, тип подписки и состояние адресного действия; доступ проверяется повторно |
| Напоминания/повторы | Часовой пояс, правило, следующий запуск, политика пропущенных запусков/отмены, ключ экземпляра и outbox |
| Граф зависимостей | Обратное чтение, жизненный статус цели и общая проекция; сохранение запрета циклов и межпроцессной сериализации |
| Метрики потока | Однозначные события входа/выхода этапов; интервалы ожидания; версия методики; повторное открытие не переписывает прошлое |
| AI и правила | Предложение/diff, субъект и права команды, подтверждение, журнал применения и защита от циклов |

Улучшать модульность вокруг общих query, projection, command и activity. В существующем frontend постепенно выделять из крупных модулей контроллер условий, очередь, инспектор и редакторы, когда это нужно для поставки. Выбор нового фреймворка не является предпосылкой продуктовых улучшений.

Текущий SQL/ACL-профиль измерить до добавления поиска, подписок и фоновых задач. Отдельно проверить индексирование даты, автора, приёмщика, статуса и выборок активности; индексы добавлять по планам запросов и реальной нагрузке.

## 10. Критерии успеха и приёмки

Ниже предложены цели пилота; текущие результаты по ним не измерялись. Исходную базу снять на одинаковых заданиях до реализации S1/S2.

| Проверка | Предлагаемая цель |
|---|---|
| Найти известную доступную работу по ID из любого раздела | Не более 5 секунд; недоступная работа не раскрывается |
| Понять следующий шаг, ответственного и препятствие | Верное понимание минимум в 9 из 10 контрольных заданий; фиксировать абсолютный результат при небольшой выборке |
| Зафиксировать простое поручение | До 20 секунд на готовом примере без искусственных обязательных полей |
| Изменить частое поле | Не более двух действий после выбора поля, без отдельного открытия полного редактора; время ввода значения учитывать отдельно |
| Пройти исполнение и приёмку | Минимум 90% контрольных заданий без подсказки; причины ошибок сохраняются |
| Повторить серию операций | Снижение медианного времени минимум на 30% относительно базы; сохранение правильности решений |
| Сохранность | Нет потерянного ввода и дублированных бизнес-команд в согласованной матрице повторов/сбоев |
| Доступность | Критический путь пройден клавиатурой и screen reader; без блокирующих дефектов на mobile и zoom |
| Производительность | Для предварительного профиля 10 000 доступных работ и 10 одновременных активных сессий: p95 HTTP списка/карточки ≤500 мс, первоначальной доски ≤800 мс; содержательный интерактивный экран ≤1,5 с на согласованной сети |
| Принятие продукта | В пилоте снижается число внешних уточнений статуса; пользователи возвращаются для работы, а не только ради обязательного отчёта |

Профиль нагрузки должен отдельно описать объём истории, комментариев и файлов, холодные/тёплые запросы, устройство, сеть и длительность прогона. Производительные цели уточняются после baseline; ранее измеренный сервисный benchmark доски не подтверждает эти HTTP-цели.

Пользовательский пилот: 5–8 представителей исполнителей, постановщиков, приёмщиков и координаторов; одинаковые задания, смена порядка вариантов, медиана времени, ошибки и короткая оценка понятности. Это проверка удобства, а не статистическое доказательство поведения всей организации. После неё — наблюдение реального командного использования.

### Обязательные сквозные сценарии

1. Захватить самостоятельное поручение, уточнить готовность и передать в работу.
2. Создать работу из проекта и задачи бэклога, не менять защищённые атрибуты контекста.
3. Найти работу из глобального поиска, по прямой ссылке и за первой страницей.
4. Сохранить/переоткрыть представление; проверить его под другим допустимым пользователем.
5. Изменить поле из списка; повторить при внешнем изменении версии.
6. Выбрать страницу и всю выборку; получить смешанный результат массовой команды без скрытых изменений.
7. Передать поручение другой команде, отклонить, уточнить и принять повторно.
8. Развести личный план и обязательный срок; проверить переход календарного дня.
9. Добавить препятствие и зависимость, завершить/отменить предшественника; проверить разные причины ожидания и отсутствие утечек.
10. Выполнить работу с чек-листом; отличить прогресс пунктов от принятого результата.
11. Предъявить результат, вернуть с замечаниями, предъявить новую редакцию и принять.
12. Изменить условия после старта/приёмки; подтвердить правильную редакцию.
13. Заменить недоступного приёмщика штатным разрешённым способом без изменения команды/роли.
14. Ошибочно отменить, восстановить, переоткрыть выполненное; сохранить источник и историю.
15. Прочитать более 200 комментариев и 100 событий; открыть точное сообщение из уведомления.
16. Упомянуть участника, получить ответ, отписаться от обычных обновлений без потери обязательного действия.
17. Загрузить несколько файлов, прервать связь, повторить; проверить скачивание после отзыва доступа.
18. Потерять связь/ответ, получить 409, завершение сессии и внешнее событие; восстановить ввод без дубля.
19. Повторить фоновый запуск напоминания/серии; проверить пропущенные запуски, отмену и тихие часы.
20. Подтвердить поручение встречи; повторить команду и получить ту же WorkTask.
21. Связать несколько запросов с работой, переоткрыть результат и заново проверить fulfillment.
22. Пройти весь путь в проекте, списке, доске и уведомлении; сравнить числа и объяснения фильтров.
23. Проверить доступ участника, приёмщика, координатора, наблюдателя, заказчика и пользователя без команды готовыми QA-профилями.
24. Пройти критический путь на mobile, в обеих темах, с клавиатурой, screen reader и реальным zoom.
25. Восстановить данные после сбоя поставки; сравнить задачи, связи, файлы и историю решений.

## 11. Решения до реализации и расширения

S0/S1 можно начинать с подтверждённых проблем без ожидания ответа на весь список. Следующие вопросы решаются в проектировании соответствующей поставки:

- Кто может восстанавливать отменённое, когда допустимо обратное действие и как уведомляются участники?
- Что именно считается согласованными условиями и какие изменения требуют повторной приёмки?
- Нужны ли варианты без обязательной даты исполнения для отдельных процессов? До отдельного решения сохраняется нынешнее условие готовности.
- Какие зависимости только предупреждают, а какие ограничивают переход? Как трактуется отменённый предшественник: снято ожидание, заменена работа или нужен новый план?
- Каков допустимый круг упоминаний/подписок и что делать при утрате доступа адресатом?
- Кто публикует общие виды и шаблоны? Настройки контента не должны незаметно менять защищённые команды/справочники.
- Требуются ли несколько исполнителей? Предпочтение — один ответственный за результат, дополнительные участники и связанные работы; множественная ответственность требует отдельного обоснования.
- Какие оценки и сведения о доступности реально ведутся? Без них обзор числа работ не называть расчётом мощности.
- Как обрабатывать изменение серии, пропущенный запуск, отсутствие исполнителя и остановку worker?
- Какие каналы уведомлений допустимы, какие тихие часы и маршруты эскалации нужны?
- Нужны ли учёт времени, спринты, диаграммы зависимого плана и внешние интеграции именно этому процессу? Это рассмотренные расширения, не обязательная часть первого выпуска.
- Какие правила хранения/архивирования применяются к материалам и истории и кто владеет восстановлением?

## 12. Что не следует делать частью ближайшего выпуска

Не вводить вложенные WorkTask, новый объект «Обязательство», обязательные спринты, учёт времени, произвольный конструктор процессов и десятки обязательных полей. Эти изменения увеличивают цену ведения данных и затрагивают принятые границы модели. Точечная потребность может стать отдельным решением после пилота.

Не показывать прогноз без данных как достоверную дату, сумму закрытых задач как эффект, количество карточек как часы загрузки и ссылку как внешний статус. Не закрывать работу и не принимать результат автономным AI. Не выводить корпоративную замену Jira/SberTrack из одного лишь списка возможностей рабочего контура.

## 13. Повторная проверка полноты

После подготовки видения выполнен второй проход по жизненному циклу, ролям, поверхностям и отказам. Проверка учитывает уже имеющиеся чек-листы, шаблоны, несколько категориальных значений фильтров, поиск цели зависимости, проекты с планированием и результатами, межкомандное принятие, локальные черновики и клавиатурное подтверждение. Их наличие не заменено повторным обещанием «добавить».

| Направление второго прохода | Где учтено |
|---|---|
| Захват, разбор входящих, копия, дубли, шаблоны | W16, W27–W28, W40–W41, W51 |
| Поиск, все страницы, виды, избранное, возврат | W09–W12, W17–W18, W60 |
| Личный план, сроки, рабочие дни, напоминания, серии | W21–W27 |
| Исполнение, изменение ожиданий, результат, приёмка | W01, W04, W13, W19, W31, W47 |
| Межкомандность, отказ назначения, отсутствие участника | W41, W47, сценарии 7 и 13 |
| Зависимости, отменённая цель, WIP, старение, прогноз | W05, W29, W42–W48; решения раздела 11 |
| Обсуждения, адресность, подписки, длинная история | W02, W31–W37 |
| Файлы, ссылки, исходный запрос, встреча, внешний трекер | W38, W40, W51–W56 |
| Ошибочная отмена, архив, восстановление, история | W03, W08, W34, W69–W70 |
| Частичные права и результат массового изменения | W01, W14–W15, W71 |
| Истёкшая сессия, сеть, конкуренция, повтор команды | W07, W20, W54, W67–W69 |
| Календарные границы, пропущенные фоновые запуски | W24–W27, W57, сценарий 19 |
| Проекты как направления, KPI и исторические снимки | W06, W49, W61, W64 |
| Mobile, обе темы, клавиатура, screen reader, zoom | W59–W66 |
| Производительность, наблюдаемость, rollout и restore | W67–W71 |
| Ценность, измеримость удобства, принятие продукта | W72 и раздел 10 |
| Расширения: время, спринты, поля, процессы, интеграции | W30, W50, W55–W56 и раздел 11 |

При повторной сверке особо учтены: терминальность отмены; невидимость новых комментариев после лимита; различие срока и личного плана; отдельная судьба поручения встречи; зависимость от отменённой работы; отсутствие приёмщика; неполное применение массовой команды; различие нуля и исключённого KPI; восстановление файлов вместе с БД. Эти случаи входят в план и критерии, а не оставлены общим пожеланием «улучшить UX».

Полнота перечня не равна полной приёмке существующего приложения. Остаются необходимые живые многоролевые проверки, mobile/touch, доступность, большая активность и HTTP-нагрузка. Закрытие соответствующих пунктов подтверждается отдельными результатами на актуальном коде.
