# Квартальные метрики: ТЗ на реализацию

Дата: **03.11.2026**. Версия: **1.0**.

**Статус: TO-BE.** Продуктовая логика согласована пользователем в текущем
чате. Этот документ детализирует её для разработки; структуры хранения,
контракты и этапы ниже являются проектом реализации, а не описанием
работающей системы. Создание ТЗ не означает выполнения миграций или приёмки.

Текущее поведение описано в [METRICS.md](../dmb-backlog/docs/METRICS.md).
При конфликте прежнего [дизайна](metrics-design.md) с настоящим ТЗ для новой
реализации действует настоящее ТЗ. Исполняемый код остаётся источником AS-IS.
Интерактивный макет в чате иллюстрирует пользовательские сценарии;
упрощения макета, его демонстрационные ID и ограничения ввода не являются
требованиями к реализации. Рабочие ID `MET-…` сохраняются.

## 1. Цель и согласованные решения

Цель: дать владельцу метрики единое место для квартального планирования,
ведения факта, наблюдения за динамикой и подтверждения результатов, а
руководителю — сопоставимый квартальный реестр и годовой обзор.

| ID | Обязательное решение |
|---|---|
| BR-01 | Основной период — календарный квартал; год — представление кварталов |
| BR-02 | Независимо редактируемая годовая цель в новой модели не создаётся |
| BR-03 | Прогресс зависит от типа метрики; универсальная формула для всех типов запрещена |
| BR-04 | У квартала есть явно сохраняемый факт; внутри квартала могут существовать отдельные замеры |
| BR-05 | Замер не заменяет факт автоматически; перенос замера в факт — явное действие |
| BR-06 | До закрытия факт предварительный; итог подтверждает владелец после окончания квартала |
| BR-07 | Автоматического закрытия квартала нет; закрытие не означает достижения плана |
| BR-08 | Диапазон оценивается по итоговому факту; нарушения среди замеров показываются отдельно |
| BR-09 | Подтверждение непрерывного удержания диапазона весь квартал в поставку не входит |
| BR-10 | История планов, фактов, замеров, прежних закрытий и снимков встреч сохраняется |
| BR-11 | Ноль отличается от отсутствия данных; незапланированный период отличается от периода без факта |
| BR-12 | Годовой итог зависит от смысла метрики; усреднять проценты выполнения разных метрик нельзя |

## 3. Границы поставки

Включить: два режима реестра, карточку, создание/черновик, квартальные планы,
предварительный и итоговый факт, замеры и исправления, закрытие, отмену,
приостановку/возобновление метрики, архив, вычисляемый годовой итог,
обсуждение с привязкой к периоду, аудит, права, переход прежних данных.
Сохранить файлы, связи с задачами, статусы встреч и старые ссылки.

Не включать: новые редактируемые годовые цели, новые месячные/произвольные
периоды, непрерывный контроль диапазона, линейный прогноз отставания,
автоматический импорт факта, произвольный исполняемый редактор формул,
средний процент портфеля, новые роли и рассылки. Существующие нестандартные
периоды остаются доступны по правилам раздела 13.

## 4. Термины, календарь и состояния

### 4.1. Календарь

- Часовой пояс бизнес-даты — `Europe/Moscow`, как в текущем `today()`.
- Кварталы: 01.01–31.03, 01.04–30.06, 01.07–30.09, 01.10–31.12 включительно.
- Год/квартал в новом API — целые числа; даты выводит сервер. Для новых
  периодов клиент не может задавать произвольные границы или название.
- Закрытие разрешено при `business_today > end_date`, то есть с 00:00
  следующего дня по Москве. Последний день квартала ещё не разрешает закрытие.
- Бизнес-даты хранятся как `DATE`, время действий — UTC с часовым поясом.
  Нельзя преобразовывать дату факта в UTC и сдвигать календарный день.
- Существующий период и его ID не заменяются при добавлении следующего.
  Внутри одного контура периодов пересечения запрещены.

### 4.2. Метрика

Состояния новой метрики: `draft` («Черновик»), `tracking` («Ведётся»),
`paused` («Приостановлена»). Архивность — существующий `is_archived`,
в интерфейсе имеет приоритет и отображается как «Архив».

Черновик можно сохранить с названием и доступной командой, остальные
обязательные поля проверяются при начале ведения. Владелец и команда
предзаполняются из доступного профиля, но не создаются автоматически.
Начало ведения требует хотя бы одного полностью настроенного периода.

Приостановка с причиной прекращает текущий контроль сроков обновления,
но не меняет даты, планы и прошлые факты. Внесение данных, закрытие и
исправления остаются доступны по обычным правам. Исторические пропуски
сохраняются. Сроки внутри паузы не считаются пропущенными; после возобновления
следующий контроль — ближайшая дата исходного расписания после возобновления.
Интервалы пауз сохраняются для воспроизводимости.

Архивирование требует отсутствия периодов `active`: их нужно закрыть либо
явно отменить. Восстановление не меняет итоги: прежний draft возвращается в
draft, tracking/paused — в paused. Прежнее состояние сохраняется в истории;
контроль сроков возобновляется только явным действием владельца/редактора.

### 4.3. Период

Сохранить состояния хранения `draft / active / completed / cancelled`.
Для новой модели `active` означает утверждённый план, в том числе будущий;
отдельного фонового перевода по наступлению даты не требуется.

| Отображение | Условие |
|---|---|
| Не запланирован | Квартального периода нет |
| Черновик плана | Есть `draft`, настройка не утверждена |
| Запланирован | `active`, начало ещё не наступило |
| В работе | `active`, текущая дата внутри периода |
| Ожидает итога | `active`, дата окончания прошла |
| Закрыт | `completed`, есть подтверждённый итог новой модели |
| Отменён | `cancelled`, причина обязательна |

«Нет факта», «Нет замеров», «Требует обновления» и «Цель не достигнута» —
отдельные признаки, а не состояния жизненного цикла. Будущий период никогда
не попадает в проблемную выборку только из-за отсутствия факта.

## 5. Целевая модель данных

Физические имена ниже — контракт проекта реализации. Разрешено выбрать
эквивалентную нормализованную схему при сохранении инвариантов, аудита и API.
Новые записи не должны переиспользовать таблицы пользователей или справочников.

### 5.1. Паспорт `kr_metrics`

Сохранить ID, связи, название, описание, единицу, команду, владельца, источник,
методику, проект, дополнительные атрибуты, автора, даты и `version`.

Добавить:

| Поле | Назначение |
|---|---|
| `lifecycle_state` | draft/tracking/paused |
| `preferred_result_type` | volume/change/threshold/range; шаблон для новых периодов |
| `default_direction` | up/down/range, согласованное с типом |
| `annual_aggregation` | sum/last/ratio/none |
| `aggregation_scale` | 1 или 100 для ratio; без произвольного кода |
| `display_precision` | 0–10, по умолчанию 2; не меняет точность хранения |
| `model_version` | legacy_v1 / mixed / quarterly_v2; mixed означает наличие двух контуров периодов |

Единица блокируется после утверждения периода, появления факта или замера.
Смена единицы требует новой метрики. Назначение существующего владельца
меняет только ссылку в паспорте, не его учётную запись или команду.

### 5.2. Квартальный период `kr_periods`

Сохранить существующий ID, связь с метрикой, даты, состояние, направление,
цель, верхнюю границу, базу и дату базы, настройки расписания и снимки.
Добавить `model_version`, `calendar_year`, `quarter`, `result_type`,
`current_plan_revision_id`, `current_fact_revision_id`, `closure_revision_id`.

Для `quarterly_v2` обязательна уникальность `(metric_id, calendar_year, quarter)`.
Тип, направление, единица, источник и методика фиксируются при утверждении
плана. Последующее изменение паспорта не переписывает снимки старых периодов.
Переход между типами после появления фактов/замеров требует новой метрики;
для будущего пустого периода допустим отдельный пересмотр настройки с причиной.

### 5.3. Редакции плана `kr_period_plan_revisions`

Неизменяемая редакция: `id`, `period_id`, `revision_no`, цель, верхняя граница,
база, дата базы, тип, направление, снимки источника/методики/единицы,
`author_id`, `created_at`, `reason`, `previous_revision_id`.
Поля действующего периода могут служить проекцией текущей редакции.

Первый утверждённый план остаётся доступен как «Первоначальный план».
Пересмотр сохраняет новую редакцию и связь с предыдущей. Нельзя задним числом
заменять первоначальный план или редактировать уже сохранённую редакцию.

### 5.4. Факт и его редакции `kr_period_fact_revisions`

Одна текущая редакция на период; все предыдущие сохраняются:

| Поле | Правило |
|---|---|
| `value` | Конечное десятичное число, включая 0 |
| `as_of_date` | Дата, к которой относится значение; внутри квартала, не в будущем |
| `status` | preliminary/final |
| `source`, `comment` | Источник обязателен после наследования; комментарий опционален |
| `author_id`, `created_at` | Фактический автор и время записи, не дата измерения |
| `reason` | Обязательна при исправлении сохранённого значения/даты и итогового факта |
| `source_measurement_id` | Опциональная ссылка на явно выбранный замер этого периода |
| `source_measurement_snapshot` | Значение, дата и источник замера на момент копирования |
| `numerator`, `denominator` | Опциональная пара исходных величин для годового ratio |
| `previous_revision_id`, `revision_no` | Цепочка версий и уникальный номер внутри периода |

«Обновить предварительный факт» на более позднюю дату — обычное обновление;
для него причина не обязательна. Замена значения на той же/более ранней дате
считается исправлением и требует причины. Сохранение неизменившихся данных
не создаёт пустую редакцию.

Новая редакция итогового факта заменяет текущую проекцию, но не изменяет
предыдущее подтверждение и ранее опубликованные снимки.

### 5.5. Подтверждение закрытия `kr_period_closure_revisions`

Неизменяемая запись: период, редакции плана и факта, автор подтверждения,
время, комментарий, рассчитанный результат, число нарушений замеров,
версия расчётных правил и предыдущая редакция подтверждения.

Первое закрытие, исправление итогового факта и пересмотр закрытого плана
создают новую запись. Первое `closed_at` сохраняется; время последнего
подтверждения передаётся отдельным полем. Старый снимок закрытия не пересчитывается.

### 5.6. Замеры и сотрудничество

- `kr_measurements` остаются отдельными датированными наблюдениями: один замер
  на дату в периоде, число, источник, комментарий, автор и история исправлений.
- Замеры объёмной метрики по умолчанию означают накопленное значение внутри
  квартала. Суммирование замеров запрещено. Иную методику нужно явно описать;
  автоматический расчёт итогов из наблюдений не входит в поставку.
- Добавить необязательный `period_id` к комментариям и общим файлам;
  проверить принадлежность периода метрике. Привязку файла к замеру сохранить.
- Ссылки на задачи и прежние материалы не переносятся в другие сущности.
- Снимок встречи включает редакции факта/плана, статус факта и версию правил.
  Изменение данных после состоявшейся встречи не меняет её снимок.
- Интервалы пауз хранить отдельно либо в эквивалентной восстанавливаемой
  структуре с датами, автором и причиной; одного текущего флага недостаточно.

### 5.7. Область годового обзора

Хранить настройки года: ожидаемые кварталы, исключения с причинами,
правило агрегации и его версию. Это не годовой период и не годовая цель:
в этой структуре нет редактируемого годового плана или факта.

При создании показать «Ведение с … квартала»; предложить первый заполненный
квартал — IV квартал включительно. Пользователь видит и подтверждает область.
Пустой план внутри выбранной области означает незаполненный ожидаемый план,
а квартал вне области — «Не ведётся». Изменение области после начала ведения
требует причины; удаление из неё квартала с данными запрещено, применяется отмена.

## 6. Расчёты и валидация

### 6.1. Числа и единицы

Расчёты на сервере — Decimal, хранение — существующая точность `NUMERIC(30,10)`.
Для новых команд диапазон по модулю не более `1e15`; NaN/Infinity запрещены.
До 10 десятичных знаков, лишняя точность вызывает ошибку, а не тихое округление.
В новом контракте десятичные значения передаются каноническими строками;
UI принимает запятую и точку, нормализует до отправки. Нельзя рассчитывать
достижение по округлённому отображению или по числам JavaScript.

Отображать проценты с точностью до одного знака, значения — с настроенной
для метрики точностью 0–10. Изменение точности отображения не меняет данные.
`-0` выводить как `0`. Для volume факт/план неотрицательны; для остальных
типов отрицательные значения допустимы, если не запрещены методикой.
Единица «%» сама по себе не задаёт границы 0–100 для всех возможных показателей.

### 6.2. Типы результата

Обозначения: F — текущий факт, T — план/нижняя граница, U — верхняя граница,
B — база. При отсутствии факта результат `no_data`, процент `null`, не 0.

| Тип | Проверка цели | Прогресс |
|---|---|---|
| volume | F ≥ T; направление up | F / T × 100, только если T > 0 |
| change/up | T > B; достигнуто F ≥ T | (F − B) / (T − B) × 100 |
| change/down | T < B; достигнуто F ≤ T | Та же формула |
| threshold/up | F ≥ T | null; показывать отклонение |
| threshold/down | F ≤ T | null; показывать отклонение |
| range | T ≤ F ≤ U, границы включительно | null; «В диапазоне / Вне диапазона» |

Нулевой volume-план допустим: процент отсутствует, условие F ≥ 0 проверяется.
Это отличается от упрощённой формы демонстрационного макета.
Для change база и её дата обязательны; T = B запрещено. Дата базы не позднее
начала квартала и текущей бизнес-даты. Копирование предыдущего итогового факта
в базу — предложение с показом источника и явным подтверждением, без каскада
при последующих исправлениях предыдущего квартала.

Отклонение для up/down: F − T с пояснением направления. Для range — 0 внутри,
F − T ниже, F − U выше. Не кодировать «хорошо/плохо» только знаком числа.
Прогресс может быть < 0 и > 100; ограничивается только длина полосы.

### 6.3. Диапазон и замеры

Результат квартала определяет только текущий факт; после закрытия — итоговый.
Отдельно вернуть `measurement_violation_count` по текущим редакциям замеров,
список нарушивших дат и количество наблюдений. При отсутствии замеров писать
«Замеров нет», при отсутствии нарушений — «Нарушений среди замеров нет».
Никогда не писать «Диапазон удержан весь квартал».

Исправленный ошибочный замер исключается из текущего счётчика, его прежнее
значение остаётся в истории. При пересмотре диапазона текущий счётчик
пересчитывается по действующему плану; старое подтверждение хранит прежний
счётчик и границы. Итог вне диапазона виден и при отсутствии нарушивших замеров.

### 6.4. Актуальность и риск

Расписание по умолчанию `none`. Существующие cadence и календарное поведение
сохраняются. Расписание контролирует **замеры**, а не выполнение плана.
Факт имеет собственную дату; ввод факта не создаёт замер и не закрывает
пропущенный интервал наблюдений. В UI это подписано «Срок замера».

При `none` нет просрочки обновления. «Нет факта» остаётся самостоятельным
признаком. При паузе контроль отключён по разделу 4.2. В закрытом/отменённом
периоде новые сроки не появляются. Автоматического риска достижения цели
по доле прошедшего квартала нет.

### 6.5. Годовые итоги

| Правило | План года | Факт года |
|---|---|---|
| sum | Сумма планов участвующих кварталов | Сумма итоговых квартальных фактов; только аддитивные величины |
| last | План последнего ожидаемого неотменённого квартала | Его итоговый факт; более ранний не подставляется вместо отсутствующего |
| ratio | Не вычислять из процентов квартальных целей | Σnumerator / Σdenominator × scale при полной паре во всех участвующих кварталах |
| none | Не рассчитывается | Только квартальное представление |

Для ratio годовой прогресс/достижение не выводить: отдельной годовой цели нет,
а сравнимый план не задан. Поля numerator/denominator раскрываются только для
этого режима; denominator > 0, масштаб 1 или 100. При их наличии квартальный
факт должен совпадать с отношением в пределах принятой точности; показывать
рассчитанное значение до сохранения. Отсутствие пары не мешает сохранить и
закрыть квартал, но годовой итог получает причину `missing_components`.
Средние, требующие иной формулы, используют none; произвольные формулы отложены.

Для last допускается сравнение с планом последнего квартала. Годовой прогресс
change вычислять только при явно подтверждённой общей базе года; в первой
поставке общей базы нет, поэтому выводить факт, план, отклонение, без процента.
Для sum прогресс допустим только для volume. Различные единицы, типы или
несовместимые методики дают `not_comparable`, а не искусственный агрегат.

Годовая проекция возвращает отдельно:

- `confirmed_value` — сумма закрытых кварталов для sum, с явной подписью
  неполного охвата; для last — значение нужного квартала либо null;
- `preliminary_value` — текущая оценка с использованием имеющихся
  предварительных фактов, с перечнем отсутствующих кварталов;
- `final_value` — только при закрытии всех ожидаемых неотменённых кварталов
  с итоговыми фактами и выполнении условий правила;
- `coverage` — ожидаемые, закрытые, незаполненные, исключённые кварталы;
- `completeness` — empty/partial/complete/not_calculable;
- `scope_adjusted` и причины исключений/отмен.

Все четыре квартала без исключений — полный год. Иная область подписывается
«Итог за II–IV кварталы» или соответствующим набором, даже если completeness=complete.
Отмена исключает квартал из текущего расчёта, но первоначальный план и причина
видны; такой итог нельзя обозначать как полный исходный год. При отсутствии
хотя бы одного участвующего квартала итог не равен нулю автоматически.
Если все кварталы отменены, итог отсутствует. Будущие кварталы входят в план,
но не становятся подтверждённым фактом. Все суммы рассчитываются по редакциям
одной согласованной версии чтения.

## 7. Страницы и пользовательские сценарии

### 7.1. Реестр `#/metrics`

Режим по умолчанию — текущий год/квартал; переключатели «За квартал / За год».
Оба режима — одна выборка метрик, без дублирования паспортов по кварталам.
Метрика без плана выбранного квартала не исчезает: показывается соответствующая
пустая ячейка. Legacy-метрики без квартального представления имеют явную отметку.

Квартальные колонки: ID/название/единица, план, факт с датой и статусом,
результат, владелец, состояние метрики/периода. Колонки можно скрывать через
общий механизм; ID, название, план, факт и результат остаются базовым набором.
Название открывает карточку; факт открывает редактор выбранного квартала
только при наличии права и доступности операции. В режиме чтения — карточку.

Годовые колонки: метрика и четыре квартала, в ячейке план/факт/результат.
Переход по ячейке открывает конкретный квартал. Годовой итог раскрывается в
карточке; дополнительный общий процент над реестром не показывается.

Фильтры: поиск по существующему `MET-…`, названию и владельцу; команда,
владелец, проект, состояние метрики, состояние периода; область «Все / Мои»;
архив отдельным переключателем. Категориальные фильтры множественные:
ИЛИ внутри поля, И между полями. Год/квартал — одиночные контексты.

Быстрые выборки: `missing_fact`, `awaiting_close`, `not_achieved`, `overdue`.
«Мои» — область `owner_id == current_user.id`, а не отдельное право доступа.
`not_achieved` учитывает только закрытые периоды. `missing_fact` — начавшиеся
active-периоды без явного факта, даже если замеры имеются. `overdue` относится
к графику замеров. В годовом режиме метрика подходит, если существует хотя бы
один подходящий квартал года. Несколько условий периода должны выполняться
на **одном квартале**, а не на разных кварталах одной метрики.

Счётчики быстрых выборок учитывают поиск, основные фильтры и «Мои», но не
выбранные быстрые фильтры. Несколько быстрых фильтров объединяются ИЛИ.
Категории могут пересекаться; не выдавать их сумму за число уникальных метрик.

Поиск через 350 мс либо Enter, сохранение фокуса и допечатанного текста.
Условия применяются сразу, сбрасывая страницу на первую. Пагинация 25,
серверный предел 100; стабильный дополнительный ключ сортировки — ID.
Сортировки: название, дата изменения, ближайший срок замера; прогресс —
только квартальный режим, значения null в конце. Смешанные типы не образуют
рейтинг эффективности; подпись сортировки — «По числовому прогрессу».

Сброс возвращает текущий год/квартал, все метрики, название и снимает архив.
Смена режима сохраняет год, поиск, область и фильтры; выбранный квартал
запоминается для возврата. Архив и «Мои» не сбрасываются неявно.

### 7.2. URL и возврат

Сохранить `#/metrics/{id}` и модальную карточку поверх реестра на desktop;
на узком экране — полноэкранную карточку. Прямой адрес восстанавливает фон
реестра. Escape закрывает сначала верхнюю форму, затем карточку с защитой ввода.

Новые параметры: `view=quarter|year`, `year=2026`, `quarter=1..4`,
`metric_state`, `period_state`; существующие поиск/фильтры/пагинация сохраняются.
`section=overview|discussion|history` и `period_id` остаются каноническими
параметрами карточки. Видимую вкладку overview назвать «Показатели».
`tab` не переиспользовать: он принадлежит общей карточке задачи.

Старая точная пара дат в `period` преобразуется в год/квартал только при полном
совпадении границ. Иначе открывается legacy-контекст. `period_id` должен
принадлежать метрике; ошибочный ID не подменяется молча другим кварталом.
При конфликте валидного period_id и year/quarter приоритет имеет period_id,
URL нормализуется. Старые вкладки и ссылки на KR сохраняют текущие перенаправления.

### 7.3. Карточка

Шапка: ID, название, единица, владелец, состояние. Основное действие зависит
от выбранного периода: «Внести факт», «Обновить факт», «Зафиксировать итог»
или «Исправить итог». Все формы явно повторяют метрику и квартал.

Показатели: сводка выбранного квартала, годовой график и таблица периодов,
годовой итог с охватом, замеры выбранного квартала. Выбор строки синхронно
меняет сводку, замеры и действие. Годовой график показывает квартальные факты,
а раскрываемая динамика квартала — замеры. Эти две серии не смешиваются.
Предварительные значения визуально отличаются и имеют текстовую подпись.
Отсутствующие точки оставляют разрыв; ноль расположен на нулевой отметке.
Для range отображается допустимая область выбранного периода и список нарушений.

В раскрываемом паспорте: методика, источник, команда, проект, дополнительные
атрибуты, тип результата, правило годового итога. Связанные задачи сохраняются.
Действия с состоянием и архивом — во вторичном меню, рядом нет нескольких
конкурирующих основных кнопок.

Обсуждение: общий поток с фильтром «Все / выбранный квартал», комментарии,
файлы, выбранная привязка перед отправкой. История: фильтр по периоду и типу
события, сравнение до/после, автор, время, причина, редакция; снимки встреч
и сведения исходного KR доступны в отдельных раскрываемых блоках.

### 7.4. Создание и черновик

Одна форма: название, единица, владелец, команда, тип/направление, источник,
год, область ведения, четыре строки квартальных планов. Источник может
наследоваться, но перед началом ведения должен быть заполнен.

У change каждая заполненная строка содержит базу и её дату; у range — две
границы. Не применять одну базу ко всем кварталам неявно. Сроки/частота замеров,
методика, проект, теги и прочие поля находятся в дополнительных настройках.
График по умолчанию «Без расписания». Незаполненные кварталы не создают
фиктивные периоды или нулевые планы.

«Создать и начать» атомарно создаёт паспорт, планы и утверждает заполненные
периоды. «Сохранить черновик» допускает неполные планы и не включает контроль.
Ошибка любой строки откатывает всё; форма сохраняет ввод. Двойной клик и
повтор после сетевого таймаута не создают второй паспорт.

### 7.5. Редактор планов

Таблица четырёх кварталов; закрытые периоды в обычном редакторе недоступны.
Новые и будущие планы можно заполнить/изменить; изменение уже утверждённого
плана требует причины. Сохранение нескольких строк — одна атомарная команда.
Сравнение старого/нового плана доступно до отправки. Границы квартала не редактируются.

Для закрытого квартала отдельное действие «Пересмотреть план»: владелец с
правом изменения указывает причину, видит прежний и новый результат и явно
подтверждает пересмотр. Факт остаётся прежним; создаются редакция плана и
новое подтверждение результата, период остаётся закрытым. Первоначальный
план и прежнее закрытие доступны. Это не путь для изменения типа/единицы.

### 7.6. Внести факт / использовать замер

Основные поля: значение, дата актуальности; источник предзаполнен из снимка
периода, комментарий раскрывается дополнительно. При ratio — опциональная
пара исходных величин. Дата по умолчанию — min(сегодня, конец квартала).
Для будущего периода ввод запрещён, доступно планирование.

«Использовать как факт» открывает эту же форму с выбранными значением,
датой и источником. До подтверждения записи нет. Позднейшее исправление
исходного замера не меняет факт; карточка сообщает о расхождении с источником.
При сохранении изменённого относительно замера значения требуется комментарий.

### 7.7. Замер и исправление

Один замер на дату; будущие даты и даты вне периода запрещены. При дубле
предлагается открыть исправление существующей записи, сохранив ввод.
Автоматического overwrite нет. Исправление требует причины.

В закрытом периоде новые замеры не добавляются. Исправление существующего
ошибочного замера разрешено владельцу с правом изменения отдельной командой,
не меняет итоговый факт и создаёт запись истории. Текущий счётчик нарушений
обновляется; сохранённый снимок закрытия остаётся прежним и помечается как
имеющий последующие исправления наблюдений.

### 7.8. Закрытие и исправление итога

Закрытие доступно после конца квартала, только владельцу с правом изменения.
В форме показаны действующий план, предварительный факт, дата, источник,
результат и нарушения замеров. Пользователь может уточнить факт и подтверждает
«Зафиксировать итог и закрыть». Замеры не обязательны; числовой факт обязателен.
Если факта нет, квартал нельзя закрыть как 0; можно внести факт либо отменить
период с причиной. `confirm_no_data` новой модели не поддерживается.

Дата итогового факта может быть раньше конца квартала: владелец подтверждает,
что выбранное значение является итогом. Если дата раньше окончания, UI явно
показывает предупреждение и отдельное подтверждение; исходная дата не меняется
на дату закрытия. Подтверждение хранится в записи закрытия.

Закрытие выполняется одной транзакцией: редакция final-факта, подтверждение,
состояние completed, аудит, новая версия. Частично закрытый период невозможен.
Исправление итога требует причины, показывает до/после, оставляет completed
и создаёт новую редакцию закрытия. Повторное открытие закрытого quarterly_v2
не нужно и не допускается; корректировки выполняются адресными командами.

Отмена draft/active требует причины. Восстановление отменённого квартала —
отдельное действие владельца с причиной, возвращает active; временная фаза
определяется датой. Ранее сохранённые данные остаются предварительными и
требуют нового закрытия. Отмена completed не является обычной операцией.

### 7.9. Пустые, ошибочные и мобильные состояния

- Различать «метрик ещё нет» и «нет совпадений фильтра»; действия — создать
  при наличии права либо сбросить фильтры.
- Показывать skeleton/ViewState без подстановки 0; при сбое чтения — повтор.
- 409 сохраняет ввод и предлагает сравнить с актуальными данными; повтор
  изменения только после выбора пользователя. 422 — ошибка поля и сводка.
- При таймауте записи повторять тот же ключ команды; не сообщать об успехе
  без подтверждения сервера. 401 использует штатное восстановление сессии.
- Несохранённые поля защищены при Escape, закрытии и смене маршрута;
  сохранение блокирует повторные кнопки. Ошибка не закрывает форму.
- Использовать действующий UI Kit, Inter и общие токены тем. На 320/390 px
  квартальный реестр переходит в карточки; годовая матрица прокручивается
  внутри контейнера с видимой привязкой к названию, а не расширяет страницу.
- Клавиатура, фокус, возврат фокуса, labels, aria-live и текстовые статусы
  обязательны. Цвет не является единственным носителем результата.
- На ширинах 320/390/768/1024/1440 px и при zoom 200% основные действия доступны.

## 8. Права и ответственность

Не создавать новые роли. Чтение/изменение/комментарии наследуют действующие
области `task_read_scope_clause`, `can_access_task` и политику customer-only.
Владение само по себе не расширяет область доступа.

| Операция | Условие |
|---|---|
| Читать карточку, реестр, историю, снимки | Существующее право чтения метрики |
| Создать, изменить паспорт/открытый план, предварительный факт/замер | Существующее право edit в нужной области |
| Закрыть, исправить final-факт/закрытый замер, пересмотреть закрытый план | edit И `current_user.id == owner_id` |
| Восстановить отменённый период | edit И владелец |
| Комментарий/файл | Существующая политика соответствующего действия |
| Пауза/возобновление/архив | edit, проверки переходов и обязательная причина |

Администратор не получает неявное право подтвердить результат за владельца.
Если владелец неактивен или лишён edit, показать причину; исправить назначение
в паспорте может существующий уполномоченный редактор. Учётные записи,
пароли, роли и командные назначения при этом не изменяются.

`GET` возвращает конкретные capabilities и причины недоступности действий;
frontend не выводит права из названия роли. Backend повторно проверяет их
под блокировкой, включая смену владельца между чтением формы и записью.
Периоды, редакции, замеры и файлы проверяются на принадлежность метрике;
скрытые сущности не раскрываются через поиск, счётчики, ошибки и агрегацию.

## 9. API новой модели

### 9.1. Версионирование и общие правила

Ввести `/api/v2/metrics` для изменившейся семантики факта и результата.
Переиспользовать сервисы доступа/файлов/сотрудничества, не копировать политику
безопасности в независимую реализацию. Текущий `/api/v1/metrics` остаётся
legacy-контрактом; правила сосуществования — раздел 13.

Все изменяющие команды существующей метрики принимают `version >= 1`;
блокировка строки паспорта и проверка версии предшествуют записи.
Для создания, факта, закрытия, исправления, пакета планов и перехода модели
обязателен `Idempotency-Key` 8–64 символа. Ключ связан с пользователем,
операцией, метрикой и нормализованным телом. Повтор идентичной успешной
команды не создаёт редакций; другой payload с тем же ключом даёт 409.
Проверка доступа выполняется и при воспроизведении результата команды.
Reservation и запись коммитятся атомарно; после валидационной ошибки ключ
не должен блокировать корректный повтор согласно принятой политике сервиса.

Ответ команды: актуальная версия и изменённая проекция, IDs редакций,
при необходимости компактный результат закрытия. Номер версии монотонно
растёт; клиент не предполагает обязательное увеличение ровно на единицу.

### 9.2. Операции

Пути таблицы указаны после `/api/v2/metrics`.

| Метод и путь | Назначение |
|---|---|
| `GET /options` | Бизнес-дата, доступные владельцы/команды/проекты, типы, правила агрегации, возможности создания |
| `GET /` | Квартальная/годовая проекция с серверными фильтрами, сортировкой и пагинацией |
| `POST /` | Паспорт, область года и массив планов; `save_mode=draft|start` |
| `GET /{id}` | Паспорт, capabilities, выбранный год, компактные периоды и годовой итог |
| `PATCH /{id}` | Только явно переданные поля паспорта; версия обязательна |
| `PUT /{id}/years/{year}/plans` | Атомарный пакет upsert квартальных планов, без удаления пропущенных строк |
| `PATCH /{id}/years/{year}/settings` | Область года/правило агрегации с причиной; не годовая цель |
| `POST /{id}/periods/{pid}/activate` | Утвердить черновик плана |
| `PUT /{id}/periods/{pid}/fact` | Создать/обновить preliminary-факт; optional measurement reference |
| `POST /{id}/periods/{pid}/close` | Final-факт и закрытие одной транзакцией |
| `POST /{id}/periods/{pid}/fact-corrections` | Исправить итог с причиной и новым подтверждением |
| `POST /{id}/periods/{pid}/plan-revisions` | Пересмотр плана, включая отдельное подтверждение закрытого |
| `POST /{id}/periods/{pid}/cancel` | Отменить draft/active с причиной |
| `POST /{id}/periods/{pid}/restore` | Восстановить отменённый с причиной |
| `GET, POST /{id}/periods/{pid}/measurements` | Постраничный список / новый замер |
| `PATCH /{id}/measurements/{measurement_id}` | Исправление замера с причиной и проверкой закрытого периода |
| `GET /{id}/history` | Постраничный аудит; фильтры period_id/action |
| `POST /{id}/lifecycle` | start/pause/resume; причина для pause/resume |
| `POST /{id}/archive` | Архив/восстановление по существующему назначению |
| `POST /{id}/migration-preview`, `POST /{id}/migrate` | Предпросмотр и явное применение перехода legacy |

Комментарии, файлы, связи, legacy resolution и статусы встреч предоставить
через v2 с прежними назначениями путей v1, добавив period_id и снимки новой
модели. Старые авторизованные URL скачивания должны продолжать работать.

`GET /`: `view=quarter|year`, `year`, `quarter` для quarter, `q`, множественные
`team_id/owner_id/project_id/metric_state/period_state/attention`, `scope`,
`archived`, `sort`, `page`, `per_page`. Использовать существующее кодирование
множественных фильтров. В годовом режиме quarter не ограничивает выборку,
а сохраняется только frontend как контекст возврата.

Годовая строка всегда содержит четыре позиции с `availability`:
`outside_scope|unplanned|draft|planned|active|awaiting_close|completed|cancelled`.
Не возвращать фиктивный period_id для отсутствующего квартала.
Ответ: `items`, `total`, `page`, `pages`, `summary`, `business_date`.

### 9.3. Пример команды и проекции

```json
{
  "version": 12,
  "value": "120.5",
  "as_of_date": "2026-11-02",
  "source": "Отчёт сервисной системы",
  "comment": "Сверено с источником",
  "source_measurement_id": null
}
```

Это тело `PUT .../fact`; статус final через него установить нельзя.
`close` принимает аналогичный факт, `confirm_final=true`,
`confirm_early_as_of=true` при дате факта раньше конца квартала и комментарий.
Для `fact-corrections` дополнительно обязательна `reason`.
Поля автора, времени, результата и статуса закрытия устанавливает сервер.

```json
{
  "id": 42,
  "year": 2026,
  "quarter": 4,
  "state": "active",
  "phase": "in_progress",
  "model_version": "quarterly_v2",
  "plan": {"revision_id": 7, "result_type": "volume", "target": "180"},
  "fact": {"revision_id": 9, "status": "preliminary", "value": "120.5", "as_of_date": "2026-11-02"},
  "result": {"outcome": "not_achieved", "is_final": false, "progress": "66.9444444444", "deviation": "-59.5"},
  "observations": {"count": 2, "violation_count": null, "latest_date": "2026-10-31"},
  "capabilities": {"write_fact": true, "add_measurement": true, "close": false},
  "disabled_reasons": {"close": "period_not_ended"}
}
```

`outcome=not_achieved` при `is_final=false` отображается как «Пока не достигнута»,
а не как провал. При отсутствии факта весь объект fact равен null.
`observations.violation_count` для нерелевантного типа — null, не оценка диапазона.
Значение 0 применяется к range при наличии замеров без нарушений; отсутствие
замеров определяется отдельным count=0 и соответствующей подписью.

### 9.4. Ошибки

Единый объект: `code`, человекочитаемое `message`, ошибки полей `fields`,
при конфликте `current_version` без автоматической перезаписи.

| HTTP | Код / условие |
|---|---|
| 401 | Штатная аутентификация |
| 403 | Действие запрещено / подтверждает не владелец |
| 404 | Метрика или вложенная сущность недоступна в области чтения |
| 409 | version_conflict, duplicate_measurement_date, invalid_transition, idempotency_conflict, model_upgrade_required |
| 422 | period_not_ended, fact_required, invalid_baseline, invalid_range, invalid_date, invalid_decimal, reason_required, missing_source |
| 503 | Временная недоступность, форма сохраняет ввод |

Неверная принадлежность measurement_id/period_id не должна раскрывать
другую метрику. Поле с неизвестным назначением отклоняется, а не игнорируется.

## 10. Транзакции, история и производительность

Все изменения метрики сериализуются блокировкой её строки; чтение
консистентной годовой проекции не смешивает версии плана и факта.
Проверка дат, состояния, владельца и версии выполняется внутри транзакции.
Сохранение нескольких планов, создание, закрытие и переход модели атомарны.

События: metric_created/started/paused/resumed/archived/restored,
plan_created/activated/revised, fact_recorded/updated/corrected,
measurement_added/corrected/used_as_fact, period_closed/cancelled/restored,
year_scope_changed, aggregation_changed, model_migrated, comment/file/link/report.
История содержит before/after, причину, автора, период и IDs редакций;
секреты, cookies, токены и реквизиты в неё не попадают.

Реестр не загружает все замеры всех метрик. Фильтры/сортировка/пагинация
выполняются на сервере; owners/teams и годовые периоды загружаются пакетно,
без запросов на каждую строку. Индексы: метрика+год+квартал, period+date,
period+revision_no, metric+created_at истории, поля областей доступа.
История и замеры имеют серверную пагинацию, по умолчанию 25, максимум 100.

Приёмочные бюджеты, не заявления о текущей производительности: на тестовом
наборе 1 000 метрик, 4 000 периодов и 100 000 замеров p95 квартального/годового
реестра ≤ 1 с, первого чтения карточки ≤ 1,5 с после прогрева при 10
параллельных читателях. Зафиксировать машину, PostgreSQL, число SQL-запросов,
объём ответа и метод замера. Не создавать для этого защищённые записи.

## 13. Миграция и совместимость

### 13.1. Аддитивный запуск

Перед реализацией определить актуальные Alembic heads, не фиксировать новый
`down_revision` по устаревшему документу. Текущая миграция ручного расписания
`e7c012d83f41` зависит от `d6b901c72e30`; граф мог измениться в параллельной работе.
Изменение схемы и преобразование бизнес-смысла — отдельные шаги.

Сначала добавить nullable-поля/таблицы и пометить прежние данные legacy_v1.
Не изменять факты, даты, состояние completed, outcome, legacy_snapshot и
снимки встреч при добавлении схемы. Новые метрики создаются quarterly_v2.

### 13.2. Прежние периоды

Существующие квартальные, годовые и произвольные периоды читаются с пометкой
«Прежняя модель». Для них остаётся прежняя интерпретация, включая legacy
результат диапазона; выводится подпись, что правило отличается от нового.
В карточке они доступны отдельно от новой годовой матрицы, без потери ID.

Прежний годовой период не делится на четыре равных плана/факта, не становится
новой редактируемой годовой целью и не участвует в новой агрегации автоматически.
Периоды с нестандартными датами и пересечениями требуют ручного выбора
квартального покрытия. Старые данные остаются самостоятельным legacy-контуром;
пересечение с новым контуром допустимо только после явного перехода и
исключения legacy-периодов из новых агрегатов. Внутри каждого контура пересечений нет.

### 13.3. Предпросмотр и подтверждение перехода

Команда preview ничего не записывает. Показывает для каждого периода:
распознанный квартал, предлагаемый тип, план, базу, последнюю датированную
точку, факт без даты, прежнее закрытие, несовместимости и необходимые решения.

Правила предложения: range → range; up/down с базой → change; без базы →
threshold. Тип volume нельзя выводить только из единицы «шт.» — нужен выбор.
Последний замер предлагается как предварительный факт с сохранением ссылки;
не становится подтверждённым итогом автоматически. `legacy_fact` без даты
показывается отдельно: дату не брать из updated_at, created_at или конца периода.

Переход точного квартального периода сохраняет его ID и все связи. Прежнее
состояние/итог сохраняются в неизменяемом снимке перехода. Открытый период
получает preliminary-факт только после подтверждения пользователя.
Маркер паспорта становится mixed при наличии обоих контуров и quarterly_v2,
когда legacy-периодов не осталось; версия каждого периода определяется отдельно.
Для ранее completed владелец выбирает:

- оставить период в legacy-контуре для чтения;
- явно подтвердить итог новой модели с достоверной датой, источником и
  выполненными правилами закрытия; original legacy closure сохраняется.

Нельзя снимать прежнее закрытие или переводить его в новое подтверждение
одним техническим backfill. Закрытый старый период без факта остаётся legacy,
пока владелец не внесёт достоверные данные. Смешанный год отмечается неполным
для новой модели; legacy значения не добавляются в сумму скрыто.

Применение перехода — versioned/idempotent команда с сохранением выбранного
плана преобразования и актором. Фоновая миграция не назначает пользователя
автором подтверждения. Ошибка любого шага откатывает преобразование метрики.

### 13.4. Старый API и откат

V1 читает и изменяет legacy_v1 по прежнему контракту. Изменяющая v1-команда,
затрагивающая quarterly_v2, возвращает 409 `model_upgrade_required` и адрес
нового контракта; нельзя снова начать вычислять факт как последний замер.
V1-чтение карточки новой/смешанной модели также сообщает о необходимости
обновления клиента. Если в области старого реестра есть записи новой модели,
он возвращает такую же явную ошибку вместо тихого неполного списка.
Авторизованные старые ссылки скачивания и разрешение legacy ID сохраняются.

После появления v2-данных откат на старый бинарник, не знающий этих проверок,
небезопасен. До открытия записи подготовить совместимый rollback build:
он сохраняет новую схему, читает v2 либо явно блокирует её изменение.
Разрушительный downgrade, удаление редакций и обратная запись итогов в замеры
запрещены. При дефекте временно отключить новые команды, сохранив чтение и аудит.

## 14. Проверки и критерии приёмки

Новая функциональность принимается по проверкам ниже. Существующие тесты
legacy сохраняются; их ожидаемые результаты нельзя просто заменить так,
чтобы исчезла проверка обратной совместимости.

| ID | Проверка / ожидаемый результат |
|---|---|
| AC-01 | Создание паспорта и четырёх планов атомарно; ошибка одного не оставляет частичных записей |
| AC-02 | Повтор создания с тем же ключом возвращает ту же метрику |
| AC-03 | Черновик неполон; начало ведения валидирует владельца, источник, единицу, тип и план |
| AC-04 | Границы четырёх кварталов, високосный год, полночь Москвы и смена года корректны |
| AC-05 | Будущий период принимает план, но не факт/замер и не считается проблемным |
| AC-06 | Ноль, отсутствие факта, отсутствие плана и отсутствие замеров различимы |
| AC-07 | volume: 80/100=80%, 120/100=120%; при плане 0 процент null |
| AC-08 | change: B=10,T=5,F=6 → 80%; F=11 → −20%; T=B отклоняется |
| AC-09 | threshold up/down: отрицательные и нулевые значения сравниваются без деления |
| AC-10 | range: границы включительны; F внутри и нарушивший замер → итог в диапазоне плюс отдельное нарушение |
| AC-11 | Без замеров числовой итог можно подтвердить; без факта закрытие запрещено |
| AC-12 | Замер не меняет факт; явное использование сохраняет ссылку и копию источника |
| AC-13 | Исправление использованного замера не меняет сохранённый факт, расхождение видно |
| AC-14 | Дубликат даты даёт 409; открытие исправления сохраняет ввод и требует причину |

Уровни: чистые расчётные тесты без БД; контрактные и конкурентные API-тесты
на PostgreSQL; миграционные проверки на разрешённых временных сущностях;
изолированные браузерные фикстуры; живой прогон существующих QA-профилей.
Исторические результаты старого набора не являются приёмкой этого ТЗ.

Существующие команды-основы (пути относительно корня проекта):

```powershell
# Из dmb-backlog/backend; для каждого прогона новый basetemp.
python -m pytest metric_tests --confcutdir=metric_tests --basetemp D:\Проект\.runtime\metric-quarterly-run-unique -q

# Из dmb-backlog; расширить testMatch для новых сценариев до запуска.
node node_modules/@playwright/test/cli.js test --config=playwright.metrics.config.mjs
```

Список новых тестовых файлов и фактические команды зафиксировать в отчёте
реализации. Суффикс `unique` — шаблон, его нужно заменить уникальным значением.
В отсутствие PostgreSQL интеграционные проверки отмечаются BLOCKED;
SQLite не считается заменой. Не запускать seed и RUN_STARTUP_SEED.

Тесты используют внешнюю транзакцию с откатом и SQL-guard: разрешены только
таблицы метрик/новых редакций/идемпотентности. Защищённые таблицы только
читаются. Для входа применять существующие готовые QA-профили по
[паспорту тестовых данных](dev-testing/TEST_DATA_PASSPORT.md), без вывода секретов.
