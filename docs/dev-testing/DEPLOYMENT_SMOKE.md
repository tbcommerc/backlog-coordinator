# Smoke-проверка после развёртывания на DEV

Публичную и токенизированную read-only часть можно зафиксировать сценарием
`scripts/verify-multiuser-stand.ps1`. Он не выполняет login и не меняет данные:
access-токены заранее подготовленных профилей передаются оператором только в
памяти процесса.

## 1. Когда выполнять

- после первичного развёртывания;
- после обновления приложения или конфигурации;
- после миграции/изменения БД;
- после смены LLM, базы знаний, reverse proxy или сертификата;
- после восстановления из backup;
- перед началом полноценного тестового цикла.

Целевое время обычного прогона после подготовленного deployment — 15–30 минут. Это ориентир процесса, а не утверждённый SLA.

## 2. Роли участников

| Участник | Область |
|---|---|
| DevOps | процесс, конфигурация, внутренние endpoints, volumes, logs, restart |
| QA/тестировщик | внешний URL, login, пользовательские сценарии, evidence |
| Владелец данных | готовность защищённых справочных и ролевых данных |
| Владелец LLM/KB | provider, модель, квоты и версия базы знаний |

`X-Agent-Secret`, `SECRET_KEY`, LLM API key и пароли не передаются QA и не включаются в протокол. Внутренний `/api/agent/config` вызывает DevOps с секретом из secret storage.

## 4. Gate 0 — конфигурация до запуска

Выполняет DevOps без публикации значений секретов.

| ID | Проверка | Ожидаемый результат | Статус/evidence |
|---|---|---|---|
| DS-001 | Версия артефакта совпадает с поставляемым commit/tag. | Версия однозначно идентифицируется. | |
| DS-002 | `DEBUG=false`. | Dev defaults не активны. | |
| DS-003 | `RUN_STARTUP_SEED=false`. | Startup не создаёт/изменяет защищённые данные. | |
| DS-004 | `RUN_STARTUP_MAINTENANCE` задан явно. | Значение согласовано; для первого запуска рекомендуется `false`. | |
| DS-005 | `RUN_NOTIFICATION_SCHEDULER=false` у web backend. | Scheduler не размножается с web instances. | |
| DS-006 | `SECRET_KEY` и `AGENT_SECRET` заданы через secret storage и не являются default. | Runtime validation проходит; значения не видны в manifests/logs. | |
| DS-007 | Backend `AGENT_BASE_URL` указывает на внутренний agent URL. | Соединение возможно только по требуемому маршруту. | |
| DS-008 | `AGENT_SECRET` согласован между сервисами. | Agent принимает backend и отклоняет запрос без секрета. | |
| DS-009 | `DATABASE_URL`, Redis и persistent paths указывают на DEV-ресурсы. | Нет связей с production. | |
| DS-010 | PostgreSQL session DB, uploads и logs размещены на persistent storage. | Рестарт/пересоздание процесса не удаляет данные. | |
| DS-011 | LLM endpoint/model/key и сетевой маршрут согласованы. | Provider может быть проверен без раскрытия ключа. | |
| DS-012 | KB смонтирована read-only и версия зафиксирована. | Agent видит ожидаемый набор документов. | |
| DS-013 | CORS содержит точный внешний HTTPS origin. | Не используется небезопасный wildcard при credentials. | |
| DS-014 | TLS-сертификат действителен для DEV URL. | Browser trust проходит без обхода предупреждения. | |
| DS-015 | `PRIORITISER_BASE_URL` указывает на внутренний `:9100`, timeout зафиксирован. | Порт не опубликован наружу; backend достигает `/health`. | |

При `FAIL` DS-003 smoke останавливается до подтверждения владельца данных: запуск с seed в общей DEV-БД недопустим.

## 12. Критерии результата

### PASS

- DS-001–014, DS-101–108, DS-201–207, DS-301–307 и DS-401–406 пройдены;
- Gate 5 выполнен или согласованно `BLOCKED` до подготовки обычной тестовой задачи;
- restart gate пройден при первичном deployment;
- нет P0/P1 deployment-дефектов;
- protected data не изменялись;
- версия стенда и evidence зафиксированы.

### FAIL

- приложение/agent/LLM недоступны;
- есть связь с production-ресурсом;
- включён несанкционированный startup seed;
- секрет раскрыт в UI/log/evidence;
- данные теряются после штатного restart;
- авторизация, session isolation или TLS не работают;
- scheduler запущен в нескольких экземплярах;
- deployment нельзя однозначно связать с commit/tag.

### BLOCKED

Используется, когда проверка невозможна из-за отсутствующего согласованного доступа, тестовых данных или контролируемой DevOps-операции. Причина, владелец и ожидаемая дата разблокировки обязательны.
