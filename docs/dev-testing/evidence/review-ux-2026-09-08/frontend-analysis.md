## Вывод о продуктовой задаче

Экран должен помогать специалисту решить четыре последовательно разные задачи: выбрать следующий запрос; восстановить бизнес-контекст; проверить достаточность формулировки; безопасно принять и зафиксировать решение. Сейчас первые две задачи поддержаны визуально, но достоверность отдельных индикаторов и замкнутость рабочего цикла нарушены. В результате экран может показывать «Сигналов нет» при наличии замечаний качества, предлагать уже обработанный запрос как следующий, потерять описание старого запроса и различать статус одной записи в очереди и detail.

Критерий хорошего ревью здесь — не скорость нажатия зелёной кнопки. Ревьюер должен понимать, какую версию потребности он изучил, какие вопросы остались, кому и с каким обоснованием он передаёт ответственность, где потом найти принятое решение. У интерфейса пока нет устойчивой модели этих четырёх фактов.

## Реальный интерфейс и пользовательские пути

В коде очередь выводится карточками-ссылками, а не таблицей. Старые классы `review-table-*` и старые таблицы в CSS не доказывают наличие табличного режима. Переключателя «таблица / карточки» в действующем `renderReviewPage` нет.

| Путь | Действия пользователя | Реализованная поддержка | Что мешает |

| Утренняя сортировка очереди | Посмотреть объём, выбрать свои/новые/срочные, открыть запись | Быстрые фильтры, поиск, сортировки, счётчик, сохранение состояния | «Все» исключает закрытые; ID не ищется; «срочность» не учитывает приближение срока |
| Первое ревью | Открыть, закрепить за собой, прочитать паспорт, проверить вопросы | Кнопка claim, паспорт, ссылки на разделы, блок сигналов | Часть замечаний не показывается; некоторые ссылки ведут в отсутствующий DOM-раздел |
| Возврат на уточнение | Сформулировать конкретные пробелы, отправить комментарий | Обязательный текст, disabled до заполнения, защита при Esc/закрытии | Нет связки комментария с полями; обновление после ошибки выбрасывает текст; мобильная защита переполняется |

## Подтверждённые дефекты

### F01 — P1. Защита несохранённого комментария разваливается на мобильном экране

**Условия и шаги:** открыть возврат на уточнение, ввести текст, нажать Escape или закрытие; ширина 390 px либо 330 px. Основной агент воспроизвёл горизонтальное переполнение, при котором «Продолжить» / «Закрыть без сохранения» оказываются справа за видимой областью. Доказательство браузера: `05-discard-mobile.jpg` основного прогона.

**Причина:** `pages.css:6791` определяет `.review-modal-discard` как grid. Позднее подключённый `modal-system.css:279–290` включает этот класс в общий notice и задаёт `display:flex` без `flex-direction:column`. Три прямых ребёнка — заголовок, длинное пояснение, группа кнопок — становятся одной горизонтальной строкой. Мобильный `pages.css:6948` меняет направление только вложенного `>div`. Порядок CSS: `index.html:14` и `index.html:28`. Общие overlay и modal имеют `overflow:hidden` (`modal-system.css:19`, `44`).

**Последствие:** защитный сценарий сам затрудняет восстановление; пользователь может потерять текст, пытаясь закрыть окно альтернативным способом.

**Исправление:** выделить discard в самостоятельную композицию; исключить из общего горизонтального notice либо задать ему grid/column, `min-width:0`, перенос длинного текста. Все действия должны помещаться по ширине; вертикальная прокрутка тела допустима. Проверить 320, 390, 768 px, zoom 200%, длинный комментарий, Tab/Shift+Tab/Esc.

### F02 — P1. Замечания новой модели качества не попадают в ревью

**Источник:** `requestPresentation.js:118–129` считает только `open_questions`, `conflicts`, `risks`, `assumptions`. `review_findings`, `quality_issues`, severity и статус решения замечания не используются. При этом `agentChat.js:2089–2110` читает `review_findings` и `quality_issues`; составитель агента сохраняет `review_findings` (`agent/agent/composer/composer.py:178`).

**Воспроизведение:** draft содержит `review_findings:[{severity:'warning',field:'acceptance_criteria',message:'Нет измеримого порога'}]` и `quality_issues:['Неизмеримый критерий']`, старые четыре массива отсутствуют. Node-проба получает `signalCount === 0`. Очередь исключает запись из фильтра «Сигналы», пишет «Сигналов нет», detail пишет «Ассистент не выявил открытых сигналов».

**Последствие:** индикатор готовности не отражает все переданные замечания; решения принимаются при искусственно заниженном числе проблем. Синтетическая проба подтверждает несовместимость поддерживаемых структур, но не утверждает частоту таких записей в живой БД.

**Исправление:** единый нормализатор findings для ассистента, клиента и ревью: устойчивый ID, поле, текст, severity, источник, состояние open/resolved/accepted. Считать и показывать открытые замечания из канонического массива; legacy-массивы использовать как fallback с дедупликацией. Отдельно разделить обязательные исправления, вопросы и принятые бизнес-риски. Если оценка не проводилась, писать «Проверка не выполнена».

### F03 — P1. У старых запросов исчезает единственное содержательное описание

**Источник:** `reviewPage.js:189–194` всегда вызывает `renderRequirementSections(draft)`, не используя `request.description`. API явно отдаёт description (`agent_router.py:378`). Customer detail корректно проверяет структурированный паспорт и имеет fallback (`customerPortal.js:163–169`).

**Воспроизведение:** запрос имеет полноценный `description`, а `draft:{}` или отсутствует. На ревью все блоки пишут «Не уточнено», критерии «Не сформулированы»; description отсутствует в HTML. Node-проба подтверждает потерю контрольной строки.

**Последствие:** ревьюер может вернуть или отклонить содержательный legacy-запрос как пустой; заказчик и специалист видят принципиально разный объём информации.

**Исправление:** общий для двух ролей fallback «Исходное описание»; явно отмечать отсутствие структурированного паспорта и автоматической оценки. При частичном draft сохранить доступ к полному исходному тексту, не утверждая его отсутствие.

### F04 — P2. Ссылка «Следующий запрос» возвращает к уже обработанным

**Источник:** массив `reviewRows` обновляется только в `loadReviewQueue` (`reviewPage.js:82–83`). После PUT `updateStatus` перерисовывает только активный detail (`246–252`), а `findNextReviewId` снова фильтрует старый массив и циклически возвращается к первой записи (`331`).

**Воспроизведение:** открыть очередь из двух доступных для решения запросов A/B; принять A; перейти «Следующий» в B; принять B. Следующим снова становится A. Node-проба на двух синтетических строках подтверждает `A → B → A` после выполненного updateStatus. Вход по прямой ссылке без загрузки очереди, наоборот, оставляет `reviewRows=[]`, поэтому «Следующий» вообще отсутствует.

**Последствие:** последовательная обработка зацикливается, счётчик оставшихся дел недостоверен; эффективность страдает именно у активного ревьюера с несколькими решениями подряд.

**Исправление:** после успешного действия обновлять/удалять строку в кеше результата, а следующий выбирать из актуальной серверной выборки с учётом фильтров и доступных действий. При отсутствии следующего выводить «В этой выборке больше нет запросов, требующих решения». Для прямой ссылки загрузить лёгкий контекст очереди либо дать честную ссылку «Выбрать следующий в очереди».

### F05 — P2. «Все запросы» не включает отклонённые и запланированные

**Источник:** option `all` обещает «Все запросы» (`reviewPage.js:40`), но серверный endpoint заранее отбирает только submitted/in_review/in_progress/returned (`agent_router.py:789–797`). Frontend-фильтр all просто возвращает true для уже усечённого массива (`reviewPage.js:140`).

**Воспроизведение:** после отказа перейти в очередь, выбрать «Все запросы», искать название. Отклонённая запись не попадает даже в исходный набор. Прямой detail остаётся возможен при знании ID.

**Последствие:** не замыкается путь проверки собственного решения, ответа заказчику и поиска ранее отклонённой похожей потребности. «Ничего не найдено» воспринимается как отсутствие записи, а не исключение архивных статусов.

**Исправление:** рабочая очередь + доступная история решений/закрытые с единым поиском; либо переименовать в «Все активные» и дать отдельную явную точку входа к истории. Добавить фильтры «Отклонены», «Запланированы», «Завершены» с серверным контрактом.

### F06 — P2. Очередь и detail показывают разный статус одной реализации

**Источник:** карточка вызывает `badge(request.status)`, helper передаёт в общий рендерер только `{status}` (`reviewPage.js:182`, `370`). Detail передаёт `request` целиком (`194`). Общий `getRequestStage` учитывает task_status/task_progress (`requestPresentation.js:62–65`).

**Воспроизведение:** request.status=in_progress, task_status=ВЫПОЛНЕНА, task_progress=100. Detail: «Выполнен»; очередь: «В проработке» + «Контролировать проработку». Node-проба подтверждает.

**Последствие:** специалист повторно открывает завершённую работу, неверно оценивает объём активной проработки; фильтрация и действия не соответствуют видимому этапу.

**Исправление:** передавать весь request в общий presenter; единообразно определить status workflow и фактический этап исполнения. Оба значения допустимы, но должны быть названы отдельно и последовательно использоваться фильтрами, next step, badges, journey.

### F07 — P2. Кликабельные сигналы могут ничего не делать

**Источник:** `getSignalTarget` поддерживает структурный `section_key` и эвристический поиск по тексту (`requestPresentation.js:139–168`). Но `extraDetails` добавляет отсутствующий раздел только для точной строковой формы `Требуется уточнение: field` (`201–210`). `focusRequestSection` молча делает return, если DOM-узел отсутствует (`reviewPage.js:229–231`).

**Воспроизведение 1:** `open_questions:['Какие данные передаются при интеграции?']`, `data_integrations` пусто. Кнопка имеет target data-integrations, блока нет.

**Воспроизведение 2:** структурный вопрос `{text:'Уточнить источники',section_key:'data_integrations'}`, данных раздела нет. Аналогичный результат. Оба случая подтверждены Node-пробами.

**Последствие:** нарушено прямое обещание «Каждый сигнал открывает связанный раздел паспорта», пользователь считает элемент сломанным и теряет связь вопроса с контекстом.

**Исправление:** строить множество требуемых разделов тем же `getSignalTarget`, которым строятся ссылки; отсутствующий раздел выводить как «Не уточнено — требуется ответ». Для нераспознанной привязки явно показывать «Общий вопрос», а не делать произвольный прыжок к проблеме.

### F08 — P2. Фильтр стирает ошибку загрузки и возвращает старые данные

**Источник:** `loadReviewQueue` не очищает `reviewRows` и не хранит отдельный status loading/error (`reviewPage.js:76–90`). Все контролы остаются активны и вызывают `renderReviewList` независимо от загрузки (`59–65`, `105–107`). Catch меняет тело, но оставляет счётчик «Загрузка…».

**Воспроизведение:** успешно загрузить очередь; при повторном открытии/обновлении получить сетевую ошибку; изменить фильтр либо начать печатать. Ошибка с кнопкой повтора исчезает, показываются строки предыдущей загрузки без метки неактуальности. При первом входе с пустым кешем вместо ошибки появится «Очередь пуста». Обе логические ветки следуют коду; вариант со старым кешем и вечным loading-счётчиком подтверждён Node-пробой.

**Последствие:** пользователь не отличает действительную пустоту, устаревший снимок и недоступный сервер. Особенно рискованны счётчики и чужие закрепления.

**Исправление:** отдельная модель `{status,data,error,updatedAt}`; фильтрация не изменяет статус получения данных. Если сохраняется кеш, маркировать его и оставить предупреждение/повтор. После ошибки счётчик должен сообщать состояние ошибки или время снимка.

### F09 — P2. Disabled подтверждения не удерживается во время запроса

**Источник:** click ставит busy через `setBusy` (`reviewPage.js:304–305`), но input/change вызывают `syncValidity`, который присваивает disabled только по непустоте полей (`299–302`). Поля, Cancel, крестик и закрытие фона не блокируются.

**Воспроизведение:** заполнить комментарий; подтвердить на медленной сети; допечатать символ либо изменить BA. `syncValidity` снова делает confirmButton.disabled=false, хотя PUT ещё выполняется. Можно подтвердить повторно, либо закрыть окно и продолжить считать действие отменённым.

**Последствие:** повторные изменяющие запросы, ложные конфликты версии, несовпадение текста в форме с отправленным комментарием. Backend-проверка version снижает риск двойной применённой операции; это не доказательство появления двух задач, а подтверждённая ошибка жизненного цикла UI.

**Исправление:** переменная `isSubmitting`; `disabled = isSubmitting || !valid`; заморозить snapshot полей на момент отправки; блокировать повторный submit и конфликтующие изменения. Если закрытие допускается, прямо показать, что отправка продолжится, и предоставить устойчивый результат в карточке/очереди. Текст кнопки во время отправки: «Возвращаем…» / «Создаём задачу…».

### F10 — P2. Обновление после ошибки принудительно выбрасывает написанный комментарий

**Источник:** error CTA делает `requestClose(true)` перед refresh (`reviewPage.js:308`), обходя проверку `isDirty`, хотя обычное закрытие эту проверку использует (`282–296`).

**Воспроизведение:** написать содержательную причину, получить 409 или сетевую ошибку, нажать предложенное «Обновить данные». Комментарий исчезает, пользователь оказывается на новой версии detail. Предупреждения о потере нет.

**Последствие:** наиболее затратная часть ревью — качественное объяснение — теряется ровно в сценарии, где интерфейс сам предлагает способ восстановления.

**Исправление:** сохранить черновик локально по request ID + тип решения; после refresh открыть сравнение с актуальным состоянием и восстановить текст для пересмотра. Минимальный вариант — «Скопировать комментарий», «Обновить и сохранить черновик», явная защита от потери. Нельзя автоматически повторять решение на новой версии без перечитывания.

### F11 — P2. Подготовка передачи не даёт обратной связи и допускает несколько одинаковых модалок

**Источник:** `btn-approve` вызывает `assignModal` без busy/guard (`reviewPage.js:201`); `assignModal` последовательно ждёт два GET и только затем создаёт overlay (`255–260`).

**Воспроизведение:** замедлить сеть, трижды нажать «Передать в проработку». Каждый handler проходит через GET request/BA и может добавить собственный диалог; в DOM появляются повторяющиеся assignee-select/modal-confirm IDs. API GET single-flight может объединить транспорт, но не три продолжения функции с `modal(...)`.

**Последствие:** ощущение неработающей кнопки; несколько окон и неожиданные повторные подтверждения при закрытии верхнего; клавиатурный возврат фокуса становится неоднозначным.

**Исправление:** сразу показывать одно окно со состоянием «Загружаем аналитиков» либо busy на исходной кнопке; guard на один pending/open dialog данного действия; локальная ошибка/повтор в том же окне.

### F12 — P2, риск целостности решения. При передаче используется версия, которую ревьюер мог не видеть

**Источник:** detail показал request версии N; в approve HTML записана N (`reviewPage.js:217`), но обработчик её не передаёт (`201`). `assignModal` GET'ит новый request и отправляет его версию (`257`, `260`). Return/reject используют версию с видимой кнопки (`202–203`).

**Условия:** между отображением паспорта и GET при открытии передачи актуальная запись меняется до N+1, а видимый detail ещё не обновился; например, задержка доставки realtime, изменение другой сессией или импортом. Assign modal никак не показывает обновлённый паспорт и не сравнивает versions.

**Последствие:** optimistic concurrency может успешно принять решение на N+1, хотя пользователь читал N. Версионный guard защищает только состояние после подготовительного GET. Проба не изменяла БД; это подтверждённое поведение frontend при соответствующем изменении источника, а не утверждение о частоте такого сценария.

**Исправление:** привязать решение к renderedVersion; если свежий GET обнаружил отличие, остановить поток до перечитывания и показать изменившиеся поля. Все три решения должны использовать одинаковый принцип «подтверждаю изученную версию».

### F13 — P2. Асинхронный detail не имеет собственного loading и защиты от запоздавшего ответа

**Источник:** `renderReviewDetailPage` ждёт GET до возврата HTML (`reviewPage.js:185–188`). Router делает `container.innerHTML = await resolved.render(...)`, не проверяя, что hash/поколение навигации не изменились (`router.js:195`, выражение `container.innerHTML = await resolved.render(this.app)`).

**Воспроизведение:** на медленной сети открыть A, затем до ответа перейти к B или очереди. Поздний ответ A может заменить содержимое нового маршрута. Пока A грузится, старый экран остаётся без маркера загрузки detail.

**Последствие:** видимый запрос и адрес могут расходиться; пользователь не уверен, произошло ли открытие. В худшем случае решения относятся к неожиданно показанной записи. Нужна интеграционная проверка с контролем порядка ответов; отсутствие route-generation guard видно в коде.

**Исправление:** generation token/AbortController, проверка актуальности до commit render/init, явный detail skeleton с заголовком «Загружаем запрос», фокус на новом h1 после завершения навигации.

### F14 — P2. Поиск не понимает идентификатор, который сам интерфейс ставит на карточку

**Источник:** индекс поиска содержит только title, author_name, team_name, reviewer_name, assignee_name (`reviewPage.js:149`). Карточка явно показывает «Запрос #ID» (`182`).

**Воспроизведение:** ввести существующий числовой ID или `#ID`, скопированный из карточки/обсуждения. Результата нет, если цифры случайно не встречаются в имени/названии. Node-проба подтверждает.

**Последствие:** критический короткий путь «найти известную заявку» хуже свободного просмотра; пользователь начинает листать длинную очередь или вручную править адрес.

**Исправление:** exact ID/public ID/связанный task ID; нормализовать `#`, пробелы и распространённый префикс. Placeholder: «ID, название, заказчик, команда». Точное совпадение ID ставить первым.

### F15 — P2. Отсутствующая оценка приравнивается к плохому качеству

**Источник:** `qualityScore` подменяет отсутствие quality_score полнотой, затем нулём (`reviewPage.js:367`); detail также подменяет качество полнотой (`191`). Сортировка «Низкое качество» и urgency используют это число (`158`, `165`).

**Воспроизведение:** draft без оценки → «0% Низкая»; draft только completeness_score=95 → «95% Высокая» для качества, хотя измерялась заполненность. Node-проба первого случая подтверждена.

**Последствие:** визуально уверенное ложное знание; старые/неоценённые заявки искусственно поднимаются в очередь низкого качества, заполненный, но плохой текст получает высокое качество.

**Исправление:** отдельные nullable metrics со статусом расчёта и временем; «Не оценено» вместо нуля; полнота и качество не заменяют друг друга. Не использовать неполученные оценки в ранжировании как худший результат без явной выбранной политики.

### F16 — P2. История в detail не содержит фактическую цепочку решений

**Источник:** frontend умеет читать status_history/history (`requestPresentation.js:235–244`), но текущий `_request_to_dict` не отдаёт ни один такой массив (`agent_router.py:373–402`). Fallback создаёт два синтетических события по created_at/updated_at и текущему статусу (`requestPresentation.js:245–248`).

**Условия:** несколько возвратов, повторная отправка, повторное закрепление. Пока draft сам не несёт history, видна лишь реконструкция текущего состояния, а не реальная последовательность. Поле последней причины очищается при claim (`agent_router.py:934–936`).

**Последствие:** ревьюер не видит, что именно уже просили уточнить, кто и когда менял решение; последовательность циклов не восстанавливается из блока «Ключевые события». Это особенно осложняет передачу дела другому специалисту.

**Исправление:** неизменяемый журнал событий в API: action, actor, timestamp, request version, comment, changed fields; история комментариев должна переживать последующие статусы. Fallback назвать «Текущее состояние», если полной истории нет.

## Проблемы сценариев, которые стоит рассматривать совместно с backend

1. **Возврат и повторное ревью не разделены по ответственности.** Сервер возвращает claim для любого returned (`agent_router.py:366–367`), и карточка сразу пишет «Проверить уточнения» (`reviewPage.js:351`), хотя заказчик ещё может не ответить. В summary при returned ответственность правильно принадлежит заказчику (`requestPresentation.js:218`). Требуется явное различие «Ожидаем ответа заказчика» и «Уточнения получены»; «Вернул на уточнение» должно уходить из моих текущих действий до повторной отправки. Одно только переименование кнопки не исправит модель состояния.
2. **Нельзя штатно освободить или передать ревью.** Available actions включают claim/approve/return/reject; отдельного release/reassign нет. Уход ревьюера в отпуск или ошибочное claim не имеют доступного пути восстановления. Это продуктовый пробел, не рекомендация обходить ограничения БД или менять защищённый состав команд.
3. **«Просрочен» сейчас основан на expected_date запроса/дедлайне задачи.** `_request_deadline` (`agent_router.py:341–345`) не представляет самостоятельный SLA ревью. Приоритет доставки результата и срок решения ревьюера — разные задачи. Требуются отдельные даты с понятной причиной срока, без автоматического объявления любого пожелания заказчика SLA команды.
4. **Сроки и возраст считают разные интервалы.** Карточка показывает возраст с created_at, если нет deadline; это может включать время до отправки и все циклы ожидания заказчика. Нужны «В ревью с…», «Ожидаем заказчика с…», дата последнего поступления; текущее «N дней в очереди» слишком сильное утверждение.

## Дизайн, информационная архитектура и содержательные улучшения

### Очередь

**Сильное:** крупная карточка целиком является настоящей ссылкой; виден заказчик, команда, текущий ответственный, статус, сигналы и следующий шаг. Быстрые фильтры имеют aria-pressed. Search/filter/sort/scroll сохраняются в sessionStorage. Пустая общая очередь и пустой результат поиска различаются. Внутренняя прокрутка отключается на мобильном экране.

**Что изменить:**

- Развести три режима задач: «Нужно моё решение», «Ожидаем других», «История решений». Статусы, mine и signals сейчас смешаны в одном взаимоисключающем select. Нельзя одновременно выбрать «Мои + с сигналами + команда», хотя это естественная рабочая выборка.
- Показать назначение главного режима «Требуют действия». Он стоит по умолчанию, но среди пяти быстрых фильтров не выделен; новичок видит отдельные счётчики без ясного представления, какой фильтр сейчас активен.
- Счётчики быстрых фильтров считаются на всём наборе и не учитывают поисковую строку (`reviewPage.js:96–102`). Это допустимо, если подписать «Во всей очереди»; иначе при поиске нуля рядом остаются большие числа, что выглядит противоречием.
- Состояние «ничего не найдено» должно сообщать действующие ограничения и иметь отдельные «Очистить поиск», «Сбросить фильтры», «Показать все активные». Сейчас общий сброс возвращает action, который тоже может быть пуст, поэтому CTA не гарантирует выход из тупика.
- «По срочности» — скрытая сумма баллов: просрочка +1000, новый неназначенный +600, доступное действие +300, сигналы до +180, недостающее качество до +100 (`164–165`). Ближайшая дата и draft.priority не учитываются; возраст — только tie-break. Нужны прозрачные причины порядка: «Срок сегодня», «Без ревьюера 3 дня», «Ожидает моего решения». Порядок должен быть продуктовым решением, а не случайной арифметикой.
- Сигналы и проценты занимают существенную часть карточки, хотя полезный вопрос очереди — «почему мне нужно открыть это сейчас». Поднять давность этапа и причину приоритета, убрать повторяющийся объёмный taxonomy у карточек без срочной проблемы либо показывать первые два типа + итог.
- Для больших очередей добавить компактный режим строк с настраиваемой плотностью. Он нужен для сравнения нескольких заявок; карточки сохранить для обзора и мобильного чтения. Сервер сейчас отдаёт все записи и полные draft, а frontend перестраивает HTML на каждый символ; пагинация/виртуализация — будущий критерий масштаба, производительность большого набора в этом аудите не измерялась.
- Сохранённая выборка хранится только в sessionStorage, не в URL и не по пользователю (`reviewPage.js:21`, `333–340`). Полезны URL query parameters для пересылки фильтра, «Мои сохранённые виды» для повторяющейся работы; при смене аккаунта контекст нужно разделять.

### Detail и принятие решения

**Сильное:** есть общий статус и journey, сводка владельца следующего действия, выделенная причина возврата, паспорт, критерии приёмки, явный action-panel. Отдельные оценки ИИ спрятаны в details и подписаны как справочные. Доступные действия приходят от сервера.

**Что изменить:**

- Разделить чтение на «Потребность и ожидаемый результат», «Что проверить», «Обсуждение и изменения», «Решение». Текущий порядок ставит все сигналы до паспорта, поэтому при длинном наборе замечаний ревьюер начинает с фрагментов без контекста. Нужен компактный summary проблемы/эффекта сверху, затем приоритизированные замечания со ссылками.
- Превратить список проблем в рабочий список проверки: «Открыт», «Уточнён заказчиком», «Принят как риск», «Не относится». Сейчас любое упоминание риска всегда даёт жёлтый сигнал и число; элемент нельзя закрыть, обосновав решение. Известный и принятый риск не эквивалентен отсутствующим данным.
- Для возвратов показывать diff версии, ответ на каждый вопрос и исходный комментарий ревьюера. CTA «Проверить уточнения» оправдан только при наличии именно новых уточнений.
- Сохранить возможность посмотреть источник формулировки. «Источники базы знаний» выводятся только названиями без ссылки/фрагмента (`requestPresentation.js:214`); у ревьюера нет способа сверить вывод с источником. Ссылка на исходный диалог допустима в рамках прав, вместе с явным различием слов заказчика и автоматического вывода.
- Подпись «Подтверждённая заказчиком формулировка потребности» постоянна (`requestPresentation.js:172`). Если нет отдельного факта подтверждения и версии, лучше «Формулировка, отправленная заказчиком на ревью» с датой/версией. При наличии подтверждения показать именно его фактические реквизиты.
- Добавить частный комментарий/черновик решения ревьюера. Сейчас единственный способ сохранить мысль — отправить итоговый возврат/отказ. Для сложного чтения нужен промежуточный результат, не меняющий workflow.
- Контроль критериев приёмки оформить как осмысленную проверку проверяемости, а не декоративные зелёные круги. Сейчас строки не интерактивны (`requestPresentation.js:196–198`), и визуальная ассоциация с checklist может создавать ложное ощущение выполненной проверки.
- При status rejected detail попадает в общий next-step «Ожидает следующего этапа» + «Отклонён» (`reviewPage.js:220`), что противоречит терминальному исходу. Нужен «Решение принято: запрос отклонён» и дальнейший путь, если он разрешён правилами продукта.
- Участники повторяют многие сведения из summary/header. Блок называется «Участники и сроки», но перечисляет только Создан/Обновлён и людей (`requestPresentation.js:103–110`); реальный deadline там отсутствует. Свести повторения, дать фактическую дату решения/ожидания.
- На экранах ≤1000px action-aside переезжает перед основным содержанием (`pages.css:5987`). Это повышает доступность действий, но отодвигает паспорт; после длинного чтения действия остаются далеко сверху. Для мобильного лучше компактная закреплённая панель действия и переход «К решению», а подробных участников оставить ниже.

### Модальные окна и доступность

**Что уже работает и не надо объявлять отсутствующим:** role=dialog, aria-modal, именование заголовком, обязательные label/aria-describedby, общий initial focus, Tab trap, Escape, попытка вернуть фокус на вызвавший элемент. Глобальная логика находится в `modalAccessibility.js:17–55`, `65–100`, `103–120`. Ввод комментария защищён при обычных close/Esc/background. Существующие тесты этого компонента прошли.

**Что улучшить:**

- Initial focus попадает на крестик как первый focusable (`modalAccessibility.js:52`). Для модалки возврата логичнее autofocus на textarea, для передачи — на select или заголовок loading. Это улучшение скорости, не дефект отсутствия фокуса.
- Dialog не находится внутри form; Enter в select не является явным единым submit-сценарием. Определить предсказуемое поведение клавиатуры, сохранив многострочный ввод комментария; не отправлять textarea по обычному Enter.
- При отправке и последующем refresh исходная кнопка заменяется. `restoreFocus` работает только если прежний элемент ещё isConnected (`modalAccessibility.js:67`), поэтому после успеха нужен явный перевод фокуса в success-banner/заголовок результата. Сейчас после удаления окна фокус может оказаться на body.
- Guard навигации `app.js:758–767` проверяет task forms, quick edit, reporting status, но не review modal. При browser Back/hash-navigation overlay, добавленный в body, может остаться поверх другой страницы; закрытие страницы/refresh не сохраняет текст. Включить review draft в общий lifecycle навигации.
- Ошибка «Обновить данные» не должна быть единственной универсальной реакцией. Разделить: конфликт → прочитать изменения; сеть → повторить без потери ввода; нет права → объяснение и выход; нет BA → понятная точка обращения к администратору. При пустом списке BA текущая модалка имеет disabled submit и только «Отмена» (`reviewPage.js:260`).
- В модалке отказа явно объяснить последствие терминального решения и возможность/невозможность повторной подачи. Нынешняя подсказка «Укажите ... ожидаемое действие заказчика» одинакова для возврата и отказа, хотя это разные outcomes.
- Ссылка-карточка содержит весь текст метаданных, taxonomy, процентов и CTA. Для screen reader это длинное название ссылки; полезна короткая accessible name «Запрос #…: …» и описательная связь с основными метаданными. Список карточек можно семантически оформить как ul/li.
- Анимация перехода к разделу всегда `behavior:'smooth'` (`reviewPage.js:235`); учитывать reduced-motion пользователя и обеспечить стабильный focus-target. Контраст и фактические размеры клика/текста следует сверять по браузерным измерениям основного прогона, а не только по токенам CSS.
