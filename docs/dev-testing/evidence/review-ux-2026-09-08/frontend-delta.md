# Дополнение к frontend-аудиту после параллельных изменений

Контрольная проверка: **08.09.2026 12:46:11 UTC / 15:46:11 МСК**. Основной [frontend-analysis.md](frontend-analysis.md) и [frontend-probes.mjs](frontend-probes.mjs) сохраняют исходный срез: старые пробы повторно не запускались. Это дополнение имеет приоритет над исходными формулировками F02, F07, F16 и связанной частью R28 при оценке текущего рабочего дерева.

Проверен узкий набор presenter/frontend функций и контракт `_request_to_dict`; повторное исследование всего проекта, миграции и изменяющие API-операции не выполнялись. Выполнены четыре новые чистые синтетические проверки текущего presenter. Наличие изменений в исходниках не означает, что запущенный сервер уже перезагружен или что новая модель проверена end-to-end.

| Пункт исходного аудита | Текущее состояние | Основание и оставшаяся работа |
|---|---|---|
| **F02 / R03: review_findings и quality_issues полностью потеряны** | **Исходный дефект устранён в текущем frontend-коде. Не считать открытым в прежней формулировке.** | `requestPresentation.js:152–168` добавляет обе группы, gaps и дедупликацию по тексту. Новая проба: draft только с одним review_finding даёт `signalCount=1`, а не 0. Остаток: severity не отображается и не ранжируется, lifecycle исключения resolved применяется лишь к gaps; одинаковый текст в разных группах/полях может дедуплицироваться в пользу первой записи. Эти остатки требуют отдельного уточнённого пункта P2, а не прежнего P1 «полная потеря» |
| **F07 / R08: signal target отсутствует в DOM** | **Сохраняется.** | `getSignalTarget:182–212` расширен `slot` и aliases. Однако `extraDetails:276–285` по-прежнему создаёт пустой дополнительный раздел только по regex `Требуется уточнение: field`. Новая проба `{open_questions:[{text:'Уточнить источники',section_key:'data_integrations'}]}` даёт target `request-section-data-integrations`, но соответствующего id в HTML нет. Это остаток именно для пустых дополнительных разделов. Новые основные process/primary_role/department/priority теперь создаются постоянно и на них старое обобщение не распространяется |
| **F16 / R02: API не отдаёт историю, frontend показывает только реконструкцию** | **Исходное утверждение больше неверно для текущего кода; значительно переработано.** | `agent_router.py:354–355` теперь отдаёт revision_history/status_history; вызовы append_revision/append_status_event видны на `676–677`, `705–706`, `945`. `requestPresentation.js:121–134` добавляет «Отправленные редакции», снимки, список изменившихся полей и отметку legacy-снимка. Новая проба подтверждает рендер содержимого revision_history. История статусов нормализуется на `310–319`. Остаток: нет визуального before/after diff внутри поля и связи «замечание → ответ → разрешение»; старая история может отсутствовать и честно отмечается как недоступная. Сохранность на реальных повторных отправках и применение схемы БД здесь не проверены; не заявлять полное end-to-end исправление |
| **R28: источники только названия, нет происхождения** | **Часть про источники и происхождение уже исправлена; часть про скрытую архитектуру чтения сохраняется.** | `renderSource:269–273` показывает безопасную HTTP(S)-ссылку из uri, версию, раздел и цитату. Новая проба подтверждает href. `renderFieldEvidence:252–260` показывает источник, подтверждение/допущение, status/confidence, evidence и message_id. Подзаголовок паспорта `223` больше не утверждает универсальное подтверждение, а говорит об отправленной редакции. `extraDetails:276–289` всё ещё помещает сценарии/правила/интеграции/зависимости/риски/регуляторику в общий закрытый details; явного полного оглавления этих разделов не добавлено. Это отдельное UX-предложение, не прежняя потеря источников |
| **F03: legacy description не показывается на review detail** | **Сохраняется при текущей узкой проверке.** | Несмотря на смену хеша `reviewPage.js`, строка `194` по-прежнему безусловно вызывает renderRequirementSections(draft) и не имеет fallback request.description/hasStructuredDraft. Новая модель редакций не гарантирует наличие содержательного legacy draft |

Дополнительные изменения, которые надо учитывать в общем отчёте: паспорт теперь явно выводит бизнес-процесс, основную роль, затронутых пользователей, подразделение и приоритет (`requestPresentation.js:215–224`); прежнюю фразу «эти поля вообще не представлены» использовать нельзя. `sources.uri` стал ссылкой только для HTTP(S); локальная ссылка БЗ остаётся текстом, что допустимо при отсутствии просмотрщика. Объектные значения редакций пока выводятся как форматированный JSON (`readableValue:263–266`), поэтому наличие полного снимка не равно удобному сравнению бизнес-формулировок.
