## Что должен помогать делать интерфейс

Основная работа ревьюера — принять обоснованное решение о передаче потребности в проработку. Это не проверка красивого текста и не достижение определённого процента AI-оценки. Ревьюер последовательно определяет, кому принадлежит следующий ход, почему запрос требует внимания, что в потребности подтверждено, какие неизвестные мешают решению, можно ли передать запрос аналитику и на каких условиях.

| Момент работы | Вопрос пользователя | Какой ответ должен давать экран |
|---|---|---|
| Открытие очереди | Что мне делать первым? | Мои доступные действия, срок именно ревью, причина приоритета |
| Выбор запроса | Стоит ли брать его сейчас? | Смысл потребности, команда, текущий владелец, блокирующие замечания |
| Чтение | Что меняется и почему? | Последовательный документ с проблемой, текущим процессом, целевым результатом и критериями |
| Разбор замечания | Что неверно и где это исправить? | Исходный фрагмент, конкретная проблема, значение для решения, адресат уточнения |
| Повторное ревью | Что изменилось с предыдущего раза? | Изменения по разделам, ответы на прежние замечания, предыдущие решения |
| Решение | Каковы последствия нажатия? | Создание задачи, ответственный, причина возврата или отклонения, понятное подтверждение |
| После решения | Что произошло и что делать дальше? | Фактический новый статус, ссылка на результат, следующий подходящий запрос |

Реализация уже содержит значительную часть этой основы: поиск, рабочие фильтры, сохранение параметров очереди, возврат к её прокрутке, нативные ссылки-карточки, текстовые статусы, сводку текущей ответственности, объяснение последствий передачи, обязательный комментарий к возврату/отклонению, защиту от потери комментария и сообщение об успешном действии. Эти контракты следует сохранить при переработке композиции.

## Основные выводы и критерии доработки

Приоритет P1 означает влияние на смысл решения, доступность основного действия или способность разобраться в запросе. P2 — заметное замедление и ошибки ориентации. P3 — улучшение удобства без подтверждённого блокирования сценария.

### D01 · P1 · Семантические цвета не обеспечивают читаемость основных действий

**Доказательство.** `btn-success` и `btn-danger` используют белый текст на `--success` и `--danger` ([components.css](../../../../dmb-backlog/frontend/css/components.css): 709–719). Именно эти классы используются для передачи и отклонения ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 217, 260, 268). Счётчик «Требует внимания» — белый текст на `--warning` ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 5973). Значения не переопределяются светлой темой в `tokens.css`.

Расчёт для CSS-пар, без оценки сглаживания шрифта:

**Рекомендация.** Разделить цвета декоративного акцента, текста статуса и заливки кнопки. Для светлой темы использовать тёмный текст статуса и более тёмную заливку кнопок; для чисел на ярком warning-фоне возможен тёмный текст. Все пользовательские accent-настройки также должны выбирать совместимую пару текста/заливки, а не произвольно менять один цвет.

**Приёмка.** В светлой и тёмной темах normal/hover/focus-состояния основных действий, оценок, ссылок и счётчиков дают не менее 4,5:1 для обычного текста. Семантика состояния остаётся понятной по тексту без различения цвета. Проверять computed colors на реально выбранных темах; повторять замер на смешанных фонах `color-mix`, а не автоматически переносить результат для `bg-primary`.

### D02 · P2 · Самые нужные служебные сведения имеют размер 10–11 px; часть исправления контраста не применяется

**Доказательство.** Сводка использует `small` 10 px uppercase, история — 10 px для дат и авторства, участники — 11 px ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 6161, 6164–6165). Селектор `.review-detail-layout .request-summary small` на строке 6533 должен осветлять подпись, но `renderRequestSummary()` вставляется до `.review-detail-layout`, а не внутрь него ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 194). Значит, для этой страницы действует исходный `--text-muted`.

**Почему это важно.** Ответственный, время события и срок — не декоративные метаданные. По ним человек определяет, можно ли вмешиваться и нарушается ли ожидание заказчика. Они должны считываться при быстром сравнении и длительной работе. WCAG не задаёт универсального минимального размера шрифта, поэтому 10 px здесь — оценка удобства, отдельно от подтверждённого недостаточного контраста.

**Рекомендация.** Названия полей 12–13 px, значения 13–14 px; основное чтение 14–16 px с межстрочным интервалом порядка 1,5. Сократить uppercase до коротких технических маркеров. Настроить селектор для самой `request-summary`, а не для отсутствующего предка.

**Приёмка.** Значимые метаданные не требуют наведения и масштабирования, полностью переносятся на следующую строку. Размер и контраст проверены на 100% и 200% масштаба. Не регистрировать старое обрезание summary как текущий дефект: оно уже отменено строкой 6544 (`white-space:normal; overflow:visible`).

### D03 · P1 · На узком экране композиция предлагает решение раньше содержания

**Доказательство.** Ниже 1000 px `.review-detail-aside` переносится в первую строку grid и перестаёт быть sticky ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 5987). В aside находятся целиком «Следующий шаг» и «Участники и сроки». В main находятся навигация, сигналы, паспорт и критерии. В DOM main стоит первым ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 194).

**Следствие из структуры.** Визуальный путь на узком экране: заголовок → этапы → четыре блока сводки → действия → подробные участники → навигация → сигналы → начало потребности. Само требование откладывается. Клавиатурный и экранный порядок, напротив, идёт сначала по main, затем по aside. Это создаёт расхождение между видимой композицией и порядком фокуса; конкретную геометрию необходимо измерять в браузере.

**Рекомендация.** Сохранить сверху компактный статус и текущего ответственного, затем показывать суть запроса и замечания. Участников свернуть в служебные сведения. Для принятого на ревью запроса предусмотреть компактную панель решений внизу рабочей области, но не перекрывать ей читаемый текст и фокус. В DOM установить осмысленный порядок, совпадающий с визуальным.

**Приёмка.** На 390×844 и 768 px ревьюер видит начало содержания без прохода через развёрнутую карточку участников; переход к критериям и решение доступны из длинного документа. При Tab фокус не скачет между верхом и низом вследствие CSS-перестановки. На 320 CSS px сохраняется чтение без горизонтальной прокрутки всей страницы; нормативный ориентир — [W3C, Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

### D04 · P1 · Процент на карточке лишён названия и смешивает разные метрики

**Доказательство.** `scoreView()` выводит только «N%» и «Высокая/Средняя/Низкая» ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 364). Он расположен под заголовком «Следующий шаг», хотя оценка не является шагом. `qualityScore()` выбирает качество, иначе полноту, иначе 0 (367). Детальная страница аналогично подставляет полноту вместо отсутствующего качества (191), при этом подпись метрики остаётся «Качество». Шкала находится в закрытом блоке внизу страницы (194).

**Почему это важно.** Один человек прочтёт 80% как готовность к передаче, другой — как завершённость работ. При fallback сравниваются разные величины, а отсутствие оценки выглядит как подтверждённо плохое качество. Это влияет на решение и порядок обработки, поскольку оценка участвует в сортировке.

**Рекомендация.** На карточке писать «Качество формулировок: 80% · оценка ИИ». Если рассчитана только полнота — показывать именно полноту с её подписью. При отсутствии оценки — «Не оценено», без красного нуля. Срок, доступное действие и критичность замечаний должны быть главными ориентирами; справочная оценка — второстепенным.

**Приёмка.** Каждый процент имеет видимое название и корректный источник. Объекты без `quality_score` не отображают чужую величину под подписью качества. Отсутствующая оценка не воспринимается и не сортируется как достоверное 0%. Проверки включают 0, null, отсутствующее поле, полноту без качества и различающиеся quality/completeness.

### D05 · P1 · Сигналы собраны по типу, но не показывают, что мешает решению

**Доказательство.** `signalGroups()` и `signalCount()` одинаково учитывают открытые вопросы, противоречия, риски и допущения ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 118–129). Сигналы выводятся одним warning-стилем без критичности, состояния проверки, автора или решения ревьюера ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 223–226). Приоритет очереди прибавляет 20 за каждый сигнал, до девяти, а наличие регуляторных флагов только меняет оформление карточки (165, 175–176).

**Почему это важно.** Пять безопасных допущений могут выглядеть важнее одного неустранённого противоречия. Количество — объём материала, а не тяжесть проблемы. При повторном ревью непонятно, сигнал уже рассмотрен, устарел или действительно блокирует передачу.

**Рекомендация.** Развести «Блокирует передачу», «Проверить при ревью», «Учесть при проработке». У сигнала иметь привязанный раздел, объяснение последствий, происхождение и состояние «Открыто / Подтверждено / Уточнено / Не применимо». Это проектное предложение, потребующее согласовать модель процесса, а не только перекрасить чипы. На карточке достаточно ключевой причины и числа нерешённых блокеров; полная таксономия остаётся в документе.

**Приёмка.** Ревьюер может объяснить причину приоритета без чтения всех замечаний. Один блокер не теряется среди множества допущений. Устранённые сигналы не продолжают увеличивать текущий счётчик. Отсутствие сигналов подписано как результат автоматического анализа и не обещает готовность запроса; существующую осторожную формулировку детального экрана следует сохранить.

### D06 · P1 · Обещание «каждый сигнал открывает связанный раздел» сильнее гарантии кода

**Доказательство.** Текст обещания находится на строке 226 `reviewPage.js`. `getSignalTarget()` сначала учитывает явное поле, затем текстовую эвристику, а по умолчанию отправляет к проблеме ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 139–168). Для «Противоречия» всегда выбирается проблема, для «Допущения» — целевой процесс раньше анализа текста. Если целевой раздел отсутствует, `focusRequestSection()` молча заканчивается ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 229–236). Дополнительный раздел создаётся только при содержимом или строковом маркере `Требуется уточнение: field` ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 201–214), хотя явное поле сигнала может быть объектом.

**Рекомендация.** Передавать связь сигнала с полем или фрагментом как данные. Для неподтверждённой связи показывать «Раздел не указан» и само замечание, а не уверенно прокручивать к случайной области. Создавать пустой целевой раздел для явно адресованного замечания. После перехода показывать рядом текст замечания и кнопку «Вернуться к замечанию».

**Приёмка.** Для каждого видимого сигнала нажатие даёт предсказуемый результат; отсутствующие и эвристические связи обозначены. Сигнал о критериях, записанный в группе «Противоречия», открывает критерии при наличии явной связи. Явная ссылка на пустые интеграции создаёт и открывает их раздел. Переход сохраняет контекст замечания и место возвращения.

### D07 · P2 · Паспорт оформлен как сетка полей, хотя часть запросов является длинным документом

**Доказательство.** Основные шесть разделов всегда раскладываются в две равные колонки до порога 700 px; размер текста 13 px ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 5973, 5988). Текущий процесс находится рядом с проблемой, целевой — рядом с бизнес-ценностью, поэтому сравнение текущего и целевого процессов не образует пары. `field()` помещает единственное значение в `<p>`, не преобразуя переводы строк ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 191–194). Навигация из шести кнопок находится только перед документом и не sticky ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 208–210; [pages.css](../../../../dmb-backlog/frontend/css/pages.css): 6546–6550).

**Почему это важно.** На содержательных запросах две узкие колонки увеличивают число переносов и фрагментируют чтение. Неравные объёмы соседних полей оставляют пустое место. Из длинного конца документа нельзя сразу вернуться к проблеме или следующему замечанию. Переводы строк могут терять исходное смысловое членение; это следует отдельно воспроизвести на многострочном тексте.

**Рекомендация.** Показать сначала краткую суть, затем последовательный документ. Текущий/целевой процесс расположить рядом только когда это действительно сравнение и ширины достаточно; для длинных значений перейти на одну колонку. Сохранить абзацы, списки и перенос длинных идентификаторов. Оглавление должно показывать текущий раздел и быть доступным при чтении нижних частей, не вытесняя сам текст.

**Приёмка.** На запросе с 500–1000 словами, десятью критериями и длинным URL не появляется скрытый текст или горизонтальная прокрутка документа. Исходные абзацы сохранены. Переход к проблеме, критериям и активному замечанию доступен из конца документа. Группировка «Текущий → Целевой» поддерживает сравнение изменения.

### D08 · P1 · Существенные основания решения спрятаны под нейтральным «Дополнительные материалы»

**Доказательство.** По умолчанию закрытый `<details>` объединяет сценарии, бизнес-правила, данные и интеграции, зависимости, риски, регуляторные аспекты и источники ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 201–214). Summary показывает лишь число разделов. Основное оглавление не содержит ни одного из них ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 209). На карточке регуляторное требование отмечено ярким тегом, но с карточки переходят только на общий паспорт (175–182).

**Почему это важно.** Для части запросов интеграция, обязательное правило или ограничение — главное основание отказа/передачи. Название «Дополнительные материалы» придаёт этим данным необязательный характер. Яркий маркер регуляторики не даёт краткого содержания ограничения.

**Рекомендация.** Назвать область «Правила, интеграции и ограничения». В summary перечислять присутствующие разделы и число нерешённых критичных вопросов. Разворачивать относящийся к решению раздел автоматически при наличии блокера. Источники вынести в отдельную доказательную область с возможностью открыть конкретный документ или фрагмент; сейчас отображаются только названия.

**Приёмка.** Наличие регуляторного ограничения и его суть видны до решения. Ревьюер может открыть каждый присутствующий раздел непосредственно из оглавления. Сценарий без сигналов, но с существенным бизнес-правилом, не скрывает само существование этого правила. Нельзя принять подпись источника за проверенную ссылку: интерактивные источники действительно открываются, остальные явно помечены как недоступные.

### D09 · P2 · Критерии и замечания нельзя устойчиво процитировать при возврате

**Доказательство.** Критерии выведены одинаковыми `<div>` с декоративным кружком и текстом; индивидуальных номеров и идентификаторов нет ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 196–198). Форма возврата — одно пустое textarea без связи с выбранным сигналом или разделом ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 264–268). Кнопки замечаний только прокручивают документ.

**Рекомендация.** Нумеровать критерии стабильными обозначениями вроде «КП-1», а замечания — отдельными ID. Из замечания предлагать «Добавить в комментарий к возврату» с названием раздела и цитатой. При повторном ревью сопоставлять ответ заказчика с исходным замечанием. Не делать кружки критериев похожими на выполненные checkboxes: решение о выполнении реализации здесь ещё не принимают.

**Приёмка.** Ревьюер может написать «Уточнить КП-3» и заказчик однозначно находит критерий. Перестановка критериев не привязывает комментарий к другому тексту. Комментарий к возврату сохраняет раздел и суть замечания; пользователь редактирует итог перед отправкой.

### D10 · P2 · Очередь перегружает каждую карточку сигналами, но плохо объясняет порядок

**Доказательство.** В карточке есть ID, название, badge, приоритет, продукт/модуль, регуляторный тег, автор+команда, ответственный, время, таксономия до четырёх типов, процент, общее число сигналов, подпись действия и «Открыть запрос» ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 168–182). Часть информации дублируется: сумма сигналов рядом с подробными числами; весь элемент — ссылка, но «Взять на ревью» визуально находится внутри неё, фактическое назначение происходит на следующем экране. Высота области списка ограничена `clamp(280px,52vh,620px)` ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 6112). На mobile это ограничение уже отменяется (6928).

**Рекомендация.** Выделить три уровня: 1) суть и стадия; 2) текущий ответственный и срок ревью; 3) главная причина внимания. Справочные продукт, оценку и полную таксономию показывать компактно по запросу. Явно объяснять сортировку («Сначала просроченные, затем новые без ревьюера…») или указывать на карточке причину высокого положения. Подпись ссылки — «Открыть для ревью»; действие «Взять на ревью» оставить реальной кнопке в паспорте. Для интенсивной ежедневной работы предложить компактный режим списка, сохраняя подробные карточки для небольшого потока.

**Приёмка.** Для первых пяти карточек ревьюер определяет следующий доступный шаг, срок и причину внимания без открытия каждого запроса. В компактном режиме 1366×768 отображается не менее пяти строк запросов при обычных длинах данных; это целевой продуктовый показатель, не норматив WCAG. Настройка не уменьшает основной текст до 10 px. «Взять на ревью» не выглядит мгновенным действием там, где клик только открывает страницу.

### D11 · P2 · Быстрые фильтры выглядят переключателями, но повторное нажатие не снимает отбор

**Доказательство.** Кнопки имеют `aria-pressed`, активный стиль и цифровой счётчик (94, 115–118). Клик всегда присваивает один и тот же фильтр, не переключает обратно (62–66). Сброс существует только внутри состояния «Ничего не найдено» (124–127). Значит, при непустой выдаче вернуться к исходным «Требуют действия» можно через select. Счётчики вычисляются по всей `reviewRows`, а число показанных карточек — по текущему поиску и фильтру (96–102, 122).

**Рекомендация.** Определить единый контракт: либо одновыборный фильтр с явно выбранным значением и постоянной кнопкой «Сбросить», либо toggle-chip, где повторное нажатие возвращает исходную очередь. Подпись «Мои» уточнить до «Я ревьюер»/«Я отвечаю», поскольку код включает и ревьюера, и назначенного аналитика (352). Обозначить, что счётчики относятся ко всей очереди, если поиск на них не влияет.

**Приёмка.** Пользователь видит, какие ограничения действуют, и снимает их одним понятным действием при любой непустой выдаче. После поиска счётчики не создают ложного впечатления, что кнопка гарантированно покажет указанное число. При возврате из паспорта сохраняются исходные фильтры и место; текущий полезный механизм sessionStorage не теряется.

### D12 · P2 · Маршрут из четырёх этапов не отражает цикличность ревью и смешивает завершение с отказом

**Доказательство.** `renderRequestJourney()` всегда строит четыре позиции и для returned только переименовывает вторую в «Уточнение». Для rejected текущим становится индекс 3, то есть «Этап 4 из 4», а проработка помечается пропущенной ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 73–82). На mobile показывается только эта строка; весь подробный маршрут скрыт ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 6938–6940). Версии и циклы уточнений в маршруте отсутствуют.

**Рекомендация.** Показывать прежде всего текущее состояние и следующего участника. Для возврата — «Уточнение у заказчика · ревью приостановлено», для повторной отправки — номер итерации и изменения. Отклонение выводить как самостоятельный исход, а не числовое достижение четвёртого этапа. Процент или «из N» использовать только если этапы действительно последовательны и одинаковы для этого пути.

**Приёмка.** Отклонённый запрос не воспринимается как прошедший проработку. На mobile сохраняется причина и смысл завершения. Для возврата явно показано, кто должен действовать, и отсутствует визуальное противоречие между «требуется уточнение» и «начните ревью».

### D13 · P1 · История может выглядеть доказательством события, хотя она синтезирована из текущего состояния

**Доказательство.** Если история не передана, `normalizeHistory()` строит события из `status`, `updated_at`, текущего исполнителя и причины ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 235–259). Например, текущее `in_review` превращается в «Начато ревью», а временем становится последнее обновление объекта. UI подписывает это «Ключевые события — Решения и изменения по запросу» (98–100); сводка аналогично строит «Последнее событие» из текущего статуса (85–95, 225–232).

**Почему это важно.** При споре о сроке, возвращении или назначении эта область выглядит как журнал. Дата обновления сущности не гарантирует дату конкретного решения, а текущий ревьюер не гарантирует автора исторического действия. Это проблема достоверности представления, даже если сам API работает штатно.

**Рекомендация.** Для настоящих событий использовать отдельный журнал переходов с автором и временем. Пока его нет, обозначать «Текущее состояние обновлено…», не приписывая точное действие и автора. В повторном ревью показывать версии текста и решения предыдущих итераций.

**Приёмка.** Изменение несвязанного поля не переносит дату «Начато ревью». Автор события не выводится из текущего назначения. При отсутствии журнала UI прямо сообщает, что доступно только текущее состояние, и не рисует псевдохронологию решений.

### D14 · P1 · Видимое «Отмена» превращается для assistive technology в «Закрыть диалог»

**Доказательство.** Кнопка отмены имеет класс `.modal-cancel-btn` и текст «Отмена» без собственного aria-label ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 275). Глобальный `CLOSE_SELECTOR` включает этот класс, а enhancer присваивает всем совпадениям `aria-label="Закрыть диалог"` ([modalAccessibility.js](../../../../dmb-backlog/frontend/js/modalAccessibility.js): 2, 38–40). Accessible name больше не содержит видимый текст.

**Рекомендация.** Сохранять название из видимого текста для текстовых кнопок. Явный aria-label «Закрыть диалог» нужен только безымянному кресту. При открытии комментария первичный фокус направлять в textarea или заголовок содержательного диалога по выбранному паттерну, а не автоматически в первую кнопку-крест; сейчас такой порядок задаётся строками 50–53 enhancer.

**Приёмка.** Accessible name кнопки «Отмена» содержит «Отмена» и отличается от имени крестика; голосовая команда по видимой подписи работает. Escape, удержание Tab внутри диалога и возврат фокуса продолжают работать: в текущем коде эти механизмы уже реализованы, отсутствие локального keydown в reviewPage не является дефектом. Критерий — [W3C, Label in Name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html), поведение модального окна — [WAI APG, Dialog Modal](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

### D15 · P2 · Семантика документа и фокуса неполна именно на пути глубокого чтения

**Доказательство.** Названия основных полей выполнены `<div class="review-field-label">`, а не заголовками ([requestPresentation.js](../../../../dmb-backlog/frontend/js/components/requestPresentation.js): 193). Критерии — последовательность div (198). На narrow layout область списка остаётся `tabindex=0` и подписана как прокручиваемая ([reviewPage.js](../../../../dmb-backlog/frontend/js/components/reviewPage.js): 52), хотя внутренний скролл отключён, а outline принудительно скрыт ([pages.css](../../../../dmb-backlog/frontend/css/pages.css): 6928–6929). После перехода к разделу `focus()` ставится на `tabindex=-1`, outline скрыт, временная подсветка удаляется через пять секунд (6162; reviewPage 236).

**Рекомендация.** Оформить документ реальной структурой h2/h3, критерии — нумерованным списком. Не создавать лишнюю фокусируемую область, когда она не прокручивается; при сохранении tabindex обеспечить видимый фокус и корректную подпись. Текущий раздел должен оставаться обозначенным, пока в нём фокус/контекст чтения. Снять вложенный `main` в компоненте, если оболочка уже является main, и оставить один основной landmark.

**Приёмка.** Навигация экранного диктора по заголовкам находит проблему, текущий и целевой процесс, ценность, пользователей, критерии и ограничения. На 390 px нет невидимой остановки Tab на обычном контейнере. Нажатие на замечание даёт понятный фокус и обратный путь. У страницы один основной landmark, проверенный в полном DOM. Нормативные ориентиры: [W3C, Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html), [W3C, Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html).

## Предлагаемая структура интерфейса

Это рекомендация для проектирования, не описание уже внедрённого экрана.

**Очередь.** Заголовок и компактная сводка нагрузки → поиск и постоянный видимый текущий отбор → список запросов. В каждой строке: название потребности; статус и текущий ответственный; срок ревью; одна главная причина внимания; открыть. Оценка ИИ и типология замечаний вторичны. Для отложенного/чужого запроса текст прямо объясняет, чьё действие ожидается.

**Паспорт на desktop.** Компактная шапка с идентичностью запроса, стадией, сроком и владельцем. Основная широкая область — потребность, изменения, критерии, ограничения. Слева или в компактной строке — доступное оглавление с текущим разделом. Справа — решения и контекст активного замечания. Служебные участники и история доступны ниже или по раскрытию; они не конкурируют с текстом потребности.

**Паспорт на mobile.** Суть и состояние → критичное замечание → документ. Участники и хронология свёрнуты. Решения доступны из компактной панели, которая не перекрывает нижние строки документа и элементы при фокусе. Навигация показывает текущий раздел и даёт выбрать другой без длинной горизонтальной полосы малопонятных AS-IS/TO-BE кнопок.

**Возврат.** Выбранные замечания с разделами → редактируемый итоговый комментарий → объяснение дальнейшего хода → подтверждение. После повторной отправки ревьюер начинает с изменений и ответов на прежние замечания. Это сокращает повторное чтение и превращает ревью в последовательную проверку гипотез.

## Что обязательно сохранить

- Нативные ссылки-карточки и кнопки, а не заменять их кликабельными div.
- Текстовые статусы, количество сигналов и названия их типов: информация уже не полностью зависит от цвета.
- `role=status`, `aria-live` для количества результатов и `role=alert` для ошибок. Их наличие подтверждено кодом; отдельно проверить отсутствие двойного озвучивания после обновления. Ориентир — [W3C, Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).
- Раскрытие закрытого дополнительного раздела при переходе к найденной цели и перенос фокуса на эту цель.
- Обязательный комментарий к возврату/отклонению, защиту от его потери, объяснение создания задачи и назначения аналитика.
- Видимый итог действия, ссылку на созданную задачу, возврат к очереди и сохранение очереди в sessionStorage.
- Уже внедрённые mobile-исправления: обычную прокрутку вместо внутреннего списка, полноценный перенос заголовков карточек и текстовое название текущего этапа. Не предлагать их как отсутствующие функции.

## Контрольный набор для последующей приёмки

| Проверка | Набор данных / условие | Проверяемый результат |
|---|---|---|
| Чтение длинного документа | 1000 слов, несколько абзацев, 10 критериев, длинный идентификатор | Абзацы сохранены, нет обрезания, оглавление и решения доступны |
| Разбор содержания | Единственный критичный конфликт + 8 допущений | Критичность заметнее количества |
| Отсутствие AI-оценки | Нет quality и completeness; отдельно только completeness | «Не оценено» либо правильное имя доступной метрики |
| Работа с замечаниями | Явная ссылка на пустые интеграции; неизвестное поле; конфликт о критериях | Нет молча неработающих и неверно уверенных переходов |
| Повторное ревью | Возврат → исправление → отправка | Видны изменения и ответы по исходным замечаниям |
| Ошибка и конкуренция | Конфликт версии при заполненном комментарии | Причина понятна, текст не пропадает, дальнейший шаг однозначен |
| Mobile и zoom | 390×844; 320 CSS px; 200% текст | Суть раньше служебной карточки, нет невидимых Tab-остановок, не теряются действия |
| Темы | Светлая/тёмная, все разрешённые accent | Достаточный контраст текста кнопок/статусов/счётчиков |
| Клавиатура | Только Tab, Shift+Tab, Enter, Escape | Корректный порядок, видимый фокус, замкнутый диалог, возврат к исходному элементу |
| Голос/диктор | Кнопка «Отмена», оглавление, изменение числа результатов | Имена соответствуют надписям, структура и изменения объявляются |
| Touch-target | Крест, быстрые фильтры, оглавление, сигналы | Минимум 24×24 CSS px либо допустимое исключение/расстояния; 44 px — рекомендуемый продуктовый ориентир, не универсальное требование AA |

Последняя строка опирается на [W3C, Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). CSS задаёт 32–36 px высоту ряда фильтров и 34 px mobile-оглавления; само по себе это не доказывает нарушение. Геометрические нарушения target size следует регистрировать только после фактического замера и проверки исключений.

## Техническая воспроизводимость расчёта контраста

Использована формула W3C для sRGB: компоненту 0…255 делим на 255; для значения ≤0,04045 применяем деление на 12,92, иначе `((c+0.055)/1.055)^2.4`. Яркость `L=0.2126R+0.7152G+0.0722B`; контраст `(Lmax+0.05)/(Lmin+0.05)`. Значения округлены только при выводе до двух знаков. Смешанные и прозрачные фоны должны предварительно композироваться с фактическим фоном поверхности; их результаты в таблицу выше не включены.
