## Важные остатки в новой истории

- `current_revision_history` явно помечает созданный из прежней записи снимок `legacy_snapshot=True`; UI поясняет недоступность более ранних редакций. Это корректное ограничение новой модели (`requirement_artifacts.py:56–69`; `requestPresentation.js:133`).
- При переносе старого `reject_reason` функция `ensure_request_history` вызывает `append_status_event(... legacy=True)`; у такого события `created_at` устанавливается текущим временем переноса, а не исторической датой решения (`requirement_artifacts.py:72–78`, `93–104`). Renderer событий не использует `legacy_event` для пояснения даты (`requestPresentation.js:310–319`). Поэтому полностью снимать замечание о достоверности дат старой истории пока нельзя: дата фиксации доступного legacy-факта должна отличаться от даты самого решения.
- Для старой записи без status_history сохраняется синтетический fallback текущего состояния (`requestPresentation.js:310–323`). Новый контракт устраняет его необходимость для новых событий, но не делает весь исторический журнал полным задним числом.

## Как отражать в итоговом отчёте

Сохранить R01–R34 как результаты исходного прогона и рядом явно указать это обновление. R01 — «исправлено в свежем backend-коде, runtime не перепроверен». R02, R03, R05 и WF-08/R28 — «существенно/частично изменено параллельной работой; выше перечислены закрытая часть и остатки». Не называть все прежние проблемы действующими без оговорки и не объявлять полную приёмку новых изменений.

Базовый `workflow-probe.py` извлекает функции из текущего файла при запуске, а его asserts описывают первоначальный дефект. После этих изменений он больше не является проходящим regression-тестом новой реализации. Его прежний успешный результат относится только к исходному срезу; повторно в этом delta-аудите он не запускался.
