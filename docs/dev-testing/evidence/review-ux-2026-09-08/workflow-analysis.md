## 1. Что пользователь пытается сделать

Очередь обслуживает не просто чтение карточки, а передачу ответственности за бизнес-потребность. Успех ревью — обоснованное решение, после которого автор понимает результат, а следующий исполнитель получает полные и проверяемые сведения. Полнота пути включает ожидание между действиями, повторное уточнение, отсутствие сотрудника и одновременную работу коллег.

| Участник | Работа пользователя | Вопросы перед действием | Ожидаемый результат |
|---|---|---|---|
| Ревьюер команды | Разобрать входящие и выбрать следующий запрос | Что новое? Что действительно ждёт меня? Что давно не разобрано? Кто уже занимается этим запросом? | Очередь с объяснимым порядком, актуальным владельцем и отличием ожидания автора от ожидания команды |
| Ревьюер конкретного запроса | Проверить обоснованность потребности и пригодность для проработки | Кому мешает проблема? Как происходит процесс сейчас? Какой результат нужен? Какие ограничения обязательны? Чем подтверждена информация? | Решение с понятными основаниями, без потери исходных данных |
| Автор | Получить содержательный ответ, уточнить требование | Что конкретно изменить? Где это править? Сохранились ли прошлые ответы? Отправлена ли новая версия? | Один непрерывный запрос, адресные замечания, видимость новой версии и следующего ответственного |
| Аналитик | Принять переданное требование и начать проработку | Что решили на ревью? Какие риски и допущения остались? Где исходный запрос? Как найти автора? | Задача с полным контекстом и обратной ссылкой на запрос |
| Координатор / руководитель | Контролировать зависшие и ошибочно направленные запросы | Где узкое место? Кто отсутствует? Можно ли переназначить? Почему запрос отклонён? | Управление очередью и ответственностью, доступ к истории решений |

Это аналитическая модель задач пользователя, выведенная из реализованных действий и сущностей, а не результат интервью. Частота сценариев, объём очередей, нормативы времени и разделение полномочий между PO/BA должны быть проверены на пользователях.

## 2. Реальная модель данных и доступа

### Сущности

1. В AI-сервисе живёт диалог и `RequirementDraft`; до отправки это не `Task` и обычно ещё не `RequirementRequest` координатора.
2. При отправке создаётся `RequirementRequest` с JSON `draft`, текстовым `description`, автором, командой и статусом `submitted`. `Task` на этом этапе не создаётся.
3. При передаче в проработку создаётся `Task` с заголовком и описанием запроса, командой, бизнес-заказчиком, выбранным аналитиком и стартовым статусом «СБОР ТРЕБОВАНИЙ».
4. `RequirementRequest.task_id` связывает запрос с задачей. Поля `task_status`, `task_progress`, `task_deadline` возвращаются при чтении запроса.

Доказательства: `dmb-backlog/backend/models.py:792–827`; `dmb-backlog/backend/routers/agent_router.py:647`, `690–718`, `937–956`, `389–393`.

### Права

Право ревью определяется `role.review_access` со значениями `none/team/all`; строковое имя роли используется только как совместимый fallback. По fallback PO/PL/CL, BA и лидер трайба работают в своей команде; проектный офис и администратор — во всех. Нельзя считать название роли единственным актуальным источником права.

| Действие | Реальная проверка |
|---|---|
| Увидеть список своих запросов | `user_id == current_user.id` |
| Увидеть очередь ревью | `review_access != none`, при team — фильтр по `current_user.team_id` |
| Открыть запрос | Автор **или** право ревью его команды |
| Изменить статус | Запрещено `customer_portal_only`, затем требуется право ревью команды |
| Решить запрос в `in_review` | Требуется совпадение `reviewer_id` с текущим пользователем, в том числе для администратора |
| Выбрать аналитика | Активный пользователь той же команды, имя роли BA/Участник команды или BA/Бизнес-аналитик |
| Вернуться в исходный диалог | Только автор, только `returned`, нужна сохранённая `agent_session_id` |
| Удалить запрос через API | Автор или `review_access=all`; ограничений по стадии в этом endpoint нет |

Доказательства: `auth.py:41–59`; `agent_router.py:129–138`, `763–844`, `855–930`, `975–1025` (все пути в `dmb-backlog/backend/`).

Важный нюанс: защита запрещает заказчику без права ревью забрать свой запрос. Но явного запрета ревью собственного запроса у пользователя с правом ревью в status endpoint нет. Комментарий `agent_router.py:867–870` нельзя трактовать как реализованное правило разделения автора и ревьюера. Если организация требует независимого согласования, это отдельное требование к продукту и серверной policy.

### Состояния и доступные переходы

| Исходное состояние | Серверные целевые состояния | Что реально предлагает страница |
|---|---|---|
| `draft` | `submitted` | В UI ревью отдельного пути нет; обычная отправка сразу создаёт `submitted` |
| `submitted` | `in_review` | «Взять на ревью» |
| `in_review` | `in_review`, `in_progress`, `returned`, `rejected` | Свой запрос: передать, вернуть, отклонить; чужой: имя ревьюера и обновление |
| `returned` | `in_review` через status API; `submitted` через повторную отправку автора | Ревьюеру снова предлагается claim; автору — «Уточнить с ИИ-ассистентом» |
| `in_progress` | `approved` | Ссылка на созданную задачу; действия перехода в `approved` нет |
| `approved` | Нет | Статус отображается как «Запланирован»; обычная очередь его не возвращает |
| `rejected` | Нет | Причина видна при прямом открытии; обычная очередь его не возвращает |

Доказательства: `agent_router.py:100–108`, `363–369`, `673–688`; `reviewPage.js:213–220`; `requestPresentation.js:3–10` (frontend-файлы в `dmb-backlog/frontend/js/components/`).

Состояний `new` или `accepted` в этом контракте нет. «Новые» — это `submitted`, «Передать в проработку» — переход в `in_progress`. Следует избегать смешения термина «одобрено» с внутренним `approved`: последний подписан как «Запланирован» и следует уже после передачи.

## 3. Разбор клиентских путей

### Путь A. Найти следующий запрос и забрать его

Текущий путь: открыть `#/review` → загрузить **все** доступные серверу записи → применить сохранённые поисковый запрос/фильтр/сортировку → выбрать карточку → изучить → «Взять на ревью» → PUT с текущей `version` → обновить маршрут → увидеть подтверждение и варианты «К очереди»/«Следующий запрос».

Что уже работает хорошо:

- Backend выдаёт `available_actions`; клиент использует их раньше своего fallback. Это сокращает расхождения действий и прав (`reviewPage.js:343–349`).
- Есть отдельные состояния загрузки, ошибки с повтором, пустой очереди и отсутствия совпадений (`reviewPage.js:77–127`).
- Фильтры и внутренняя позиция списка сохраняются в `sessionStorage` (`reviewPage.js:333–341`).
- Claim защищён ожидаемой версией и запретом чужого владения (`agent_router.py:874–909`).
- Итог действия не ограничен кратким toast: выводится persistent feedback со следующими ссылками (`reviewPage.js:246–251`, `314`).

Проблемы этого пути: возвращённые запросы считаются требующими действия ревьюера; «Все» не включает архив; показатель срочности не объяснён; владелец отсутствующей команды/ревьюера не может быть исправлен в продукте; следующее действие выбирается из старого локального списка, а не из актуального ответа сервера (`reviewPage.js:331`).

### Путь B. Прочитать и принять решение

Текущий путь: заголовок → линейная схема этапов → сводка → навигация по полям → сигналы → паспорт → критерии → дополнительные материалы → текущие «Ключевые события» → справочные оценки ИИ → справа действия и участники.

Хорошая основа: важные смысловые поля разделены, сигналы могут открывать раздел, оценка ИИ описана как справочная, решения отделены от чтения, destructive action визуально менее заметен.

Но содержательное ревью требует сравнить утверждения, источник, риски и критерии, а текущая поверхность не показывает происхождение поля, уверенность каждого поля, найденные дубликаты и результаты `review_findings`. Не все сведения из черновика вообще видны в паспорте. Процент качества хорошо заметен в очереди, но не является полноценным объяснением готовности.

Предлагаемая последовательность работы: «Что просит автор» → «Что изменилось с прошлой проверки» (если повторно) → «Что мешает решению» с явной важностью → контекст/источники → решение. Переход к разделу должен работать для каждого пункта замечаний; непросмотренные регуляторные материалы не следует скрывать только в общем аккордеоне.

### Путь C. Передать аналитику

Текущий путь: «Передать в проработку» → повторно получить запрос → получить BA команды → выбрать сотрудника → «Создать задачу и передать» → создать `Task`, связать запрос, отправить notification assignment → показать номер задачи.

Положительно: обязательный выбор, конкретное последствие до подтверждения, выбор ограничен активными BA команды, повторная проверка сервера, создание внутри транзакции статуса, ссылка на результат.

Слабое место: форма не показывает сводку переносимых сведений; риски и зависимости остаются только в исходном запросе; у задачи нет автоматически сформированной ссылки в `link_requirements`; если подходящего аналитика нет, форма заканчивается неактивной кнопкой. При неправильной команде исправить маршрут передачи на этой странице нельзя.

### Путь D. Вернуть автору и получить уточнение

Текущий путь: свой `in_review` → комментарий → `returned` → автор открывает портал → запрос → исходный диалог → редактирует → повторно отправляет → та же запись перезаписывается новым draft, становится `submitted`, reviewer/comment очищаются, `version` увеличивается → команда снова забирает запрос.

Это самый проблемный путь. Состояние ожидания автора сейчас не защищено от повторного claim. Нет устойчивого списка замечаний, их состояния, ответа на каждое замечание или сравнения предыдущего/нового текста. После ресабмита предыдущий ревьюер и причина возврата исчезают из текущей модели. Слова «Проверить уточнения» могут появиться ещё до появления уточнений.

Целевой путь: вернуть с адресными замечаниями → состояние «Ожидаем автора», единственный деятель — автор → черновик ответа не меняет версию на ревью → явная повторная отправка создаёт новую содержательную revision и `resubmitted_at` → ревьюеру видны предыдущие замечания, ответ и diff → принять/вернуть следующий цикл. Номер технической версии optimistic locking следует отделить от номера содержательной редакции.

### Путь E. Отклонить и объяснить результат

Текущий путь: обязательный комментарий → `rejected` → причина видна в detail → запись исчезает из очереди, включая «Все запросы» → автор может прочитать результат в портале; возврата в работу через текущий UI нет.

Комментарий обязателен, подтверждение ясно подписано. Однако подсказка обеих форм просит «ожидаемое действие заказчика», хотя для окончательного отказа дальнейшее действие может отсутствовать. После отказа нужен явный текст о завершённости, возможность обратиться по решению/создать связанный новый запрос и доступ к журналу отклонённых. Последние два пункта — предложения, а не отсутствующие подтверждённые требования.

### Путь F. Одновременная работа и восстановление

У модели есть optimistic locking (`version_id_col`, `version_id_generator=False`); status API сравнивает version и ловит `StaleDataError`. Повторная первоначальная отправка защищена локальным lock и unique constraint по сессии, а при ошибке сохранения после подтверждения агента предусмотрена компенсация. Это существенные готовые механизмы сохранности, их следует сохранить.

Изменения запроса попадают в event outbox и SSE; приложение обновляет маршруты списка/detail. При открытой review modal обновление не выполняется, выводится предупреждение. Следовательно, вывод «страница не обновляется между пользователями» неверен. Правильная проблема — качество восстановления формы при конфликте и ограниченность уведомлений за пределами открытой страницы.

Доказательства: `models.py:799–818`, `1101–1135`; `agent_router.py:306–338`, `641–741`, `874–909`, `957–970`; `frontend/js/eventStream.js:38–39`; `frontend/js/app.js:115–143`, `503`.

## 4. Подтверждённые проблемы и предложения

Приоритеты: **P1** — блокировка существенного пути, потеря контекста решения или риск решения не по актуальным требованиям; **P2** — систематическая ошибка понимания/неэффективность, исправляемая обходным действием; **P3** — улучшение зрелости продукта. Это UX-приоритеты, не оценка безопасности.

### WF-01 · P1 · Возвращённый запрос можно забрать до ответа автора

**Факт.** `_request_available_actions` отдаёт `claim` для любого `returned` в области ревью. При возврате `reviewer_id` сохраняется. Поэтому тот же ревьюер может снова перевести запрос в `in_review` и очистить `reject_reason`; у коллеги та же кнопка приводит к 409. UI подписывает следующее действие «Проверить уточнения», хотя повторная отправка ещё не состоялась.

**Доказательства:** `agent_router.py:363–369`, `901–909`, `931–936`; `reviewPage.js:351`. Изолированная проба выполнена: прежний reviewer → status `in_review`, comment `null`, version `3`; другой reviewer → offered `claim`, затем `request_owned_by_another_reviewer`.

**Влияние.** Автор может потерять возможность открыть уточнение: resume допускает только `returned` (`agent_router.py:832–833`). Если диалог уже открыт, последующая отправка при `existing.status != returned` вернёт «уже отправлен» без переноса новых правок (`661–672`). Это вывод из композиции двух подтверждённых ветвей, без live-модификации данных.

**Изменение.** Убрать claim из `returned`; обозначить «Ожидаем уточнения от автора». Claim разрешать после фактической повторной отправки. Если нужен отзыв возврата ревьюером, сделать отдельную операцию с сохранением причины и ясным последствием для автора.

**Приёмка.** Пока автор не отправил новую редакцию, ни прежнему, ни другому ревьюеру не предлагается claim; API отклоняет его. Автор сохраняет возможность уточнения. После ресабмита старая причина остаётся в истории, новая редакция доступна для решения.

### WF-02 · P1 · «Ключевые события» не являются историей решений

**Факт.** Backend возвращает текущее состояние, created_at/updated_at/version, но не history. UI при отсутствии history синтезирует «Создан» и одно событие из текущего статуса. При повторной отправке `draft`, описание и title перезаписываются, comment/reviewer очищаются. В модели нет сущности содержательной редакции или review decision.

**Доказательства:** `agent_router.py:373–402`, `673–679`; `models.py:792–827`; `requestPresentation.js:235–259`.

**Влияние.** Невозможно на этой странице доказать, кто и когда возвращал запрос, что просил, что изменилось и почему следующий ревьюер принял решение. Список «Решения и изменения по запросу» создаёт впечатление полного аудита. `version` увеличивается также при claim/return/approve (`agent_router.py:957`), поэтому это не номер редакции текста.

**Изменение.** Хранить неизменяемые review events и snapshots редакций: actor/time/from/to/reason/revision; отдельно `request.version` для конкуренции и `draft_revision` для содержания. В повторном ревью показывать «Изменено автором» и соответствующие замечания. До внедрения реальной истории переименовать блок в «Текущее состояние и дата создания».

**Приёмка.** После двух циклов возврата доступны обе причины, авторы/даты решений, три содержательные редакции; изменение статуса не увеличивает видимый номер редакции требования.

### WF-03 · P1 · При передаче в задачу часть контекста остаётся за пределами задачи

**Факт.** `_render_request` переносит основные поля, открытые вопросы, допущения и regulatory flags, но не dependencies, risks, conflicts, duplicates, field_provenance, field_confidence, review_findings. Созданная задача получает `req.description`; `link_requirements` или иной origin-параметр при создании не заполняется. Полный JSON остаётся у исходного запроса — речь о потере при передаче, не об удалении данных из БД.

**Доказательства:** `agent_router.py:252–303`, `943–952`; `schemas.py:244`, `373`; `tasks_router.py:270`, `1351–1357`. AST-проба подтверждает отсутствие маркеров dependency/risk/conflict в результирующем description.

**Влияние.** Аналитик открывает созданную задачу из уведомления и может не увидеть ограничения, по которым принималось решение. Исходные данные существуют, но в точке начала работы не представлены.

**Изменение.** Автоматически связывать задачу и request/revision в обе стороны; показывать полный snapshot принятого требования или структурированную вкладку. До структурной миграции переносить все бизнес-поля единым renderer. В confirm показывать команду, аналитика, итоговую стадию и перечень сохраняемого контекста.

**Приёмка.** Из созданной задачи открывается именно редакция, по которой приняли решение; все риски/зависимости/противоречия доступны без поиска номера запроса.

### WF-04 · P1/P2 · Нет пути исправить неверную команду или заменить ревьюера

**Факт.** Команда задаётся при создании запроса (`req.team_id or current_user.team_id`), повторная отправка не меняет её. Status DTO содержит только status/version/reason/assignee. Любой другой reviewer, включая глобального, блокируется в `in_review`; UI предлагает только обновление. Нет release/transfer claim в матрице переходов или на странице.

**Доказательства:** `agent_router.py:67–83`, `673–698`, `892–909`; `reviewPage.js:218`, `255–261`.

**Влияние.** Неверная команда, отсутствие BA или недоступность закреплённого сотрудника превращают запрос в операционный тупик. Если у запроса нет команды, assignModal ограничивается toast. Это не предложение править защищённый состав команды: необходима операция над рабочим запросом.

**Изменение.** Разрешённое перенаправление самого запроса в другую команду с причиной; освобождение/передача ревью при контролируемых правах; различать «ещё не назначен», «сотрудник недоступен», «команда не выбрана». Для отсутствующего BA — понятный следующий шаг и владелец разрешения ситуации.

**Приёмка.** Координатор может восстановить зависший путь через UI без изменения справочников/пользователей и без пересоздания запроса. Причина, инициатор и новый ответственный записаны в историю.

### WF-05 · P2 · «Все запросы» исключает отклонённые и запланированные

**Факт.** Сервер `/agent/requests/review` возвращает только submitted/in_review/in_progress/returned. Клиентское «Все запросы» означает просто отсутствие дополнительного фильтра среди этих записей. Нет фильтра rejected/approved.

**Доказательства:** `agent_router.py:789–797`; `reviewPage.js:24`, `40`, `134–146`.

**Влияние.** Сразу после отказа запрос исчезает; поиск по заголовку в «Все» его не найдёт. Руководителю и ревьюеру сложно проверить предыдущее решение или найти похожий отказ.

**Изменение.** Разделить «Активная очередь» и «История решений» либо сделать «Все» настоящим полным списком с явными терминальными статусами. Сохранить переход к отклонённому запросу из результата действия и поиска.

**Приёмка.** Отклонённый запрос находится поиском в явно полном разделе; количество и подписи не обещают больше фактической области.

### WF-06 · P2 · «Просроченные» не опираются на действующий норматив ревью

**Факт.** `review_deadline` берётся из `draft.expected_date` либо срока связанной task. В активной схеме `RequirementDraft` поля expected_date нет; в изученном коде агента/формы отправки нет его заполнения. Для обычного submitted/in_review задачи ещё нет. Уже переданные запросы исключены из overdue. При этом фильтр и отдельная сводная кнопка «Просрочены» существуют.

**Доказательства:** `agent_router.py:341–359`, `690–698`, `940`; `agent/agent/composer/schema.py:28–69`; `reviewPage.js:40`, `48`, `354–355`.

**Вывод.** По штатному контракту новые запросы не получают вычисляемого срока ревью. Импортированные/вручную подготовленные drafts могут иметь expected_date, поэтому нельзя утверждать отсутствие overdue у всех существующих записей. Кроме того, бизнес-дата результата и норматив рассмотрения — разные понятия.

**Изменение.** Ввести `submitted_at`, `review_due_at`, правила ожидания автора и бизнес-срок отдельным полем. Пока SLA нет, использовать «Давно в очереди», рассчитывая возраст с последней отправки и явно указывая порог.

**Приёмка.** Новый запрос автоматически получает норматив по утверждённой политике; ожидание автора обрабатывается явно; сутки и timezone согласованы; фильтр отражает срок решения, а не дату бизнес-результата.

### WF-07 · P2 · Сигналы не отражают полный результат автоматической проверки

**Факт.** Счётчик и блок «Требует внимания» используют только open_questions/conflicts/risks/assumptions. Agent draft дополнительно содержит review_findings с severity, review_blocked, quality_issues, gaps, duplicates и provenance/confidence. `confirm_and_send` проверяет review_findings; страница ревью их не отображает. Regulatory flags выделяются отдельным чипом, но не входят в signalCount.

**Доказательства:** `requestPresentation.js:118–129`; `reviewPage.js:170–183`, `223–227`; `agent/agent/composer/schema.py:48–67`; `agent/agent/orchestrator.py:1025–1036`.

**Влияние.** «Сигналов нет» не равнозначно «нет замечаний автоматической проверки». Все типы сигналов считаются одинаково, хотя риск, допущение и вопрос требуют разных решений. Страница не позволяет отметить, что сигнал рассмотрен или принят с обоснованием; он продолжает влиять на очередь.

**Изменение.** Использовать единую модель finding с severity, field, source, blocker, status/resolution. Отдельно показывать блокирующее, требующее решения и справочное. Термин «Сигналы» заменить понятной пользователю формулировкой «Замечания и риски»; проценты не использовать как замену содержательным основаниям.

**Приёмка.** Один finding имеет одно представление в агенте, detail и счётчиках; принятый риск отличается от необработанного; отсутствие оценки показывается как «Не рассчитано», а не 0%.

### WF-08 · P2 · Детальный паспорт скрывает часть существенных полей

**Факт.** Основной паспорт показывает problem/current/target/value/user_roles/product/module, затем критерии и дополнительные scenarios/rules/integrations/dependencies/risks/regulation. `primary_role`, `affected_users`, `process`, `department`, `priority`, `duplicates`, field provenance/confidence не имеют полноценного представления. Приоритет виден на карточке очереди, но в detail отсутствует. Источники выводятся только заголовками, хотя DraftSource содержит text/uri/version/section.

**Доказательства:** `requestPresentation.js:171–174`, `201–215`; `reviewPage.js:177–183`; `agent/agent/composer/schema.py:11–25`, `36–67`.

**Влияние.** Ревьюер не может независимо оценить основную роль и затронутых участников, вернуться к фрагменту источника или проверить дубликат. Это особенно чувствительно для конфликтных и регуляторных утверждений.

**Изменение.** Добавить бизнес-процесс и приоритет/обоснование; раздельно основного пользователя и затронутые группы; раскрывать источник конкретного утверждения, фрагмент, версию, ссылку и происхождение «автор/ИИ/БЗ». Блок дубликатов должен позволять связать запросы или объяснить отличие.

### WF-09 · P2 · Не все клики по сигналам ведут к обещанному разделу

**Факт.** Target выбирается по явному section, затем групповой эвристике: все противоречия ведут к проблеме, допущения — к целевому процессу, риски — к рискам. Дополнительная секция создаётся только если в поле есть текст или строковый сигнал вида «Требуется уточнение: field». Объектный finding с явным section_key и пустым полем может ссылаться на неотрендеренную секцию. `focusRequestSection` тогда молча возвращается.

**Доказательства:** `requestPresentation.js:139–168`, `201–214`; `reviewPage.js:229–236`.

**Влияние.** Обещание «Каждый сигнал открывает связанный раздел» оказывается неверным для части допустимых данных. Противоречие критериев может открыть проблему; клик без результата не объясняет отсутствие раздела.

**Изменение.** Использовать стабильную привязку finding → поле; гарантировать отрисовку target для каждого сигнала, даже пустого. Если привязка неизвестна, открывать сам finding с пояснением, а не произвольный раздел.

### WF-10 · P2 · Восстановление после ошибки может удалить набранный комментарий

**Факт.** При обычном закрытии модалка спрашивает, сохранить ли редактирование, и при API-ошибке поле остаётся. Но кнопка «Обновить данные» в error area вызывает `requestClose(true)` и обновление, обходя dirty guard. Во время запроса busy устанавливается только на confirm; cancel/close/textarea остаются доступными. При выборе BA dirty guard вообще не настроен.

**Доказательства:** `reviewPage.js:268`, `271–310`.

**Влияние.** Рекомендованный путь восстановления конфликта уничтожает пояснение, хотя соседний механизм обещает защиту несохранённого текста. Редактирование textarea во время отправки также может создать различие между видимым новым текстом и уже отправленным payload.

**Изменение.** Хранить черновик решения по request/revision/типу действия; после refresh возвращать текст и показывать diff состояния. Во время отправки зафиксировать payload и ясно обозначить pending; закрытие окна должно сохранять черновик и не создавать впечатление отмены серверной операции.

**Приёмка.** 409 → обновление → комментарий сохранён; отмена/таймаут/закрытие вкладки не приводят к незаметной потере текста; повторное нажатие не создаёт две модалки или действия.

### WF-11 · P2 · Решение опирается на версию, которую пользователь мог не прочитать

**Факт.** Для claim/return/reject версия берётся из открытой страницы. Для передачи `assignModal` повторно GET-ит request и использует **новую** version в payload, но не обновляет отображаемый паспорт и не показывает пользователю, что он изменился.

**Доказательства:** `reviewPage.js:200–203`, `255–260`.

**Вывод.** При изменении запроса между чтением detail и открытием формы optimistic locking защищает версию GET формы, а не фактически просмотренный текст. Это риск взаимодействия, подтверждённый структурой кода; реальную гонку в БД не воспроизводили.

**Изменение.** При расхождении версии detail и свежего ответа показывать «Запрос изменился» с отличиями и требовать повторного просмотра изменённых полей. Отправлять revision, которую ревьюер явно проверил.

### WF-12 · P2 · Автор и очередь не получают устойчивого сообщения о следующем действии

**Факт.** Статусный маршрут явно создаёт только assignment notification при создании задачи. Создание/возврат/claim/отклонение запроса формируют requirement event для SSE, но не сохраняют персональное уведомление об этом действии. Активные категории notification — assignment/reporting/mention/comment. При назначении самому себе notification исключается по assigned_by_user_id, хотя confirm безусловно обещает получение уведомления выбранным BA.

**Доказательства:** `agent_router.py:931–956`; `models.py:1101–1135`; `notifications.py:24–35`, `272–308`; `reviewPage.js:217`, `260`.

**Влияние.** Когда автор или ревьюер не держит соответствующую страницу открытой, следующий шаг обнаруживается только при самостоятельной проверке портала/очереди. SSE — обновление открытого интерфейса, не адресная inbox-задача.

**Изменение.** Включить в общий центр уведомлений новый запрос ответственному кругу, возврат автору, повторную отправку прежнему ревьюеру/команде и решение автору; при переходе состояния автоматически закрывать старое требуемое действие. Сохранить централизованную notification policy; не строить отдельную ленту внутри review.

### WF-13 · P2 · Порядок «По срочности» и возраст смешивают разные основания

**Факт.** Priority — сумма overdue 1000, нового unassigned 600, доступного действия 300, числа сигналов ×20 и 100−quality. Приоритет draft в расчёт не входит. Тайбрейк и сортировка «старые» используют created_at, а не время последней отправки. `requestAge` пишет «N дней в очереди» по дате создания, включая ожидание автора и проработку.

**Доказательства:** `reviewPage.js:153–164`, `178–183`, `361`.

**Влияние.** Пользователь может принять порядок за бизнес-срочность или SLA. Повторно отправленный запрос выглядит как обычный новый старой давности, и нельзя понять, как давно именно команда должна действовать.

**Изменение.** Показывать основания порядка («ждёт ревью 4 дня», «повторно отправлен», «нет ревьюера»), развести бизнес-приоритет и очередь обработки. Считать время в текущем actionable состоянии; дополнить сортировку по последнему изменению/повторной отправке. Для экспертной очереди предпочтительнее прозрачные уровни приоритета, чем скрытая сумма баллов.

### WF-14 · P2 · Список и detail по-разному отражают завершённую работу

**Факт.** Detail передаёт целый request в status badge, который учитывает task_status/progress. Карточка очереди вызывает `badge(request.status)` с одним статусом; для любого `in_progress` подписывает действие «Контролировать проработку». Серверная очередь сохраняет такие запросы независимо от фактического завершения task. Переход `in_progress→approved` существует в API, но его нет в available_actions/UI.

**Доказательства:** `requestPresentation.js:62–70`; `reviewPage.js:183`, `351`, `370`; `agent_router.py:105`, `369–370`, `791`.

**Влияние.** В очереди завершённый запрос может выглядеть находящимся в проработке, а detail — выполненным. «Мои» дополнительно включает и reviewer, и assignee (`reviewPage.js:352`), поэтому список смешивает обзор решений и исполнение.

**Изменение.** Использовать единый stage resolver для всех поверхностей; чётко отделить очередь решений от контроля исполнения. Определить, нужен ли request.approved и каким бизнес-событием он достигается; избегать двух несогласованных источников стадии.

### WF-15 · P2/P3 · Масштабирование и контекст списка ограничены локальным snapshot

**Факт.** Сервер делает `.all()` без пагинации; UI фильтрует/сортирует/рендерит все записи локально. Search ищет title/author/team/reviewer/assignee, но не id или содержимое; placeholder перечисляет лишь название/автора/команду. Состояние живёт в общем ключе sessionStorage, без user ID и URL; «Следующий запрос» рассчитывается из module-level reviewRows, не перепроверяя актуальность следующей записи.

**Доказательства:** `agent_router.py:796`; `reviewPage.js:21–28`, `38`, `134–151`, `331–341`.

**Влияние.** При большом количестве активных запросов растёт размер ответа и объём DOM. Нельзя поделиться точным срезом ссылкой; поиск по номеру запроса не сработает. Deep link сразу в detail может не иметь контекста следующего запроса. Производительность на больших объёмах не измерялась — это архитектурный риск, а не доказанный лаг.

**Изменение.** Серверные поиск/фильтры/сортировка/пагинация с totals; поиск по #ID; query params для воспроизводимого среза; отдельные ключи состояния по пользователю; next-review endpoint или обновление snapshot перед переходом, при этом сохранение места чтения.

## 5. Что проверяют существующие тесты и чего они не доказывают

- `frontend/tests/reviewPage.test.mjs` проверяет регулярными выражениями наличие элементов, классов, подписей, основных calls и CSS. Это полезный structural regression, но не доказательство реальных переходов, focus/dirty поведения, контрастности, responsive компоновки или обработки гонок.
- `backend/tests/test_customer_task_scope.py:83–174` проверяет запрет заказчику менять status, область роли и available_actions для собственных/чужих in_review; returned в этих проверках не покрыт.
- `backend/tests/test_task_concurrency.py:137–173` проверяет ORM-конфликт двух решений; это защита от lost update, но не проверка того, что пользователь читал новую содержательную версию.
- `backend/tests/test_agent_send_for_review_access.py:34–164` описывает чужую сессию, идемпотентность, resend после soft delete, rollback и компенсацию. Не запускались из-за записывающих фикстур.
- `backend/tests/test_agent_workflow_metadata.py` сохраняет workflow metadata и технический номер версии, а также перенос process/priority в description; это не проверка полного переноса рисков/зависимостей.
- Выполненный `workflow-probe.py` детерминированно подтвердил WF-01 и частично WF-03. Он работает с извлечёнными реальными функциями и памятью, не эмулирует весь HTTP/ORM/браузер.

## 6. Предлагаемые улучшения сверх исправления дефектов

Эти пункты — продуктовые предложения, а не утверждение о нарушении существующих требований.

1. **Рабочая очередь решений.** Первая группа — «Ждут решения команды», затем «На моём ревью», отдельно «Ждём автора». У каждого запроса виден следующий действующий участник и причина нахождения в очереди. Архив решений доступен из того же поиска.
2. **Режим повторного ревью.** Сразу показывать число исправленных/оставшихся замечаний и только изменённые разделы с возможностью раскрыть полный паспорт. Сохранять контекст старого решения и не обнулять работу ревьюера при каждой отправке.
3. **Структурированные замечания.** Добавить комментарий к полю и тип «вопрос/ошибка/риск/допущение»; собрать их в итоговый комментарий автору. Массовый возврат без объяснения и принудительное чтение каждого информационного пункта не нужны.
4. **Передача с договорённостями.** Включить в результат решения критерии готовности к проработке, принятые риски и оставшиеся вопросы с ответственными. Аналитик должен понимать, какие вопросы уже решили, а какие оставили его работе.
5. **Состояния исключений.** Сотрудник отсутствует, команда выбрана неверно, нет BA, исходный диалог недоступен, соседняя сессия изменила запрос — отдельные состояния с адресным восстановлением, а не общий toast.
6. **Качество вместо декоративного процента.** Счётчик заполнения и показатели ИИ оставить справочными. В рабочей зоне показывать конкретные препятствия для решения и их объяснение; для показателей без данных использовать «Нет оценки».
7. **Измерение процесса.** После исправления модели событий измерять время до claim/первого решения, длительность ожидания автора, число циклов возврата, долю перенаправлений, ошибки 409/422, частоту пустого BA directory и время передачи в задачу. Не выводить фиктивные нормативы без SLA и не оптимизировать только число кликов.

## 7. Приёмочные сценарии для следующей итерации

| Сценарий | Что проверить |
|---|---|
| Два ревьюера открыли новый запрос | Один claim успешен; у второго понятный новый владелец; нет второго решения/задачи |
| Автор ещё не ответил после возврата | Ревьюеру не предлагается «Проверить уточнения»; автор свободно продолжает нужный диалог |
| Автор ответил и повторно отправил | Видны новая редакция, предыдущие замечания, diff и дата ресабмита; номер запроса тот же |
| Два цикла возврата | Все причины и решения сохранились; текущий комментарий не заменяет журнал |
| Ошибка/409 при отправке комментария | Текст доступен после refresh; clear/close не уничтожает его незаметно |
| Запрос изменён перед передачей | Пользователь видит изменение до подтверждения; task содержит проверенную редакцию |
| Неверная команда / нет BA | Есть разрешённый путь продолжить процесс, понятен ответственный за устранение |
| Ревьюер ушёл в отпуск / деактивирован | Координатор может передать ответственность с журналом причины |
| Запрос содержит риски, dependencies и противоречия | Всё видно ревьюеру и затем в задаче; исходный запрос/редакция доступны из задачи |
| Пустое поле с объектным finding | Клик открывает существующий target и объясняет, что именно требуется |
| Запрос отклонён | Находится в истории и полном поиске; автор получает понятный итог |
| Связанная задача завершена | Статус согласован между очередью, detail и customer portal |
| Пользователь не держал страницу открытой | Возврат/ресабмит/решение доступны в inbox с корректным следующим действием |
| 500–5000 активных запросов | Измерить время ответа, рендера и памяти; поиск/сортировка не блокируют интерфейс |

Для live-проверок использовать только разрешённые обычные рабочие записи; изменение пользователей, ролей, состава команд и справочников не требуется для исправления UX этих страниц. Сценарии отсутствия сотрудника и пустого справочника можно воспроизводить на изолированных HTTP fixtures.
