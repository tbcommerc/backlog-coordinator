# Исправления демонстрационного развёртывания — 23.11.2026

Статус: реализация и изолированная проверка завершены в перечисленных границах.
Банковская ВМ недоступна из чата; её фактическая приёмка остаётся у разработчика
внутри контура. [Порядок применения](../DEMO_STAND_SETUP.md).

Расширенная проверка настоящего production-режима без ИИ, включая два backend,
HTTPS, естественное истечение access, перезапуск, миграцию и восстановление:
[отдельный протокол core-репетиции](DEMO_CORE_PREFLIGHT_2026-11-23.md).
Приведённый ниже первый браузерный прогон не подменяет этот протокол.

## Что исправлено

1. Первый администратор создаётся явной `bootstrap-admin` с приглашением.
   Пустая БД больше не требует ручной вставки логина/хэша. Нет пароля по умолчанию
   и автоматического seed. Необязательный `--demo-data` создаёт только небольшой
   синтетический набор на пустом стенде.
2. Явная `configure-admin-access --user-id ID` назначает отдельную полную роль
   только согласованной активной учётке. Существующий пароль/логин/команда,
   прежняя общая роль и другие пользователи сохраняются. Сессии выбранного
   пользователя отзываются. Разрешение на добавление этой команды получено
   отдельно; на рабочей БД она не запускалась.
3. Login/refresh/me используют одну карту полномочий. NULL/неизвестные уровни
   безопасно возвращаются как `none`, NULL флаги — false. Такое же преобразование
   есть в response-моделях списков пользователей/ролей; чтение не исправляет БД.
4. Справочники фильтров загружаются общим Bearer-клиентом. Безопасные GET
   `/auth/me`, `/admin/users`, `/admin/roles` поддерживают refresh/retry.
   Запоздалый 401 использует уже обновлённый access. Чувствительные изменяющие
   запросы после 401 не повторяются. После обычного входа загружаются field labels
   и общий справочный контекст. Кнопки учитывают явный `task_edit`.
5. Семь административных справочников связаны с типизированными FK посредством
   `DictionaryItem.reference_id`; запись, переименование и порядок сохраняются
   в одной транзакции. Архивирование сохраняет FK и прежние названия в связанных
   записях, но исключает значение из новых вариантов. Исправлен usage count.
   Проекты, команды и канбан используют типизированные ID. После сохранения
   справочника обновляется контекст приложения и очищается тот же кеш фильтров,
   который использует Бэклог.
6. Schema-only миграция `d352a19c40e8` и отдельная идемпотентная
   `reconcile-references` готовят старые данные без перенумерации ID.
   Неоднозначность приводит к 409 и rollback, а не к случайному связыванию.
7. Общие настройки отображения читаются из того же хранения, куда пишутся;
   новая БД получает пустой read-only default без 404 и без создания строки.
8. Production Compose/шаблон передают обязательные AUTH origin/hosts/HMAC.
   Alembic разрешает путь относительно конфигурационного файла.
9. `stand_smoke.py` на стандартной библиотеке Python проверяет внешний URL,
   cookie, полномочия, справочники, refresh/logout; поддерживает банковский CA
   и ожидание реального истечения access. Секреты не входят в отчёт.

## Функциональная проверка

Использованы одноразовые PostgreSQL 16 и Redis 7 на отдельных loopback-портах,
без подключения рабочих томов. БД имеют отдельные имена `codex_deploytest_*`.
Полная цепочка Alembic от пустой PostgreSQL до `d352a19c40e8` прошла.

| Проверка | Результат |
|---|---|
| `backend/deployment_tests` на PostgreSQL | **33 PASS**: bootstrap, активация/вход, задачи, batch и индивидуальный CRUD семи справочников, сохранение ID, архив/восстановление, старые NULL, repair выбранной учётки, cookie-jar/redirect smoke |
| `backend/account_tests` | **59 PASS**: прежняя безопасность учётных записей и согласованный контракт сроков сессий |
| `test_auth_cookie_policy.py`, `test_route_uniqueness.py` | **6 PASS**: HTTPS/Origin/cookie и уникальность маршрутов; cookie-тесты используют правильный `AUTH_ORIGINS` |
| `admin_empty_dictionary_contracts.py` | **4 PASS**: пустой справочник, версии и блокировка; чистые doubles без рабочей БД |
| Целевые Node.js тесты auth/context/permissions | **28 PASS** |
| Windows Chromium: accountSecurity, adminAuditFixes, adminAuditReview, uiKitAdminEditors | **32 PASS** |
| Windows Chromium, настоящее приложение + PostgreSQL + Redis | **1 PASS**, сценарий ниже |
| `stand_smoke.py` против изолированного приложения | **PASS**: вход, все административные GET, реальные cookie/refresh/logout; ожидание пяти минут в этом прогоне не включалось |

В реальном браузерном сценарии выполнены обычный вход, админка, восстановление
после reload, открытие формы штатной кнопкой, выбор справочников, сохранение
новой задачи через UI и проверка сохранённого приоритета. Затем access искусственно
сделан недействительным: параллельные GET me/users/roles/reference восстановились
через настоящую cookie без выхода. Это проверка отказа access и refresh/retry;
не выдаётся за ожидание естественных пяти минут.

Пример запуска новых backend-проверок из корня (только отдельная тестовая БД):

```powershell
$env:DMB_DEPLOY_TEST_DATABASE_URL='postgresql+psycopg://postgres@127.0.0.1:55439/codex_deploytest_contracts_20261123'
.\.venv\Scripts\python.exe -m pytest dmb-backlog/backend/deployment_tests -q -p no:cacheprovider
```

Если PostgreSQL URL не задан, эти же контракты допускают SQLite в памяти;
это не замена PostgreSQL-приёмки. На данном прогоне использовалась PostgreSQL.
Браузерный helper `deployment_tests/serve_demo.py` допускает только отдельную
loopback PostgreSQL `codex_deploytest_*`, не применяется для развёртывания.
Он создаёт синтетическую тестовую учётку; её реквизиты не являются реквизитами
рабочего приложения. В браузерном прогоне фоновые процессы/агенты не запускались.
