# Паспорт тестовых данных DEV

## 1. Назначение

Документ фиксирует, какие данные разрешено использовать при испытаниях, кто их предоставляет, какие сценарии они покрывают и как выполняется очистка. Паспорт заполняется до функционального и UX/UI-прогона.

Пароли, токены, API keys и другие секреты в этот файл не вносятся. Для учётных данных указывается только идентификатор секрета или способ получения доступа.

## 2. Границы безопасности

В общей DEV-БД запрещено создавать, изменять и удалять:

- справочники и их записи;
- пользователей и их учётные данные;
- роли, политики ролей и назначения ролей;
- команды, состав команд и привязку пользователей;
- атрибуты и ответственных команд, включая `PO`, `PL`, `CL` и аналогичные поля.

Ограничение действует при UI-, API-, SQL- и автоматизированном тестировании. Защищённые поля не должны передаваться в изменяющих запросах даже с прежними значениями.

Подготовку этих данных выполняет уполномоченный владелец стенда до начала испытаний. Тестировщик использует их только для входа и проверки разрешённого поведения.

## 3. Общие правила

- Все изменяемые обычные записи имеют согласованный маркер, рекомендуемый формат: `DEV-QA-<цикл>-<сценарий>`.
- В описании записи указывается дата плановой очистки, если поле допускает это без нарушения бизнес-сценария.
- Не используются реальные персональные, клиентские, финансовые и конфиденциальные данные.
- Вложения содержат синтетические данные и не содержат макросов или секретов.
- Тестировщик не очищает данные, если не подтверждены точный объект и допустимость удаления.
- Общие записи не переиспользуются параллельными тестировщиками без блокировки/владельца.
- Golden-сценарии агента не содержат реальных ФИО, номеров договоров, счетов или клиентских идентификаторов.

## 8. Набор текстов агента

### Основной feature/change-сценарий

> Нужно добавить в карточку сделки поле «Причина изменения срока». Поле должен заполнять менеджер при переносе плановой даты. Значение должно быть видно руководителю при проверке сделки.

Исправление:

> Исправление: поле должен заполнять не менеджер, а руководитель группы.

Проверяемый критерий:

> Если пользователь переносит плановую дату, сохранение недоступно, пока не заполнена причина. После сохранения причина отображается в карточке сделки руководителю группы.

### Тексты для layout

- короткий ответ: `Да`;
- многострочный ответ из 3–5 абзацев;
- строка без пробелов допустимой длины — только если не нарушает входные ограничения;
- список из 8–10 пунктов;
- русский текст с кавычками, тире, числом и датой;
- сообщение около верхней разрешённой границы, но не превышающее её.

Содержательные ожидаемые ответы фиксируются позднее в golden dataset. Здесь тексты предназначены прежде всего для UX/UI и сохранения состояния.

## 10. Состояния и способы получения

| Состояние | Безопасный способ подготовки |
|---|---|
| Empty backlog/customer/review | использовать подготовленный профиль/область без записей; не удалять чужие записи |
| Loading | network throttling в DevTools либо контролируемая задержка стенда |
| API error | разрешённая DevOps fault injection, а не повреждение данных |
| Agent unavailable | контролируемое отключение маршрута/сервиса DevOps |
| LLM timeout/429/5xx | тестовый stub/provider policy или контролируемая fault injection |
| Forbidden | подготовленный AP-07; не менять роль текущего пользователя |
| Task conflict | два разрешённых пользователя редактируют TD-TASK-04 |
| Long content | отдельные обычные записи TD-TASK-02/TD-AGENT-02 |

## 12. Очистка и закрытие цикла

Перед очисткой:

1. получить список только из журнала созданных записей;
2. проверить точные ID и владельца;
3. убедиться, что запись не используется открытым дефектом;
4. удалить/архивировать только разрешённые обычные записи штатным способом;
5. зафиксировать результат и ошибки;
6. не выполнять массовую очистку по одному лишь текстовому префиксу без проверки ID.

Защищённые данные не очищаются тестировщиком. Если для них требуется изменение, оно оформляется владельцу стенда как отдельное согласованное действие вне тестового прогона.

## 13. Критерий готовности данных

Набор готов, если:

- AP-01–AP-07 сопоставлены фактическим профилям либо ненужные профили согласованно исключены;
- определена команда для TC-AUX-009;
- подготовлены обязательные обычные записи;
- указан владелец очистки;
- нет секретов и реальных защищённых данных в документах;
- все отсутствующие данные отражены как `BLOCKED`, а не заменены несанкционированным seed.
