# Связи полей карточки задачи со справочниками — 23.11.2026

**Исторический снимок до исправления.** Все шесть замечаний ниже исправлены;
текущие результаты и границы приёмки перечислены в
[отчёте об исправлениях](TASK_CARD_REFERENCE_FIX_2026-11-23.md).
Описания поведения и номера строк далее относятся к исходной проверке.

**Результат: проверка полностью не пройдена. Найдено 6 воспроизводимых дефектов,
из них 2 с приоритетом P1.** В штатном случае все 11 одиночных ссылок работают:
селекторы передают правильные ID, PostgreSQL сохраняет их, API возвращает ID и
названия. Ошибки проявляются на совпадающих названиях, некорректных ID, архивных
значениях и отказе загрузки справочника.

Это проверка текущего исполняемого кода. Код приложения, рабочие пользователи,
роли, команды и справочники не изменялись. Использованы отдельная одноразовая
PostgreSQL и синтетическая браузерная fixture; банковская ВМ недоступна.
Тестовый контейнер и его том удалены.

## Как устроены связи

Создание задачи получает `/tasks/reference` и сохраняет ID из `option.value`.
Открытая карточка получает тот же endpoint, но большинство одиночных селекторов
содержат **название** в `option.value`; перед PATCH название преобразуется в ID.
Подразделение и клиент ДИД в редакторе используют ID непосредственно.

Для пяти типизированных справочников `DictionaryItem.id` относится к редактору,
а `reference_id` — к строке справочника, на которую ссылается задача.
Их путаницы в положительной проверке не обнаружено.

в коде. Восемь строк трудозатрат соответствуют фиксированным полям модели;
произвольная новая компетенция не добавляет новое поле задачи автоматически.

## Подтверждённые дефекты

### REF-01 — P1: ID восстанавливается по неуникальному названию

`cardSel()` использует название как значение option; `cardBuildMaps()` делает
`m[name] = id`, перезаписывая предыдущую запись. Пользователи, заказчики и проекты
могут иметь совпадающие названия: уникальность их `name` в модели не задана.
Нельзя решать проблему запретом одинаковых ФИО.

В Windows Chromium добавлены два синтетических исполнителя с одним именем,
ID **110** и **112**. Выбор первого option отправил `owner_id=112`.
Оба option имели одно и то же строковое value.
В выполнении настоящего JS-модуля два заказчика дали ещё и смешанную пару:
`business_customer_id=32`, но `department_id=101`, хотя у заказчика 32 подразделение
102. Причина: карта ID берёт последнего, а автоподстановка через `.find()` первого.

Источники: [modal.js](../../dmb-backlog/frontend/js/components/modal.js), строки
5757, 5923–5945, 7255–7274, 7856–7858. Доказательства:
[браузерный запрос](../../artifacts/task-field-reference-audit-2026-11-23/duplicate-owner.json),
[полный экран](../../artifacts/task-field-reference-audit-2026-11-23/duplicate-owner-full.png),
[выполнение JS-модуля](../../artifacts/task-field-reference-audit-2026-11-23/frontend-evidence.json).

Нужно хранить и передавать стабильные ID во всех селекторах и состоянии черновика;
название оставлять подписью. Совпадающие имена различать логином/командой,
подразделением заказчика, кодом проекта. Автоподстановку подразделения выполнять
по выбранному ID заказчика.

### REF-02 — P1: неверное подразделение даёт 500

В списках проверяемых ссылок создания и изменения нет `department_id`.
PostgreSQL отклоняет несуществующий FK, а обработчик изменения превращает это
в общий 500. В тесте PATCH с `department_id=987654321` вернул **500**, ожидается
управляемый **422** с указанием поля. Корректный ID проходит.

Источник: [tasks_router.py](../../dmb-backlog/backend/routers/tasks_router.py),
строки 965–974, 1277–1292 и обработчик исключения в конце `update_task`.
[Доказательство PostgreSQL](../../artifacts/task-field-reference-audit-2026-11-23/backend-evidence.json).
Нужно включить подразделение в общую проверку ссылок POST/PATCH и вернуть
ошибку поля до записи; предусмотренный карточкой mapper ошибок также должен
распознавать `department_id`.

### REF-03 — P2: отказ загрузки маскируется пустым справочником

`cardLoadDict()` ловит ошибку `/tasks/reference`, заменяет ответ на null и берёт
кеш либо пустые массивы. Функция возвращает `true`. В воспроизведении отказ 503
дал `load_result=true`, `priorities=0`, `statuses=0`; отдельного состояния отказа
и кнопки повторной загрузки справочников здесь нет.

Источник: `modal.js:5872–5919`.
[Доказательство JS-модуля](../../artifacts/task-field-reference-audit-2026-11-23/frontend-evidence.json).
Нужно различать пустоту, отказ и устаревший кеш, сохранять уже загруженные данные,
показывать повтор и ограничивать изменение полей, варианты которых не получены.

### REF-04 — P2: архивная метка остаётся в вариантах

`/tasks/reference` берёт все `Tag` без `is_active`. Синтетическая метка с
`is_active=false` вернулась в списке; карточка показывает весь полученный набор.
Это отличается от фильтрации статусов, приоритетов, сроков, подразделений и ДИД.

Источник: `tasks_router.py:799`; `modal.js:5795–5798`.
[Доказательство PostgreSQL](../../artifacts/task-field-reference-audit-2026-11-23/backend-evidence.json).
Нужно исключать архивные метки из новых вариантов и отдельно сохранять показ
исторически выбранных значений, не стирая прежние связи.

### REF-05 — P2: сохранённое архивное подразделение выглядит пустым при изменении

API правильно исключает архивные подразделения из активных вариантов.
В режиме просмотра карточка использует сохранённое название. Но при изменении
`cardCustomerReference()` не добавляет option для текущего ID, если его нет
в активном списке. В воспроизведении для сохранённого ID 101 отсутствуют и option
101, и его историческое название; select отображает «Не выбрано».
Это дефект отображения/выбора: автоматическое стирание FK этим тестом не установлено.

Источник: `modal.js:6204–6212`.
[Доказательство JS-модуля](../../artifacts/task-field-reference-audit-2026-11-23/frontend-evidence.json).
Нужно показывать текущий исторический вариант с пометкой архива и сохранять ID,
пока пользователь явно не очистит или не заменит значение. Проверить тот же
компонент для архивного клиента ДИД.

### REF-06 — P2: вовлечённая команда может ссылаться в никуда

`Task.involved_teams` — JSON, а не FK-таблица. В обработчике изменения нет проверки
существования каждого ID. PATCH с `[987654321]` вернул **200** и сохранил этот
список, хотя такой команды нет. Основной `team_id` проверяется отдельно.

Источники: [models.py](../../dmb-backlog/backend/models.py), строка 551;
`tasks_router.py:1277–1292`.
[Доказательство PostgreSQL](../../artifacts/task-field-reference-audit-2026-11-23/backend-evidence.json).
Нужно проверять все ID массива при POST/PATCH и отвечать 422 до записи.
