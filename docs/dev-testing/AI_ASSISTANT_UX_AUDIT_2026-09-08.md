# UX-аудит ИИ-ассистента подготовки бизнес-требований

Дата проверки: **08.09.2026**. Статус: датированный аудит и предложение TO-BE, **не описание внедрённого интерфейса**.

## Вывод

Перегрузку создаёт сочетание трёх рабочих пространств — истории, диалога и формы из 18 полей — и нескольких независимых объяснений готовности. При переходе к проверке приоритеты экрана почти не меняются: длинный диалог занимает центральную часть, документ остаётся узкой боковой колонкой, а отправка находится под документом. Пользователь должен самостоятельно понять, какую из поверхностей сейчас использовать.

Предлагается единое рабочее место с последовательностью **«Описать → Проверить → Отправлено»**. Во время сбора главным остаётся диалог; на проверке главным становится документ; после отправки показываются фактический статус и следующий шаг. История, происхождение данных и дополнительные разделы открываются по потребности.

До визуального переустройства необходимо согласовать правила готовности и исправить пути изменения черновика. Иначе более спокойный экран сохранит те же остановки и повторные действия.

## Метод и границы доказательности

- Изучены текущие frontend, основной agentic runtime, переиспользуемые им операции workflow, backend-маршруты запросов и существующие UX-тесты.
- Через работающий интерфейс просмотрены восстановленный незавершённый диалог, готовый черновик, история, отправленный диалог и связанный запрос. Проверены компоновки 1440×900, 1280×800 и 390×844; дополнительно наблюдалось начальное узкое окно браузера.
- Вызов штатного `project-status.ps1` показал `health=ready` для backend, agent и prioritiser. Проверка Docker получила отказ доступа; для просмотра уже работающего приложения Docker-команды не требовались.
- Граф связей использован только для навигации. Источник выводов о текущей реализации — код и текущий рендеринг.
- Содержимое просмотренных диалогов создано ранее. Оно показывает нагрузку восстановления и реальные примеры затруднений, но **не доказывает качество генерации текущей версии модели**. Новые LLM-диалоги, отправка на ревью, возврат, архивирование и действия за другие роли в этом аудите не выполнялись.
- Для сверки полей выполнено чтение JS и AST Python без обращения к БД: в карте 18 полей; `process` и `priority` не поддерживаются операцией изменения готового черновика; `role` проходит через `user_roles` в `users`.
- Ни защищённые данные, ни содержание требований не изменялись. Переключение существующих диалогов меняло только активную сессию; в конце восстановлен исходный черновик.
- Это экспертный аудит. Время выполнения сценариев, конверсия и эффект рекомендаций на реальных пользователях не измерялись. Существующие тесты прочитаны как свидетельство покрытия; полный функциональный прогон не заявляется.

Обозначения в матрице: **UI** — просмотр текущего интерфейса; **Код** — прослежен исполняемый путь; **Гипотеза** — улучшение требует проверки с пользователями. Просмотр UI не равен полному выполнению сценария с изменением данных.

## Главные находки и решения

### F01. Иерархия экрана не соответствует текущей задаче — P1

В `renderAgentChat()` установлен `focusMode=true`, но это всё равно три колонки. В просмотренной компоновке 1440×900 рабочая область имела ширину 1336 px: история 252 px, диалог 716 px, требование 344 px. Документу отведено около 26% ширины даже на финальной проверке. Эти числа описывают конкретный viewport и состояние раскрытой истории, а не все экраны.

Внутри карты рендерятся 18 полей в четырёх группах. Группа раскрывается, если она задана открытой **или** содержит значение/замечание. При обновлении вся карта строится заново; выбор пользователя свернуть группу не сохраняется. По мере наполнения документ становится всё более раскрытым.

**Решение:** управлять главным пространством по этапу; при проверке отдавать документу основную ширину, сохранять раскрытие разделов, убрать постоянно раскрытую историю. Сохранить возможность закрепить вспомогательную область для опытного пользователя, но не делать её стартовым условием.

**Приёмка:** при входе в проверку заголовок, содержание документа и главное действие доступны без поиска по боковым колонкам; обновление ответа не раскрывает закрытые пользователем разделы.

### F02. Отправка спрятана ниже длинного документа — P1

На 390×844 область проверки имела высоту около 599 px при содержимом 2579 px. Панель действий начиналась примерно на координате y=2630 до прокрутки. Это больше трёх высот доступной области. Горизонтального переполнения в проверенном состоянии не обнаружено.

**Решение:** один основной скролл документа; закреплённая нижняя строка «Готово к отправке / Нужно уточнить …» и действие. Детали ошибок открывать из этой строки и возле соответствующего раздела. Не переносить весь перечень блокеров над документом: это снова отодвинет сам результат.

**Приёмка:** на телефоне можно открыть замечание и вернуться к отправке без прокрутки документа до конца; экранная клавиатура не закрывает редактируемое поле и его действия.

### F03. Правила готовности расходятся между интерфейсом и сервером — P0

Четыре обязательных слота: потребность, целевое состояние, роль, процесс. `can_generate_draft` вычисляется по их состояниям. Но `composer.build_draft()` помечает вопрос блокирующим также по текстовому префиксу **«Уточните:»**. Поэтому рекомендация по ценности может стать запретом отправки, хотя ценность находится в дополнительных деталях. Это наблюдается на восстановленном черновике.

Frontend блокирует кнопку по `open_question_details[].blocking`. Серверная `confirm_and_send()` использует другой механизм — `review_draft()` и критичность его findings. `getDraftIssueSummary()` не включает допущения и неблокирующие вопросы в общий `attention`. Значения «Не знаю» после адресной правки записываются как заполненный слот с confidence=1.0, тогда как клиент классифицирует их как неразрешённые. Так возникают несовместимые сигналы готовности.

**Решение:** один серверный результат проверки: `can_submit`, уникальные `blockers`, `review_questions`, `assumptions`, `next_action`. Правило блокировки задаётся кодом и типом проблемы, а не формулировкой текста. Состояния «неизвестно» и «не применимо» должны быть отдельными значениями статуса. Неполный полезный черновик можно передать специалисту, если отсутствуют заранее определённые жёсткие препятствия.

**Приёмка:** одна и та же формулировка даёт одинаковое решение кнопки и API; необязательный вопрос не превращается в обязательный только из-за текста; неразрешённое обязательное поле не получает статус готового.

### F04. «Продолжить в диалоге» не гарантирует применение правки — P0

`AgenticOrchestrator.handle_message()` при наличии `state.draft` возвращает `_handle_draft_ready()` **до** обычной записи и анализа пользовательского сообщения. Унаследованный обработчик для обычной реплики повторяет готовность черновика; по маркерам правки сбрасывает draft и просит описать изменение, не применяя его в этой же реплике.

Одновременно клиент обновляет `currentDraft` только при truthy `resp.draft`: ответ с `draft=null` сам по себе не очищает старый документ. Возникает риск, что backend уже ждёт новый этап, а справа остаётся прежний черновик.

**Решение:** отдельная операция уточнения готового документа, которая принимает полную реплику, сохраняет её и изменяет текущую версию. Явно обрабатывать очистку/замену draft на клиенте. В диалоге показывать краткое подтверждение изменения и ссылку на раздел.

**Приёмка:** фраза «Срок формирования отчёта — 30 секунд» в готовом черновике сохраняется и меняет нужный критерий за одну отправку; повторный ввод этой же правки не требуется; после перезагрузки сервер и UI показывают одинаковый документ.

### F05. Доступные поля и операции сохранения не совпадают — P0

Автоматическая сверка подтвердила: `process` и `priority` присутствуют в карте, но отсутствуют в `field_to_slot` операции `edit_draft_section()`. Клиент также не отделяет все ответы `action=error` от успешного результата сохранения. «Основная роль» и «Пользователи» через `MAP_TO_DRAFT_FIELD` попадают в `user_roles`; сервер меняет `users`, а сборщик объединяет прежний `role` и `users`. Замена роли может сохранить старую роль в документе.

**Решение:** общий каталог редактируемых полей и серверных ошибок, единая модель роли/аудитории. Неподдерживаемое действие не показывать как доступное. При ошибке не рисовать «Было/Стало» как подтверждённое изменение.

**Приёмка:** каждое доступное поле действительно сохраняется; ошибка отображается рядом с редактором и оставляет введённый текст; замена основной роли не добавляет вторую устаревшую роль.

### F06. Прогресс требует интерпретации вместо помощи — P1

На экране конкурируют готовность требования, обязательные разделы над вводом, счётчики групп, число у вкладки «Требование», статус карты, блокеры и проценты в текстах ответов. Например, «Требование 12» означает число разрешённых полей, но выглядит как номер требования или число замечаний. Сохранившиеся сообщения с процентами могут не соответствовать последующим правкам.

**Решение:** одна актуальная строка прогресса с пользовательским смыслом: «Нужно уточнить, кто пользуется решением», «Можно перейти к проверке», «Нужно решить один вопрос». Числовые оценки оставить в раскрываемых сведениях для ревьюера. Удалять исторические сообщения не требуется; важно не использовать их как текущий статус.

**Приёмка:** пользователь понимает готовность без сравнения счётчиков и без знания числа внутренних полей.

### F07. Проверка повторяется в нескольких формах — P1

Обычный путь включает резюме и «всё верно», затем создание draft, финальную проверку, окно с ещё одной сводкой, checkbox и финальную отправку. Особенно заметно это после нажатия «Сформировать черновик», которое фактически ведёт к резюме.

**Решение:** предварительный документ формировать без обязательного подтверждения его существования. Проверять и править его в одном месте. На последнем шаге сохранить одно явное подтверждение отправляемой версии и понятный маршрут. Если команда требует отдельного юридически/организационно значимого подтверждения содержания, его назначение должно быть сформулировано отдельно; в просмотренном коде такого основания не обнаружено.

**Приёмка:** пользователь не перечитывает одну и ту же структуру в чате, боковой карте и модальном окне; отправка остаётся явным действием человека.

### F08. Жизненный цикл распадается между историей и «Моими запросами» — P1

Черновики живут в сессиях, отправленные документы — в запросах. История показывает служебные фазы и ID. В просмотренном UI один связанный запрос уже находился «В проработке», но диалог продолжал сообщать «готов к ревью». Backend передаёт `request_status`; `renderRequestLink()` его не использует. Возвращённый запрос не выделен отдельной веткой в `getSessionLifecycle()`, а проверка наличия draft предшествует `needs_user_response`.

**Решение:** сквозная сущность для пользователя — «запрос», начинающийся с черновика. Одинаковые статусы и актуальный следующий шаг во всех поверхностях. Служебный ID сессии убрать в сведения для поддержки. «Новый запрос» и «Продолжить запрос» должны различаться по поведению.

**Приёмка:** возвращённый запрос попадает в «Нужно действие», отправленный в проработку не выглядит ожидающим ревью, новый запрос не открывает старую переписку.

### F09. Возврат с ревью нужно превратить в работу по замечаниям — P1

Повторная отправка уже сохраняет номер запроса и увеличивает версию — это следует сохранить. Но комментарий становится частью длинной истории, а `lastDraftChange` хранит только одно последнее изменение и очищается при повторном открытии.

**Решение:** закрепить причину возврата, привязать замечания к разделам, хранить отправленные снимки и показывать разницу с предыдущей версией. Название действия — «Отправить уточнения». Содержательные исправления можно вносить как в полях, так и репликой.

**Приёмка:** после перезагрузки видны комментарий и все изменения текущего цикла; аналитик проверяет изменённые разделы, а не ищет отличия во всём документе.

### F10. Маршрут передачи описан неточно — P1

В окне можно оставить команду пустой; backend использует `req.team_id or current_user.team_id`. Поэтому «Не знаю / пропустить» не обязательно означает запрос без команды. При повторной отправке existing request сохраняет прежнюю команду независимо от выбора в этом окне. Обещание ревью только PO/PL/CL уже, чем фактическая ролевая матрица, включающая разрешённых BA и другие роли.

**Решение:** сервер возвращает вычисленный маршрут; UI показывает «Первичная проверка: команда …» либо конкретную очередь без назначения. При повторной отправке — «Вернётся в …». Управление справочниками, пользователями, ролями и составом команд для этого не требуется.

**Приёмка:** показанный получатель совпадает с сохранённым маршрутом; недоступный для изменения маршрут не отображается как редактируемый.

### F11. Обещание передачи человеку не подтверждено операцией — P0

В обработанном пути эскалация устанавливает флаг и пишет событие, затем сообщает «передаю диалог аналитику». Backend чата не создаёт для `escalated` отдельного запроса или подтверждённого назначения. Это может заставить пользователя ждать человека, которому ничего не поступило.

**Решение:** использовать реальный путь передачи незавершённого материала с явным согласием пользователя, подтверждённым номером и статусом. До его реализации заменить обещание на доступное действие и понятный адресат/маршрут помощи.

**Приёмка:** сообщение «передано» появляется только после успешной операции, видимой получателю. Ошибка передачи сохраняет контекст и предлагает повтор.

### F12. Вторичные сведения занимают слишком много места — P2

Режим и отсутствие внешних источников постоянно находятся над диалогом. У заполненных полей повторяются «Источник» и «Уверенность». Высокая уверенность после ручного ввода, включая «не знаю», не означает, что бизнес-смысл проверен. Кнопка «Контекст» у старого ответа открывает общую текущую панель источников, а не обязательно сведения этого ответа. Описание экспертного режима в UI («более детальные вопросы») расходится с коротким путём в mode selector.

**Решение:** возле факта оставить только значимые исключения: предположение, противоречие, требуется проверка. Происхождение раскрывать по запросу; источник привязывать к конкретному сообщению/полю. Режим диалога не делать самостоятельной задачей пользователя. Важные ограничения модели объяснить один раз и в нужном месте.

**Приёмка:** основной текст читается без повторяющихся метаданных; источник старого ответа относится именно к нему; достоверность содержания не подменяется уверенностью извлечения.

### F13. Некоторые сбои маскируются под нормальные состояния — P1

Ошибка первоначального восстановления сессии поглощается, после чего выводится приветствие. `formatAgentError()` превращает любой 409 в «данные уже изменились», хотя при отправке этот код может означать содержательную валидацию. Во время генерации textarea становится readOnly, хотя пользователь мог бы готовить следующую реплику.

**Решение:** отдельное состояние восстановления с повтором и сохранённым вводом; структурированные коды ошибок с адресным действием; разрешить набор следующего сообщения, блокируя только преждевременную отправку. Называть отмену именно «Остановить ожидание», поскольку сервер может продолжить обработку.

**Приёмка:** временный сбой не выглядит исчезновением истории; причина запрета отправки показана содержательно; повтор не создаёт дубликатов.

## Предлагаемая структура интерфейса

### 1. Описание и уточнения

Шапка: название запроса, состояние сохранения, компактный переход к своим запросам. Главная область: диалог удобной ширины. Внизу: поле ответа, одно основное действие, короткое объяснение следующего шага. «Что уже собрано» — раскрываемое краткое резюме, а не постоянно видимая анкета.

Когда достаточно данных, рядом с вводом появляется «Перейти к проверке». Дополнительный вопрос не должен отнимать эту возможность. При неоднозначности — понятные варианты ответа или свободный текст; не требовать знания внутренних типов и названий разделов.

### 2. Проверка документа

Главная область переключается на читаемый документ: потребность, текущее и желаемое поведение, пользователи, критерии приёмки. Остальные разделы раскрываются по содержанию и выбору пользователя. «Уточнить с ассистентом» открывает вспомогательный диалог с контекстом выбранного раздела.

Сверху — краткое состояние проверки; внизу — доступная строка отправки. Незавершённые вопросы передаются аналитику открыто. Критическое препятствие содержит причину и ссылку на поле. Подтверждённые данные, выводы ассистента и предположения различимы по запросу, а существенные предположения видны сразу.

### 3. Передача и дальнейшая работа

Одна итоговая зона с маршрутом и явным подтверждением. После успешной передачи: номер, текущий статус, кто выполняет следующий шаг, ссылка на документ и возможность начать новый запрос. Срок показывается только если он известен из данных. При возврате основной режим — исправление замечаний, а не начало нового интервью.

Это не обязательный линейный мастер: между описанием и проверкой можно свободно переключаться без потери текста. Меняется приоритет содержимого, а не доступность накопленной информации.

## Что сохранить

- Свободное описание и примеры, которые сначала заполняют поле, а не отправляются автоматически.
- Автоматическое извлечение фактов, ограничение до одного вопроса и существующий ранний выход к черновику.
- Адресное редактирование, если исправить его контракт; явное человеческое подтверждение отправки.
- Сохранение введённого текста, идемпотентность сообщений/отправки, понятный retry и SSE.
- Режим чтения отправленного документа, исходную сессию и номер запроса при возврате.
- Доступность: клавиатурные переходы, восстановление фокуса, inert, отдельное объявление новых ответов, управление прокруткой.
- Отдельное пространство ревьюера: заказчику не нужно видеть весь его набор диагностических сигналов.

## Очерёдность внедрения

Приоритеты здесь продуктовые: **P0** — риск неприменённой правки, недостоверного результата или невозможности завершить путь; **P1** — заметное затруднение основного сценария; **P2** — снижение шума и дополнительные удобства. Это не оценка безопасности или аварийности production.

| Этап | Объём | Результат | Сложность относительно остальных работ |
|---|---|---|---|
| A. Надёжность путей | F03–F05, F11; адресные коды ошибок из F13 | Правки применяются, правила отправки едины, передача человеку честная | Средняя/высокая: затрагивает контракты и состояние |
| B. Упрощение главного экрана | F01–F02, F06–F07, визуальная часть F12 | Диалог и документ получают приоритет по этапу; одна актуальная готовность | Средняя: frontend + переход проверки |
| C. Сквозной запрос | F08–F10, восстановление из F13 | Черновик, ревью и уточнения воспринимаются как одна работа | Средняя/высокая: версии, выборки, маршруты |
| D. Адаптивность | Профили небольшого изменения, БЗ, инцидента; источники по сообщениям | Меньше нерелевантных уточнений без ухудшения качества | Средняя/высокая: оценка модели и regression-набор |
| E. Дополнительные возможности | Импорт документа, экспорт, поиск похожих запросов — только после проверки спроса | Улучшение отдельных профессиональных сценариев | Отдельная оценка после основных изменений |

Не предлагается начинать с замены цветовой схемы, уменьшения шрифта, нового набора иконок или полной переписи frontend. Часть текущих компонентов можно использовать повторно. Визуальное спокойствие должно получаться из меньшего числа одновременно показанных задач.

## Как проверить улучшение

Провести сравнительный тест текущего и предлагаемого вариантов на одинаковых исходных описаниях. Практический первый цикл — по 4–6 участников из группы бизнес-заказчиков и опытных BA/PO; порядок вариантов чередовать. Это качественная проверка и поиск препятствий, не статистическое доказательство роста конверсии.

Обязательные задания: новое описание с нуля; готовый развёрнутый текст; небольшое изменение интерфейса; «не знаю»; ранний черновик; исправление роли и критерия в поле и в диалоге; возврат после перезагрузки; просмотр замечаний на телефоне; отправка без знания команды; возврат с ревью; временный сбой; запрос помощи человека.

Измерять:

1. Активное время пользователя до первого пригодного черновика и до передачи; ожидание модели учитывать отдельно.
2. Число содержательных уточнений, повторных вопросов и повторных вводов одной правки.
3. Долю завершения без подсказки модератора; точки отказа от сценария.
4. Может ли пользователь правильно назвать текущее состояние, следующий шаг и получателя.
5. Успех исправления и отсутствие потери текста после сбоя/перезагрузки.
6. Принятие BA без возврата, объём существенных правок и проверяемость критериев приёмки — качество не должно снижаться ради короткого чата.

Целевые технические критерии: все доступные редактируемые поля сохраняются; содержательная правка применяется за одну реплику; UI и сервер дают одинаковый результат проверки; повтор отправки создаёт один запрос; возвращённый запрос виден как требующий действия; главное действие доступно на узком экране. Процент экономии времени заранее не заявляется: базовые значения пока не сняты.

Текущую аналитику также нужно сверить: событие `request_sent` отправляется из `renderAgentResponse()`, а основной modal-путь обрабатывает успешную отправку самостоятельно. Воронка, построенная только по этому frontend-событию, может быть неполной. Событие передачи следует фиксировать на сервере после commit; тексты требований в продуктовые события не включать.
