# Улучшения ассистента бизнес-требований после аудита

Дата: 08.09.2026. Изменения внесены в рабочее дерево проекта по разрешению
пользователя. Документ описывает реализацию и её ограничения; исходный
[аудит](AI_ASSISTANT_LOGIC_AUDIT_2026-09-08.md) и его воспроизведения остаются
историческими свидетельствами состояния до исправлений.

## Что меняется для пользователя

Дополнение требования сохраняет прежние пункты. Для замены, удаления и
подтверждения используется отдельная операция с опорой на текущую реплику.
Если новая версия противоречит прежней, обе сохраняются до уточнения. Ответ
ассистента отражает фактический результат применения, поэтому отклонённая
правка не сопровождается обещанием «записал».

Модель больше не может закрыть обязательные поля сведениями без опоры на слова
заказчика: сомнительные кандидаты остаются в реестре предположений. Повторение
предположения не повышает его достоверность. Происхождение, цитата, ссылка на
реплику и состояния «не знаю», «не применимо», «отложено» переживают сохранение
сессии и сокращение истории, которую получает модель.

Короткое «нет» относится к заданному вопросу. Подтверждение относится к
непосредственно показанному резюме; «понял» и «продолжай» не считаются согласием.
Сбой модели сохраняет реплику и фокус вопроса без восстановления фактов по
случайным подстрокам старой истории. Сигнал о необходимости аналитика позволяет
продолжить исправления. После минимального ядра лимит вопросов и усталость
завершают сбор с открытыми вопросами.

В резюме и итоговом артефакте видны As-Is, регуляторные ограничения, риски,
зависимости, предположения и конфликты. Нумерация расплывчатого критерия не
превращает его в проверяемый. Каждый критерий проверяется отдельно, а
критические проблемы ограничивают оценку качества и уверенности.

Отправляется редакция, сверенная с просмотренным черновиком. Устаревший экран
получает конфликт редакций. Возвращённый запрос сначала уточняется автором;
повторное взятие на ревью не заменяет его доработку. Отправленные версии и
решения с комментариями сохраняются, а перенос в задачу сохраняет содержимое
требования и ограничения.

## Связь с выводами аудита

| Выводы | Реализация | Предел проверки |
|---|---|---|
| F01 — потеря дополнений | add/replace/remove/confirm/defer; объединение списков без стирания прежних пунктов; результаты применения | Семантика произвольного дополнения зависит от правильной операции модели; неоднозначная замена сохраняется как конфликт |
| F02 — потеря противоречий | Устойчивый реестр с версиями, статусом, источником и разрешением по явно исправленному полю; перенос в gaps и draft | Свободное противоречие без привязки к полю требует экспертного уточнения |
| F03–F04 — недостоверные факты и слабые типы | Строгая проверка JSON-типов, цитаты и связи со значением; неподтверждённый кандидат не заполняет каноническое поле | Проверка цитаты консервативная и лексическая; сложная корректная перефразировка может потребовать уточнения |
| F05 — исчезновение предположений | Отдельный реестр; сохранение при retrieval и сериализации; видимость в резюме и артефакте | Старые сессии не получают выдуманную историю доказательств |
| F06 — эвристическое восстановление при ошибке | Active runtime возвращает unavailable без изменения фактов; реплика и фокус сохранены | Доступность внешнего провайдера — отдельная предпосылка |
| F07–F08 — глобальное «нет» и блокировка исправлений | Контекст подтверждения, отдельное завершение, сброс OOD после возврата к задаче, обработка исправления до оценки необходимости аналитика | Автоматическая передача живому аналитику не добавлялась |
| F09 — потеря смысла вопроса и грубый фильтр ролей | Сохранение вложенных вопросительных конструкций; исключение вводной перепроверки; более узкое различение роли и внешнего согласующего | Выбор лучшего смыслового фокуса в произвольной многосоставной реплике требует модельной оценки |
| F10 — противоречивые условия завершения | Общая проверка модельных сигналов готовности; лимит, усталость и защита от повторения вопроса; ранний draft остаётся доступен | Неполное обязательное ядро по-прежнему требует уточнения |
| F11 — формальная высокая оценка | Проверка каждого AC после удаления нумерации, наблюдаемые исходы без обязательных чисел, ограничение high при critical | Это набор проверяемых признаков, а не универсальная экспертная оценка |
| F12–F13 — ложные/пропущенные противоречия | Учёт отрицаний и ограниченных шаблонов прав; независимый пересчёт по финальному тексту draft | Произвольная логика сложных бизнес-правил остаётся зоной экспертного ревью |
| F14–F15 — утрата статусов и разные пробелы | Статусы, цитаты и происхождение в модели/артефакте; единый реестр gaps, explicit questions, unknown/deferred, resolved N/A | Даты и доказательства отсутствовавших исторических решений не восстанавливаются автоматически |
| F16 — поисковая выдача вместо ответа | Честная маркировка справочных фрагментов, полные разделы без немого обрезания, version/updated_at из manifest | Частично: семантическая достаточность ответа и проверка актуальности всего корпуса не реализованы |
| F17 — неполное резюме и ложное подтверждение | Все существенные разделы и неопределённости в резюме; подтверждение резюме не повышает достоверность всех полей; UI различает происхождение | Экспертная проверка содержания остаётся обязательным этапом процесса |
| F18 — разные редакции при отправке | Полный fingerprint, expected_draft_hash, проверка в сериализованной сессии; DMB хранит подтверждённый ответ агента | Старые клиенты без хеша защищены на участке DMB→agent, но не от собственного устаревшего preview |
| F19 — неправильная работа возвращённого запроса | Возвращённый запрос не берётся на ревью до повторной отправки; различающаяся повторная редакция не считается успешным дублем | История уже утраченных в прошлом комментариев не восстанавливается |
| F20–F21 — неполный перенос и интерфейс ревью | Полный экспорт полей, рисков, зависимостей и доказательств; видимые процесс/приоритет/подразделение и проверки; контекст запроса при восстановлении | Структурные доказательства раскрываются отдельно от основного текста |
| F22 — счётчик вместо истории | Снимки отправленных редакций и события с комментариями; UI показывает реальные записи | Требуется миграция схемы; история начинается с доступного snapshot, без вымышленных прежних редакций |
| F23 — проверки legacy вместо active runtime | API-тесты используют AgenticOrchestrator; новые сценарии отрицаний, сбоев, конфликтов, лимитов и stale snapshot; обновление метрик каждого ответа | Частично: продуктовые метрики принятия и репрезентативная оценка реальной LLM пока отсутствуют |

Дополнительно активный SSE-путь передаёт проверенный ответ без второго вызова
LLM на переформулировку. Это сохраняет указанные в ответе ограничения и снижает
число модельных вызовов на ход.

## Проверки

Итоговый общий прогон агента: **330 passed**, 13 предупреждений об устаревающих
интерфейсах Pydantic/httpx. Изолированные backend-проверки: **14 passed**;
профильные frontend-файлы: **5 passed**. Синтаксис изменённых Python/JS и
локальные Markdown-ссылки проверены отдельно.

Backend-набор проверяет сохранение именно подтверждённого snapshot, гонку
правки и отправки, устаревший preview, различающиеся повторы, историю возвратов,
полный перенос старого требования в Task и отсутствие компенсации после
успешного commit. Миграция проверена генерацией PostgreSQL DDL offline.

При независимом повторном разборе дополнительно найдены и исправлены случаи:
новый конфликт в готовом draft без изменения канонического поля; обещание
правки при пустом наборе операций; неверный фокус после отклонённого факта;
вопрос по конфликту с фокусом другого раздела. Новые регрессии подтверждают,
что метаданные меняют snapshot, критический конфликт блокирует отправку, а
сообщение и следующий вопрос соответствуют фактическому состоянию.

Тесты выполняются с mock-провайдером и изолированным хранилищем сессий.
Для backend используются чистые функции и подставные зависимости без создания
пользователей, ролей, справочников или состава команд. Исторические скрипты,
которые специально подтверждали наличие ошибок, не переписаны под новый код.

Воспроизводимые команды из корня проекта в отдельном тестовом терминале:

```powershell
$env:LLM_PROVIDER = 'mock'
$env:SESSION_DATABASE_URL = 'sqlite:///:memory:'
$env:DEBUG = 'true'
$env:AGENT_SECRET = 'dmb-agent-local-secret-2026'
Push-Location agent
python -B -m pytest agent/tests -q -p no:cacheprovider
Pop-Location
python -B dmb-backlog/backend/tests/test_requirement_artifact_integrity.py
node --test dmb-backlog/frontend/tests/requirementIntegrity.test.mjs dmb-backlog/frontend/tests/requestPresentation.test.mjs dmb-backlog/frontend/tests/reviewPage.test.mjs dmb-backlog/frontend/tests/agentChatWorkflow.test.mjs dmb-backlog/frontend/tests/agentChatUx.test.mjs
```

Переменные относятся к окружению тестового терминала, production PostgreSQL
не заменяется. Локальный тестовый secret соответствует fixture API-тестов.

## Применение и оставшаяся работа

Добавлена миграция обычной таблицы `requirement_requests` с полями
`revision_history` и `status_history`. При обновлении сервиса миграция должна
быть применена вместе с backend. Во время этой задачи рабочая БД и credentials
не изменялись, сервисы не перезапускались.

Следующий содержательный этап — прогон согласованного набора реальных диалогов
на доступной модели с оценкой сохранности фактов, ложных утверждений, количества
повторных уточнений и приемлемости итогового требования для BA. Последняя
разрешённая проверка внешнего провайдера во время аудита вернула HTTP 401;
нынешние изменения не подтверждают качество ответов этой модели.

Также остаются семантическая проверка достаточности ответа из KB, верификация
дат её документов и постоянные продуктовые метрики принятия/возврата требований.
Изменения проверок качества не следует интерпретировать как полное автоматическое
доказательство корректности бизнес-требования.
