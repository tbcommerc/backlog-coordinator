# Методика приоритизации

> Методологический контракт интегрированной версии; сверено с core и reference
> YAML 02.09.2026. Изменение формул требует решения владельца методики.

Конспект ТЗ v2.0 в объёме, нужном для чтения кода. Решения приняты в ходе четырёх
итераций согласования и не пересматриваются без явной просьбы владельца.

## Что вычисляет агент

Для каждой задачи Единого бэклога:

* **приоритет P1–P5** — многофакторная свёртка;
* **`value_internal`** — финансовый эффект в млн ₽ для приоритизации;
* **`value_external`** — финансовый эффект для отчётности вовне;
* **подсказку** под полем Value: метод, вводные, уверенность, что уточнить.

## Ключевое ограничение

На Стратком и в любой отчётности за пределы трайба эффект **нельзя** подсвечивать
как «экономию времени сотрудников» — это воспринимается как скрытое указание на
сокращение штата. Ограничение введено руководством банка, а не методологом.

Отсюда раздвоение Value:

* `value_internal` — для приоритизации внутри трайба, любая методика;
* `value_external` — только доходный метод, для отчётности вовне.

В коде это закреплено структурно: схема `TaskExternalOut` в
`app/api/schemas.py` физически не содержит поля `value_internal`, поэтому выгрузка
через `GET /backlog/external` не может его отдать даже по ошибке.

## Классификация команд

| Класс | Команды | Метод Value |
|---|---|---|
| Зарабатывающие (Фронт) | IB, Pre-Trade | Доходный |
| Обслуживающие (Бэк) | Core, Finance, Post-Trade (Products & Service), Post-Trade (Finance), Methodology, AI, Delivery, ИТ ЛТ, Проектный офис | Экономия времени |

Единая методика внутри команды — требование согласования: до этого одни команды
считали через доход, другие через экономию времени, третьи брали долю от общего
эффекта, и оценки были несопоставимы.

## Формулы Value

**Зарабатывающие команды:**

```
value_internal = N_сделок_в_год × горизонт × стоимость_сделки × дисконт_фактор
value_external = value_internal
```

**Обслуживающие команды, внутренний контур:**

```
value_internal = N_польз × минут_на_операцию × частота_в_год
                 × стоимость_минуты_ПШЕ × горизонт × дисконт_фактор
```

**Обслуживающие команды, внешний контур** — ex-ante не считается. Значение
`TBD` до запуска периодической атрибуции:

```
R = Факт_дохода_фронта − Σ value_internal инициатив фронта
value_external_команды = R × (Σ value_internal команды / Σ value_internal всех обслуживающих)
value_external_инициативы = value_external_команды × (value_инициативы / Σ value_команды)
```

Вычитание уже объяснённого дохода фронта — защита от double-count: доход,
приписанный инициативам фронта, второй раз не распределяется.

**Регуляторные задачи и RnD/L2P:** `value_internal = 0`. Это не признак
неважности — такие задачи входят в приоритет через правила-овверрайды, а не через
фактор Value.

**Оценка по аналогии.** Если Value не заполнен вручную, агент сначала ищет
похожие задачи, у которых его заполнил человек, и берёт медиану их значений.
Формула применяется только при полном наборе числовых драйверов из постановки
задачи и ответа настроенной модели. Если нет ни подходящих аналогов, ни полного
набора драйверов, агент возвращает `insufficient_data`, а не типовую оценку.
Устройство и оговорки — `docs/VALUE-ANALOGY.md`.

**Диапазон оценки.** Рядом с расчётным Value показываются границы, в которые
истинное значение попадает в 95% случаев. Множители откалиброваны на фактических
ошибках (`scripts/value_calibrate.py`) отдельно для каждого метода и уровня
уверенности, поэтому ширина диапазона и есть численное выражение уверенности.
У ручного значения и у нуля по методике диапазона нет: они точны.

## Величины расчёта

Отдельного справочника констант больше нет. Все величины живут в
`data/references/value_drivers.yaml` рядом с указанием источника и уровня
достоверности, а ставки труда **выводятся** из бюджета ПШЕ и производственного
календаря, а не хранятся отдельно.

| Величина | Значение | Откуда |
|---|---|---|
| Бюджет ПШЕ | 8 000 000 ₽/год | Обоснования Post, восемь строк |
| Часов в рабочем дне | 8 | — |
| Рабочих дней | 247 (2028 — 248) | Производственный календарь |
| Ставка человеко-часа | **выводится**, 4 049 ₽/ч | Бюджет ПШЕ ÷ дни ÷ часы |
| Стоимость минуты ПШЕ | **выводится**, 67.5 ₽/мин | То же |
| Ставка дисконтирования | 24% годовых | ROE Сбера |
| Горизонт | 3 года | Методика |
| Стоимость сделки | **по командам**, у Pre-Trade 27 млн ₽ | Средний доход × средний срок |

**Почему упразднён `constants.yaml`.** В нём стояли числа с пометкой «ТЗ v2.0,
Ф4», но владелец их не задавал, а происхождение подтвердить не удалось: ни ТЗ,
ни handoff в репозиторий не попали. Проверка на обоснованиях команд показала,
что значения расходятся с практикой: стоимость сделки 50 млн против 27 млн у
Pre-Trade, ставка 3000 ₽/час против 4049 ₽/час, которые следуют из бюджета ПШЕ.
Решение владельца от 2026-08-14: файл упразднён, источником истины считается
справочник драйверов.

**Бюджет ПШЕ — 8 млн ₽ в год.** В обоснованиях команд встречаются ровно два
значения без промежуточных: отношение «млн ₽ ÷ доля ПШЕ» даёт 8.00 в восьми
строках и 6.00 в пяти. Словами названо только 6 млн, 8 млн выводится из пары
«= X ПШЕ = Y млн». Решением владельца принято 8 млн как более распространённое.

Следствие: пять расчётов, сделанных командой по 6 млн, агент больше не
воспроизводит и оценивает их примерно на треть выше. Это цена единой ставки —
при двух ставках оценки задач перестают быть сопоставимыми, ради чего методика
и писалась. Расхождение зафиксировано тестом, чтобы оставаться видимым выбором,
а не превратиться в незамеченную ошибку.

**Единой ставки сделки больше нет.** Она разрешается по команде: у Pre-Trade
выводится как средний доход на сделку за средний срок сделки, у остальных
зарабатывающих команд драйвера нет, и доходный метод честно отказывается
считать вместо того, чтобы подставить чужое число. IB в своих обоснованиях
сделки поштучно не оценивает вовсе — он считает от годового дохода и прироста.

## Уровень уверенности

Выставляется автоматически по доле явно заданных вводных:

* **Высокий** — все вводные взяты из атрибутов задачи;
* **Средний** — часть числовых вводных вернула модель с достаточной уверенностью;
* **Низкий** — числовые вводные модели требуют подтверждения или используется
  разрешённая замена справочного драйвера.

Уверенность входит в скор **множителем при факторе F1**, а не отдельным
слагаемым, и показывается в подсказке.

**Почему множителем.** Уверенность — не самостоятельное свойство задачи, а
свойство того, насколько хорошо мы знаем её Value. Слагаемым она вела себя
неверно: задача с Value 0.1 млн ₽ и высокой уверенностью получала прибавку
больше, чем задача с Value 3000 млн ₽ и низкой. Это та же природа ошибки, что
была у фактора C/V, — величина, выведенная из другой, входила в модель
отдельным членом. Множителем ненадёжная оценка ослабляет собственный вклад, а
не добавляет задаче балл со стороны.

Решение владельца от 2026-08-21. Вес бывшего F9 (0.03) передан F1: 0.31 → 0.34.

## Cost и C/V

```
Cost_₽ = Оценка_трудозатрат_ч/д × 8 ч × 3 000 ₽/ч
C/V    = Cost_₽ / value_internal_₽
```

Меньше — лучше. Показатель считается и показывается в карточке задачи, но
**в приоритет не входит**: он выводится из Value и трудозатрат, которые уже
учтены факторами F1 и F4. Причина исключения — ниже.

Если трудозатраты не заполнены или Value равен нулю, отношение не определено и
остаётся `None` — «не посчитано» и «посчитано и вышло нейтрально» в коде
различаются.

## Семь факторов

`Priority Score = Σ (wᵢ × Sᵢ × mᵢ)`, где `Sᵢ ∈ [0, 1]`, `Σ wᵢ = 1`, а `mᵢ` —
множитель, отличный от единицы только у F1.

| Код | Фактор | Вес | Нормализация |
|---|---|---:|---|
| F1 | Value (внутренний) × уверенность | 0.34 | Логарифмическая по максимуму, умноженная на уверенность в оценке |
| F2 | Уровень бизнес-заказчика | 0.15 | Дискретно 0.2 / 0.5 / 0.8 / 1.0 |
| F3 | Срочность | 0.15 | 1.0 при ≤30 дней, 0.7 ≤90, 0.4 ≤180, иначе 0.1 |
| F4 | Ресурсоёмкость | 0.17 | Обратная: 1.0 при <5 ч/д, 0.3 при >50 |
| F5 | Стратегическое соответствие | 0.10 | Балл 1–10 по рубрике → 0.1–1.0 |
| F6 | Зависимость от команд | 0.05 | 1.0 − штрафы по типу связи, пол 0.2 |
| F7 | Тип задачи | 0.04 | Дискретно из справочника |

Коды идут подряд, F1–F7. До версии 4 нумерация шла от ТЗ и сохраняла дыру на
месте исключённого C/V; дыра ничего не обозначала, а последний фактор носил при
семи факторах номер F8. Решение владельца от 2026-08-26: коды сброшены,
соответствие прежним записям восстанавливается по версии методики в аудите.

**Почему C/V не фактор.** `C/V = Cost / Value`, а `Cost` — трудозатраты,
умноженные на константу. То есть показатель целиком выводится из двух величин,
которые уже входят в модель через F1 (Value) и F4 (ресурсоёмкость), и не
приносит ни одной новой вводной. Вред был не теоретический: объявленные веса не
соответствовали действующим. Регрессия C/V на F1 и F4 даёт коэффициенты +0.29 и
+0.21, поэтому реальное влияние Value составляло 0.15 + 0.25×0.29 ≈ 0.22, а
трудозатрат — 0.08 + 0.25×0.21 ≈ 0.13. Методолог настраивал одни числа,
работали другие.

Вес 0.25 возвращён тем двум факторам, которые C/V дублировал, в пропорции
измеренного влияния: F1 0.15 → 0.31, F4 0.08 → 0.17. На реальном бэклоге это
уменьшило скученность: доля задач в P3 упала с 83% до 62%, потому что C/V был
вырожден в нейтральный балл у 94.5% задач и четверть веса работала константой.

F1 нормализуется относительно всего бэклога, поэтому пересчёт одной задачи
всё равно читает агрегаты по остальным — иначе задача получила бы балл в другой
шкале, чем соседи.

Логарифм в F1 принципиален: эффекты в бэклоге различаются на два порядка, и
линейная шкала схлопнула бы все задачи кроме одной-двух в ноль.

Просроченная задача получает по F3 максимальный балл: она не может быть менее
срочной, чем задача со сроком завтра.

F5 и F6 оцениваются внутренними субагентами по рубрике: они отвечают на критерии,
балл считает код, оценка хранится с обоснованием и источниками. По ТЗ эти
значения приходили от внешнего Strategy Decomposer одним числом — устройство и
причина переноса описаны в `docs/FACTOR-ASSESSMENT.md`.

## Правила-овверрайды

Действуют вне зависимости от скора и только **повышают** приоритет.

Дефолтный набор:

| Правило | Условие | Результат |
|---|---|---|
| `regulatory_deadline` | Регуляторная задача, срок ≤ 90 дней | P1 |
| `blocking_flag` | Признак блокирующей | P1 |
| `tribe_leader_customer` | Заказчик уровня лидера трайба | Минимум P2 |
| `tz_quarterly_goal_deadline` | Квартальная цель, срок ≤ 90 дней | P1, **выключено** |

Почему последнее выключено — `docs/DEVIATIONS-FROM-TZ.md`, раздел 1.

## Шкала приоритетов

| Приоритет | Скор |
|---|---|
| P1 «Критично» | ≥ 0.8 или сработал овверрайд |
| P2 «Высокий» | 0.6 ≤ скор < 0.8 |
| P3 «Средний» | 0.4 ≤ скор < 0.6 |
| P4 «Низкий» | 0.2 ≤ скор < 0.4 |
| P5 «Отложено» | < 0.2 |

Как эти пороги легли на реальные данные — `docs/CALIBRATION-FINDINGS.md`.

## Триггеры пересчёта

* создание задачи;
* изменение ключевых атрибутов (название, тип, команда, трудозатраты, срок, заказчик);
* изменение любого справочника.

Пересчёт `value_external` обслуживающих команд — только по инициативе методолога
или финансиста, никогда автоматически.

## Как методика применяется в ПРОМ-варианте

Всё выше описано для полного прогона по бэклогу. В Backlog coordinator агент
работает без доступа к базе: атрибуты одной задачи приходят в запросе. Методика
при этом та же — расчёт идёт через то же ядро, — но два места опираются на
остальной бэклог и потому едут в зашитом слепке:

* **аналоги** для оценки Value;
* **максимум Value** для логарифмической шкалы фактора F1.

Слепок обновляется отдельно от агента, с согласованной периодичностью, и его
версия возвращается в каждом ответе. Контракт — `docs/COORDINATOR-CONTRACT.md`.

Одинаковые атрибуты обязаны давать одинаковую цифру, поэтому совпадение
проверяется **до** обращения к модели: она недетерминирована, и два вызова с
одним промптом могли бы выбрать разные наборы драйверов.

## Роль языковой модели

Модель решает ровно две задачи: определяет тип задачи по описанию, когда явных
атрибутов не хватает, и помогает сформулировать подсказку. **Value, приоритет и
C/V она не считает.**

Это требование воспроизводимости, а не архитектурная придирка. Если бы числа
считала модель, два прогона одного бэклога давали бы разные приоритеты, и
методику нельзя было бы защитить перед методологом как объективную.

По той же причине мок-провайдер детерминирован и не выдумывает числовых вводных:
отсутствующая вводная должна становиться вопросом автору задачи и пониженной
уверенностью, а не правдоподобной подстановкой.
