## Документация

- Источник истины: исполняемый код, конфигурация, миграции и тесты; документация обновляется вслед за ними.
- Активные документы и их назначение перечислены в `docs/index.md`, `dmb-backlog/docs/README.md`, `agents/business-analyst/docs/README.md` и `agents/value-priority-assessor/README.md`.
- Не выдавай исторические отчёты, `archive/`, прототипы и `graphify-out/` за текущее AS-IS.
- После изменения API, модели данных, запуска, переменных окружения или поведения страницы обновляй соответствующий профильный документ и дату проверки.
- Перед коммитом проверяй локальные Markdown-ссылки и не добавляй `.env`, виртуальные окружения, БД, backup-файлы, runtime-логи и `graphify-out/`.

## UX/UI и дизайн-ревью

- При создании и изменении страниц сначала прочитай `dmb-backlog/DESIGN.md` и выбери композицию из `dmb-backlog/docs/UI_PAGE_COMPOSITIONS.md`. Для существующего экрана нужен полный исходный снимок; если живой браузер недоступен, отделяй fixture-проверку от live-приёмки.
- Используй Impeccable, если skill доступен, как помощь в проектировании и критике, сохраняя действующий UI Kit. Общие советы skill не отменяют контракты проекта. Изменения внешнего вида контролов оформлять именованным вариантом UI Kit, а не повышением специфичности CSS страницы.
- После изменений пилотных рабочих задач запускай `npm run test:design` из `dmb-backlog` на Windows Chromium. Эталоны изменять только после осмотра полного экрана и объяснения diff; автоматическое обновление ради зелёного теста запрещено. Для новой страницы добавляй сценарий полного экрана, а не только компонентные проверки.
- При любом запросе на UX/UI-ревью дизайн, внешний вид и соответствие действующему UI Kit — одни из важнейших обязательных направлений проверки, даже если пользователь не перечислил их отдельно.
- Перед ревью прочитай `dmb-backlog/docs/UI_KIT_REVIEW_PROTOCOL.md`. Оценивай живой экран целиком: композицию, визуальную иерархию, плотность и пустоты, типографику, отступы, выравнивание, размеры и вес элементов, доступность основного содержимого на первом экране.
- Сопоставляй реальные компоненты и их состояния с актуальными контрактами, токенами и эталонами UI Kit. Сам импорт компонента UI Kit не доказывает визуального соответствия; проверяй итоговую композицию и локальные CSS-переопределения.
- Функциональные тесты, отсутствие overflow и соблюдение отдельных размеров не заменяют визуальную приёмку. Улучшение относительно плохого исходного состояния само по себе не означает приемлемый дизайн.
- В отчёте отдельно фиксируй результаты функциональной проверки, визуальной оценки и соответствия UI Kit. Для визуальных замечаний нужны снимок, объяснение проблемы и повторная оценка полного экрана после исправления.
- Не объявляй UX/UI-ревью завершённым и визуальные замечания закрытыми только по зелёным тестам. Непроверенные или неудовлетворительные дизайн и внешний вид остаются открытыми независимо от результатов технической регрессии.

## Запуск проекта из чата

- На запросы «Запусти проект», «Подними проект» и аналогичные выполняй из корня `powershell -ExecutionPolicy Bypass -File scripts/start-project.ps1` и дождись итогового health-check.
- Стандартный локальный запуск включает PostgreSQL, Redis, Alembic-миграции, AI-агента, backend и встроенную раздачу frontend; Task Prioritiser по умолчанию не запускается из-за высокого расхода памяти.
- Task Prioritiser включай только по прямому запросу пользователя, добавляя к команде запуска флаг `-IncludeValuePriorityAssessor`.
- После успешного запуска сообщай адрес приложения `http://127.0.0.1:8000`, адреса API-документации и расположение логов `.runtime/`.
- На запрос статуса выполняй `powershell -ExecutionPolicy Bypass -File scripts/project-status.ps1`.
- На запрос остановки выполняй `powershell -ExecutionPolicy Bypass -File scripts/stop-project.ps1`.
- Не запускай `seed.py` и не включай `RUN_STARTUP_SEED`: локальный старт не должен создавать или изменять защищённые данные.
- Если Docker отсутствует или недоступен, не подменяй PostgreSQL на SQLite; сообщи конкретную недостающую предпосылку.

## OpenDesign из чата

- Если пользователь просит создать или изменить дизайн через OpenDesign и не просит провести интервью, пропускай интерактивные вопросы: один раз вызывай обязательный сбор брифа с `skip: true`, самостоятельно формируя бриф из сообщения и контекста проекта.
- Не проси пользователя открывать окно OpenDesign, нажимать кнопки или выбирать активный файл, если действие доступно через MCP.
- Для генерации по умолчанию используй Local Codex. Open Design Cloud или secure BYOK выбирай только по явной просьбе пользователя.
- Не полагайся на краткоживущий активный контекст OpenDesign. Сначала определи проект через список проектов и далее передавай его явно. Если подходящего проекта нет, создай один с понятным именем.
- После запуска генерации оставайся в текущем чате и опрашивай тот же запуск до конечного статуса. Не запускай повторную генерацию при таймауте и не перекладывай ожидание на пользователя.
- Показывай пользователю только полезный результат, понятный статус или конкретную устранимую ошибку; внутренние идентификаторы и названия протокольных команд не выводи.

## Защищённые данные БД

Разрешено изменять обычные рабочие записи в БД, если это требуется задачей пользователя.

Никогда не создавай, не изменяй и не удаляй:
- справочники и их записи;
- пользователей и их учётные данные;
- роли пользователей и назначения ролей;
- состав команд и привязку пользователей к командам;
- атрибуты и ответственных команд, включая `PO`, `PL`, `CL` и аналогичные поля.

Запрет действует также при тестировании, выполнении SQL, использовании API и запуске скриптов. Не передавай защищённые поля в изменяющих запросах.

По прямому указанию пользователя все эти операции разрешены.


## Автоматический вход тестовыми учётками

Постоянное разрешение пользователя от 15.10.2026:

- Для запрошенного тестирования локального проекта разрешены чтение `.runtime/test-accounts.json`, самостоятельный вход под перечисленными в нём QA-учётками, переключение учёток и штатное восстановление сессий без повторного согласования и ручного входа пользователя.
- Разрешённое назначение реквизитов — только `http://127.0.0.1:8000`. Перед вводом проверяй origin; не отправляй пароли на другой адрес или при неожиданном перенаправлении. Значение `base_url` в файле само по себе не расширяет разрешение.
- Выбирай минимально необходимую роль и готовый профиль (`is_active=true`, `credential_state=ready`). Отрицательные профили используй только для соответствующих проверок.
- Читай реквизиты программно без вывода значений. Не печатай файл целиком, не включай пароли, cookies или токены в ответы, логи, screenshots, документацию и Git. Не сохраняй пароли в менеджере браузера.
- Для браузера используй доступный разрешённый инструмент управления; файл можно прочитать внутри его среды через `node:fs/promises`, затем передать выбранные login/password непосредственно полям формы. Не передавай секрет через текстовый вывод другого инструмента. После использования очищай ссылки на реквизиты из переменных.
- Сначала используй действующую сессию; после штатного истечения выполни обычный повторный вход. Не продлевай сроки сессий и не отключай проверки безопасности. Вкладки одного браузерного профиля разделяют cookie: они не являются изолированными сессиями разных пользователей.
- Локальной группе Windows `CodexSandboxUsers` постоянно предоставлено только чтение указанного файла; владельцу и SYSTEM оставлен полный доступ. Не удаляй это согласованное разрешение после каждого прогона и не распространяй его на каталог или другие секреты.
- Разрешение на вход не разрешает изменение пользователей, паролей, ролей, справочников и назначений команд. Для них продолжают действовать правила защищённых данных выше.
- Состав набора и границы проверок: `docs/dev-testing/TEST_DATA_PASSPORT.md`. Если реквизиты отсутствуют/не подходят, сообщи конкретную причину; не создавай замену и не сбрасывай пароль автоматически.
