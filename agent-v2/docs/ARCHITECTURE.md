# Архитектура Assistant V2

> AS-IS проверено по коду и изолированным тестам 09.10.2026.

Assistant V2 — файловый fork `agent/` с Python package `agent_v2`. Он сохраняет
проверенные компоненты V1 (guardrails, session store, LLM adapter, KB,
оркестрацию и composer), но имеет отдельные entrypoint, namespace, конфигурацию,
порт, secret и БД.

LLM-клиент передаёт собственный User-Agent. Для OpenCode контекст API-сессии
задаёт стабильный непрозрачный `x-opencode-session` через ContextVar, включая
потокового worker. Другим провайдерам этот заголовок не передаётся.
Незавершённый JSON (`finish_reason=length`) считается ошибкой, а не результатом.

## Поток запроса

```text
браузер #/agent-v2
  -> DMB /api/v2/agent (JWT, pilot и BA/PO role)
  -> Assistant V2 /api/agent-v2 (X-Agent-Secret)
  -> V2Orchestrator
  -> отдельный SessionStore
```

DMB gateway удаляет присланные клиентом `user_id`, `operator_role` и context,
после чего строит их из текущего аутентифицированного пользователя. Связанный
Task или RequirementRequest сначала проверяется правилами доступа DMB и только
затем передаётся V2 как ограниченный snapshot полей `title` и `description`.
Поиск для привязки также фильтруется теми же object-level правилами.

## Режимы и артефакты

`assignment_capture` собирает происхождение, поручение, цель, результат, scope,
инициатора, срок и следующий шаг. После итогового подтверждения создаётся
`AssignmentPassport`. Handoff сохраняет паспорт и переносит подтверждённые
слоты с provenance в `requirement_copilot`.

`requirement_copilot` собирает проблему, цель, AS-IS/TO-BE, scope, роли,
сценарии, правила, критерии, зависимости и риски. Результат —
`BusinessRequirementDraftV2`, совместимый с базовым `RequirementDraft` V1 и
расширенный origin, linked object, scope и V2 quality.

Пользовательский контур `requirement_copilot` является document-first:
структурный документ расположен в центре, слева доступны структура, источники
и версии, справа — детерминированные замечания и контекстный co-pilot. Импорт
готового требования проходит через отдельный детерминированный parser: он
сопоставляет только известные заголовки, сохраняет фрагменты как provenance и
создаёт неполную ревизию, не маскируя отсутствующие разделы.

Стартовый экран разводит три намерения пользователя: проверку готового
требования, создание требования с нуля и быструю фиксацию поручения. После
открытия документа интерфейс ведёт аналитика по этапам «материал → структура →
проверка → review». Основные разделы открыты сразу, дополнительные свёрнуты;
контроль качества сначала показывает пять приоритетных замечаний, а остальные —
по запросу. Быстрые команды co-pilot запускают проверку критериев,
противоречий или рекомендуют следующий шаг, не подменяя решение аналитика.

Каждая ревизия получает canonical fingerprint и сохраняется целиком. Readiness
считает Python-policy, а не модель. Для обязательных фактов проверяется
provenance; открытый критический конфликт блокирует переход.

Runtime prompt V2 не использует продуктовую роль V1 «интервьюер
бизнес-заказчика»: сначала исполняется явная команда BA/PO, затем формируются
замечания и предлагаемая правка; вопрос допустим только при критической нехватке
факта. Ответ модели остаётся строгим JSON и проходит серверную валидацию до
применения к slots.

## Интеграция с DMB

Legacy-путь подтверждённого V2 requirement создаёт или обновляет существующий
`RequirementRequest`. `agent_session_id` имеет namespace `v2:`; отдельная
review-очередь и новая пользовательская/ролевая модель не создаются. Ошибка
commit после подтверждения агента компенсируется `cancel-review`.

`ProposedPatch` строится только по allowlist полей snapshot. Защищённые поля
владельца, команды, роли, пользователя и назначения исключаются. Решение по
операциям сохраняется как `human_decision`, но код применения patch в DMB
отсутствует.

Новый документный контур публикует конкретную редакцию БТ отдельным предметом
человеческого ревью в DMB. Он не вызывает legacy `send-for-review`, не создаёт
пользовательский запрос или Task ради согласования и не блокирует рабочую
редакцию. Авторизованные Request/Task по-прежнему передаются snapshot. Gateway
повторно проверяет доступ; агент сам не читает и не изменяет DMB.

## Написание и независимое AI-ревью

`v2/document_workspace.py` реализует действия над документом отдельно от
интервью: review, draft, propose_change, apply_proposal, resolve_finding,
add_source и next_revision. API использует блокировки, optimistic version и
receipts SessionStore. Ключ идемпотентности привязан к actor и телу операции;
повтор другого тела с тем же ключом запрещён.

Review вызывает детерминированный reviewer и отдельный structured LLM prompt.
Модель получает документ, разрешённый контекст и текстовые источники как
недоверенные данные. Поля, ссылки и точные цитаты результата проверяются на
сервере. Проверка записывает отчёт и замечания вне документа: текст, fingerprint
и история редакций остаются прежними. При недоступной модели или некорректном
ответе фиксируется `degraded` с результатом только детерминированных правил.

Draft/propose_change используют отдельный prompt существующего провайдера.
Результат — предложения по allowlist полей с before/after, причиной и
источниками. Модель не применяет их. Аналитик выбирает операции; сервер сверяет
hash документа, sources, linked snapshot и before каждого поля, затем сохраняет
одну новую редакцию. Стабильные ID документа и BR-элементов, неизвестные поля и
невыбранные разделы сохраняются. Стандартный `ProposedPatch` для внешнего объекта
остаётся другим механизмом и не получает write-клиент.

Оригиналы источников, включая неизвестные разделы импорта, сохраняются целиком
в state JSON как неизменяемые версии с адресами фрагментов. Точность извлечения
не означает подтверждение бизнес-факта. Отчёты и предложения привязаны к
`canonical_fingerprint(document_sources)` и fingerprint связанного snapshot.
Новый источник делает прежнюю проверку и предложения устаревшими. Решение по
замечанию хранит автора, причину и проверенную редакцию; отложенное критичное
замечание не означает устранение дефекта.

Существующие сессии читаются с пустыми коллекциями нового контура. Их прежняя
редакция не меняется при чтении/review: недостающий artifact ID хранится в
envelope и включается в следующую созданную редакцию. Команды «проверь»,
«напиши», «предложи», «перепиши» и «улучши» направляются в документный контур.
Прочие аналитические ответы в существующем документе больше не подавляются
веткой «нет новых изменений»; ложное подтверждение невыполненной правки
по-прежнему блокируется.

## Изоляция

- `agent/` не импортирует `agent_v2`;
- `agent-v2/` не импортирует package `agent`;
- `assistant-v2/` не импортируется новым контуром;
- V2 gateway не регистрируется при выключенном feature flag или kill switch;
- отказ V2 не блокирует readiness основного DMB.
