Master-Detail Design Pattern

Одна и та же сущность задача имеет разные «проекции» в зависимости от контекста использования. Мини-карточка — «быстрый взгляд», детальная — «полный паспорт с редактированием». Связь между ними — через единый компонент <TaskCard mode="mini|full">.

MOEX API Compliance + тег
UX/UI rationale · Пара №1

Принцип Progressive Disclosure: мини-карточка содержит только то, что нужно для сканирования канбан-доски (8 атрибутов). Полная форма открывается в модале/drawer при клике.

Разделение на "read" vs "write":

  • Мини — только для чтения + drag&drop. Быстрое восприятие периферийным зрением.
  • Детальная — все 24 поля в режиме редактирования (input, select, textarea). Каждое поле интерактивно.

Цветовые секции в детальной форме:

  • Фиолетовая плашка — метрики. Выделяет "числовую зону", где чаще всего ошибаются при вводе.
  • Розовая плашка — множественные статусы. Критично: один статус для разных аудиторий. Визуально предупреждает PO: "Проверь все 5 перед встречей".

Множественные статусы — это уникальная особенность DMB: задача одновременно может быть "Зелёная для директорской", но "В рисках для ДИД". Каждый статус виден своей аудитории в своих отчётах.

C/V — disabled field: рассчитывается автоматически (фин. эффект / трудозатраты ₽). Пользователь не может редактировать напрямую — это защита от "рисования" метрик.

Компромисс: детальная форма длинная (~480px со скроллом). Это OK, т.к. редактирование — не частая операция (2-3 раза в неделю на задачу).

UX/UI rationale · Пара №2

Гибрид "таблица + карточка": list row даёт плотность таблицы (12+ строк на экран), но с визуальными якорями карточки (цветная полоса, бейджи, прогресс-бар).

Ключевая фича — checkbox: массовые операции ("Перевести 10 задач на холд", "Сменить статус ДИД у 5 задач"). Это то, чего не умеет обычная карточка.

Статус ДИД прямо в row: PO видит "что горит для директорской" без открытия карточки. Это главный операционный вопрос на день.

Side panel vs modal: slide-over справа оставляет контекст списка видимым. Пользователь не "теряется" в бэклоге при редактировании. Это паттерн "Continuous context" (Linear, Notion).

Табы внутри panel: 24 поля не помещаются без скролла → разбиваем на 5 логических секций. Пользователь видит 4-5 полей одновременно, а не 24. Chunking по Miller's Law (7±2).

Bulk actions bar: появляется только при выборе, не занимает места в обычном состоянии. Это Progressive Disclosure в действии.

Служебная плашка снизу: системные поля (создана/обновлена/заказчик) отделены от редактируемых — user не может случайно их изменить.

Описание

Реализовать двусторонний обмен данными между торговой платформой и compliance-движком для блокировки ордеров до исполнения.

MOEX API Compliance
UX/UI rationale · Пара №3

User story: "Как CIO, я хочу увидеть на директорской 20 задач за 3 минуты и понять какие 'горят'."

Mini card = "светофор":

  • Цветная полоска сверху + цветной индикатор — преаттентивный сигнал "всё хорошо / всё плохо". Директор видит статус за 100мс.
  • Только 4 цифры в сетке 3×1: Срок, Прогресс, Эффект. Всё остальное — шум для этого сценария.
  • Высота карточки ~180px → на экране помещается 6-8 задач в grid 3×2. Это и есть "один взгляд = весь статус".

Project Passport (full) — printable artefact:

  • Формат A4 для раздачи в печатном виде на директорской (да, банки всё ещё печатают).
  • Dark header = VIP-статус, отделяет ключевые проекты от рутинных.
  • Все 5 статусов в одной таблице — уникальная фича. Директор видит: "для меня задача зелёная, но для ДИД — в рисках". Это предотвращает ситуации "а почему мне сказали другое".

Read-only: passport не редактируется — это отчёт. Редактирование через отдельную форму. Разделение "presentation layer" и "edit layer" = защита от случайных изменений перед встречей.

Печать-кнопка: открывает clean PDF без UI-элементов, с логотипом банка.

UX/UI rationale · Пара №4

Контекст использования: уведомления PO, email-дайджест "Что горит сегодня", push-уведомления.

Mini — "сигнал тревоги":

  • Красный banner + border-2 + pulse-анимация. Должна "кричать".
  • Блокер в 1 строку (11 слов максимум) — пользователь решает за 2 сек: открыть или нет.
  • Фин. риск — главная цифра для CIO. "-8.2 млн" работает лучше, чем "-20 п.п. от графика".
  • Кнопка CTA прямо внутри — действие без перехода.

Full — "досье для решения":

  • 4-квадрантная матрица рисков (срок/прогресс/фин/зависимости) — полная картина за 5 сек.
  • Блокер в тёмной плашке + ответственный + контакт. Решение: "кому звонить прямо сейчас".
  • Все 5 статусов одновременно — PO видит рассинхронизацию аудиторий ("Почему для директорской красная, а внутренний рабочий?").
  • 3 CTA-кнопки: эскалация (главная), созвон, инцидент. Это разные сценарии, не нужно выбирать из меню.

Что НЕ показываем: описание, трудозатраты, C/V, теги. Это "пожарная" карточка — не время для аналитики.

UX/UI rationale · Пара №5

User story: "Как Leader Трайба, я хочу быстро отобрать задачи с высоким Value для защиты бюджета на квартал."

Mini — "Value-карточка в списке":

  • C/V как hero-элемент (3xl). Это главная метрика портфеля — должна быть видна сразу.
  • Фиолетовый градиент header — отличает Value-карточки от обычных (белых).
  • Только 4 ключевых цифры: C/V, затраты, эффект, прогресс. Этого достаточно для сортировки и отбора.

Full — "Financial Passport":

  • Hero с S/V 4xl — визуальный якорь, первое что видит ЛТ.
  • 3-метрический блок (дни/руб/эффект) — для CFO и фин. контролёров.
  • Payback timeline с точкой безубыточности — уникальная визуализация "когда начнёт окупаться".
  • Позиция в портфеле — "#3 по Value" говорит ЛТ "это одна из наших главных ставок".
  • CTA → переход в аналитику ЛТ (дэшборд с графиками).

Что опущено: статусы (кроме прогресса), assignees, теги, описание. Это финансовый документ, а не операционный.

Почему отдельная пара (не совмещать с парой №1): аудитория другая (ЛТ + CFO, а не команда). Им не нужны технические детали — им нужен ROI и payback.

Итоговая стратегия реализации

Рекомендую реализовать как единую компонентную систему, а не как 10 отдельных UI.

API компонент
<TaskCard
variant="kanban|list|report|risk|value"
mode="mini|full"
taskId={id}
/>
Рендеринг
Каждый variant определяет набор атрибутов. mode — мини или детальная форма. Данные — из единого API.
Переход mini ↔ full: клик по мини-карточке открывает модал/drawer/side-panel в зависимости от variant (для kanban — drawer, для list — side-panel, для report — fullscreen modal).
Консистентность данных: все 24 атрибута всегда живут в одной модели, но UI-слои показывают разные "срезы". Это гарантия, что "задача везде одна и та же".
Множественные статусы — ключевая архитектурная особенность: хранятся как отдельная таблица task_statuses (task_id, audience, status, updated_at). Это фундамент для отчётов по разным аудиториям.
Приоритет внедрения: Пара 1 (Канбан) → Пара 2 (Бэклог) → Пара 3 (Отчёты) → Пара 4 (Риски) → Пара 5 (Value). Это порядок частоты использования.
