# Бэклог для бизнес-заказчиков ДИД

Проверено по коду, тестам и работающей странице 04.09.2026. Миграция
`a9246d1c7e30` применена в локальной PostgreSQL с разрешения владельца продукта;
backend перезапущен. Справочник клиентов ДИД создан пустым, записи не добавлялись.

## Страница и правила

Маршрут: `#/reports/detail?r=did-backlog`, раздел «Статусы для встреч».
Компонент: `frontend/js/components/didBacklog.js`; стили: `frontend/css/did-backlog.css`.

Отбор серверный, не редактируется настройками пользовательских отчётов:

- тип «Квартальная/годовая цель» или «AD-HOC»;
- срок содержит выбранный квартал; распознаются `1Q 2027`, `Q1 2027`, список
  полных квартальных значений через запятую;
- годовой срок `Y2026` / `2026` относится к IV кварталу;
- исключены удалённые задачи и статусы «Холд», «Отклонена», «Не актуальна»;
- применяется общая политика видимости задач текущего пользователя.

**Открытый вопрос:** правило BR-02 исходных бизнес-требований включает годовые
сроки в IV квартал, тогда как п. 4.2, описание реализации и T-04 исключают их.
Код следует BR-02 до уточнения владельцем продукта. Аналогично явное BR-03
имеет приоритет над противоречащим ему T-06 о независимости от статуса.

Девять колонок: клиент ДИД, команда, проект, задача, тип, подразделение заказчика,
контактное лицо, срок, финансовый эффект. Трудозатраты, прогресс, исполнитель и жизненный статус не выводятся.
Финансовый эффект уже хранится в млн рублей; повторного деления нет.

Пробелами считаются `NULL`, пустая строка и `(без названия)`. Ноль заполнен.
Янтарные ячейки содержат «не заполнено»; сводка отражает видимые после фильтрации
строки. Подвал показывает число видимых строк относительно квартальной выборки.
Клик или Enter на строке открывает штатную карточку задачи.

У каждой колонки есть сортировка и мультифильтр с поиском заполненных значений.
Пустые значения при сортировке всегда последние. По умолчанию — порядок
справочника клиентов, внутри клиента убывание эффекта; без клиента — в конце.
Ширины — проценты, сумма 100%, минимум 4%; изменение компенсируется соседней
колонкой справа. Доступны перетаскивание, клавиатура и возврат исходных ширин.

## Настройки и выгрузка

Настройки хранятся в `user_report_prefs`, уникально по `(user_id, report_key)`.
Пользователь определяется серверным сеансом; подмена `user_id` в команде
отклоняется. JSON содержит `quarter`, `filters`, `sortField`, `sortDir`, `widths`.
Неизвестные настройки игнорируются, неверные ширины заменяются исходными.
Сохранения в одной странице выполняются последовательно, сервер использует
атомарный upsert. При недоступности хранилища страница остаётся работоспособной.
Сброс удаляет только настройки текущего пользователя для этого отчёта.

По умолчанию выбирается текущий квартал. Он доступен даже без задач.
Недоступный сохранённый квартал заменяется текущим. Смена квартала очищает
фильтры и сортировку, сохраняя ширины.

Excel и PDF формируются сервером после повторной проверки прав и выборки.
Переданные идентификаторы определяют порядок видимых строк; несовпадение
состава с актуальной выборкой вызывает 409 и предложение обновить отчёт.
Excel — настоящий XLSX с числовым эффектом до десятых, янтарной заливкой
пробелов и четырьмя строками метаданных. Тексты записываются как строки,
а не формулы. PDF — безопасный HTML для печати браузером: A4, альбомная
ориентация, повторяемая шапка и сохранение заливки. Пустая выгрузка разрешена.

## Новые поля и справочники

- `tasks.did_client_group_id` → `did_client_groups`;
- существующий `tasks.business_customer_id` → `business_customers` — контактное лицо заказчика;
- подразделение — существующий `tasks.department_id`;
- новый справочник контактных лиц не создаётся: уточнение владельца продукта от 04.09.2026 имеет приоритет над описанием реализации.

Поля доступны в создании и карточке задачи, настраиваемых колонках общего и
командного бэклога, быстром и массовом редактировании, импорте CSV/Excel.
В карточке и быстром редактировании контакт выбирается сначала из подразделения,
при необходимости раскрывается полный список. В массовом редактировании
доступен общий список, поскольку задачи могут принадлежать разным подразделениям.
Импорт принимает названия и коды клиента ДИД и ФИО контакта. Неизвестное или
неоднозначное значение оставляет поле пустым с предупреждением, не создаёт
справочную запись. При совпадении ФИО учитывается подразделение строки.

Администратору с `admin=full` доступен новый справочник «Клиенты ДИД» в
«Администрирование → Справочники»: добавление, переименование, деактивация и
восстановление. Изменение требует совпадения исходного снимка, чтобы не
перезаписать чужое изменение. Существующие «Бизнес-заказчики» ведутся прежним
административным интерфейсом, с имеющейся привязкой к подразделению.

Миграция создаёт только структуру клиента ДИД и персональных настроек.
Восемь клиентов из требований не добавляются автоматически. Существующие записи
«Бизнес-заказчики» не преобразуются и не переименовываются.

### Маппинг клиента ДИД и подразделения

Проверка существующих справочников выполнена read-only 04.09.2026. Утверждённого
маппинга и автоматического заполнения клиента ДИД по подразделению в коде нет.
По названиям совпадают ЦУП, ФИНАНСЫ, РИСКИ, IB, ЦР. УСИ → «УСИ (РГ ППРБ)» —
предположение, требующее подтверждения. Для OPS и «ВНУТР. (ПЛАТФОРМА)» прямого
совпадения нет. L2P, M&A, РЕГ. ДИРЕКТОРЫ, УРК, ЦИ пока не сопоставлены.

## Проверки

- `backend/tests/test_did_backlog.py`: запуск через `pytest --noconftest`, без
  общей seed-фикстуры. Проверяются правила SQL-отбора на CTE, нормализация сроков,
