# DMB Backlog — Спецификация системы

**Версия:** 3.2  
**Дата:** 2026-07-25  
**Статус:** Актуальная

---

## 1. Общее описание

DMB Backlog — корпоративная система управления портфелем задач для подразделения Digital & Mobile Banking (DMB). Система обеспечивает полный жизненный цикл задачи от поступления до выполнения, включая:

- Централизованное управление задачами платформы (бэклог DMB)
- Управление бэклогом отдельных команд
- Канбан-доска с 13 статусами полного workflow
- Портал бизнес-заказчика (просмотр и создание задач)
- Аналитика для Tribe Leader и PO/PL
- Формирование статус-отчётов для встреч
- Ролевая модель доступа (6 ролей с гранулярными правами на 7 разделов)
- Уведомления, трекинг рисков, аудит действий
- Администрирование: пользователи, команды, роли, справочники, шаблоны уведомлений, пользовательские отчёты

```
                                                                                                    ├── ОТКЛОНЕНА
                                                                                                    ├── НЕ АКТУАЛЬНА
                                                                                                    ├── ХОЛД
                                                                                                    └── ЭСКАЛАЦИЯ НА ЛТ
```

**Группы статусов:**
| Группа | Статусы | Описание |
|--------|---------|----------|
| Backlog | НОВАЯ ЗАДАЧА, НАЗНАЧЕНА КОМАНДА, СБОР ТРЕБОВАНИЙ, ПРОВЕРКА ТРЕБОВАНИЙ, УТОЧНЕНИЕ ТРЕБОВАНИЙ, ЭКСПРЕСС-ОЦЕНКА, ПРИНЯТИЕ РЕШЕНИЯ | Предварительные фазы |

## 4. Жизненный цикл задачи

### 4.1 Описание статусов

| Статус | Код | Группа | Описание |

### 4.2 Создание задачи

Задача создаётся через `POST /api/v1/tasks` с обязательными полями `title`, `team_id`, `priority_id`.

**Процесс создания:**
1. Валидация обязательных полей на клиенте (подсветка красным при пустых)
2. Валидация Pydantic-схем на сервере (title min_length=1, team_id/priority_id required)
3. Установка `status_id = 1` (НОВАЯ ЗАДАЧА) если не указано
4. Установка `created_by` из JWT-токена
5. Авторассчёт `cv = financial_effect / effort_rub` (если оба заполнены и effort_rub > 0)
6. Авторассчёт `ice_score = (ice_impact × ice_confidence × ice_ease) / 10` (если все три заполнены)
7. Запись в `task_history` (все обязательные + заполненные опциональные поля)
8. Запись в `audit_log` (action=create, entity_type=task)
9. Возврат объекта задачи (201 Created)
10. Тост «Задача создана» + обновление таблицы на клиенте

**Доступ к созданию:**
- Бэклог DMB (ЛТ, Администратор): `backlog_dmb >= read_write`
- Бэклог команды (PO, IT PL): `backlog_team >= write_own`
- Портал бизнес-заказчика: чат-интерфейс (POST /api/v1/tasks)

### 4.3 Блокировка задач при редактировании

Для предотвращения параллельного редактирования задачи реализована механизм блокировки:

- **Длительность блокировки:** 15 минут, продлевается при повторном захвате
- **Захват блокировки:** POST `/api/v1/tasks/{id}/lock` при входе в режим редактирования
- **Проверка блокировки:** PUT `/api/v1/tasks/{id}` возвращает 423 если задача заблокирована другим пользователем
- **Освобождение блокировки:** DELETE `/api/v1/tasks/{id}/lock` при сохранении или закрытии модалки (fire-and-forget)
- **Автоистечение:** если lock не был освобождён (закрыли вкладку) — через 15 минут блокировка снимается
- **Просмотр:** GET `/api/v1/tasks/{id}/lock` возвращает статус блокировки; polling каждые 30 сек на клиенте
- **Индикация:** жёлтый баннер «Редактируется пользователем X (до HH:MM)» + серая кнопка редактирования
- **Уведомление:** при захвате блокировки — уведомление категории `editing` получателям задачи (medium importance)

### 4.3.1 Отслеживание «кто просматривает»

В дополнение к блокировке (один редактор) реализован механизм отслеживания нескольких зрителей:

- **Таблица:** `task_viewers` (task_id, user_id, last_seen_at)
- **Регистрация:** POST `/api/v1/tasks/{id}/viewers` при открытии модалки
- **Обновление:** polling каждые 15 сек (POST), обновляет `last_seen_at`
- **Список:** GET `/api/v1/tasks/{id}/viewers` — возвращает активных зрителей (кроме текущего), записи старше 10 минут удаляются автоматически
- **Удаление:** DELETE `/api/v1/tasks/{id}/viewers` при закрытии модалки
- **Индикация:** голубой баннер «Просматривает: Иванов» (1 чел.) / «Просматривают: Иванов, Петров» (2+ чел.)

### 4.4 Оптимистическая блокировка (Optimistic Locking)

В дополнение к пессимистичной блокировке (lock) реализована оптимистичная блокировка через поле `version`:

- Каждая задача имеет поле `version` (int), увеличивающееся при каждом успешном PUT-запросе.
- При открытии карточки клиент получает текущую версию задачи в ответе API.
- При сохранении клиент передаёт версию в поле `version` запроса.
- Сервер сравнивает: если `submitted_version ≠ task.version` → HTTP 409 Conflict.
- Ответ 409 содержит текущее состояние задачи для отображения diff.
- При "Принудительном сохранении" клиент отправляет PUT с серверной версией → сохранение выполняется.

**Обработка на клиенте:** Модальное окно конфликта с вариантами: Обновить и продолжить, Показать различия, Принудительно сохранить, Отмена.

### 4.5 Правила переходов между статусами

Переход между статусами осуществляется через PUT `/api/v1/tasks/{id}` с указанием нового `status_id`. Система не накладывает программных ограничений на последовательность переходов — любой статус может быть установлен в любой момент в зависимости от прав пользователя.

**Рекомендуемые переходы (business workflow):**

```
НОВАЯ ЗАДАЧА ──► НАЗНАЧЕНА КОМАНДА ──► СБОР ТРЕБОВАНИЙ ──► ПРОВЕРКА ТРЕБОВАНИЙ
       │                                                          │
       └──────────────────── ◄──────── УТОЧНЕНИЕ ТРЕБОВАНИЙ ◄─────┘
                                                      │
                                                      ▼
                                              ЭКСПРЕСС-ОЦЕНКА
                                                      │
                                                      ▼
                                              ПРИНЯТИЕ РЕШЕНИЯ
                                             /       |       \
                                            ▼        ▼        ▼
                                     ПРИНЯТА В   ОТКЛОНЕНА  НЕ АКТУАЛЬНА
                                     РАБОТУ
                                        │
                                   ┌────┴────┐
                                   ▼         ▼
                                ХОЛД      ЭСКАЛАЦИЯ
                                   │         НА ЛТ
                                   ▼         │
```

### 4.3 Кто и при каких условиях может переводить задачу

| Роль | Может менять статус | Условия |
|------|--------------------|---------|
| Администратор | Любые статусы любых задач | Всегда |
| ЛТ (Tribe Leader) | Любые статусы любых задач | Требуется `backlog_dmb >= read_write` |
| IT PL | Любые статусы задач своей/любой команды | Требуется `backlog_team >= write_own` |
| PO | Статусы задач своей команды | Требуется `backlog_team >= write_own` |
| BA | Не может менять статусы | Read-only доступ |
| Бизнес-заказчик | Не может менять статусы | Read-only доступ |

### 4.4 Bulk-операции

Для массового изменения статуса используется POST `/api/v1/tasks/bulk`:
- `action: "close"` — устанавливает статус ВЫПОЛНЕНА и progress = 100
- `action: "hold"` — устанавливает статус ХОЛД
- `action: "delete"` — мягкое удаление (is_deleted = true)

Право на bulk-операции: `backlog_team >= write_all` (ЛТ, Администратор).

## 6. Ключевые сущности

### 6.1 Задача (Task)

**Основные атрибуты:**
- `title`, `description` — название и описание
- `status_id` → `statuses` — статус по workflow (13 значений)
- `priority_id` → `priorities` — приоритет (ВЫСОКИЙ, СРЕДНИЙ, НИЗКИЙ)
- `team_id` → `teams` — ответственная команда
- `progress` — прогресс выполнения (0-100%)

**Сроки и оценки:**
- `deadline_id` → `deadlines` — срок выполнения
- `effort_days`, `effort_rub` — трудозатраты в днях и рублях
- `financial_effect` — финансовый эффект (руб.)
- `cv` — Cost/Value (авторасчёт: financial_effect / effort_rub)
- `ice_impact`, `ice_confidence`, `ice_ease` — компоненты ICE (1-10)
- `ice_score` — ICE Score (авторасчёт: impact × confidence × ease / 10)

**Организационные:**
- `channel_id` → `channels` — канал поступления (Почта, СберЧат, Встреча/Звонок, Бизнес-план)
- `department_id` → `departments` — подразделение заказчика
- `project_id` → `projects` — проект
- `task_type_id` → `task_types` — тип задачи
- `business_customer` — бизнес-заказчик (строка)
- `owner_id`, `responsible_po_id`, `business_analyst_id`, `it_product_lead_id` → `users` — ответственные
- `involved_teams` — вовлечённые команды (текст)
- `key_project` — признак ключевого проекта

**Статусы для аудиторий:**
- `directorate_status` — статус для директорской оперативки (текст, max 1000 символов)
- `directorate_status_updated_at` — дата/время последнего обновления статуса (авто при PUT)
- `did_status` — статус для оперативки ДИД (текст, max 1000 символов)
- `did_status_updated_at` — дата/время последнего обновления статуса (авто при PUT)
- `key_project_status` — статус для ключевых проектов (список значений)

**Методология и артефакты:**
- `dod` — Definition of Done
- `what_if` — What-If анализ
- `link_mockups`, `link_jira` — ссылки (макеты, Jira)
- `rejection_reason` — причина отклонения
- `comment`, `status_comment` — комментарии
- `is_from_leadership` — задача от руководства
- `is_regular` — регулярная задача

**Блокировка и версионирование:**
- `version` — версия задачи (optimistic lock, инкрементируется при каждом PUT)
- `lock_owner_id` → `users` — владелец пессимистичной блокировки
- `lock_until` — время окончания блокировки (UTC)

**Вложения (task_attachments):**
- Файлы загружаются через `POST /tasks/{id}/attachments` (multipart/form-data)
- Хранятся в `backend/uploads/{task_id}/` с UUID-именами
- Каждый файл: `filename` (UUID.ext), `original_name`, `mime_type`, `file_size`
- Связь `Task.attachments` — `cascade="all, delete-orphan"` (удаляется при удалении задачи)
- Ссылки `link_mockups` и `link_jira` — текстовые поля задачи, обновляются через `PUT /tasks/{id}/links`
- Все изменения (загрузка/удаление файлов, изменение ссылок) фиксируются в `task_history`

**Служебные:**
- `created_by`, `created_at`, `updated_at`
- `is_deleted` — мягкое удаление

| Таблица | Назначение | Примеры значений |

| `tags` | Теги (many-to-many) | Гибкая классификация задач и проектов |

**Блокировка справочников (dictionary_items):**
- Поля `lock_owner_id`, `lock_until`, `version` добавлены в `dictionary_items` (миграция `ensure_schema()` — auto ALTER TABLE)
- Паттерн идентичен блокировке задач (tasks.lock_owner_id / lock_until)
- Захват: `POST /admin/{dict_type}/lock` при входе в модалку редактирования
- Проверка: PUT/POST/DELETE проверяют `_is_dict_lock_active()` — HTTP 423 если заблокирован другим
- Освобождение: `DELETE /admin/{dict_type}/lock` при сохранении или закрытии модалки (fire-and-forget)
- Автоистечение: 15 минут (`DICT_LOCK_MINUTES`)
- Просмотр: `GET /admin/dict-locks` — все словари (для индикации на карточках)

### 6.7 История и аудит

| Таблица | Назначение |
|---------|-----------|
| `task_history` | Версионирование изменений задач (кто, когда, что, старое/новое значение) |
| `task_comments` | Комментарии к задачам с древовидной структурой (parent_id) и @-упоминаниями |
| `audit_log` | Лог всех write-операций (user_id, action, entity_type, entity_id, ip_address, details) |

**audit_log — Интерфейс просмотра:**
- Страница аудита доступна по маршруту `#/audit-log` (требуется `admin: read`)
- Таблица: дата/время, пользователь, действие, тип сущности, ID сущности, детали (метод/путь/статус), IP-адрес
- Фильтрация: по пользователю, типу действия (CREATE/UPDATE/DELETE), типу сущности (tasks/teams/users/roles и др.), диапазону дат
- Пагинация: 50 записей на страницу
- API: `GET /admin/audit-log` (с фильтрами и пагинацией), `GET /admin/audit-log/filters` (доступные значения фильтров)

### 6.8 Уведомления

- `notifications` — уведомления пользователей (6 типов: overdue, effort, update, attrs, deadline, **mention**)
- `notification_templates` — настраиваемые шаблоны (CRUD через админку)
- Тип `mention` — создаётся автоматически при @-упоминании пользователя в комментарии

## 7. Нормализация БД

Схема полностью нормализована (3NF). Все атрибуты-справочники вынесены в отдельные таблицы с внешними ключами:

```
tasks.channel_id      → channels.id
tasks.department_id   → departments.id
tasks.project_id      → projects.id
tasks.task_type_id    → task_types.id
tasks.priority_id     → priorities.id
tasks.status_id       → statuses.id
tasks.deadline_id     → deadlines.id
tasks.owner_id        → users.id
teams.team_type_id    → team_types.id
users.team_id         → teams.id
users.role_id         → roles.id
projects.status_id    → project_statuses.id
```

Для совместимости с админкой существует также таблица `dictionary_items` (обобщённый справочник), которая дублирует нормализованные таблицы для целей CRUD-редактирования через интерфейс администрирования.

## 8. Уведомления

### 8.1 Типы уведомлений

Генерируются на фронтенде через `buildSystemNotifications()`:
- Заполнить статусы для Оперативки ДИД

## 12. Обработка ошибок и исключений

### 12.1 Типовые HTTP-ошибки

| Код | Описание | Примеры ситуаций |
|-----|----------|-----------------|
| 400 | Bad Request | Неверные данные запроса, дубликат email, попытка удалить роль с пользователями |
| 401 | Unauthorized | Отсутствует или истёк JWT-токен |
| 403 | Forbidden | Недостаточно прав для выполнения операции |
| 404 | Not Found | Задача, пользователь, роль или команда не найдены |
| 409 | Conflict | Email уже зарегистрирован, код проекта существует, **конфликт версий задачи (optimistic lock)** |
| 422 | Validation Error | Ошибка валидации Pydantic (неверный формат полей) |
| 429 | Rate Limit Exceeded | Превышен лимит запросов (login — 5/мин, refresh — 10/мин) |
| 500 | Internal Server Error | Внутренняя ошибка сервера |

**Формат ответа об ошибке:**
```json
{
  "detail": "Описание ошибки"
}
```

### 12.2 Обработка на уровне API

- **Валидация входящих данных**: Pydantic-схемы с Type Hints автоматически проверяют типы, обязательность полей, ограничения длины и диапазоны значений (например, `progress: int = Field(ge=0, le=100)`).
- **Проверка прав доступа**: декораторы `require_permission()` и функция `check_permission()` проверяют, имеет ли пользователь требуемый уровень доступа к разделу. При недостатке прав возвращается 403.
- **Проверка существования ресурса**: перед операциями UPDATE/DELETE выполняется проверка наличия записи в БД. При отсутствии возвращается 404.
- **Защита от дурака**: запрещено лишать себя admin_access (проверка в `update_role`). Запрещено удалять команду, если к ней привязаны пользователи или задачи.

### 12.3 Исключения на уровне кода

- `HTTPException` из FastAPI — стандартный способ возврата ошибок с кодом и деталями.
- `JWTError` (библиотека `python-jose`) — перехватывается в `decode_token()`, при ошибке возвращается None, что ведёт к 401.
- Ошибки БД (IntegrityError, SQLAlchemyError) — не перехватываются специально, приводят к 500. Для продакшена рекомендуется добавить глобальный обработчик исключений.

### 12.4 Логирование ошибок

- `LoggingMiddleware` записывает все request/response (метод, путь, статус, длительность) в файл и stdout в формате JSON.
- `AuditMiddleware` записывает все write-операции в таблицу `audit_log` для последующего аудита.

### 12.5 Обработка на стороне клиента

- API-клиент (`api.js`) автоматически обрабатывает 401: пытается обновить токен через `/auth/refresh`, при неудаче выполняет logout и редирект на `/login`.
- Ошибки 4xx/5xx отображаются пользователю через тост-уведомления.
- **409 Conflict (optimistic lock):** отображается модальное окно конфликта с вариантами: обновить и продолжить, показать различия, принудительно сохранить, отмена.
- Debounce поиска 250 мс для снижения количества запросов.
