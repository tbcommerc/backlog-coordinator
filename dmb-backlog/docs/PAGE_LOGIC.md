# Логика страниц Backlog coordinator

Документ является проверенным навигатором по страницам. Детальное поведение каждого элемента определяется соответствующим JS-компонентом и его тестами; оно не дублируется здесь вручную.

### Детализация аналитики ЛТ

Отчёты «Трудозатраты», «Профиль команд», «Проекты по кварталам» и часть кликабельных
срезов «Проекта 360°» используют единый блок детализации: путь выбранного среза,
контекст и количество задач, группы проектов и табличный список задач. Если в
срезе один проект, дополнительный уровень раскрытия не создаётся; при нескольких
проектах по умолчанию открыт только первый. Изменение фильтра или проекта
закрывает прежнюю детализацию, чтобы она не расходилась с основным отчётом.
Пустые ячейки матриц не интерактивны. Выбранный квартал «Проекта 360°» раскрывает
задачи непосредственно под квартальной лентой, а выбор узла контура ответственности —
внутри соответствующего аккордеона после явного действия «Посмотреть задачи».

«Карта зависимостей» сохраняет специализированный путь команда → направление
связи → проект → задачи; ребро графа открывает выбранное направление напрямую.
«Поток задач» открывает общий блок задач как по узлу, так и по связи. В отчёте
«Трудозатраты и финансовый эффект» точка диаграммы раскрывает соответствующий
проект в единственной inline-иерархии проект → команда → задачи; скрытого лимита
на 50 проектов нет. Все варианты поддерживают переход в карточку задачи,
клавиатурную активацию доступных элементов и закрытие по Escape.

Иерархия общей детализации отображается как плоское табличное дерево: проект —
строка первого уровня с шевроном слева, задачи — вложенная таблица с отступом и
вертикальной направляющей. Массовые действия «Раскрыть все» и «Свернуть все»
расположены слева над деревом и дополнены двойными шевронами. В отчёте «Эффект»
уровни дополнительно подписаны как «Проект», «Команда» и «Задача»; массовые
действия управляют всей трёхуровневой иерархией.

## Ограничения навигации

- Customer portal only пользователь перенаправляется на `/customer`, если открывает другой статический route.
- `/admin` и `/audit-log` показывают forbidden state при `admin=none`.
- `/reporting-meetings` и `/outbox-dead-letters` доступны только при `admin=full`.
- Перед сменой маршрута `onBeforeNavigate` может остановить переход, например при несохранённых изменениях.
- Эти клиентские проверки улучшают UX, но безопасность обеспечивают backend dependencies.

## Общая модель страницы

Router вызывает `render(app)`, вставляет HTML в `#page-content`, активирует Lucide icons и затем вызывает `init(app)`. Компоненты самостоятельно загружают данные, привязывают события и управляют loading/error/empty состояниями.

Нет единого формального контракта состояний для всех страниц. Для конкретной страницы проверяй её `render*`, `init*`, API calls и профильные frontend tests.

## Карточка задачи

Карточка открывается через событие `open-task` и поддерживает deep link. Реализованы просмотр, редактирование, вкладки, version conflict UI, комментарии, вложения и связанные данные. Точный состав полей зависит от response schema, labels и пользовательских прав.

Вкладка «Отчётные статусы» отдельно загружает ближайшую и предыдущую встречу каждого типа. Предыдущий статус доступен только для чтения; текущий сохраняется собственной кнопкой и собственной версией. Если для ближайшей встречи ещё нет отдельной версионной записи, карточка показывает актуальный статус из задачи; первое сохранение переносит этот текст в модель встречи. До назначения даты плавающей встречи ввод закрыт.

## Управление отчётными встречами

Административный функционал вынесен со страницы отчётов на отдельный маршрут `#/reporting-meetings`, доступный только проектному офису с `admin=full`. `#/reports` содержит только готовые отчёты и больше не загружает календарь.

На административной странице основное представление содержит не более трёх компактных строк-карточек — по одной ближайшей встрече каждого типа. В каждой строке рядом расположены тип встречи, основная дата, следующие даты, готовность статусов и действия. В блоке следующих дат отдельная кнопка «Планировать встречи» открывает все незавершённые экземпляры выбранного типа: администратор может изменить любую дату или добавить новый экземпляр. Короткие даты в самой карточке служат обзором и не маскируют редактирование неочевидной интерактивностью. Для директорской и ДИД система по-прежнему автоматически поддерживает график на 90 дней, а ручное добавление позволяет расширить или дополнить его; новая директорская назначается на понедельник, ДИД — на вторник. Остальные экземпляры доступны в хронологии. Фильтры по типу, состоянию и диапазону дат применяются к обоим представлениям; закрытые встречи показываются компактным списком. Для любой встречи проектный офис может открыть её срез статусов, увидеть версию и журнал изменений статуса каждой задачи. Срез состоявшейся встречи доступен только для чтения. Справочная схема фиксации статусов расположена после календаря и по умолчанию свёрнута, чтобы не отодвигать основные действия.

Проектный офис с полным admin-доступом управляет встречей вертикальной колонкой одинаковых кнопок рядом с отдельным компактным полем ближайшей даты: «Встреча состоялась», «Изменить дату», «Отменить встречу» и расположенная снизу «История». Цвет действия не зависит от типа встречи: подтверждение всегда зелёное, изменение и планирование — основного акцентного цвета, отмена — красная, история — нейтральная. Подтверждение проведения становится активным в день последней актуальной даты и остаётся доступным после неё, пока встреча не подтверждена, не отменена или не перенесена; это правило проверяется и клиентом, и сервером. Для просроченной встречи под датой показывается одно явное прямоугольное уведомление со скруглением и знаком восклицания о необходимости подтвердить проведение, отменить или перенести встречу; отдельный чип просрочки не дублируется. При неполных статусах завершение требует отдельного явного подтверждения. Первая дата ДИД валидируется как вторник и на клиенте, и на сервере. Конфликт версии перечитывает календарь вместо повторной отправки устаревших данных. Кнопка «История» открывает единый журнал всех экземпляров выбранного типа встречи, поэтому назначение, перенос, проведение или отмена остаются видны и после перехода карточки к следующему экземпляру; для каждой записи показываются автор, время и причина.

При отмене встречи заполненные статусы переносятся в следующую встречу, не перезаписывая уже подготовленные данные. Быстрое заполнение статусов PO/PL/CL на административной странице не реализуется: команда продолжает использовать вкладку отчётных статусов в карточке задачи до отдельного следующего этапа.

Планировщик уведомлений напоминает только PO/PL/CL команд с незаполненными задачами: за один рабочий день до директорской оперативки, за два календарных дня до ДИД и за три календарных дня до встречи по ключевым проектам. В день встречи все активные администраторы получают запрос актуализировать факт. Без подтверждения встреча не закрывается автоматически и отображается просроченной.

Нельзя считать поле доступным или редактируемым только потому, что оно существует в модели: проверяются component rendering, permissions и request payload.

## Backlog и team backlog

Обе страницы используют общий `filterToolbar.js`, quick filters, table utilities, quick edit и sticky table header. Общий поиск проверяет только ID, название и описание задачи; совпавший текст подсвечивается в этих полях таблицы, а также в ID и названии карточки. Отличия области данных и разрешений находятся в `taskTable.js`, `teamBacklog.js` и backend task scope. В табличном представлении каркас и заголовки таблицы сохраняются при загрузке, пустом результате и ошибке; соответствующее состояние выводится одной строкой внутри `tbody`, а ошибка предоставляет повторную загрузку.

Обычные фильтры образуют персональную панель и полный каталог. По умолчанию в
DMB backlog закреплены статус, приоритет, команда, срок и проект; в team backlog —
статус, приоритет, срок, владелец и тип задачи. Пользователь может закрепить до
пяти любых фильтров из каталога или восстановить исходный набор; настройка
хранится отдельно для каждой страницы и не входит в сохранённые представления.
Быстрые сценарии имеют фиксированный состав и не настраиваются пользователем.

Каталог фильтров покрывает все доступные пользователю колонки таблицы. Для
справочников и перечислений используется множественный выбор, для текста — поиск
по фрагменту, для чисел и дат — диапазон, для логических значений — выбор
«Да/Нет». Там, где поле может отсутствовать, доступно условие «Не заполнено».
Фильтр ответственного за выполнение задачи называется «Исполнитель» и следует
настраиваемому названию одноимённой колонки.
На desktop каталог открывается поверх страницы, на средней ширине — боковой
панелью, на мобильной — нижней панелью; закреплённые фильтры на узком экране
остаются доступны в горизонтально прокручиваемой строке.

## Kanban

Kanban отображает 13 колонок и обновляет `status_id` через task PUT. Универсальная backend state machine разрешённых переходов не подтверждена; drag-and-drop не следует документировать как формальное бизнес-правило перехода.

## Admin

Admin объединяет несколько вкладок и API справочников/пользователей/ролей/команд. Реальная доступность действий определяется backend. Защищённые данные не используются для тестовых мутаций документации.

## Customer и review

Customer portal получает задачи текущего заказчика. Создание требования выполняется через Agent chat. Review routes работают с persisted `requirement_requests` и требуют отдельного review access.

Detail-экраны `#/customer/request/{id}` и `#/review/{id}` используют общий каркас запроса: единый словарь статусов, путь запроса, сводку текущего этапа, структурированный паспорт из `RequirementRequest.draft`, ключевые события и одинаковый блок участников и сроков. Customer-вариант акцентирует следующий шаг, комментарий специалиста и связанную реализацию; открытые уточнения показываются заказчику только при возврате запроса. Review-вариант добавляет сигналы ассистента с переходом к связанным разделам паспорта, сворачиваемые метрики качества и действия ревьюера. История использует переданный API массив событий, а при его отсутствии показывает только события, достоверно выводимые из дат и текущего состояния запроса. Текстовое поле `description` используется в customer detail только как fallback для старых записей без структурированного draft.

## UI-безопасность

Компоненты используют `innerHTML`; недоверенные значения должны проходить `escapeHtml`, `escapeHtmlAttribute`, URL validation или безопасное DOM assignment. Правила и ограничения описаны в `SECURITY.md`.

## Как документировать изменение страницы

1. Сверить route и component.
2. Зафиксировать фактические API calls.
3. Проверить permissions и object scope.
4. Проверить loading, empty, error, conflict и success состояния, которые реально существуют в коде.
5. Добавить/обновить frontend test.
6. Не придумывать альтернативные сценарии, если они не реализованы и не утверждены.

Историческое подробное описание сохранено в `archive/legacy/PAGE_LOGIC_STALE_2026-07-25.md`.
