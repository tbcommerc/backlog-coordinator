## Структура страницы

`#/work-projects` сохраняет каталог, поиск и пагинацию. Карточка проекта содержит
«Обзор», «План», «Гант и вехи», «Отклонения», «Результаты» и существующий

Обзор показывает существующее описание проекта, PL, команды доступных работ,

не рассчитывается. Пять записей в обзорных блоках — явно краткое представление;
ссылки открывают полный раздел с пагинацией по 30 записей.

Год и квартал задают период плана и результатов; «Весь год» — календарный год.

задачи без распознанного горизонта и без точных дат. Поиск, выбранный период,
область, только вехи и страница сохраняются в URL. Старые ссылки `planning` и
`backlog` открывают план, `metrics` — метрики в результатах; `execution`, `major`,
`scope` и карточки `task` сохраняют назначение.

## Даты, вехи и исходный план

План принадлежит обычной задаче бэклога, а не справочнику проектов.
`project_task_plans` хранит одну запись на Task:

| Поле | Назначение |
|---|---|
| `task_id` | PK/FK задачи, каскад при физическом удалении |
| `starts_on`, `ends_on` | Обе точные даты либо обе NULL, начало не позже конца |
| `baseline_start`, `baseline_end` | Первый сохранённый точный план, далее не перезаписывается |
| `is_milestone` | Явная отметка ключевой задачи |
| `expected_result` | Ожидаемый результат задачи |
| `change_reason` | Последняя введённая причина изменения плана |

При отсутствии точных дат используются распознанные годовые/квартальные значения
`deadline_id` и месяц старта `start_shift_id`. Это **плановый горизонт**, а не
доказанные даты начала/окончания. Несмежные кварталы остаются отдельными полосами.
Дата получения задачи никогда не подставляется вместо начала выполнения.
Точные даты имеют приоритет для попадания задачи в период; исходный справочный
срок в карточке задачи не изменяется и остаётся доступен.

Веха использует конец точного плана либо конец последнего планового горизонта
задачи. Для горизонта это явно обозначенная граница периода. Веха без срока
не получает выдуманную дату и не входит в число датированных вех периода.
Задача с несколькими кварталами даёт одну веху, а не копию на каждый квартал.
Достигнутая веха определяется текущим статусом Task `done`.

Редактор доступен в плане при праве редактирования исходной задачи. Изменение
сохранённых точных дат требует причины. В API передаются только плановые поля
и текущая `Task.version`; роли, команды, справочники и их ответственные не меняются.
Проверяются ACL, принадлежность проекту, блокировка другим пользователем и версия.
Версия Task увеличивается; в TaskHistory создаётся запись `project_plan`.
При конфликте форма сохраняет ввод и предлагает явное обновление версии перед
повторным сохранением. Это не автоматический повтор записи.

## Отклонения и результаты

Отклонения показывают **текущее состояние всего проекта**, независимо от выбранного
отчётного периода. В одной строке могут быть несколько признаков:

- активная задача бэклога с истёкшим точным сроком или целиком истёкшим горизонтом;
- активная задача с концом плана позже исходного точного срока;
- доступная незавершённая рабочая задача с истёкшим `due_date`;
- рабочая задача на приёмке.

Отменённые/закрытые задачи не объявляются текущей просрочкой. Признак препятствия
рабочих задач не используется: он удалён из актуальной модели. Риски и решения
не генерируются автоматически. Причина переноса показывается только при наличии.

Результаты используют существующий API: выполненные WorkTask по `completed_at`,
историю переходов Task в `done`, историю справочного срока и нового точного плана,
метрики с периодами, пересекающими выбранный интервал. WorkTask после повторного
открытия не считается текущим выполненным результатом; повторное выполнение Task
может дать отдельное событие истории. Это разные показатели.

Для legacy-метрик факт — последний замер до конца интервала и не позже сегодня.
Для `quarterly_v2` факт — явная текущая FactRevision; наблюдения не подставляются
вместо факта. Будущий относительно интервала факт не показывается. Цели и редакции
показываются текущими, это не исторический снимок состояния на конец периода.
Границы событий рассчитываются в Europe/Moscow.

## API и миграция

- `GET /api/v1/projects/{id}/management`: обязательный `year` (2000–2099),
  `quarter` (0–4), `view=plan|gantt|deviations`, `horizon=period|all|undated`,
  `page>=1`, `q` до 200 символов, `milestones`; `team`, `owner`, `state`
  (до 200 символов, точные значения из `filter_options`), `sort=start|due|owner|title`.
  Фильтрация и сортировка выполняются до пагинации. Ответ содержит `filter_options`,
  `can_edit`, а в отклонениях — `overdue_days`, ответственного и команду.
- `GET /api/v1/projects/{id}/tasks/{task_id}/plan`: ACL-проверенная проекция
  одной задачи, её плана и доступности редактирования.
- `PUT` по тому же адресу: `version`, `starts_on`, `ends_on`, `is_milestone`,
  `expected_result` (до 4000), `change_reason` (до 2000). Лишние поля запрещены.
  Ошибки: 403 — нет права записи, 404 — задача недоступна/другого проекта,
  409 — другая версия, 423 — чужая блокировка, 422 — неверные данные/нет причины.

Миграция `b0f345ab6274` после `a9e234fa5163` создаёт только `project_task_plans`.
Нет заполнения справочников, seed и массовой записи в задачи. Старые задачи
читаются без плановой записи. Откат схемы удаляет новые плановые данные, поэтому
не выполняется автоматически.

Источники: [проекция](../backend/services/project_management.py),
[API](../backend/routers/projects_router.py), [контракт](../backend/project_contract.py),
[интерфейс](../frontend/js/components/projectManagement.js),
[миграция](../backend/alembic/versions/b0f345ab6274_project_task_plans.py).
