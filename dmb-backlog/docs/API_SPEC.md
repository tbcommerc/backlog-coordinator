# API Backlog coordinator

## Запросы заказчиков — проверено 29.10.2026

- `GET /api/v1/agent/requests/registry` — полный серверный поиск, фильтры,
  счётчики и пагинация в разрешённой области.
- `POST /api/v1/agent/requests/{id}/lifecycle` — принятие в бэклог, откладывание,
  пересмотр, отзыв и изменение сопровождения; обязательные версия и причина.
- `GET /api/v1/agent/requests/{id}/coordinators` — допустимые ответственные.
- DTO запроса включает `effective_status`, сопровождение и `lifecycle_actions`.
  Удаление отправленного запроса возвращает 409; используется отзыв.
- Размещение допускает `accepted`; подтверждение полного результата проверяет
  завершение всех связанных рабочих и текущих задач.

Параметры, ограничения доступа и проверки: [REQUESTS.md](REQUESTS.md).

## Наборы значений фильтров — проверено 29.10.2026

Перечисленные query-параметры принимают прежнее одиночное значение или
JSON-массив в строке, например `team_id=["1","2"]` (с обычным URL-кодированием).
Внутри поля действует ИЛИ, между полями — И. Пустая строка снимает ограничение.
Сервер валидирует положительные ID, enum и максимум 100 элементов; ACL не меняются.

| GET endpoint | Параметры с несколькими значениями |
|---|---|
| `/api/v1/metrics` | `team_id`, `owner_id`, `project_id`, `state`, `attention` |
| `/api/v1/work-tasks`, `/api/v1/work-tasks/board`, `/api/v1/work-tasks/board/columns/{column_status}` | `status`, `priority`, `work_direction`, `execution_team_id`, `assignee_id`, `effective_project_id`, `focus` |
| `/api/v1/work-reports` | `team_id`; `meeting_id` остаётся одним снимком |
| `/api/v1/admin/audit-log` | `user_id`, `action`, `entity_type` |
| `/api/v1/notifications` | `category`, `importance`; новый `views` объединяет `unread`, `action`, `resolved`, `open` через ИЛИ; `all` снимает ограничение |

Прежние флаги уведомлений `unread_only`, `requires_action`, `resolved` сохраняют
свою семантику. Новый UI передаёт `views` для нескольких состояний без этих
одиночных флагов. Все списки и агрегаты используют общий отбор без дублирования
строк. [Решение по каждому фильтру](FILTER_CARDINALITY.md).

## Быстрые выборки рабочих задач — проверено 21.10.2026

`GET /api/v1/work-tasks` и API доски принимают `focus=today|overdue|blocked`
(пустое значение отключает условие). «Сегодня» определяется по
московской дате; все три выборки исключают завершённые и отменённые задачи.
Ответ списка и начальный ответ доски содержат `focus_counts` с ключами
`today`, `overdue`, `blocked`. Счётчики учитывают ACL, подборку и остальные
фильтры, но вычисляются до применения самого `focus` и пагинации.
Подборки `collection_counts` также не сужаются самим `focus`; сводка и задачи
его учитывают. Условие входит в ключ подписанного курсора доски.
[Поведение интерфейса и проверки](WORK_TASKS.md).

## CUSTOMER-04: области доступа — проверено 17.10.2026

Сохранён существующий контракт «Моих запросов»: личные RequirementRequest (user_id текущего пользователя), его черновики и общие неудалённые Task привязанного business_customer_id. Общая задача не означает доступ к запросу другого автора, его черновику или уведомлениям. Если задача уже представлена личным запросом, отдельная строка задачи исключается до поиска. Тип записи задан kind=request/task/draft.

`GET /customer/tasks` выдаёт только задачи business_customer_id; без привязки список пуст. `GET /customer/tasks/{id}` дополнительно допускает неудалённую задачу по собственному неудалённому RequirementRequest.task_id, в том числе без business_customer_id или при другой привязке. Чужие, удалённые и отсутствующие задачи дают 404, неавторизованный вызов — 401. CustomerTaskResponse остаётся белым списком полей без внутренних финансовых, рейтинговых и lock-полей. Маршрут UI — `#/customer/task/{id}`, без перехода в общий бэклог.

Общая область относится именно к привязанному бизнес-заказчику; принадлежность к юридической организации сама по себе не даёт доступа. Расширение доступа на чужие запросы не вводилось. [Политика](../backend/services/backlog_assistant_integration/policy.py).

## CUSTOMER-03: непрочитанные события — проверено 17.10.2026

`GET /api/v1/customer/queue` возвращает `unread_event_count` для запросов текущего пользователя. Счётчик берётся из существующих Notification категории request по точному action_url запроса, is_read=false и is_dismissed=false; запрос агрегируется только для выданной страницы. Для черновиков и legacy-задач — 0, дата updated_at сама по себе не считается новым событием.

`GET /api/v1/customer/requests/{request_id}/events` возвращает `{total, items: [{id, title, body, created_at, type}]}`: до 100 последних непрочитанных событий, сортировка created_at/id по убыванию. Доступ только автору неудалённого запроса; чужой, удалённый или отсутствующий запрос — 404. GET ничего не записывает.

Прочтение сохраняется существующим `PUT /api/v1/notifications/read` с IDs показанных событий. Новые события, пришедшие после загрузки, не включаются в подтверждение. После успешной записи клиент перечитывает события и обновляет общий notification store. Отметка не означает выполнение обязательного действия. [Реализация](../backend/services/customer_events.py).

## Результат связанной задачи — проверено 17.10.2026

Для legacy-связи `RequirementRequest.task_id` изменение статуса или признака удаления задачи через ORM синхронизирует запрос в той же транзакции. Новые значения `status` в detail, списках запросов и `/customer/queue`: `completed` (ВЫПОЛНЕНА), `not_relevant` (НЕ АКТУАЛЬНА), `task_rejected` (ОТКЛОНЕНА), `task_deleted` (задача удалена). Возврат задачи в нетерминальный статус возвращает запрос в `in_progress`. Смена связи существующего запроса также учитывает текущий результат задачи.

Обновляются только `in_progress` и перечисленные автоматические результаты. `rejected` означает решение на ревью; `returned`, `submitted`, `in_review` и ручной `approved` не перезаписываются. Новые результаты нельзя присвоить через ручной endpoint решения ревьюера. Прогресс 100% сам по себе не закрывает запрос.

Каждый переход увеличивает version, добавляет status_history с source=task_result и создаёт уведомление автору с URL `#/customer/request/{id}`; outbox-события сохраняются атомарно. Повтор того же результата не добавляет историю/уведомление и не меняет прочитанность. Конфликт optimistic version отменяет всю транзакцию. WorkResolution/RequestWorkLink и решение о fulfillment не изменяются. Реализация: [customer_result.py](../backend/services/customer_result.py).

## Мои запросы: единая очередь — проверено 17.10.2026

`GET /api/v1/customer/queue` — авторизованная read-only проекция запросов, доступных legacy-задач и черновиков V1. Реализация: [customer_router.py](../backend/routers/customer_router.py), [customer_queue.py](../backend/services/customer_queue.py).

| Параметр | Контракт |
|---|---|
| `q` | Поиск подстроки без учёта регистра, до 200 символов; пробелы по краям удаляются. Поля: ID, публичный номер задачи, название, описание, команда, исполнитель, ревьюер, причина решения. `%` и `_` — буквальные символы, не SQL-шаблоны. Для старых задач без public_id поддержан отображаемый TASK-000-251 по числовому ID. |
| `group` | Пусто (все), action, draft, review, work, complete |
| `sort` | newest (по умолчанию) или oldest; по updated_at/created_at, затем kind и строковому ID для стабильных равных дат |
| `page` | Целое ≥1; вышедшая за диапазон страница приводится к последней, для пустой выдачи — 1 |
| `per_page` | 1–100, по умолчанию 25 |

Ответ: `items`, `total`, `page`, `per_page`, `pages`, `counts`, `warnings`, `preferred_draft`. `total/pages` учитывают поиск и фильтр; `counts` содержит all/action/draft/review/work/complete по всей доступной очереди до поиска/фильтра. Предпочтительный черновик выбирается независимо от текущей страницы и поиска. При пустой выдаче total=0, pages=0, page=1.

Элемент имеет kind=request/task/draft; поля карточки ограничены QueueItem. created_at/updated_at — datetime ISO 8601 с UTC-offset либо null; нет финансовых, lock-полей, полного draft и истории. История и содержимое запросов остаются в прежнем detail API. Для draft используются session_id/draft_session/active, для задачи — task_id/legacy_task; ID запроса сериализуется строкой.

ACL применяется до поиска и LIMIT: запросы только RequirementRequest.user_id=current_user.id и не удалённые; legacy-задачи только бизнес-заказчика текущего пользователя и не удалённые. Отсутствие business_customer_id не открывает чужие задачи. Связь с собственным неудалённым запросом исключает задачу из legacy-части до поиска; чужой запрос не раскрывается. Черновики получаются через существующий серверный agent_sessions для текущего пользователя; архивные и уже отправленные исключаются.

Поиск, группировка, подсчёт и сортировка запросов/задач выполняются SQL над UNION ALL. Без подходящих черновиков применяется OFFSET/LIMIT. При наличии черновиков сервер читает не более page*per_page строк SQL, объединяет с подходящими метаданными черновиков и возвращает страницу; список метаданных агента пока загружается целиком через его существующий API. При недоступности агента HTTP-ошибка превращается в предупреждение, SQL-часть остаётся доступной. Ошибка основной БД не выдаётся за пустой успешный результат.

Изменяющих запросов, синхронизации lifecycle и миграций нет. CUSTOMER-01/M02 не закрывается этой проекцией. Параметры с недопустимыми значениями дают 422, неавторизованный запрос — 401. Существующие `/customer/tasks` и `/customer/tasks/{id}` сохраняют контракт.


## Поручения из встреч — контракт ошибок проверен 17.10.2026

Префикс `/api/v1/meeting-capture`: список/создание/чтение/обновление разборов,
анализ, поиск и предложения связей, подтверждение. Реестр маршрутов проверен
по live OpenAPI. Все операции требуют внутреннего пользователя с правом
редактирования задач; разборы приватны. Запись связей проверяет объектный ACL.
Версии предотвращают потерю правок, подтверждение идемпотентно.
`POST /sessions/{id}/analyze` возвращает HTTP 202 со снимком и сохраняет
`queued` до ответа. `GET /sessions/{id}/status` — приватный пассивный опрос
статуса/версии/ID запуска/времени/ошибки без расшифровки и пунктов. Полный
снимок и история содержат `analysis_status`, `analysis_run_id`,
`analysis_requested_at`, `analysis_started_at`, `analysis_finished_at`,
`analysis_error_code`, `analysis_error_message`; история также `item_count`.
Статусы: `idle`, `queued`, `running`, `completed`, `failed`. Повторный analyze
для queued/running/completed не ставит второе задание, включая пустой успех.
PUT/confirm при активном анализе отвечают 409. После failed нужен явный повтор;
изменение источника/даты сбрасывает терминальное состояние в idle.
Сбой провайдера после принятия задания читается в failed: `meeting_ai_auth`,
`unavailable`, `invalid_result`, `interrupted`. Пояснения фиксированы; сырой
ответ провайдера не передаётся в UI. Это не истечение пользовательской сессии.
[Контракты, ошибки и ограничения](../../docs/meeting-capture-agent.md#api).

Машиночитаемый источник фактического контракта — OpenAPI, который создаёт запущенное приложение:

- Swagger UI: `/docs`;
- OpenAPI JSON: `/openapi.json`;
- базовый префикс прикладного API: `/api/v1`.

Этот файл служит навигатором и фиксирует сквозные правила. Он намеренно не копирует вручную все request/response поля: такое дублирование уже привело к расхождению старой спецификации с кодом.

## Fork-based Assistant V2 — проверено по коду 09.10.2026

При `AGENT_V2_ENABLED=true` и выключенном kill switch backend регистрирует
аутентифицированный gateway `/api/v2/agent/{path}` и API человеческого согласования
`/api/requirement-reviews`. Gateway доступен BA/PO пилотной группы; пользователь
с `admin_access=full` допускается как BA без включения в allowlist. Gateway
заменяет клиентские actor-поля доверенным контекстом и вызывает внутренний
`/api/agent-v2` сервиса на порту 9300. Метод и декодированный path проверяются
по закрытому списку маршрутов до построения upstream URL; произвольный proxy
и прямые service-команды перехода ревью через catch-all недоступны.

Основные маршруты нового документного сценария:

| Метод и абсолютный путь | Назначение |
|---|---|
| `POST /api/v2/agent/objects/{object_type}/{object_id}/workspace` | Открыть собственный документ по доступному `task`/`request`; при необходимости создать сессию и импортировать исходный текст. `{ "force_new": true }` запрашивает отдельный документ. Исходный запрос и его автор не меняются. |
| `POST /api/v2/agent/document-action` | Операции написания, AI-проверки, предложения/применения правок, решений по замечаниям и следующей редакции. Владелец сессии и доступ к связанному источнику проверяются сервером. |
| `POST /api/v2/agent/requirement-reviews` | Зафиксировать серверную редакцию и пакет AI-проверки в DMB; это создание `RequirementReview`, а не `RequirementRequest`. |
| `POST /api/v2/agent/requirement-reviews/{review_id}/resume` | Автору открыть рабочую сессию; если текущий документ совпадает с возвращённым/согласованным снимком, создать следующую редакцию. При возврате добавить замечание человека отдельным источником без дублей. Более новая рабочая редакция не перезаписывается. |
| `GET /api/requirement-reviews` | `{items, total}`; фильтры `status`, `artifact_id`, `limit` 1–100 (по умолчанию 50), `offset` ≥0. Объектная область применяется до пагинации. |
| `GET /api/requirement-reviews/{review_id}` | Полный неизменяемый снимок, пакет проверки, история, текущие права и признак изменения исходного контекста. |
| `POST /api/requirement-reviews/{review_id}/actions` | Независимое человеческое решение `claim`, `approve`, `return` или `withdraw`. |

В `document-action` доступны `create_draft` (сохранить первый сгенерированный
черновик с неподтверждённым происхождением), `save_sections` (атомарно сохранить
словарь текстовых разделов с проверкой `expected_draft_hash`) и `dismiss_proposal`
(оставить свой текст, отклонив оставшиеся операции). Существующий документ нельзя
перезаписать через `create_draft`. Контракт и ограничения:
[API агента](../../agents/business-analyst-experimental/docs/API.md). Проверено 09.10.2026.

Создание пакета принимает `session_id`, `expected_draft_hash` и обязательный
`Idempotency-Key` (либо одноимённый `idempotency_key` в JSON). При передаче обоих
значения должны совпадать. Полный draft и автор не принимаются от браузера:
gateway получает фактическое состояние принадлежащей пользователю сессии.
Проверяются canonical fingerprint, обязательные разделы, актуальность AI-проверки
для редакции и источников, открытые критичные замечания. Для явно обозначенной
проверки `degraded` требуется `acknowledge_degraded_review: true`.
Опциональные `supersedes_review_id` и `supersedes_version` передаются вместе как
положительные целые; только явная замена атомарно отзывает прежний активный пакет.
Обычная правка документа его не отзывает. Ответ: `{review, session_id, artifact_id, url}`.

Action JSON содержит `action`, положительную целую `version` самого согласования,
`comment` до 10 000 символов и ключ повторяемой операции. `return` требует
непустого комментария. Claim закрепляет ревьюера и оставляет статус `submitted`;
последующие состояния — `approved`, `returned`, `withdrawn`. Автор отзывает свой
активный пакет, а согласовать/вернуть его может закреплённый независимый BA/PO
с текущим правом ревью соответствующей области. Самосогласование запрещено,
включая full admin. DTO отдаёт `permissions`, `available_actions`,
`context_changed`, `artifact_snapshot`, `review_report`, `source_metadata`,
`events`, `version` и ссылку на собственную рабочую сессию, если она доступна.

`409` обозначает конфликт редакции/версии/ключа, уже активное согласование или
изменение значимых исходных материалов; `403` — недоступное действие;
`404` — отсутствующий/недоступный объект либо неизвестный proxy-маршрут.
Ключ отправки ограничен автором и содержимым; ключ действия — актором и payload.

Прежний `POST /api/v2/agent/send-for-review` сохраняет intake-контракт
`RequirementRequest` с `agent_session_id=v2:{session_id}` для самостоятельных
старых сценариев. Связанный с Task/Request документ через этот маршрут не
публикуется: используется новое согласование БТ. Новый review не создаёт Task
и не меняет intake-статус исходного запроса.

`POST /api/v2/agent/session/{id}/link-object` принимает только тип и ID;
backend сам получает snapshot после read access. Перепривязка уже связанного
документа к другому объекту запрещена; обновление того же контекста допустимо.
`GET /api/v2/agent/objects/search` ищет доступные Request/Task по ID или названию.
Доступ повторно проверяется при восстановлении сессии, работе с документом и
возврате JSON-ответов, включая cached receipts. Все изменяющие generic-запросы
gateway передают сервису `Idempotency-Key` как `idempotency_key`.

Источники реализации: [gateway](../backend/routers/agent_v2_router.py),
[проверка публикации](../backend/services/agent_v2_documents.py),
[домен согласования](../backend/services/requirement_reviews.py).
Проверены код и изолированные тесты; live OpenAPI и PostgreSQL на стенде для
этого инкремента не проверялись. Старый реестр операций ниже сохраняет свою дату.

Для `TaskResponse` поле `progress` всегда выдаётся целым числом от 0 до 100.
Унаследованные записи БД с `NULL` нормализуются в `0` на границе API, поэтому
одна такая запись не прерывает выдачу всего списка задач.

`TaskResponse.latest_pip_decision` содержит последний структурированный исход PI
(`decision`, `reason`, `decided_at`, `decided_by_name`), если он существует.
Списки задач и `GET /quick-estimate` получают этот контекст пакетным запросом к
истории, а не отдельным запросом на каждую задачу. Клиент считает возврат активным
только при сочетании текущего статуса «ЭКСПРЕСС-ОЦЕНКА» и последнего решения
`rework`, поэтому завершённый повторный цикл не остаётся помеченным как возврат.
Проверено по коду 10.09.2026.

## Группы API

### Reporting meetings

- `GET /reporting-meetings` — календарь, состояния и полнота заполнения; поддерживает фильтры `kind` (включая автоматически создаваемый `team_weekly`), `state`, `date_from`, `date_to`, параметр `include_completeness=false` для облегчённой выдачи без расчёта полноты и признак доступности подготовки;
- `POST /reporting-meetings` — добавить новый будущий экземпляр встречи; требуется `admin=full`, дата директорской должна приходиться на понедельник, ДИД — на вторник;
- `GET /reporting-meetings/{id}/history` — полная история действий с датами, причиной и автором;
- `GET /reporting-meetings/{id}/preparation` — срез статусов к встрече: проектный офис с `admin=full` видит и может редактировать задачи всех команд, PO/PL/CL и BA/участник команды — только задачи своей команды; доступность изменения каждой записи передаётся признаком `can_edit`, а для директорской возвращается встречный маркер `directorate_attention`;
- `PUT /reporting-meetings/{id}/statuses/batch` — атомарно сохранить до 500 отчётных статусов одной ближайшей встречи; для каждой задачи проверяются доступ и optimistic version, при любой ошибке весь пакет откатывается;
- `POST /reporting-meetings/{id}/schedule` — назначить дату или перенести встречу;
- `POST /reporting-meetings/{id}/complete` — подтвердить факт проведения назначенной встречи в её дату или позднее; неполные статусы не блокируют операцию и не требуют отдельного подтверждения;
- `POST /reporting-meetings/{id}/cancel` — отменить с обязательной причиной;
- `GET /tasks/{id}/reporting-statuses/context` — ближайшая и предыдущая встречи со статусами задачи;
- `PUT /tasks/{id}/reporting-statuses/{meeting_id}` — сохранить текст, признак `is_ready`, директорский маркер, недельный объект `weekly` и версию отдельно от карточки задачи; для `team_weekly` подтверждение требует непустых результата и следующего шага, а сигнал `decision` — сформулированного вопроса; изменять статус могут назначенные PO/PL/CL, а также пользователи ролей `PO/PL/CL` и `BA/Участник команды` в границах своей ответственной команды;
- `PUT /tasks/{id}/reporting-statuses/{meeting_id}/directorate-attention` — изменить только маркер «Требует показа лидеру трайба» для готового непустого статуса ближайшей директорской встречи с optimistic locking. Маркер существует только в контексте отчётной встречи и не является полем задачи.

Управляющие команды требуют полного admin-доступа. Заполнение разрешено PO/PL/CL и BA/участнику своей ответственной команды; проектный офис статус не заполняет, даже если администратор одновременно привязан к команде.

### Authentication

- `POST /auth/login`;
- `POST /auth/refresh`;
- `GET /auth/me`;
- `POST /auth/logout`.

Login возвращает access-токен и устанавливает refresh cookie. Refresh и logout используют cookie path `/api/v1/auth`; детали описаны в `SECURITY.md`.

### Tasks

Группа содержит:

- список, поиск, статистику, reference data и detail; `GET /tasks/reference`
  возвращает `sort_order` для статусов, приоритетов, сроков, типов задач,
  каналов, подразделений и клиентов ДИД;
- создание, PUT/PATCH update и soft delete;
- PIP decision и обновление ссылок;
- history и documents;
- bulk preview/action;
- import;
- locks и viewers;
- comments и attachments;
- analytics и отчёты по задачам.

`PUT /tasks/{id}/pip-decision` принимает актуальную `version`, решение `accept`,
`rework` или `reject` и необязательный комментарий. Для `rework` и `reject`
причина обязательна. `accept` переводит задачу в «Принята в работу», `rework` —
обратно в «ЭКСПРЕСС-ОЦЕНКА» ответственной команды, `reject` — в «Отклонена».
Результат и причина записываются одним структурированным событием `pip_decision`
в той же транзакции, что и статус; для отклонения причина также сохраняется в
`rejection_reason`. В этой транзакции создаются обязательные уведомления категории
`decision` для активных участников ответственной команды, имеющих доступ к задаче,
кроме автора решения. Уведомление использует стабильный type
`task.pip_decision.<decision>` и безопасную ссылку
`#/backlog?task={id}&tab=log`. PI-отчёт возвращает реальную `version` каждой задачи
для optimistic locking и сортирует очередь по Priority Score от большего к
меньшему. Проверено по коду 10.09.2026.

Ответ `GET /api/v1/tasks/analytics/po-pl-reports` содержит каталог `periods`,
идентификатор `active_period` и `period_ids` каждой задачи для клиентской
фильтрации отчётов по сроку.

Объектная авторизация находится в `backend/auth.py`. Форматы задач — в `backend/schemas.py` и OpenAPI.

CSV import принимает не более 10 MiB и 10 000 строк; каждая валидная строка
сохраняется в отдельном savepoint, поэтому конфликт одной строки не ломает
транзакционное состояние следующих. При ошибке итогового commit `task_ids`
очищается. Вложения пишутся потоково с лимитом 50 MiB, блокировкой активных
исполняемых расширений и проверкой сигнатур распространённых бинарных форматов.

Расчёты из карточки задачи:

- `POST /tasks/{id}/prioritiser/value` — рассчитать финансовый эффект;
- `POST /tasks/{id}/prioritiser/priority` — рассчитать и сохранить приоритет;

Оба endpoint принимают `{ "version": <текущая версия задачи> }` и используют те
же права, блокировки и optimistic locking, что и обычное редактирование. Value
возвращается как предложение и записывается в основные поля только отдельным
`POST /tasks/{id}/prioritiser/value/approve`. Приоритет записывается в
`priority_score` (шкала 0–100) и `priority_justification` только специализированным
endpoint prioritiser. Обычные create/PATCH задачи не принимают legacy-поля
`financial_effect_ai*` и agent-managed поля приоритета. Карточка не использует
старые AI-поля как fallback. Недостаточные входные данные возвращаются как `422`,
недоступность сервиса или нарушение им контракта — как `502`.
Backend передаёт во внутренний Prioritiser capability header
`X-Prioritiser-Secret`; его значение задаётся `PRIORITISER_SECRET` и в
production не может оставаться локальным default.
Создание комментария принимает необязательный `client_request_id`. Upload
вложения принимает его как multipart form field, удаление вложения — как query
parameter. Повтор с тем же ключом и payload возвращает исходный результат без
создания дубля; повтор ключа с иными данными возвращает `409`.

### Teams и users

Обычные `/teams` и `/users` endpoints существуют отдельно от admin endpoints. Team resources доступны через `/teams/{team_id}/resources`. Наличие endpoint не означает разрешение его вызова любой роли.

### Reports

Поддерживаются registry/CRUD отчётов, выполнение сохранённого отчёта и специализированные directorate/DID operational reports. `GET /reports/team-weekly-report` возвращает текущую и предыдущую неделю, задачи в области доступа пользователя, сигналы `on_track/risk/blocker/decision`, результат, следующий шаг, запрос решения, снимки и дельту прогресса, готовность и агрегаты командного пульса. Выполнение стандартного отчёта `quarterly-goals` дополнительно возвращает рассчитанные `progress_freshness`, `progress_freshness_label` и `traffic_reason`, чтобы клиент отличал подтверждённое отставание от отсутствующего или давно не обновлявшегося факта.
`GET /reports/quarterly-goals/preparation` возвращает доступные пользователю цели и
`AD-HOC` текущего квартала, варианты месяца старта, рассчитанный план/светофор,
признак права изменения и сводку отсутствующих или устаревших фактов. `PUT
/reports/quarterly-goals/tasks/{task_id}` принимает обязательные `progress`
(`null` либо целое 0–100), `start_shift_id` и `version`; повторно проверяет вхождение
задачи в отчёт и принадлежность пользователя ответственной команде; сохраняет одну
строку и возвращает пересчитанные значения. Конфликт версии даёт `409`.
Directorate report выбирает доступные пользователю неудалённые задачи с непустым
подтверждённым (`is_ready=true`) статусом ближайшей незавершённой директорской
встречи. Квартал и срок задачи на выборку не влияют. Источником текста, готовности
и маркера показа лидеру трайба служит `TaskReportingStatus`, а не поля задачи.
Ответ также содержит статус предыдущей проведённой директорской встречи и право
пользователя изменять маркер текущего среза. Массив `teams` содержит все команды,
доступные пользователю по области чтения задач, включая команды без готовых
статусов (`total=0`, `tasks=[]`).
`POST` принимает необязательный `client_request_id`; `PUT` требует `version` и
также поддерживает idempotency key; `DELETE` требует query `version` и принимает
query `client_request_id`. Конфликт конкурентного изменения возвращает `409` с
кодом `report_version_conflict`.

### Admin

Admin API включает:

- роли, команды и пользователей;
- справочники и workspace/batch операции;
- dictionary locks;
- competency costs;
- проекты и теги;
- notification templates;
- display settings и labels;
- audit log и deletion impact.

Элементы `GET /admin/audit-log` содержат `request_id`; поиск журнала также
проверяет это поле. Значение совпадает с ответным `X-Request-ID` и идентификатором
в backend-логах.

Справочники, пользователи, роли и ответственные команд являются защищёнными данными. Их endpoints нельзя использовать для автоматической проверки документации или тестовых мутаций.

### Customer portal

`GET /customer/tasks` возвращает задачи в области текущего бизнес-заказчика и для
каждого элемента использует ту же ограниченную read-only customer-проекцию, что и
`GET /customer/tasks/{task_id}`: `id`, `public_id`, название, описание, прогресс,
даты, команда, статус и срок. Полный `TaskResponse` с внутренними оценками,
финансовыми, служебными и lock-полями в customer list/detail не используется.
Detail доступен, если задача находится в `business_customer_id` текущего
пользователя либо связана с его собственным `RequirementRequest`; удалённая или
не входящая ни в одну из этих областей задача получает `404`. Создание и
диалоговый сбор требований выполняются через Agent API, а не отдельный customer
POST endpoint. Проверено по коду и контрактным тестам 10.09.2026.

Ответы с задачами содержат внутренний числовой `id` для совместимости маршрутов и связей, а также пользовательский `public_id` по маске `TASK-000-001`. В интерфейсе и экспортах следует показывать `public_id`; `id` остаётся техническим ключом.

### Quick estimate

Группа `/quick-estimate` обслуживает epics, stories, task efforts, сортировку, завершение оценки и импорт backlog task в оценку.
`GET /quick-estimate/backlog-tasks` возвращает только задачи текущей команды на
подготовительных этапах «Новая задача», «Назначена команда», «Сбор требований»,
«Проверка требований» и «Уточнение требований». `POST
/quick-estimate/import-task/{task_id}` повторно проверяет команду, текущую версию
и допустимость исходного статуса; терминальные, уже планируемые и выполняемые
задачи получают `409` и не переводятся в экспресс-оценку. Проверено 09.09.2026.

`GET /quick-estimate` возвращает объект `readiness`: общий признак готовности,
количество готовых задач и структурированный список блокеров по задачам, эпикам и
историям. Для завершения в каждой задаче должен существовать хотя бы один эпик;
каждый конечный эпик без историй и каждая история должны содержать минимум одну
положительную оценку трудозатрат и не должны содержать отрицательных значений.
`PUT /quick-estimate/complete` повторно рассчитывает готовность на сервере и при
наличии блокеров возвращает `409` с кодом `quick_estimate_incomplete`, не изменяя
статусы задач. После успеха клиент предлагает прямой переход в PI-очередь с
контекстом завершённой передачи; пользователь без доступа к отчётам получает
безопасный возврат в командный бэклог. Проверено 09.09.2026.

### Notifications

Поддерживаются list, атомарный snapshot, unread count, summary, read/unread/read-all,
delete, restore, UX events и пользовательские preferences. `read-all` возвращает `changed_ids`,
чтобы клиент мог отменить массовую отметку через `/notifications/unread`. Лента, счётчики и сводка
возвращают только категории `assignment`, `reporting`, `decision`, `mention`, `comment`, `request`;
исторические записи других категорий из БД не удаляются, но в активный центр не
попадают. В `NotificationResponse.type` возвращается стабильный код события.
Из настроек доступен только `comment`; назначения, упоминания, решения по запросам и напоминания по
отчётным встречам или квартальным светофорам обязательны. Квартальное напоминание
использует type `quarterly.progress_update.required` и allowlisted target
`#/quarterly-goals-update?source=notification`. Категория `request` использует type `request.review.<status>` и allowlisted target `#/customer/request/{id}`. Отдельного endpoint ручного `resolve` нет:
напоминания закрываются доменным обновлением и следующей плановой проверкой.
Незакрытое обязательное `reporting` нельзя скрыть или перевести в прочитанное:
оно исключается из `read-all`, а `PUT /notifications/read` возвращает его id в
`blocked_ids`. Прочитанным такое уведомление становится только при доменном
закрытии после фактического заполнения требуемых статусов. Перевод конкретной
встречи в `held` дополнительно скрывает все её уведомления с `group_key`
`reporting_fill_<meeting_id>`, включая уже закрытые, не затрагивая напоминания
других встреч, и публикует для каждого получателя `notification.state.changed`
с действием `removed`. Восстановление такого уведомления через
`PUT /notifications/{id}/restore` запрещено ответом `409`; возврат в unread уже
запрещён общим условием для закрытых уведомлений и не публикует ложное live-событие.
Task-linked записи повторно фильтруются по текущему object-level read scope; после
отзыва доступа содержимое уведомления не возвращается.

`GET /notifications/snapshot` возвращает одну ревизию outbox, сводку, пять
первых элементов общего списка для колокольчика и dashboard, а также пять
незакрытых `reporting` для фильтра «Требуют действия». Общий список сортируется по
состоянию чтения: непрочитанные идут первыми; внутри непрочитанных и прочитанных
записи идут от новых к старым. При равной дате больший ID идёт первым. Все поверхности
используют этот ответ как единый согласованный срез и повторяют
чтение, если ревизия изменилась во время сборки. Каждый `NotificationResponse`
содержит серверный `target` с фиксированным `kind` и allowlisted внутренним
`url`; для напоминания `reporting_fill_<meeting_id>` ответ также содержит
актуальные `deadline` и `days_remaining`, рассчитанные по дате связанной встречи,
поэтому перенос встречи не оставляет в уведомлении устаревший срок. Legacy `action_url`
сохраняется для совместимости. Внешние URL,
неизвестные маршруты и лишние query-параметры заменяются безопасным fallback.

`POST /notifications/ux-events` принимает только фиксированные event/surface,
категорию, состояние и ограниченную длительность. Заголовок, текст, user ID и
произвольные метки endpoint не принимает; данные агрегируются в Prometheus.

`GET /events/stream` — авторизованный `text/event-stream`. Клиент передаёт cursor
через query `after` либо `Last-Event-ID`. События `task.*`, `requirement.*` и
`report.*` являются сигналом
инвалидации и содержат только ID, версию и названия изменённых полей; актуальные
данные клиент получает штатным GET. Персональные `notification.*` доступны
только получателю.

### Agent proxy

Backlog proxy поддерживает JSON `POST /agent/chat`, потоковый
`POST /agent/chat-stream`, сессии, reset, send-for-review, редактирование draft
section и persisted requirement requests. Внешний контракт Agent описан
отдельно в `../../agents/business-analyst/docs/API.md`. Потоковый endpoint ретранслирует
`text/event-stream` без накопления полного ответа и запрещает proxy buffering.
События `delta` содержат отображаемый текст, а завершающий `result` — полный
структурированный ответ.

Каждое chat-сообщение передаёт стабильный `message_id`: повтор одного
HTTP-запроса возвращает сохранённый ответ и не изменяет историю второй раз.
После клиентской отмены тот же идентификатор позволяет безопасно восстановить
уже завершённый сервером результат.

`GET /agent/session`, `GET /agent/session/{id}` и элементы `GET /agent/sessions` дополняются workflow-метаданными `request_id`, `request_status`, `request_version`, `request_url`, если с диалогом связан request текущего пользователя. `POST /agent/ux-event` принимает только фиксированный набор событий и outcomes, опционально `duration_ms`; текст диалога и другие высококардинальные данные endpoint не принимает и не сохраняет.

Review-ответы `GET /agent/requests`, `GET /agent/requests/review` и `GET /agent/requests/{id}` дополнительно содержат вычисленные сервером поля `review_deadline`, `stage_started_at`, `is_overdue` и `available_actions`. `review_deadline` берётся только из отдельного одноимённого атрибута draft и не подменяется ожидаемой датой результата или сроком связанной задачи. `stage_started_at` определяется по последнему событию текущего статуса с fallback на `updated_at/created_at`. `GET /agent/requests/review` принимает `limit` 1–500 (по умолчанию 250) и `offset`, сортировка стабильна по убыванию `created_at`. `available_actions` — источник истины для UI: `claim` доступен только для `submitted`, а `approve`, `return`, `reject` и `release` — назначенному ревьюеру в `in_review`; глобальный ревьюер дополнительно получает `reroute`. Статус `returned` ожидает повторной отправки заказчиком.

Метаданные восстановления также содержат `request_team_id`, `request_team_name`
и `review_comment`. Они позволяют показать фактический маршрут и замечание при
возврате с ревью. Успешная отправка и повторная отправка возвращают
`request_status` и `request_version`. При повторной отправке сохраняются ID
запроса и исходная команда, увеличивается версия. Если команда не выбрана при
первой отправке, используется команда профиля автора, а при её отсутствии —
общая очередь. Описание запроса и создаваемой задачи сохраняет все поля draft,
включая риски, зависимости, замечания и доказательства происхождения.

Проверено по коду и изолированным регрессионным тестам 08.09.2026:
`POST /agent/send-for-review` принимает `expected_draft_hash` просмотренной
редакции. Backend сверяет его со снимком агента и передаёт хеш агенту для
повторной проверки внутри блокировки сессии. В БД записывается подтверждённый
`draft` из ответа агента. Изменённый черновик или отличающаяся уже отправленная
редакция возвращают 409; идемпотентный успех допускается только для того же
снимка. Для совместимости поле необязательно у прежних API-клиентов; SPA его
передаёт. Ответ содержит `draft_revision` — SHA-256 canonical JSON полного draft
(`sort_keys`, UTF-8, разделители `,`/`:`, без NaN).

Карточки запросов возвращают `revision_history` (снимок, хеш, номер редакции,
автор, время отправки) и `status_history` (решение, комментарий, актор, редакция,
время). Счётчик `version` по-прежнему служит optimistic locking и отличается
от номера отправленной редакции. История прежних запросов начинается с явно
помеченного `legacy_snapshot`; неизвестная дата прежнего решения не выдумывается.

Клиент проверяет `action` и `success` даже при HTTP 200: `error`,
`validation_error` и `sent_locked` не являются подтверждением сохранения.
Для отказов HTTP 409 отображается бизнес-пояснение backend.

`GET /agent/teams/{team_id}/ba` доступен только пользователю с правом ревью выбранной команды и возвращает только её активных участников с ролью `BA/Участник команды` или `BA/Бизнес-аналитик`. То же ограничение проверяет `PUT /agent/requests/{id}/status` при переводе в `in_progress`; передать запрос пользователю без допустимой BA-роли нельзя. Status command дополнительно принимает ограниченные `action_reason`, `finding_resolutions` и `team_id`: причина обязательна для возврата `in_review → submitted`; сменить команду может только глобальный ревьюер. Событие истории сохраняет причину и результаты рассмотрения findings. При создании задачи `link_requirements` содержит ссылку на принятую редакцию request.

### Операционный outbox

`GET /admin/outbox/dead-letters` доступен только с permission `admin=full` и
возвращает пагинированные dead-letter события. Поиск проверяет тип события,
aggregate и текст последней ошибки.

`POST /admin/outbox/dead-letters/{event_id}/requeue` требует
`expected_attempts` и `client_request_id`. Несовпадение attempts возвращает
`409`; успешная операция сбрасывает claim/error/attempts и пишет audit в той же
транзакции. Массовый replay отсутствует.

Ответы backend содержат `X-Request-ID`; при включённом OpenTelemetry также
`X-Trace-ID`. Полный audit admin API возвращает оба идентификатора и позволяет
поиск по ним.

## Аутентификация

Большинство внутренних групп подключено с backend dependencies, исключающими customer-only пользователя. Отдельные роутеры добавляют более точные permission и object-level проверки.

Access JWT передаётся в `Authorization: Bearer`. Refresh cookie применяется только на auth endpoints. Полная модель — `SECURITY.md`.

## Ошибки

Фактические ответы формируются FastAPI, Pydantic и явными `HTTPException` в роутерах. Типовые статусы включают:

- `400` — некорректная операция или конфликт бизнес-условий;
- `401` — отсутствующая/недействительная аутентификация;
- `403` — недостаточно прав или недоверенный Origin;
- `404` — сущность не найдена;
- `409` — конфликт версии/блокировки или другое явно реализованное столкновение;
- `422` — ошибка валидации request schema;
- `429` — rate limit;
- `5xx` — необработанная ошибка или недоступная зависимость.

Единой пользовательской error envelope для всех endpoints не подтверждено. Для конкретной операции используй OpenAPI, код router и соответствующий тест.

## Конкурентное редактирование

Изменяющие операции над задачей передают текущий `version`, включая quick estimate,
PIP, ссылки, удаление и bulk-операции. Устаревшая версия возвращает `409` с кодом
конфликта и актуальной версией. Отсутствующая обязательная версия возвращает
`422` для body-схем или `428` для query/bulk-контрактов.

Переход статуса requirement request также требует `version`. Допустимые переходы
проверяются как конечный автомат; решение может принять закреплённый ревьюер.
Версия заявки и создаваемая при передаче в проработку задача фиксируются одной
транзакцией.

Edit lock задачи является атомарной lease-блокировкой с heartbeat. Она улучшает
UX, но источником целостности остаётся optimistic lock по `version`.

`client_request_id` в create/update задачи является идемпотентным ключом на всех
backend workers. Повтор того же ключа и payload не повторяет изменение. Повтор
ключа с иным payload возвращает `409` с кодом `idempotency_key_reused`.

## Пустые справочники — уточнение 17.10.2026

`POST /api/v1/admin/{dict_type}/lock` для поддерживаемого справочника без активных строк возвращает `locked=false`, `is_mine=false`, `version=0`; строки и фиктивная lease-запись не создаются. Ранее возвращался 404, что блокировало редактор пустых тегов.

Batch-save пустого справочника принимает исходную версию 0. На PostgreSQL транзакция блокирует соответствующую таблицу (`tags`, `departments` или `dictionary_items`) в `SHARE ROW EXCLUSIVE MODE` до проверки снимка и записи: конкурирующее появление строк не обрабатывается как второй пустой снимок. Для непустого справочника по-прежнему обязательны действующая собственная блокировка и совпадающая версия; нарушение даёт 423/409. Новые строки получают версию 1 и обычный срок блокировки. Пустой batch не разрешён (422).

Проверены реальное открытие пустых тегов без записи и четыре изолированных контракта (`backend/tests/admin_empty_dictionary_contracts.py`). Конкурентная запись на PostgreSQL не выполнялась: защищённые значения не менялись.
