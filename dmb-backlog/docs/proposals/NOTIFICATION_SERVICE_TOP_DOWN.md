# Сервис уведомлений: целевая модель Top-down

Статус: концепция для согласования. Документ описывает продуктовую и архитектурную модель; он не меняет текущие данные и API.

## 1. Зачем существует сервис

Уведомление должно помогать пользователю принять решение или выполнить действие вовремя. Сервис не является журналом всех изменений задачи: полный след изменений остаётся в истории и аудите.

Целевые результаты:

1. Не пропустить действие, которое ожидают лично от пользователя.
2. Вовремя увидеть риск срока, блокировку или эскалацию.
3. Узнать результат ранее инициированного процесса.
4. Получать обзор своей зоны ответственности без потока однотипных сообщений.

Перед созданием уведомления система отвечает на пять вопросов: произошло ли значимое событие; требуется ли действие; кто персонально или по зоне ответственности должен его получить; насколько срочно его показать; можно ли объединить его с другими.

## 2. Базовые понятия

- **Доменное событие** — бизнес-факт: `task.assigned`, `task.status.changed`, `request.rejected`.
- **Сигнал** — вычисленный факт: приближается срок, задача не обновлялась, отсутствует обязательная оценка.
- **Уведомление** — персонализированное представление события для одного получателя.
- **Канал** — центр уведомлений, toast, e-mail (позже — корпоративный мессенджер).
- **Приоритет доставки** — `urgent`, `action`, `info`; это не категория события.
- **Тема** — пользовательский раздел: `requests`, `tasks`, `collaboration`, `risks`, `system`.
- **Группа** — несколько уведомлений, объединённых по объекту или рабочему контексту.

## 3. Кого считаем получателем

Получатели определяются не только ролью, но и отношением к объекту.

- **Actor** — инициатор события; по умолчанию не уведомляется о собственном действии.
- **Assignee** — тот, от кого ожидается следующее действие.
- **Owner** — ответственный за задачу или запрос.
- **Author / customer** — инициатор требования.
- **Watchers / participants** — подписчики, упомянутые и участники обсуждения.
- **Team responsibility** — PO, PL, CL, IT PL соответствующей команды.
- **Portfolio responsibility** — лидер трайба.
- **Operational responsibility** — администратор только для системных сбоев, не для бизнес-событий.

Роль задаёт право и тип ответственности, а связь с конкретной задачей задаёт фактическую аудиторию. Массовая рассылка «всем пользователям роли» допустима только для портфельных и системных событий.

## 4. Каталог событий и ролей

### 4.1 Запрос бизнес-заказчика

| Событие | Кому | Приоритет | Представление |
|---|---|---|---|
| Запрос отправлен на ревью | PO/PL/CL выбранной команды; автору — подтверждение в интерфейсе без inbox | action | Inbox + toast ревьюерам |
| Запрос взят на ревью | Автор | info | Inbox, без toast |
| Запрос возвращён на уточнение | Автор | action | Inbox + постоянный toast с действием |
| Запрос отклонён | Автор | action | Inbox + toast, причина и «Открыть» |
| Назначен аналитик/исполнитель | Исполнитель; автору — info | action исполнителю, info автору | Inbox + toast исполнителю |
| Запрос принят / создана задача | Автор, исполнитель, ответственные команды | info/action по роли | Inbox; toast только исполнителю следующего шага |
| Запрос долго ожидает ревью | PO/PL/CL команды; после порога — лидер трайба | action → urgent | Сначала сводка, затем эскалация |

### 4.2 Жизненный цикл задачи

| Событие | Кому | Приоритет | Примечание |
|---|---|---|---|
| Назначен владелец | Новый владелец | action | Не уведомлять прежнего, если ему не требуется действие |
| Изменена команда | PO/PL/CL новой команды; владелец | action | Предыдущей команде — info только при снятии ответственности |
| Статус изменён в обычном потоке | Владелец, автор/заказчик, подписчики | info | Объединять изменения одной задачи |
| Задача переведена в «ХОЛД» | Владелец, PO/PL/CL, заказчик | urgent/action | Требовать причину и показывать её |
| Эскалация на ЛТ | Лидер трайба, владелец, PO/PL/CL | urgent | Toast + inbox; e-mail при отсутствии реакции |
| Задача выполнена / отклонена / не актуальна | Автор/заказчик, владелец, подписчики | info | Итог процесса, не скрывать в общей группе изменений |
| Изменился приоритет или дедлайн | Владелец, PO/PL/CL; заказчик при существенном влиянии | action/info | Указывать старое и новое значение |
| Существенно выросла оценка | PO/PL/CL, владелец; лидер трайба сверх порога | action | Порог задаётся правилом, не каждым изменением поля |

### 4.3 Совместная работа

| Событие | Кому | Приоритет | Примечание |
|---|---|---|---|
| `@mention` | Упомянутый | action | Всегда персональное, не отключается полностью |
| Ответ на комментарий | Автор родительского комментария | action | Не дублировать mention тому же получателю |
| Новый комментарий | Владелец и подписчики обсуждения | info | По умолчанию группировать; можно отключить |
| Добавлен файл | Участники задачи | info | Обычно только в дневной сводке |
| Пользователь начал редактирование | Не создавать inbox-уведомление | — | Это presence-индикатор в карточке, а не уведомление |
| Конфликт редактирования / потеря блокировки | Текущий редактор | urgent | Локальный постоянный toast/banner |

### 4.4 Сроки, качество и риски

| Сигнал | Кому | Приоритет | Рекомендуемое правило |
|---|---|---|---|
| Срок через 7 дней | Владелец | info | Один раз либо до изменения срока |
| Срок через 3 дня | Владелец, PO/PL/CL | action | Не повторять чаще раза в сутки |
| Срок завтра / просрочен | Владелец, PO/PL/CL | urgent | Ежедневно, но объединять по пользователю |
| Нет обновления 5 рабочих дней | Владелец | action | Сбросить после значимого обновления |
| Нет обновления дольше порога команды | PO/PL/CL | action | Сводка по команде, не отдельный шум |
| Нет обязательных данных | Тот, кто отвечает за текущий этап | action | Проверять требования конкретного статуса |
| Массовый риск портфеля | Лидер трайба | urgent/action | Портфельная сводка с drill-down |

### 4.5 Система

| Событие | Кому | Канал |
|---|---|---|
| Плановые работы / изменение доступности | Затронутые пользователи | Banner + inbox |
| Ошибка интеграции, не обработано событие | Администратор/эксплуатация | Мониторинг, затем inbox; не бизнес-пользователям |
| Изменение прав пользователя | Сам пользователь; администратор видит аудит | Inbox |
| Новая функция | Только релевантная аудитория | Inbox, низкий приоритет |

## 5. Классификация

Одна плоская `category` недостаточна. Уведомление классифицируется независимо по пяти осям:

1. **Тема:** запросы, задачи, обсуждения, сроки/риски, система.
2. **Тип события:** стабильный машинный код, например `task.deadline.overdue`.
3. **Приоритет:** `urgent` — немедленная реакция; `action` — есть действие; `info` — осведомление.
4. **Ожидание:** `requires_action`, `informational`, `resolution`.
5. **Область:** личная, задача, команда, портфель, система.

Отдельно хранится жизненный цикл доставки: создано, доставлено в активную сессию, просмотрено, прочитано, выполнено/разрешено, скрыто. «Прочитано» не равно «выполнено».

## 6. Группировка и защита от шума

Используются три уровня объединения.

### Группа по объекту

Последовательные информационные события одной задачи за короткое окно показываются одной карточкой: «В задаче #2417 — 4 обновления». Внутри раскрывается хронология. `mention`, назначение, возврат на уточнение и эскалация в такую группу не прячутся.

Ключ: `recipient + topic + object_type + object_id`, окно 15–30 минут.

### Рабочая сводка

Однотипные сигналы пользователя объединяются в actionable digest: «3 задачи требуют обновления», «5 сроков на этой неделе». Каждая строка ведёт в отфильтрованный список.

Ключ: `recipient + rule_code + responsibility_scope + period`.

### Тред процесса

События одного запроса/эскалации образуют цепочку. Финальное решение показывается как отдельный результат, даже если предыдущие сообщения прочитаны.

Дедупликация выполняется по `event_id + recipient_id`; повторная доставка одного события не создаёт новую карточку. Изменение состояния сигнала обновляет существующую карточку, а не увеличивает бесконечный `group_count`.

## 7. Уведомления во время работы

### Центр уведомлений

Колокольчик открывает боковую панель поверх текущего экрана, не уводя пользователя со страницы. В панели три представления:

- **Требуют действия** — непросроченные персональные действия и риски;
- **Все** — хронологическая лента;
- **Сводки** — командные и портфельные агрегаты.

Карточка содержит: причину, объект, инициатора, время, ожидаемое действие и одну основную кнопку. Переход открывает точный объект/вкладку, а не общий backlog.

### Toast / всплывающее уведомление

- `urgent`: постоянный до действия/явного закрытия; одновременно не более одного, остальные в очередь.
- `action`: показывать 8–12 секунд с кнопкой; затем остаётся в центре.
- `info`: toast только для результата пользовательского действия или важных изменений; остальные сразу в центр.
- Не показывать toast инициатору собственного события.
- Не перекрывать формы и модальные окна; во время ввода несрочные toast откладывать.
- В toast никогда не помещать длинную сводку: максимум одна причина и одно действие.

### Доставка в браузер

Для первой версии рекомендуется **SSE**: сервер отправляет пользователю `notification.created`, `notification.updated`, `unread_count.changed`; клиент автоматически переподключается и догружает пропущенное по cursor. SSE проще WebSocket для однонаправленного потока. WebSocket имеет смысл только если единый канал одновременно обслуживает presence, совместное редактирование и двусторонние события.

При отсутствии real-time соединения остаётся fallback polling раз в 60–120 секунд и обязательная синхронизация при возврате вкладки в `visible`.

### Внешние каналы

Этап 1 — только in-app. Этап 2 — e-mail для `urgent`, если пользователь не просмотрел сообщение за заданный SLA, и ежедневные digest. Конкретный канал должен выбираться политикой события, а пользователь может отключать только необязательные каналы. Критические персональные назначения и эскалации полностью отключать нельзя.

## 8. Настройки пользователя

Настройки формулируются понятным языком, а не внутренними кодами:

- действия, назначенные мне;
- упоминания и ответы;
- изменения моих задач;
- сроки и риски;
- командная сводка;
- продуктовые и системные новости.

Для каждой темы: немедленно, сводкой, только в центре, выключено — если политика разрешает. Также задаются quiet hours; `urgent` остаются в центре и могут обходить quiet hours только по отдельной организационной политике.

## 9. Целевая архитектура

```text
Domain transaction
  -> outbox event
  -> notification worker
       -> policy/rule catalog
       -> recipient resolver
       -> deduplication + grouping
       -> notification + delivery records
       -> SSE broker / e-mail adapter
  -> client notification store
       -> bell panel
       -> toast queue
       -> badge
```

Основные правила:

- Бизнес-код публикует событие, но не формирует текст и не выбирает получателей.
- Событие и изменение доменной сущности фиксируются атомарно через transactional outbox.
- Worker идемпотентен; повторная обработка безопасна.
- Recipient resolver проверяет роль, связь с объектом, активность пользователя и доступ к объекту.
- Шаблон отвечает только за текст; аудитория, обязательность и приоритет задаются версионируемой политикой.
- Плановые правила вычисляют сигнал отдельно по каждой зоне ответственности.
- Все переходы доставки наблюдаемы: latency, ошибки, retry, dead-letter.

Минимальные логические сущности будущей модели: `notification_events`, `notification_rules`, `notifications`, `notification_deliveries`, `notification_preferences`, `notification_groups`, `notification_outbox`. Физическую схему следует проектировать после согласования каталога событий; ручные `ALTER TABLE` не нужны.

## 10. Что в текущей реализации следует изменить

1. Убрать выбор получателей из функций вида `notify_*` и централизовать правила аудитории.
2. Не считать начало редактирования inbox-событием; перенести его в presence UI.
3. Исправить плановые проверки: сейчас получатели общей выборки берутся из первой попавшейся задачи, поэтому сводка может уйти не тем людям.
4. Не подменять категории `deadline`, `stale`, `attrs` значением `system`: это ломает фильтрацию и пользовательские настройки.
5. Исключать инициатора события, когда от него не требуется дальнейшее действие.
6. Разделить прочтение, скрытие и выполнение ожидаемого действия.
7. Вместо общего `#/backlog` формировать deep link к задаче, запросу, комментарию или отфильтрованной сводке.
8. Добавить real-time доставку и синхронизацию счётчика на всех страницах.
9. Перейти от `group_count` к группам с доступными дочерними событиями и корректным разрешением сигнала.
10. Не использовать редактируемые текстовые шаблоны как место бизнес-логики.

## 11. Этапы внедрения

### Этап 0 — согласование продукта

Утвердить каталог событий, владельца каждого правила, матрицу ролей, SLA и обязательность каналов. Для каждого события определить конкретное ожидаемое действие и критерий разрешения.

### Этап 1 — качественный in-app MVP

Ввести стабильные коды событий и централизованный recipient resolver; исправить дедупликацию и плановые сводки; добавить deep links, панель колокольчика и toast queue; подключить SSE. Поддержать самые ценные события: назначение, mention/ответ, запрос на ревью/уточнение/решение, hold/эскалация, близкий и просроченный срок.

### Этап 2 — управление шумом

Добавить subscriptions/watchers, actionable digests, quiet hours, статус `resolved`, метрики реакции и административный каталог политик.

### Этап 3 — внешняя доставка

Добавить e-mail escalation и ежедневные сводки через delivery adapters; затем при необходимости корпоративный мессенджер.

## 12. Метрики качества

- доля `action/urgent`, открытых пользователем в пределах SLA;
- медианное время от события до доставки и до действия;
- число уведомлений на активного пользователя в день по теме;
- доля скрытых без открытия и отключённых тем — индикатор шума;
- доля дублей и повторно обработанных событий;
- число просроченных действий, у которых уведомление было доставлено;
- ошибки recipient resolver: уведомление без доступа к объекту — критический дефект;
- успешность SSE и fallback-доставки.

Главный продуктовый критерий: уведомление считается полезным не потому, что оно создано, а потому, что нужный пользователь вовремя понял причину и выполнил ожидаемое действие.
