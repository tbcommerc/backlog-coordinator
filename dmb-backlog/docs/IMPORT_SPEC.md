# Импорт задач из CSV — AS-IS

> Статус: проверено по `backend/import_service.py`,
> `backend/routers/tasks_router.py` и `frontend/js/components/modal.js` на 2026-09-01.

## Контракт

- Endpoint: `POST /tasks/import`, multipart-поле `file`.
- Backend принимает только файл с расширением `.csv`; пустой файл отклоняется с `400`.
- Требуется аутентификация и право `backlog_team: write_own`.
- Поддерживаются UTF-8 с BOM и Windows-1251; разделитель `,` или `;`
  определяется по первой непустой строке.
- Заголовки сопоставляются с ключами из белого списка `IMPORTABLE_FIELDS` через
  записи `field_labels`; также распознаются сами ключи без учёта регистра.
- Неизвестные заголовки игнорируются.

Frontend позволяет выбрать CSV, XLS или XLSX и преобразует Excel-файл в CSV перед
отправкой. Это клиентская возможность: прямой API-запрос с `.xls`/`.xlsx` backend
не принимает.

## Валидация строки

Источником полного списка импортируемых полей служит
`backend/import_service.py:IMPORTABLE_FIELDS`.

- Обязательность берётся из `field_labels.is_required`; строка с незаполненным
  обязательным полем пропускается (`required_missing`).
- Команда, канал, заказчик, подразделение, проект, тип, приоритет, срок и статус
  разрешаются по загруженным справочникам. Не найденное значение — фатальная
  ошибка соответствующего типа `*_not_found`.
- Не найденный исполнитель даёт нефатальную ошибку `owner_not_found`: задача
  сохраняется без исполнителя.
- Некорректные дата, число или прогресс дают соответственно `invalid_date`,
  `invalid_number`, `invalid_progress`.
- Неожиданная ошибка строки или сохранения обозначается `unknown_error`.

Поддерживаемые даты: `YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY`, `DD.MM.YY`,
`DD/MM/YY`. Прогресс должен быть целым числом от 0 до 100.

## Сохранение и результат

Валидные строки создают обычные записи `tasks`. Ошибочные строки пропускаются,
не останавливая остальные. Для созданной задачи сервис также записывает ссылки
Jira в `task_jira_links`, отдельные поля истории в `task_history` и событие
`action=import` в `audit_log`.

Ответ содержит:

```json
{
  "total": 2,
  "created": 1,
  "skipped": 1,
  "errors": [],
  "task_ids": [123]
}
```

Каждая ошибка содержит `row`, `field`, `field_label`, `value`, `type`, `message`
и `fatal`. При ошибке общего `commit` транзакция откатывается, `created`
становится равным нулю и добавляется `unknown_error`.

## Важные границы

- В модели `Task` нет поля `external_id`; поиск дубликатов по внешнему ID не
  реализован.
- Импорт читает справочники и пользователей только для разрешения ссылок; он не
  должен изменять защищённые данные.
- Значение статуса по умолчанию в сервисе импорта — числовой ID `1`. Это
  фактическое поведение кода, а не гарантированный бизнес-инвариант справочника.
- Автотесты `backend/tests/test_import.py` создают тестовые справочники и
  пользователей. В рабочем окружении их нельзя запускать против штатной БД.

## Поля отчёта ДИД — проверено 04.09.2026

Импорт поддерживает `did_client_group_id` («Клиент ДИД» / «Группировка для клиентов ДИД») и существующий `business_customer_id` («Бизнес-заказчик»). Значения сопоставляются с активным справочником клиентов ДИД по названию/коду и существующим справочником «Бизнес-заказчики» по имени. Однофамильцы разрешаются по подразделению строки; неоднозначные и неизвестные значения дают нефатальное предупреждение, поле остаётся пустым. Новые записи справочников не создаются. См. [отчёт ДИД](DID_BACKLOG_REPORT.md).
