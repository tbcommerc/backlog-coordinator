# Логика работы страниц Backlog coordinator

**Версия:** 3.2  
**Дата:** 2026-07-25

---

## Навигация

### Sidebar (левая панель)

Пункты меню сгруппированы по разделам:

**Управление бэклогом:**
- Главная (`#/dashboard`)
- Бэклог DMB (`#/backlog`) — требуется `backlog_dmb != none`
- Бэклог команды (`#/team-backlog`) — требуется `backlog_team != none`
- Канбан-доска (`#/kanban`) — требуется `backlog_dmb != none`

**Аналитика:**
- Статусы для встреч (`#/reports`) — требуется `reports != none`
- Аналитика ЛТ (`#/analytics/tribe`) — требуется `analytics != none`
- Аналитика PO/PL (`#/analytics/po-pl`) — требуется `analytics != none`

**Бизнес-заказчику:**
- Мои задачи (`#/customer`) — требуется `customer != none`
- Создать задачу (`#/customer/create`) — требуется `customer != none`

**Настройки и администрирование:**
- Мои уведомления (`#/notifications`) — всегда доступно
- Настройки (`#/settings`) — требуется `settings != none`
- Администрирование (`#/admin`) — требуется `admin != none`
- Аудит действий (`#/audit-log`) — требуется `admin != none`

Пункты, на которые у пользователя нет прав (`none`), скрываются из меню.

### Breadcrumbs (хлебные крошки)
Автоматически формируются роутером на основе текущего пути. Формат: `Главная › Бэклог DMB › ...`

## 1. Dashboard (Главная) — `#/dashboard`

### Описание
Обзорная страница с ключевыми метриками портфеля. Доступна всем пользователям.

### Состояния
- **Загрузка**: скелетон-компоненты (placeholder с анимацией pulse) для каждого виджета. 4 KPI-карточки отображаются серыми прямоугольниками, график — пустым контейнером.
- **Данные загружены**: все виджеты заполнены данными. Квартальный прогресс-бар, KPI (4 числа), уведомления (до 3), риски (до 3), кольцевая диаграмма.
- **Ошибка**: виджет ошибки с сообщением «Не удалось загрузить данные» и кнопкой «Повторить».
- **Нет данных**: KPI-карточки показывают 0, график пустой, уведомления и риски — «Нет данных».

### Состояния загрузки виджетов
- **Квартальный прогресс-бар**: вычисляется на клиенте (не требует API), всегда доступен.
- **KPI-карточки**: при загрузке `GET /tasks/stats` — скелетон. Ошибка: красный тост «Ошибка загрузки статистики».
- **Уведомления и риски**: при загрузке `GET /notifications` — скелетон. Пусто: «Уведомлений нет» / «Рисков нет».
- **Трудозатраты по типам**: при загрузке — скелетон круговой диаграммы. Пусто: «Нет данных».

### Виджеты
1. **Квартальный прогресс-бар** — визуализация текущего квартала с метками «Начало экспресс-оценки» (за 40 дней) и «PIP» (за 7 дней)
2. **KPI-карточки** (4 шт): Всего задач, В работе, Под риском, Ключевые проекты
3. **Уведомления и риски** — два виджета рядом: последние уведомления (до 3) и топ рисков (до 3), с кнопкой «Ещё N»
4. **Быстрые действия** — ссылки: Все задачи, Добавить задачу, Канбан-доска, Аналитика
5. **Трудозатраты по типам** — кольцевая диаграмма (Chart.js doughnut), переключатели: Моя команда / Трайб, Квартал / С НГ

## 2. Бэклог DMB — `#/backlog`

### Описание
Полный список всех задач платформы с тулбаром фильтрации.

### Состояния
- **Загрузка**: скелетон таблицы (10 строк с серыми прямоугольниками) + тулбар в disabled-состоянии. Индикатор загрузки «Загрузка задач...».
- **Данные загружены**: таблица с данными, активный тулбар, фильтры, поиск, сортировка, пагинация.
- **Ошибка**: сообщение «Ошибка загрузки данных. Попробуйте обновить страницу» + кнопка «Повторить».
- **Нет данных**: сообщение «Задачи не найдены» с предложением изменить фильтры или кнопкой «Создать задачу».

### Элементы
- **Тулбар**: поиск (debounce 250ms), сортировка, фильтры (статус, приоритет, команда, проект, тип, владелец, канал, подразделение), настройка колонок, переключение таблица/карточки, экспорт Excel, кнопка «Добавить задачу»
- **Таблица**: sticky-заголовок, сортировка по клику на колонку, клик по строке → карточка задачи
- **Карточки**: альтернативный вид (grid), та же информация в компактном формате
- **Кнопка «Добавить задачу»**: открывает модальное окно создания задачи с обязательными полями

### Доступ
- PO/PL/CL/Admin — полный (редактирование)
- Developer — read-only
- Бизнес-заказчик — read-only

### Состояния

- **Нет данных**: сообщение «В вашей команде нет задач» + кнопка «Создать задачу».

### Элементы

### Доступ
- PO своей команды — полный + bulk-операции
- Developer — read-only

## 4. Канбан-доска — `#/kanban`

### Описание
Визуальное управление потоком задач. 13 колонок по статусам.

### Состояния
- **Загрузка**: 13 пустых колонок с индикаторами загрузки «Загрузка...».
- **Данные загружены**: 13 колонок с карточками задач, счётчиками в заголовках.
- **Ошибка**: сообщение «Не удалось загрузить канбан-доску» + кнопка «Повторить».
- **Нет данных**: пустые колонки с надписью «Нет задач» в каждой.

### Колонки
НОВАЯ ЗАДАЧА → НАЗНАЧЕНА КОМАНДА → СБОР ТРЕБОВАНИЙ → ПРОВЕРКА ТРЕБОВАНИЙ → УТОЧНЕНИЕ ТРЕБОВАНИЙ → ЭКСПРЕСС-ОЦЕНКА → ПРИНЯТИЕ РЕШЕНИЯ → ПРИНЯТА В РАБОТУ → ЭСКАЛАЦИЯ НА ЛТ → ХОЛД → ОТКЛОНЕНА → НЕ АКТУАЛЬНА → ВЫПОЛНЕНА

### Логика
- Drag-and-drop карточек между колонками → PUT `/tasks/{id}` с новым status_id
- Клик по карточке → модальное окно задачи
- Счётчик задач в заголовке каждой колонки

## 5. Карточка задачи (Modal)

### Состояния
- **Загрузка**: модальное окно с пустыми полями и индикатором загрузки в заголовке.
- **Данные загружены**: полная карточка задачи с заполненными полями.
- **Ошибка**: тост «Не удалось загрузить задачу», модальное окно закрывается.
- **404**: тост «Задача не найдена», модальное окно закрывается.

### Режим просмотра
- **Шапка** (sticky): ID, статус, приоритет, название, бейдж «Ключевой проект»
- **Блокировка**: если задача редактируется другим пользователем — жёлтый баннер «Редактируется пользователем X (до HH:MM)», кнопка редактирования серая. Polling каждые 30с.
- **Статус и приоритет**: is_from_leadership, is_regular, rejection_reason
- **Основная информация**: команда, канал, подразделение, проект, тип, владелец, дедлайн, дедлайн PO, прогресс
- **Ответственные**: owner, responsible_po, business_analyst, it_product_lead
- **Сроки и оценки**: deadline, ICE Score, effort_days, effort_rub, financial_effect, C/V
- **Описание**: description, DoD, What-If, комментарий, status_comment
- **Ссылки**: link_mockups, link_jira
- **Вкладка «Комментарии»**: лента комментариев + форма ввода с @-упоминаниями

### Режим редактирования
- Все поля становятся редактируемыми (input/select/textarea/checkbox)
- **Блокировка**: перед входом в режим редактирования — POST `/tasks/{id}/lock`. Если 423 — тост с ошибкой, редактирование запрещено. При сохранении или закрытии модалки — DELETE `/tasks/{id}/lock` (fire-and-forget). Если lock не освобождён — автоматически истекает через 15 минут.
- **Оптимистическая блокировка (version)**: при сохранении клиент передаёт текущую версию задачи (`version`). Если версия в БД отличается — HTTP 409 Conflict.
- Причина отклонения показывается только при статусе «ОТКЛОНЕНА»
- При сохранении: PUT `/tasks/{id}` → task_history → тост

### Конфликт версий (optimistic locking)
- При 409 Conflict отображается модальное окно «Конфликт версий» с двухколоночным diff-представлением:
  - **Заголовок**: иконка предупреждения, название, описание ситуации
  - **Информация о версиях**: текущая версия на сервере и ваша версия
  - **Таблица различий** ( diff-table--selectable ):
    - Колонки: радио-кнопка «Сервер» | радио-кнопка «Ваше» | Название поля | Значение на сервере | Ваше значение
    - По умолчанию для каждого конфликтного поля выбрано значение с сервера (radio checked)
    - Подсветка выбранного значения (сервер — зелёный фон, ваше — синий фон)
    - Прокручиваемый контейнер (max-height: 360px) при большом количестве изменений
  - **Кнопки действий** (горизонтальный ряд):
    1. **Сохранить выбранные** (primary) — отправляет PUT с комбинированными данными: для каждого поля берётся значение из выбранной радио-кнопки. При конфликте показывается повторный diff
    2. **Принудительно сохранить** (danger) — отправляет PUT с `force_save=true`, перезаписывая все серверные данные вашими
    3. **Обновить с сервера** (secondary) — закрывает модалку конфликта, загружает актуальные данные с сервера, открывает карточку в режиме просмотра
    4. **Отмена** — закрывает модалку конфликта, возвращает в режим редактирования
- Закрытие модалки по клику на backdrop

### Режим создания (Новая задача)
- Открывается по кнопке «Добавить задачу» в тулбаре Бэклога DMB / Бэклога команды / Канбан-доски
- **Обязательные поля** (помечены звёздочкой, валидация на клиенте):
  - Название задачи (text, min_length=1)
  - Команда (select, загружается из API `/teams`)
  - Приоритет (select, по умолчанию СРЕДНИЙ)
  - Описание (textarea, min_length=1)
- **Дополнительные поля** (опциональные):
  - Тип задачи, канал поступления, проект, бизнес-заказчик
  - Дедлайн, дата поступления
  - Трудозатраты (дни, руб), Финансовый эффект (руб)
  - ICE: Impact, Confidence, Ease (1-10)
  - Ключевой проект, От руководства, Регулярная (чекбоксы)
  - Ссылки на макеты, Jira
  - Комментарий
- **Валидация**: при пустых обязательных полях — подсветка красным + сообщение «Поле обязательно для заполнения», кнопка «Создать задачу» не отправляет форму
- **При сохранении**:
  1. `POST /api/v1/tasks` → задача создаётся со статусом «НОВАЯ ЗАДАЧА» (status_id=1)
  2. Бэкенд авторассчитывает C/V = financial_effect / effort_rub (если оба заполнены)
  3. Бэкенд авторассчитывает ICE Score = (Impact × Confidence × Ease) / 10 (если все три заполнены)
  4. Создаётся запись в `task_history` (все обязательные поля + заполненные опциональные)
  5. Создаётся запись в `audit_log` (action=create)
  6. Тост «Задача создана» + обновление таблицы задач

## 7. Статусы для встреч — `#/reports`

### Состояния
- **Загрузка**: 4 карточки-скелетона с градиентной анимацией.
- **Данные загружены**: 4 карточки отчётов с названиями и описаниями.
- **Ошибка при выполнении отчёта**: тост «Не удалось выполнить отчёт» + данные таблицы не меняются.

### Описание
4 стандартных отчёта в виде карточек с градиентами:
- Директорат (priority = ВЫСОКИЙ + риски)
- DID (did_status в работе/требует решения/блокировано)
- Проекты (key_project = true)
- Рег-директора (ключевые проекты)

Клик по карточке → выполнение отчёта → таблица с результатами + кнопка экспорта.

### Пользовательские отчёты (вкладка «Отчёты» в админке)
Администратор может создавать, редактировать, удалять и выполнять пользовательские отчёты.

**Создание:**
1. Нажать «Добавить новый отчёт» на вкладке «Отчёты»
2. Заполнить форму: название (обязательно), описание, видимость (только я / все)
3. Выбрать поля для отображения (checkboxes: до 27 атрибутов задачи)
4. Настроить фильтры (поле + оператор + значение; динамическое добавление/удаление строк)
5. Выбрать группировку (по командам/проектам/статусам/приоритетам/подразделениям)
6. Выбрать сортировку (поле + направление)
7. Нажать «Создать» → `POST /reports`

**Просмотр и выполнение:**
- Клик по карточке отчёта → открывается страница отчёта с деталями (фильтры, группировка, сортировка)
- Нажать «Выполнить» → `GET /reports/{id}/execute` → таблица результатов с группировкой
- Кнопка «Назад» → возврат к списку

**Редактирование/удаление:**
- Иконка ✏️ на карточке → модалка редактирования → `PUT /reports/{id}`
- Иконка 🗑️ на карточке → подтверждение → `DELETE /reports/{id}`

## 8. Аналитика

#### Состояния (для обеих аналитик)
- **Загрузка**: скелетоны графиков (прямоугольники и круги с анимацией pulse).
- **Данные загружены**: графики Chart.js, таблицы с данными.
- **Ошибка**: тост «Не удалось загрузить аналитику», графики пустые.
- **Нет данных**: графики показывают пустые состояния с надписью «Нет данных для отображения».

### Аналитика ЛТ — `#/analytics/tribe`
- Топ задач по C/V (bar chart)
- Задачи с низким C/V (C/V < 1.0)
- Риски по командам
- Здоровье портфеля (pie chart статусов)
- Топ команд по фин. эффекту (таблица)

### Аналитика PO/PL — `#/analytics/po-pl`
- Загрузка команд (workload)
- Соблюдение сроков (deadline compliance)
- Прогресс ключевых проектов
- Дефицит атрибутов (missing attributes)

- **Данные загружены**: список уведомлений с разбивкой по вкладкам.
- **Ошибка**: тост «Не удалось загрузить уведомления».

## 10. Настройки — `#/settings`

### Состояния
- **Загрузка**: страница отображается сразу (настройки из localStorage). Данные пользователя загружаются через `GET /auth/me`.
- **Данные загружены**: все секции настроек активны.
- **Ошибка загрузки профиля**: тост «Не удалось загрузить профиль», настройки темы и внешнего вида доступны из кеша.

- **Внешний вид**: тёмная/светлая тема (авто по системе), 10 акцентных цветов, компактный режим
- **Профиль**: ФИО, email, роль, команда
- Настройки сохраняются в localStorage, тема — в `data-theme` на `<html>`

## 11. Администрирование — `#/admin`

### Состояния
- **Загрузка**: скелетон вкладок и содержимого.
- **Данные загружены**: активная вкладка с CRUD-интерфейсом.
- **Ошибка**: тост «Не удалось загрузить данные» + пустое состояние вкладки.
- **Нет данных**: сообщение «Нет записей» + кнопка «Добавить».

### Вкладки

**Команды:**
- Карточки команд в grid (320px min)
- Аватар с аббревиатурой, название, руководители (PL/PO/CL/IT PL), описание
- Кнопки: редактировать, удалить
- Модалка редактирования: название, тип команды, цвет, PL, PO, CL, IT PL, описание, домен
- При удалении — проверка: нет пользователей и задач в команде

**Пользователи:**
- Таблица: ФИО (с аватаром), роль, команда, email, статус
- Сортировка по всем столбцам
- Поиск по ФИО (debounce 300ms) с кнопкой очистки
- Модалка: ФИО, email, роль, команда, статус

**Роли:**
- Таблица: название, права по 7 разделам, статус
- Модалка: название, описание, 7 уровней доступа
- Защита: нельзя лишить себя админского доступа

**Справочники (9 типов):**
- Карточки: приоритеты, статусы, типы задач, бизнес-заказчики, каналы, сроки, подразделения, типы команд, статусы проектов
- Модалка: список значений с цветом, кодом, кнопками добавления/удаления
- **Блокировка:** при открытии модалки отправляется `POST /admin/{dict_type}/lock` — справочник блокируется на 15 минут
- **Индикация на карточках:** жёлтый баннер «Редактируется: [Имя]» на заблокированных карточках
- **Попытка входа:** если справочник заблокирован другим пользователем — показывается toast с именем блокирующего, вход блокируется
- **Сохранение:** PUT/POST/DELETE проверяют блокировку на сервере (HTTP 423 при конфликте)
- **Закрытие/сохранение:** снятие блокировки через `DELETE /admin/{dict_type}/lock`
- **Optimistic locking:** поле `version` инкрементируется при каждом PUT; клиент может обнаружить конфликт версий

**Уведомления (шаблоны):**
- Таблица: название, текст, адресаты, срок, регулярность, статус
- Модалка: все поля шаблона

**Отчёты:**
- Две секции: «Стандартные отчёты» (read-only) и «Пользовательские отчёты» (CRUD)
- Карточки пользовательских отчётов: название, описание, число фильтров/полей, группировка, публичность
- Кнопка «Добавить новый отчёт» → модалка с формой
- Клик по карточке → просмотр деталей отчёта и выполнение
- Иконки редактирования/удаления на каждой карточке

## 12. Ключевые пользовательские сценарии

### 12.1 Сценарий: Создание задачи бизнес-заказчиком

1. Пользователь (Бизнес-заказчик) открывает страницу `#/customer`
2. Нажимает кнопку «Создать задачу» → переход на `#/customer/create`
3. Чат-интерфейс последовательно запрашивает:
   - Название задачи
   - Описание
   - Бизнес-заказчик (автоматически)
   - Подразделение
   - Приоритет
   - Желаемый срок
4. После заполнения → нажимает «Отправить»
5. `POST /api/v1/tasks` → задача создаётся со статусом «НОВАЯ ЗАДАЧА»
6. Тост «Задача создана», редирект на `#/customer`
7. Задача отображается в таблице «Мои задачи»

### 12.1a Сценарий: Создание задачи из бэклога (PL/PO/ЛТ)

1. Пользователь открывает `#/backlog` (или `#/team-backlog`, `#/kanban`)
2. Нажимает кнопку «Добавить задачу» в тулбаре
3. Открывается модальное окно «Создать задачу»
4. **Обязательные поля**: Название, Описание, Команда, Приоритет (помечены звёздочкой)
5. Пользователь заполняет обязательные поля + опциональные (если нужно):
   - Тип задачи, канал поступления, проект, бизнес-заказчик
   - Дедлайн, дата поступления
   - Трудозатраты (дни, руб), Фин. эффект
   - ICE: Impact, Confidence, Ease (1-10 each)
   - Чекбоксы: ключевой проект, от руководства, регулярная
6. Нажимает «Создать задачу»
7. **Валидация на клиенте**: если обязательные поля пустые — подсветка красным, отправка блокируется
8. **Валидация на сервере**: `POST /api/v1/tasks` → Pydantic проверяет `title` (min_length=1), `team_id` (required), `priority_id` (required)
9. **Бэкенд обрабатывает**:
   - Устанавливает `status_id = 1` (НОВАЯ ЗАДАЧА) если не указан
   - Авторассчитывает `cv = financial_effect / effort_rub` (если оба поля заполнены и effort_rub > 0)
   - Авторассчитывает `ice_score = (impact × confidence × ease) / 10` (если все три поля заполнены)
   - Записывает в `task_history` (title, status_id, priority_id, team_id + опциональные)
   - Записывает в `audit_log` (action=create, entity_type=task)
10. Тост «Задача создана» + автоматическое обновление таблицы задач
11. Задача отображается в бэклоге с ID, статусом «НОВАЯ ЗАДАЧА» и приоритетом

3. **Загрузка файла (кнопка):** Нажимает зону загрузки → открывается системный диалог выбора файла

### 12.10 Сценарий: Разрешение конфликта версий при сохранении задачи

**Точка входа:** Кнопка «Сохранить» в модалке редактирования задачи

**Сценарий:**
1. PO редактирует задачу, параллельно другой пользователь обновляет ту же задачу
2. PO нажимает «Сохранить» → `PUT /api/v1/tasks/{id}` с текущей `version`
3. Бэкенд обнаруживает несовпадение version → HTTP 409 Conflict с `{ current_version, submitted_version, task }`
4. Открывается модальное окно «Конфликт версий» с таблицей различий:
   - Каждое изменённое поле отображается строкой с двумя радио-кнопками: «Сервер» / «Ваше»
   - По умолчанию выбрано значение с сервера
   - Выбранное значение подсвечивается (сервер — зелёный, ваше — синий)
5. **Вариант A: «Сохранить выбранные»** — PO выбирает нужные значения по полям:
   - Для каждого конфликтного поля ставит radio-кнопку на нужное значение
   - Нажимает «Сохранить выбранные»
   - Клиент собирает данные: для выбранных «серверных» полей берёт значение из серверной задачи, для «ваших» — из формы
   - Отправляется `PUT /api/v1/tasks/{id}` с комбинированными данными и новой `version`
   - Успех: тост «Задача сохранена с выбранными значениями», модалка закрывается
   - Если снова 409: повторное открытие модалки конфликта с обновлёнными данными
6. **Вариант B: «Принудительно сохранить»** — PO перезаписывает все поля своими данными:
   - Отправляется `PUT /api/v1/tasks/{id}` с `force_save: true`
   - Бэкенд принимает данные даже при несовпадении version
   - Тост «Задача сохранена (принудительно, версия перезаписана)»
7. **Вариант C: «Обновить с сервера»** — PO сдаётся:
   - Модалка конфликта закрывается, модалка задачи перезагружается с серверными данными
   - Тост «Данные обновлены с сервера»
8. **Вариант D: «Отмена»** — возврат к редактированию без изменений

**Логика выбора radio-кнопок:**
- По умолчанию: все radio в позиции «Сервер» (безопасный вариант)
- Клик по radio переключает выбор и подсвечивает выбранную ячейку
- Таблица прокручивается при большом количестве конфликтных полей (max-height: 360px)

## 12.12 Сценарий: Уведомление о начале редактирования + индикатор «Кто просматривает»

**Точка входа:** Открытие модалки задачи в любом режиме

**Сценарий:**

1. Пользователь A открывает модалку задачи (или нажимает «Редактировать»)
2. Фронтенд автоматически вызывает `POST /tasks/{id}/viewers` — регистрация как «смотрящий»
3. Одновременно фронтенд запускает polling: каждые 15 секунд `GET /tasks/{id}/viewers`
4. Если в ответе есть другие пользователи (кроме текущего) — показывается голубой баннер под баннером блокировки:
   - «Просматривает: **Иванов**» (1 человек)
   - «Просматривают: **Иванов, Петров**» (2 человека)
   - «Просматривают: **Иванов, Петров** и ещё 1» (3+ человека)
5. При закрытии модалки — `DELETE /tasks/{id}/viewers` + остановка polling

**Уведомление о блокировке (lock):**
- При `POST /tasks/{id}/lock` (получение блокировки) — сервер отправляет уведомление категории `editing` всем получателям задачи
- Текст: «Пользователь {name} начал редактирование задачи {task_label}»
- Важность: medium
- Отображение: в центре уведомлений с иконкой pencil и оранжевым цветом

**Просроченные записи viewers:**
- Очистка автоматическая при каждом `GET /tasks/{id}/viewers` — записи старше 10 минут удаляются

**Граничные случаи:**
- Если задача не найдена — 404
- Если текущий пользователь уже зарегистрирован — обновляется `last_seen_at`
- Если lock освобождён — баннер блокировки исчезает, но viewer-поллинг продолжается

## 13. Обработка ошибок на страницах

### 13.1 Dashboard (`#/dashboard`)
| Ошибка | Реакция системы |
|--------|----------------|
| `GET /tasks/stats` возвращает 401 | API-клиент пытается refresh, при неудаче — редирект на `/login` |
| `GET /tasks/stats` возвращает 500 | Красный тост «Ошибка загрузки статистики», KPI показывают прочерки |
| `GET /notifications` возвращает ошибку | Блок уведомлений показывает «Не удалось загрузить» |
| Нет данных для графика | Диаграмма отображается пустой с надписью «Нет данных» |

### 13.2 Бэклог DMB (`#/backlog`)
| Ошибка | Реакция системы |
|--------|----------------|
| `GET /tasks` 401 | Авто-refresh, при неудаче — редирект на `/login` |
| `GET /tasks` 403 | Тост «Недостаточно прав для просмотра», пустая таблица |
| `GET /tasks` timeout (>5 сек) | Тост «Сервер не отвечает», кнопка «Повторить» |
| `PUT /tasks/{id}` 403 | Тост «Недостаточно прав для редактирования» |
| `PUT /tasks/{id}` 404 | Тост «Задача не найдена», закрытие модалки |
| Сетевой сбой (fetch error) | Тост «Ошибка сети. Проверьте подключение» |

### 13.3 Бэклог команды (`#/team-backlog`)
| Ошибка | Реакция системы |
|--------|----------------|
