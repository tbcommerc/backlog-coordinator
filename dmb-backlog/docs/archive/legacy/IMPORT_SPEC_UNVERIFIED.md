# Спецификация импорта задач из CSV

**Версия:** 1.0  
**Дата:** 2026-08-07

---

## 1. Обзор

Модуль импорта задач из CSV-файлов позволяет массово загружать задачи в бэклог. Импорт поддерживает:

- Автоматическое определение разделителя (`;` или `,`)
- Декодирование UTF-8-SIG (BOM) и Windows-1251
- Сопоставление заголовков CSV с полями БД по русским меткам из `field_labels`
- Валидацию по 16 типам ошибок (см. [error-codes.md](../../error-codes.md#ошибки-импорта-задач-из-csv))
- Пропуск ошибочных строк без прерывания импорта
- Множественные ссылки на Jira (нормализованная таблица `task_jira_links` + JSON `tasks.link_jira`)
- Запись истории изменений (`task_history`) и аудита (`audit_log`)
- Обратную связь пользователю: копирование/скачивание отчёта об ошибках

---

## 2. Формат CSV

### 2.1 Разделитель и кодировка

- **Разделитель:** точка с запятой (`;`) или запятая (`,`) — определяется автоматически по первой строке
- **Кодировка:** UTF-8-SIG (с BOM) или Windows-1251 — определяется автоматически

### 2.2 Заголовки

Заголовки CSV сопоставляются с полями БД по русским меткам из таблицы `field_labels`. Если метка не найдена — используется прямой DB-ключ (без учёта регистра).

**Пример заголовков:**
```
ID задачи;Название задачи;Ответственная команда;Описание задачи;Дата получения;...
```

**Соответствие заголовков полям БД:**
| Заголовок CSV | Поле БД | Обязательное |
|---------------|---------|--------------|
| ID задачи | `external_id` | Нет |
| Название задачи | `title` | **Да** |
| Ответственная команда | `team_id` | **Да** |
| Описание задачи | `description` | Нет |
| Дата получения | `date_received` | Нет |
| Канал поступления | `channel_id` | Нет |
| Бизнес-заказчик | `business_customer_id` | Нет |
| Подразделение Бизнес-заказчика | `department_id` | Нет |
| Проект | `project_id` | Нет |
| Тип задачи | `task_type_id` | Нет |
| Приоритет | `priority_id` | Нет |
| Срок выполнения | `deadline_id` | Нет |
| Статус задачи | `status_id` | Нет |
| Исполнитель | `owner_id` | Нет |
| Ссылки на Jira | `link_jira` | Нет |
| ... | ... | ... |

Полный список полей — в `import_service.py:IMPORTABLE_FIELDS`.

### 2.3 Форматы значений

**Даты:** `YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY`, `DD.MM.YY`, `DD/MM/YY`

**Числа:** целые (`effort_days`, `progress`) или дробные (`effort_rub`, `cv`)

**Прогресс:** целое число от 0 до 100

**Ссылки Jira:** несколько ссылок через запятую или точку с запятой:
```
https://jira.example.com/ABC-1,https://jira.example.com/ABC-2
```

## 3. Валидация

### 3.1 Обязательные поля

Обязательные поля помечены `is_required=1` в таблице `field_labels`. По умолчанию: `title`, `team_id`.

Если обязательное поле пустое или отсутствует в CSV — строка пропускается с ошибкой `required_missing`.

### 3.2 Справочные поля

Справочные поля (team_id, channel_id, business_customer_id, department_id, project_id, task_type_id, priority_id, deadline_id, status_id) валидируются по справочникам:

- Поиск по `name` (без учёта регистра)
- Fallback: по `code`, `abbr`, `login`, `email` (в зависимости от таблицы)
- Если не найдено — строка пропускается с ошибкой `*_not_found`

**Исключение:** `owner_id` (исполнитель) — если не найден, строка импортируется, поле пропускается (не fatal).

### 3.3 Дубликаты

Дубликаты определяются по `external_id`:
- В том же CSV-файле — вторая строка пропускается
- В БД (если задача с таким `external_id` уже существует) — строка пропускается

### 3.4 Форматы

- **Даты:** если не соответствует ни одному из форматов — ошибка `invalid_date`
- **Числа:** если не является числом — ошибка `invalid_number`
- **Прогресс:** если вне диапазона 0-100 — ошибка `invalid_progress`

## 4. Сохранение

### 4.1 Создание задачи

Для каждой валидной строки создаётся запись в `tasks`:
- `status_id` по умолчанию = 1 (НОВАЯ ЗАДАЧА), если не указан
- `date_received` по умолчанию = сегодня, если не указан
- `created_by` = текущий пользователь
- `actual_effort_days` = сумма полей ФТЗ (авторасчёт)
- `cv` = `financial_effect / effort_rub` (если оба заполнены)

### 4.2 Ссылки Jira (двойная запись)

Множественные ссылки Jira записываются:
1. В таблицу `task_jira_links` (нормализованное хранение, одна строка на ссылку)
2. В JSON-колонку `tasks.link_jira` (для обратной совместимости)

Уникальный индекс: `(task_id, url)` — дубликаты ссылок для одной задачи не допускаются.

### 4.3 История и аудит

Для каждой созданной задачи:
- Записи в `task_history` для обязательных + заполненных полей
- Запись в `audit_log` (action=import, entity_type=task)

## 5. Обратная связь

### 5.1 Ответ API

```json
{
  "total": 10,
  "created": 8,
  "skipped": 2,
  "errors": [
    {
      "row": 3,
      "field": "team_id",
      "field_label": "Ответственная команда",
      "value": "НетТакойКоманды",
      "type": "team_not_found",
      "message": "Команда \"НетТакойКоманды\" не найдена в справочнике команд",
      "fatal": true
    }
  ],
  "task_ids": [101, 102, 103, 104, 105, 106, 107, 108]
}
```

### 5.2 Интерфейс импорта

Модальное окно импорта (`frontend/js/components/modal.js:importTasksFromExcel`):
1. **Шаг 1:** Выбор файла + предпросмотр первых 5 строк
2. **Шаг 2:** Валидация + отображение статистики (total/created/skipped/errors)
3. **Шаг 3:** Если есть ошибки — кнопки «Скопировать отчёт» и «Скачать отчёт (.txt)»
4. **Шаг 4:** Если ошибок нет — автоматическое закрытие через 1.5 сек + вызов `onSuccess()`

**Отчёт об ошибках (.txt):**
```
Отчёт импорта задач — 2026-08-07 15:30:45
Всего строк: 10
Создано: 8
Пропущено: 2

Ошибки:
Строка 3, поле "Ответственная команда": Команда "НетТакойКоманды" не найдена в справочнике команд (значение: "НетТакойКоманды")
Строка 5, поле "Название задачи": Поле "Название задачи" обязательно для заполнения (значение: "")
```

## 6. Изменение схемы

Текущая схема импорта определяется моделями в `backend/models.py`; отсутствующие
таблицы и колонки добавляет `database.ensure_schema()` при старте приложения.

`backend/migrations/2026-08-07_task_import_support.py` — исторический одноразовый
скрипт. Он содержит преобразования, которые не соответствуют полностью текущим
моделям (в частности, текущая модель `Task` не содержит `external_id`), поэтому
запускать его для актуальной базы нельзя. Общая политика и ограничения описаны в
`docs/SCHEMA_CHANGES.md`.

## 9. Архитектура

**Backend:**
- `backend/import_service.py` — сервис импорта (парсинг, валидация, сохранение)
- `backend/routers/tasks_router.py` — endpoint `POST /tasks/import`
- `backend/models.py` — модели `Task`, `TaskJiraLink`, `FieldLabel`

**Frontend:**
- `frontend/js/components/modal.js` — модальное окно импорта (`importTasksFromExcel`)

**База данных:**
- `tasks.external_id` — внешний ID задачи (уникальный)
- `task_jira_links` — множественные ссылки на Jira
- `field_labels.is_required` — флаг обязательности поля при импорте

## 10. Известные ограничения

1. **Legacy-схема:** В рабочей БД `tasks.id` не является PRIMARY KEY (pk=0 в PRAGMA). Миграция использует `PRAGMA foreign_keys = OFF` для совместимости. Приложение не включает enforcement FK по умолчанию.

2. **Размер файла:** Нет ограничения на размер CSV. Для очень больших файлов (>10000 строк) рекомендуется разбивать на части.

3. **Кодировка:** Поддерживаются только UTF-8-SIG и Windows-1251. Другие кодировки (KOI8-R, UTF-16) не поддерживаются.

4. **Дубликаты:** Проверка дубликатов только по `external_id`. Если `external_id` не указан — дубликаты не отслеживаются.
