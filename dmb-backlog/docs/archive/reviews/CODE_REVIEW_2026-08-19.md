## Резюме для руководителя

Проект представляет собой функционально богатый прототип, но пока не готов к промышленной эксплуатации в банковском контуре. Главная причина — не единичные дефекты, а отсутствие единой серверной политики авторизации: многие операции записи требуют лишь валидный JWT и позволяют пользователю менять чужие или недоступные ему сущности. Дополнительно production-конфигурация допускает известные секреты, refresh-токены нельзя отозвать, вложения публикуются без авторизации, а старт приложения сам изменяет схему и данные.

## Реестр находок

Приоритеты: P0 — блокирует безопасную эксплуатацию; P1 — исправить до пилота; P2 — ближайший технический долг; P3 — улучшение.

### P0 — критические

#### SEC-01. Горизонтальное повышение привилегий в задачах — исправлено

Единая policy-функция `authorize_task(action, task, user)` теперь применяется к карточке, истории, документам, комментариям, вложениям, блокировкам, списку просматривающих пользователей, редактированию, ссылкам, экспресс-оценке и удалению. PO/PL/CL, BA/Участник команды и IT PL редактируют только свою команду; «Проектный офис (админ)» — любые задачи. Удаление доступно только проектному офису и больше не наследуется из широкого permission-поля роли. Комментирование любых задач разрешено согласованным ролям, включая Лидера трайба. Бизнес-заказчик отвергается task-policy для всех действий и дополнительно ограничен серверным и клиентским whitelist страниц «Мои задачи» и «ИИ-ассистент». «Мои задачи» фильтруются по явной связи пользователя со справочником бизнес-заказчиков.

Риск: нарушение конфиденциальности и целостности портфеля, изменение статусов и финансовых показателей, подмена ссылок, удаление вложений.

Исправление: создать единый dependency/service `authorize_task(action, task, user)` и применять его ко всем чтениям и изменениям; покрыть матрицу ролей отрицательными тестами.

#### SEC-02. Bulk API позволяет массово менять чужие задачи — исправлено

`tasks_router.py:bulk_action()` теперь проверяет весь набор до начала изменений. PO/PL/CL, BA/Участник команды и IT PL могут массово менять только задачи своей команды и не могут переносить их в чужую. Проектный офис (админ) может менять любые задачи; массовое удаление доступно только ему. Неизвестные bulk actions отклоняются.

Риск: один обычный пользователь может массово изменить или скрыть до 500 задач за запрос.

Исправление: сначала ограничивать query областью пользователя, затем сравнивать число разрешённых задач с числом запрошенных; запрещать частичное «тихое» выполнение.

#### SEC-03. Экспресс-оценка и timeline не имеют объектной авторизации — исправлено

В `express_router.py` операции изменения Task/Epic/Story и перевода задачи в экспресс-оценку теперь проверяют доступ через родительскую задачу. Endpoint физического `db.delete(task)` удалён, как и соответствующая кнопка frontend; задачи удаляются только основным soft-delete механизмом. В `timeline_router.py` общие POST/PUT/DELETE удалены: публичная часть работает только на чтение, а создание, изменение и удаление событий доступны исключительно через `/admin` с `admin:full`.

Риск: обход ролевой модели через альтернативные endpoint’ы.

Исправление: убрать параллельные политики и использовать один authorization layer для каждой доменной сущности.

#### SEC-04. Загруженные файлы доступны публично — исправлено

Публичный mount `/uploads` удалён. Скачивание выполняется через защищённый endpoint с JWT, проверкой видимости неудалённой задачи, проверкой принадлежности файла каталогу задачи и `Content-Disposition` с исходным именем. Frontend скачивает файл авторизованным `fetch`-запросом.

Риск: утечка банковских документов через историю браузера, логи, пересылку URL или подбор ссылок.

Исправление: отдавать вложения через защищённый endpoint с `Content-Disposition`, проверкой доступа к задаче и безопасным MIME; статический mount удалить.

### P1 — высокие

#### SEC-05. Известные секреты и debug включены по умолчанию — исправлено для production

В dev-режиме сохранены локальные значения `SECRET_KEY`, `AGENT_SECRET` и `DEBUG=True`. При `DEBUG=false` основной backend теперь до инициализации БД запрещает пустой/default `SECRET_KEY`, ключ короче 32 символов и пустой/default `AGENT_SECRET`. Agent имеет аналогичную production-проверку собственного секрета.

Риск: подделка JWT и межсервисных запросов при ошибочной конфигурации production.

Исправление: не иметь рабочего secret по умолчанию; fail-fast при production/debug=false; минимум 256 бит энтропии; раздельные секреты сред.

#### SEC-06. Refresh-токены не отзываются и вращаются без replay detection — исправлено

Refresh-токены получили `jti` и `family_id`; в таблице `refresh_sessions` хранится только SHA-256 токена. Каждый refresh отзывает прежнюю сессию и создаёт новую в том же семействе. Replay старого токена отзывает семейство, logout серверно отзывает текущую сессию, неактивный пользователь не может обновить токен, а истёкшие записи очищаются во время auth-операций.

Исправление: token family + `jti`, hash refresh-токена в хранилище, revoke при logout/смене пароля/деактивации, detection повторного применения.

#### SEC-07. JWT хранится в `localStorage` — исправлено

Refresh-токен хранится только в `HttpOnly`, `SameSite=Strict` cookie (`Secure` в production) и не возвращается в JSON. Access-токен хранится только в памяти SPA; после reload сессия восстанавливается через cookie. Refresh/logout проверяют Origin, а legacy `localStorage.dmb_tokens` удаляется при bootstrap.

Исправление: refresh в Secure/HttpOnly/SameSite cookie, короткий access в памяти; строгий CSP и отказ от небезопасных HTML-вставок.

#### SEC-08. Потенциальный stored XSS и небезопасные внешние ссылки — исправлено

Ссылки задач проходят backend allow-list абсолютных `http://`/`https://` URL; опасные и относительные протоколы отклоняются при сохранении. Frontend-представления используют общий `safeExternalUrl`, а внешние вкладки получают `rel="noopener noreferrer"`. Выполнен отдельный XSS-проход по бэклогам, карточкам, quick edit, отчётам, dashboard, уведомлениям, customer/review-страницам, audit-log и админским формам: недоверенные строки экранируются перед `innerHTML`, значения атрибутов защищены, цвета тегов и справочников ограничены hex-форматом. Добавлен общий `htmlUtils.escapeHtml` и регрессионный тест с `script`, `img/onerror`, кавычками и амперсандом.

Исправление: централизованный DOM builder/sanitizer, allow-list `https:`/`http:`, автоматические DOM-XSS тесты, CSP без `unsafe-inline`.

#### SEC-09. Дефолтный пароль встроен в продукт

Пароль `dmb2026` показывается на login screen, назначается при создании пользователя и хранится в документации. Схема пользователя также имеет его как default.

Риск: предсказуемые учётные данные и отсутствие обязательной смены пароля.

Исправление: случайный одноразовый invite/reset flow, `must_change_password`, минимальная парольная политика и удаление подсказки вне demo-профиля.

#### SEC-10. Rate limit непригоден для production — исправлено

Login и refresh теперь ограничиваются непосредственно в auth endpoints. Production требует `REDIS_URL` и использует общее хранилище для всех workers; login ограничивается одновременно по IP и email, идентификаторы хешируются, повторные превышения увеличивают блокировку до 15 минут. Dev fallback ограничивает число ключей и очищает истёкшие записи.

Исправление: Redis-backed limiter, корректная trusted-proxy схема, лимиты по IP и учётной записи, backoff и наблюдаемость.

#### DATA-01. Запуск приложения изменяет схему и бизнес-данные — исправлено для production

`ensure_schema()` сохранён согласно политике проекта. Seed, миграция team FK, пересчёт трудозатрат и синхронизация отчётов теперь управляются `RUN_STARTUP_SEED` и `RUN_STARTUP_MAINTENANCE`: без явной настройки они включены только при `DEBUG=true`. Production restart по умолчанию больше не изменяет бизнес-данные; для явного первоначального заполнения остаётся команда `python seed.py`.

Риск: неожиданные изменения production-данных при каждом рестарте, гонки нескольких worker’ов, сложный rollback.

Оставшийся риск: `ensure_schema()` выполняет только аддитивные изменения и не имеет автоматического rollback. Сложные преобразования требуют отдельного согласованного плана обслуживания.

#### DATA-02. Неатомарные транзакции — исправлено

`_apply_tags` больше не выполняет собственный commit и использует `flush()`. Создание и обновление задачи сохраняют основную запись, теги, историю, аудит и уведомления одной транзакцией. В одну транзакцию также объединены импорт в экспресс-оценку с уведомлением, отправка запроса на ревью, пакетное сохранение общих настроек отображения и пересчёт задач после изменения ставки компетенции. Для промежуточных ID применяется `flush()`; отправка запроса на ревью явно выполняет rollback при ошибке внешнего агента или БД. Добавлены статические контрактные тесты транзакционных границ ключевых многошаговых маршрутов.

Исправление: транзакция на use-case, commit только на service boundary, `flush()` для промежуточных ID.

#### API-01. Дублирующиеся маршруты `/admin/projects` — исправлено

В `admin_router.py` оставлен один набор GET/POST/PUT/DELETE для проектов. Чтение требует `admin:read`, изменения — `admin:partial`; сохранены расширенные поля ответа, сортировка по имени и запрет удаления проекта, связанного с задачами. Добавлен тест уникальности method + path для всего admin router.

Исправление: оставить одну реализацию и один набор схем/прав.

#### REL-01. Автономное демо полностью неработоспособно — закрыто удалением

Автономная версия не используется и не требуется продукту. Неработоспособный `demo.html` и непереносимый генератор `build_demo.py` с абсолютными локальными путями удалены; основное клиент-серверное приложение не затронуто.

Исправление: вынести inline JS в модуль, добавить `node --check`/ESLint и smoke-тест загрузки страницы в CI.

### P2 — средние

#### ARCH-01. Чрезмерно крупные файлы и смешение ответственности — частично исправлено

`frontend/js/components/modal.js`, `admin.js`, `tasks_router.py` и CSS остаются крупными. Декомпозиция выполняется безопасными вертикальными срезами: клиентские комментарии и вложения вынесены в `taskComments.js` и `taskAttachments.js`; управление административными справочниками вынесено в `adminDictionaries.js`. Конструктор отчётов, подготовка payload, форматирование результата и выполнение административных отчётов вынесены в тестируемый `adminReports.js`; список и состояние выбранного отчёта пока оркестрирует `admin.js`. Серверные collaboration-маршруты и аналитика также разделены на тематические router/service-модули с сохранением API. `modal.js`, `admin.js` и `tasks_router.py` требуют дальнейшего последовательного разделения.

Следствие: высокие риски регрессии, конфликты merge, почти невозможные модульные тесты.

Рекомендация: вертикальные feature-модули, отдельные services/repositories/policies, компоненты до разумного размера, lint complexity budget.

#### ARCH-02. Две системы миграций противоречат друг другу — исправлено в документации

Единственнпоым поддерживаемым источником схемы зафиксирован `backend/models.py`, а механизмом аддитивного применения — `database.ensure_schema()`. Инструкции запуска Alembic и ручных скриптов удалены; `backend/alembic/` и `backend/migrations/` явно отмечены как legacy. Добавлен `docs/SCHEMA_CHANGES.md` с workflow, ограничениями и процедурой для сложных изменений.

Оставшийся риск: нет автоматического rollback, переименования, удаления колонок и преобразования данных. Для них требуется отдельный согласованный план обслуживания и восстановления.

#### ARCH-03. Синхронный I/O внутри async endpoint’ов — исправлено для CRUD и файловых маршрутов

CRUD, отчётные и аналитические маршруты с синхронной SQLAlchemy переведены из `async def` в обычные `def`, поэтому FastAPI выполняет их в thread pool. Маршруты загрузки вложений и импорта также синхронные и читают `UploadFile.file` внутри worker thread; middleware и настоящий асинхронный rate limiter оставлены асинхронными.

Оставшийся риск: содержимое загружаемых файлов по-прежнему целиком размещается в памяти. Для больших файлов нужен отдельный потоковый pipeline с лимитом размера на уровне reverse proxy и приложения.

Рекомендация: либо обычные `def` endpoints с threadpool, либо async SQLAlchemy; streaming upload и ранний контроль размера.

#### ARCH-04. Scheduler встроен в каждый web-worker — исправлено для production

Встроенный scheduler управляется `RUN_NOTIFICATION_SCHEDULER` и по умолчанию запускается только при `DEBUG=true`. Для production добавлена отдельная команда `python run_notification_scheduler.py`; web workers независимо масштабируются и не запускают плановые проверки. Эксплуатационно должен запускаться ровно один notification worker.

Рекомендация: отдельный singleton worker/очередь, distributed lock и идемпотентный ключ события.

#### REL-02. Исключения маскируются через `print` и broad `except` — исправлено в runtime-коде

Runtime-диагностика startup, schema update, audit, импорта и пересчётов переведена на стандартный logging с traceback. Ошибка аддитивного изменения схемы теперь прерывает startup; транзакции обновления задачи, импорта и аудита откатываются. Клиент больше не получает внутренний текст неожиданного исключения. Для ожидаемой ошибки deadline и сетевого вызова агента сужены классы исключений.

Оставшийся риск: формат логов пока текстовый, без correlation ID и централизованного алертинга; startup maintenance остаётся recoverable и сообщает о сбое через exception-log.

#### TEST-01. Критические правила доступа не покрыты тестами — исправлено для основной матрицы

Добавлен единый `test_security_contracts.py`: параметризованная матрица ролей проверяет редактирование своей/чужой команды, комментарии к любым задачам и запрет предметного API для бизнес-заказчика. Контрактные проверки фиксируют guards для задачи, комментариев, вложений, bulk и express estimate, а также permission dependencies для всех admin- и timeline-мутаций. Ранее добавленные тесты покрывают customer scope, timeline, duplicate routes и транзакционные границы.

Оставшийся риск: source-contract тесты подтверждают наличие guard-вызова, но не заменяют полноценные HTTP integration tests с реальной матрицей токенов и изолированной тестовой БД.

#### TEST-02. Нет единого CI quality gate — исправлено на базовом уровне

Добавлен `.github/workflows/quality.yml` для push, pull request и ручного запуска. Gate использует Python 3.12 и Node 22, компилирует backend, запускает весь pytest-набор без startup seed/maintenance/scheduler, проверяет синтаксис JS и frontend security unit tests, а также блокирует сборку при известных уязвимостях runtime-зависимостей через `pip-audit`. Dev-зависимости закреплены в `backend/requirements-dev.txt`.

Оставшийся риск: пока нет Ruff/Mypy/ESLint, браузерных Playwright/axe тестов, coverage threshold и secret scanner. Их следует вводить отдельными этапами после устранения существующего технического долга, чтобы gate оставался полезным и воспроизводимым.

#### DOC-01. Документация смешивает реализованное и целевое состояние

Документы заявляют production/deploy/monitoring/CI-практики, которых нет в дереве проекта; README упоминает `database/`, которого в актуальной структуре нет. Числа моделей и таблиц расходятся между документами.

Рекомендация: маркировать разделы `As-Is`, `Target`, `Planned`; генерировать API и schema reference из кода.

#### DOC-02. Инструкция запуска содержит неверный путь `.env.example` — исправлено

Единым расположением конфигурации зафиксирован корневой `dmb-backlog/.env`: `config.py` вычисляет абсолютный путь относительно собственного файла и больше не зависит от cwd. README, deployment, architecture, testing и error-codes приведены к фактическим путям и команде `uvicorn main:app` из `backend/`; добавлены команды копирования шаблона для PowerShell и bash.

Проверено: конфигурация находит один и тот же `.env` при импорте из корня проекта и из каталога `backend`.

### P3 — UX/UI и качество продукта

#### UX-01. Интерфейс перегружен функциональностью и скрытыми режимами

В одной карточке задачи объединены просмотр, редактирование, комментарии, вложения, bulk-конструктор, импорт и альтернативная новая реализация карточки. Это увеличивает когнитивную нагрузку и риск несогласованного поведения.

Рекомендация: разделить основные и продвинутые действия; progressive disclosure; единая карточка вместо двух параллельных реализаций.

#### UX-02. Непоследовательные диалоги и обратная связь — исправлено для системных диалогов

Добавлен единый `uiFeedback.js`: доступный toast, Promise-based подтверждение опасного действия, inline-ошибка поля и нормализация сетевых ошибок. Прямые браузерные `alert/confirm` удалены из frontend: удаление вложения использует единый диалог, ошибки операций — toast, обязательные значения в модалках ревью — сообщение рядом с полем.

Оставшийся риск: часть старых форм всё ещё показывает ошибки в toast вместо привязки к конкретному полю; полная унификация focus trap, возврата фокуса и pending-состояний требует последовательного перевода остальных custom modal.

#### UX-03. Доступность реализована фрагментарно — частично исправлено для модальных окон

Добавлен общий `modalAccessibility.js`, который автоматически обрабатывает динамические task/admin/review/agent/confirm overlays: назначает `role=dialog`, `aria-modal`, связь с заголовком, доступные имена кнопок закрытия и icon-only кнопок с `title`, удерживает Tab внутри верхнего диалога, закрывает его по Escape и возвращает фокус инициатору. Это распространяется и на модалки, добавляемые после загрузки через MutationObserver.

Оставшийся риск: таблицы, drag-and-drop, нестандартные select/combobox и часть icon-only действий без `title` требуют отдельного keyboard/screen-reader прохода и автоматизированной проверки axe.

Рекомендация: WCAG 2.2 AA checklist, axe в CI, keyboard-only сценарии, семантические таблицы, видимый `:focus-visible`, reduced-motion.

#### UX-04. Responsive-дизайн не соответствует плотности продукта — исправлено для ключевых рабочих экранов

Добавлена единая трёхрежимная модель layout: от 1280 px используется полная боковая панель (с поддержкой ручного сворачивания), на 641–1279 px она автоматически становится панелью иконок шириной 64 px, а до 640 px превращается в полноразмерный drawer с отдельной кнопкой меню и backdrop. Состояния взаимоисключающие и не протекают друг в друга при изменении размера уже открытого окна.

Таблица и карточки больше никогда не переключаются автоматически: выбранное пользователем представление сохраняется при изменении ширины, широкая таблица прокручивается только внутри контейнера и не раздвигает страницу. Фильтры и панели действий переносятся, для мобильных модальных окон ограничена высота по viewport и закреплены панели действий, а интерактивные элементы на сенсорных экранах получили область нажатия не менее 42 px. Геометрия каркаса проверена на 390/640/768/1100/1440 px отдельным статическим fixture без обращения к API и данным.

#### UX-05. Внешний Google Fonts противоречит автономности и privacy — исправлено

Inter и Unbounded размещены локально в `frontend/fonts/` и подключены через `frontend/css/fonts.css` с `font-display: swap`. Внешняя ссылка Google Fonts удалена, сохранены variable weights и системные fallback. Рядом с файлами находятся лицензии SIL Open Font License.

Проверено: frontend не содержит обращений к `fonts.googleapis.com` и `fonts.gstatic.com`, а backend отдаёт локальные файлы как static assets.

#### UX-06. Ошибки и пустые состояния недостаточно стандартизированы — исправлено для ключевых списков

Добавлен общий `viewState.js` для loading/empty/error с доступной семантикой, безопасным текстом и retry-действием. Он подключён к «Бэклог DMB», бэклогу команды, уведомлениям и списку отчётов; сетевые ошибки проходят через единый formatter, а кнопка «Повторить» восстанавливает соответствующую загрузку без перезагрузки страницы.

Оставшийся риск: detail-страницы аналитики и некоторые административные вкладки используют собственные состояния; correlation ID пока не передаётся с backend и не показывается пользователю.

## Недоделанный или спорный функционал

- Аналитика IT зарегистрирована как полноценный route, но её готовность и критерии расчёта не подтверждены тестами и бизнес-спецификацией.
- Logout не является серверным logout.
- MCP в агенте заявлен как интеграция, но dependency закомментирована, соединение лишь получает список tools и не предоставляет полноценный жизненный цикл вызова.
- Agent session store остаётся process-local; при рестарте и горизонтальном масштабировании диалоги теряются/расходятся.
- Отчёты, аналитика и task list применяют ограничения области данных не единообразно; некоторые агрегаты могут раскрывать сведения вне команды.
- Import поддерживает только CSV, хотя UI включает Excel-библиотеку и репозиторий содержит XLSX-артефакты; ожидания пользователя нужно унифицировать.
- Legacy-скрипты в `backend/migrations/` не образуют revision chain и не должны использоваться в актуальном workflow.
- Root содержит большие data/demo/debug artifacts и резервные БД; политика хранения тестовых/персональных данных отсутствует.
