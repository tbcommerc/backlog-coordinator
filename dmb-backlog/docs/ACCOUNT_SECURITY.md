# Управление учётными записями: реализация и ввод в эксплуатацию

Проверено по коду и изолированным проверкам 13.10.2026. В этом чате миграция и массовый cutover не запускались. По просьбе пользователя
выполнена read-only проверка только администратора `t.babiak@dmb.ru`: active,
ready, admin_access=full, канонический логин назначен. К моменту проверки схема
и режим сохранения паролей уже были применены параллельной работой в общем
workspace; это не является доказательством стендовой приёмки всех сценариев.

## Реализованный контракт

- Вход `POST /api/v1/auth/login` принимает только `{login,password}`. Канонизация:
  крайние пробелы удаляются, ASCII переводится в нижний регистр; 3–254 символа,
  первый — буква/цифра, остальные — буквы/цифры/`._@-`. Почтовый ящик не требуется.
- `User.id`, роли и команды при cutover сохраняются. Прежний `email` остаётся
  nullable legacy-атрибутом. Старые логины резервируются навсегда.
- Состояния credentials: `invited`, `ready`, `reset_required`; активность отдельна.
  Только активная запись `ready` может войти. По умолчанию legacy bcrypt не
  принимается: требуется проверенная активация. По явному требованию сохранить
  вход администратора поддержан `AUTH_ALLOW_LEGACY_PASSWORDS=true`: существующий
  bcrypt проверяется без NFC и без trim, ввод свыше 72 UTF-8 байт отклоняется,
  автоматического rehash нет. Новая самостоятельная смена переводит на Argon2id.
  Этот режим является согласованным исключением из исходного обязательного reset;
  известный ранее пароль остаётся действительным до самостоятельной смены.
- Новые пароли: NFC, 15–128 Unicode-символов, без trim/усечения; управляющие
  символы, совпадение с логином и встроенный локальный список слабых паролей
  отклоняются. Argon2id: минимум 19456 KiB / 2 / 1; ограниченный параллелизм.
  Хэш обновляется при успешном входе, если параметры изменены.
- Access JWT содержит `sub`, `sid`, `auth_version`, `type`, `iat`, `exp`, `iss`,
  `aud`, `jti`. Старые JWT без серверной сессии отклоняются. Каждый guard проверяет
  PostgreSQL; положительного кеша допуска нет. SSE повторно проверяется каждые
  5 секунд и закрывается при отзыве или истечении серверной сессии.
- Сессия: access по умолчанию 5 минут, абсолютный срок 8 часов, idle 30 минут
  (full admin — 15), максимум 5 устройств. Refresh, уведомления, SSE, status,
  heartbeat, viewers и lock не продлевают idle. Cookie HttpOnly, SameSite=Strict,
  Secure при DEBUG=false, path `/api/v1/auth`, без Domain и Max-Age.
- Refresh сериализуется блокировкой User, история привязана к стабильному sid.
  Повтор ротированного токена в пределах 10 секунд — 409
  `REFRESH_ALREADY_ROTATED`, без выдачи токенов. Поздний replay отзывает сессию.
  SPA объединяет refresh внутри вкладки и использует Web Locks между вкладками;
  retry ограничен одним. BroadcastChannel передаёт события, а не токены.
- Смена пароля, reset, логина, профиля/полномочий отзывает доступ и подтверждения.
  Обычный выход и отзыв устройства закрывают серверную сессию целиком.
  Ошибочный пароль не меняет credentials. Повторное включение не оживляет токены.
- Чувствительные действия администратора требуют full admin и одноразового
  подтверждения с привязкой к sid, версии, действию и цели. Проверки обоих users
  API унифицированы: старые изменения `/users` и DELETE `/admin/users/{id}`
  возвращают 410. Физического удаления пользователей нет.
- Защита собственного/последнего готового администратора использует PostgreSQL
  advisory lock `761204120`, включая изменение роли. Обычный reset самого себя
  запрещён. Операторское восстановление — только отдельная консольная утилита.
- Security events фиксируются в одной транзакции с успешным действием. В них нет
  хэшей и секретов. Ответы проверки DTO не содержат `input`/`ctx`; ошибки SQL не
  возвращают параметры запроса. Новые внутренние таблицы исключены из ORM-аудита.

## API

Все пути ниже начинаются с `/api/v1`. Изменяющие DTO запрещают лишние поля.

| Метод | Путь | Тело / результат |
|---|---|---|
| GET | `/auth/password-policy` | Длина, NFC, контакт поддержки |
| POST | `/auth/password/setup` | `{token,new_password}` → 204, без автоматического входа |
| POST | `/auth/password/change` | `{current_password,new_password}` → 204, отзыв всех сессий |
| POST | `/auth/reauthenticate` | `{password,purpose,target_user_id?}` → `{token,expires_at,operation_id}` |
| GET | `/auth/sessions` | Только свои сессии; metadata и признак текущей |
| DELETE | `/auth/sessions/{id}` | 204; чужая/неизвестная → 404 |
| POST | `/auth/sessions/revoke-others` | `{reauth_token}` → `{revoked}` |
| GET | `/auth/security-events?page=1&per_page=30` | Собственные события; per_page ≤ 100 |
| POST | `/admin/users` | Логин, имя, профильные назначения, `reauth_token`; пароля нет |
| PUT | `/admin/users/{id}` | Профиль и `reauth_token`; логин/активность — отдельные действия |
| POST | `/admin/users/{id}/invitation` | `{reauth_token}` → одноразовый секрет (24 часа) |
| POST | `/admin/users/{id}/password-reset` | `{reason,reauth_token}` → recovery (30 минут) |
| POST | `/admin/users/{id}/revoke-sessions` | `{reason,reauth_token}` → `{revoked}` |
| PATCH | `/admin/users/{id}/login` | `{login,reason,reauth_token}` |
| PATCH | `/admin/users/{id}/access-state` | `{is_active,reason,reauth_token}` |

Purpose: `create_user`, `update_user`, `invitation`, `password_reset`,
`revoke_sessions`, `change_login`, `access_state`, `revoke_others`, `update_role`.
Для `update_role` target_user_id содержит ID роли; подтверждение не совместимо
с пользовательскими действиями. Создание и выдача приглашения — два явных шага.
Потерянный секрет нельзя прочитать повторно: нужно перевыпустить.

## UI

`#/account/security` открыт любому вошедшему пользователю, включая customer-only;
ссылка находится в меню пользователя. Доступны смена пароля, сессии, собственные
события. `#/activate` принимает код вручную или из fragment: fragment очищается
сразу после извлечения. Успешная активация возвращает на обычный вход.

В списке администрирования кнопка «Доступ» открывает приглашение, reset, отзыв,
смену логина, включение/отключение. После создания предложена выдача приглашения.
Пароль вводит владелец; администратор только подтверждает свой текущий пароль.
Одноразовый код удаляется из DOM при закрытии, копируется по явному нажатию.
Никаких паролей в черновиках или Web Storage. SPA предупреждает за минуту до расчётного idle/absolute expiry и предлагает сохранить рабочий черновик. Выход с сетевой ошибкой явно сообщает,
что серверное завершение не подтверждено. 401 чувствительных запросов не приводит
к автоматическому refresh/retry.

## Сохранение текущего входа администратора

Пользователь подтвердил необходимость входа `t.babiak@dmb.ru` с текущими
учётными данными. Read-only проверка 12.10.2026 подтвердила активность, готовность
и полные права этой записи; Redis и отдельный HMAC настроены, совместимость
bcrypt включена. Реальный пароль не запрашивался, не считывался и не менялся.
Вход с конкретным паролем должен проверить его владелец; тесты проверяют тот же
путь на синтетических хэшах. Не запускать обычный cutover/reset для этой записи
без отдельного согласования.

В общем workspace также присутствует операторская команда `preserve-passwords`,
которая переносит все существующие идентификаторы из email, сохраняя хэши.
Она требует отдельного разрешения на весь набор пользователей; в этом чате
не выполнялась. В строгом режиме использовать процедуру приглашений ниже.

## Схема и порядок перехода

Alembic `c8f4b0e2d653` (после `b7e3a9d1c542`) расширяет users и добавляет
`login_reservations`, `auth_sessions`, `auth_challenges`, `security_events`,
FK refresh→auth_session. Unique index допускает не более одного непогашенного и
неотозванного invitation/recovery на пользователя. `login_normalized` временно
nullable только для additive-перехода; cutover устанавливает NOT NULL.
Миграция не подбирает логины, не создаёт пользователей/ролей и не назначает команды.
Новая версия приложения до cutover закрывает вход старых учётных записей.

Оператор выполняет следующие шаги только после отдельного разрешения на рабочие
учётные записи, в окно обслуживания и с закрытым внешним доступом:

1. Сделать защищённую резервную копию и применить Alembic-миграцию.
2. Из backend запустить `python account_operator.py report` и согласовать JSON
   сопоставления `{ "existing_user_id": "approved.login" }` для всех пользователей.
   Предложение использует прежний рабочий email; поле старого login автоматически
   не включается в поиск. Коллизии требуют ручного решения.
3. `python account_operator.py cutover --mapping approved.json --reason CHANGE-ID --apply`.
   Нужна интерактивная защищённая консоль. Команда атомарно очищает старые хэши,
   переводит в invited, резервирует логины и отзывает доступ. Повторное выполнение
   над уже перенесёнными пользователями запрещено.
4. `python account_operator.py recover-admin --user-id EXISTING_ID --reason CHANGE-ID --apply`.
   Только существующий активный full admin. Выход терминала содержит одноразовый
   секрет: не включать запись терминала и не отправлять в тикет/общий журнал.
5. Администратор активируется на ограниченно доступном стенде, затем приглашает
   остальных после проверки личности. Только после этого открыть обычный доступ.

Downgrade на версию без sid/version запрещён. После восстановления backup до
открытия доступа отозвать все сессии/приглашения и заменить JWT-ключ.
Seed и автоматическое назначение пользователей не используются.

## Настройки и эксплуатационные проверки

`AUTH_ORIGINS` — точные внешние origins, `AUTH_ALLOWED_HOSTS` — allowlist Host.
Доверие к произвольному Host для Origin удалено. Для банковского DEV:
DEBUG=false, HTTPS с корпоративным сертификатом, отдельные JWT/HMAC/сервисные
ключи, Redis и PostgreSQL внутри контура, forwarded headers только от proxy.
`AUTH_RATE_HMAC_KEY` обязателен для входа и чувствительных операций даже локально;
пустое значение или отказ Redis дают 503 без fallback в память.
`AUTH_SUPPORT_CONTACT` задаёт инструкцию на форме входа.

Начальные лимиты: 120 входов/IP/мин, 5 ошибок/логин/5 мин с backoff до 15 мин;
setup 60/IP/мин и 5 ошибок/digest/5 мин; 5 ошибок credentials/user+sid/5 мин;
выдача 5/цель/час и 30/админ/час; refresh 600/IP/мин и 60/sid/мин.
Счётчик, TTL и backoff атомарны в Redis Lua; ключи идентификаторов HMAC.
Успех не сбрасывает IP-счётчик. Все значения и сроки перечислены в `.env.example`.

Заголовки приложения: no-store на чувствительных API, no-referrer, nosniff,
CSP frame-ancestors none/object-src none/base-uri none. Полное CSP script-src
и HSTS требуют проверки и конфигурации конкретного reverse proxy. Статика локальная.
Встроенный небольшой blocklist — стартовый набор; перед DEV-приёмкой владелец
должен утвердить его полноту и параметры Argon2 по измерениям на целевом хосте.

- Frontend: `frontend/tests/accountSecurity.test.mjs`, `apiSingleFlight.test.mjs`.
- Браузер: `frontend/e2e/accountSecurity.spec.mjs`, только подменённый API.
- Миграция проверяется `alembic upgrade b7e3a9d1c542:d9a5c1f3e764 --sql`.

Гонки setup/refresh/reset/последнего администратора на реальной PostgreSQL,
несколько workers с Redis, HTTPS/VPN, restore и доставка приглашений требуют
отдельного разрешённого стендового прогона. SQLite не является заменой этой
приёмке. Полный старый backend suite создаёт защищённые тестовые записи и в этом
изменении не запускался. Эти ограничения не объявляются успешно проверенными.


Итог проверки 13.10.2026: 55 backend-тестов (чистые функции/doubles, включая
синтетический bcrypt), 11 Node.js-тестов, 5 Playwright-сценариев.
Полный администратор может читать `GET /api/v1/admin/security-events` с page,
per_page и subject_id; на странице безопасности доступен переключатель общего
журнала. Плановая очистка: `python account_operator.py prune --reason RETENTION --apply`
из защищённой интерактивной консоли; использует AUTH_EVENTS_RETENTION_DAYS и
AUTH_SESSION_RETENTION_DAYS. История refresh остаётся до absolute expiry + сутки.
Задача не запускается автоматически и при реализации не выполнялась.


Завершающая DDL-миграция `d9a5c1f3e764` проверяет наличие ограничения
password_hash для ready/reset_required и добавляет составные индексы. Она нужна
в том числе установкам, применившим ранний вариант additive-миграции во время
параллельной разработки. Данные пользователей не меняет; в этом чате не применялась.

### Уточнение 14.10.2026: успешные ответы без тела

При живой активации тестового пользователя сервер вернул 204 и перевёл запись в ready, но frontend пытался разобрать пустой ответ с Content-Type application/json и показывал «Сервис недоступен». API-клиент теперь возвращает null для успешного 204 без JSON-разбора. Добавлена регрессионная проверка POST password/setup с таким ответом. Повторная установка пароля после уже успешной активации не требуется; одноразовый код использован.

### Локальное тестовое исключение — 14.10.2026

По прямому указанию владельца всем 21 пользователю локальной PostgreSQL-базы назначен единый тестовый пароль; значение в документации не хранится. Перед операцией проверены loopback-адрес БД и DEBUG. Сохранены отдельные Argon2id-хэши, записи переведены в ready, предыдущие сессии и приглашения отозваны. Логины, роли, команды, привязки заказчиков и is_active сохранены. Для каждой записи добавлено security event local_test_password_reset. Проверены все хэши и живой вход ux-notifications-no-team. Это разовая операция над текущей локальной БД: общая политика паролей и создание будущих пользователей не изменены.

## Контекст клиентской сессии — проверено 28.10.2026

API связывает обычные запросы, JSON-body, файлы и SSE с поколением входа. Начало login/logout немедленно делает старые ответы неактуальными; они возвращают session_changed, не очищают новый токен и не вызывают перезагрузку. Login/logout и refresh сериализованы одним Web Lock; без Web Locks используется очередь. Обычная ротация внутри той же сессии сохраняет запросы, действительное истечение по-прежнему завершает вход. Серверные сроки и права не менялись. Регрессии: apiAuthContext.test.mjs (включая поздний401, старый JSON, открытый SSE и Web Lock).
