# API Assistant V2

> AS-IS проверено по коду и изолированным тестам 09.10.2026. Точные DTO публикует OpenAPI на порту 9300.

Внутренний base path: `/api/agent-v2`. Все бизнес-методы требуют
`X-Agent-Secret`; браузер не получает этот secret и работает через DMB gateway
`/api/v2/agent`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | liveness и версия |
| GET | `/ready` | readiness БД, LLM и feature state |
| GET | `/config` | режимы и версия prompt set |
| POST | `/new-session` | сессия выбранного product mode и source context |
| POST | `/chat` | один ход диалога |
| POST | `/chat-stream` | SSE-вариант хода |
| GET | `/sessions?user_id=…` | сессии владельца |
| GET | `/session/{id}?user_id=…` | восстановление сессии владельца |
| POST | `/session/{id}/archive` | архивирование владельцем |
| POST | `/session/{id}/handoff` | passport → requirement copilot |
| POST | `/session/{id}/link-object` | добавить проверенный snapshot |
| POST | `/session/{id}/proposed-patch` | preview изменений |
| POST | `/session/{id}/proposed-patch/decision` | принять/отклонить одну операцию |
| POST | `/edit-draft-section` | ручная правка с новой ревизией |
| POST | `/import-requirement-document` | разобрать существующий документ и создать проверяемую ревизию |
| POST | `/document-action` | независимое AI-ревью, предложения, выборочное применение, источники и решения по замечаниям |
| POST | `/send-for-review` | зафиксировать связь с review request |
| POST | `/reopen-review` | открыть возвращённую редакцию |
| POST | `/cancel-review` | компенсация rollback DMB |
| POST | `/reset` | удалить собственную сессию |

Все изменяющие методы принимают `idempotency_key`; для хода чата тем же
ключом служит `message_id`. Повтор `new-session`, reset и операций
над сессией с тем же ключом возвращает сохранённый ответ.

DMB gateway заменяет клиентские actor-поля значениями текущего пользователя.
`GET /api/v2/agent/objects/search` ищет только разрешённые Request/Task по ID или названию.
Для `link-object` клиент передаёт только тип и ID; полный snapshot создаёт DMB.

Ответ `AgentResponse` содержит mode, operator role, source context, artifact type, историю,
progress, readiness, текущий artifact, linked snapshot, ProposedPatch,
fingerprint ревизии и storage version.

Документный ответ дополнительно содержит `artifact_id`, `document_review`,
`document_findings`, `document_proposals`, `document_sources`, `document_generation`. В `draft` находятся
стабильный `artifact_id` и элементы `business_requirements` с неизменяемыми `BR-…`
ID. Все эти поля документа покрываются его canonical fingerprint. Поля будущих
расширений документа сохраняются при создании следующей редакции.

Сводки `/sessions` содержат `artifact_id`, `artifact_revision`, `draft_fingerprint`
и `linked_object` только с `object_type`/`object_id`. Заголовок берётся из документа.
Gateway использует эти сведения для повторной проверки объектного доступа.
Для поиска существующего рабочего документа `/sessions` принимает пару
`linked_object_type` и `linked_object_id`. Фильтр применяется к собственным
сессиям в БД до ограничения результата (50 по умолчанию), поэтому старый
связанный документ не теряется среди новых сессий. Неполная пара даёт HTTP 422.

`POST /import-requirement-document` принимает `session_id`, `content` (до
30 000 символов), trusted `user_id` и `idempotency_key`. Операция разрешена
только для `requirement_copilot`. Импорт распознаёт известные Markdown-заголовки,
не интерпретирует нераспознанные разделы как факты и сохраняет provenance
`attachment_excerpt`. Ответ — обычный `AgentResponse` с новой ревизией,
замечаниями и readiness. Оригинал целиком, включая неизвестные разделы, сохраняется
в `document_sources`; импорт не объявляет извлечённые утверждения подтверждёнными
аналитиком (`confirmed=false`).

## Действия с документом

Общий запрос `POST /document-action`:

```json
{
  "session_id": "session-id",
  "user_id": 17,
  "action": "review",
  "expected_draft_hash": "sha256:…",
  "idempotency_key": "unique-action-key",
  "instruction": "Проверь границы и критерии результата",
  "field": "",
  "proposal_id": "",
  "operation_ids": [],
  "finding_id": "",
  "decision": "resolved",
  "reason": "",
  "source": null
}
```

`user_id` задаёт доверенный gateway. Действия разрешены только владельцу сессии
`requirement_copilot`. Каждое действие выполняется под существующей блокировкой
SessionStore. Повтор с тем же ключом и тем же телом возвращает прежний ответ;
тот же ключ с изменённым телом даёт HTTP 409. Такая же привязка ключа к телу
введена для `/new-session` и `/session/{id}/link-object`.
У этих двух операций из подписи исключается только `captured_at` самого
авторизованного snapshot, который gateway обновляет при повторе; тип, ID,
версия, fingerprint, содержание полей и вложенные даты остаются частью подписи.

| action | Дополнительные поля | Результат |
|---|---|---|
| `review` | `instruction` необязателен | Замечания и отчёт без изменения документа и его редакции |
| `draft` | `instruction`, необязательный `field` | Предложения по полям; документ возникает после принятия |
| `create_draft` | `instruction` | Только первый черновик: сохраняет сгенерированный документ с `author_kind=agent_proposal`, неподтверждённым происхождением полей; существующий документ возвращает 422 |
| `save_sections` | `sections: {field: text}` | Атомарное автосохранение до 30 разрешённых текстовых разделов с новой редакцией; массивные поля разбиваются по строкам |
| `dismiss_proposal` | `proposal_id` | Отклонить оставшиеся операции предложения, сохранив текущий текст |
| `propose_change` | `instruction`, необязательный `field` | Предложения с before/after для существующего документа |
| `apply_proposal` | `proposal_id`, выбранные `operation_ids` | Одна новая редакция из выбранных операций |
| `resolve_finding` | `finding_id`, `decision`, обязательный `reason` | Решение `resolved`, `rejected` или `deferred` с автором и причиной |
| `add_source` | `source: {title, content, source_type: "text", source_ref?, id?}` | Неизменяемая версия источника; существующий ID создаёт следующую версию |
| `next_revision` | необязательный `reason` | Новая рабочая редакция; также выход из блокировки старого legacy review |

Для всех действий кроме `add_source` передаётся точный текущий
`expected_draft_hash`. Пустой hash допустим только пока документа ещё нет.
Устаревшие документ, источники или связанный snapshot запрещают применение
предложения и решение по замечанию. Частичное применение сдвигает base hash
оставшихся операций этого предложения к созданной редакции. Ручная правка
между применениями делает оставшиеся операции устаревшими.

Ошибка передаётся как HTTP 409 (`revision_conflict`, `idempotency_conflict`),
422 (`validation_error`), 503 (`unavailable`) или 404; `detail` содержит
`{code, message}`. Отказ LLM при ревью возвращает успешный HTTP-ответ с
`document_review.status="degraded"`: это только проверки правил, а не успешное
семантическое AI-ревью. Отказ написания не меняет документ.

Отчёт содержит `id`, `status`, `base_fingerprint`, `source_fingerprint`
(canonical hash полного `document_sources`), `linked_snapshot_fingerprint`,
`revision`, `profile`, `method`, `model`, `prompt_version`, `created_at`,
`findings_count`, `summary`, `stale`. Профиль MVP — `product_process_change`.

Замечание содержит стабильный ID, review ID, hashes входа, `field`, точную `quote`,
`message`, `risk`, `severity` (`critical|warning|info`), `method`, `sources`,
`related` (адреса обеих сторон противоречия), `suggestion`, `status`, `reason`
и `stale`. Решение сохраняется при повторной проверке того же замечания и входа.
Устаревшее замечание остаётся историей; решать его вместо текущего нельзя.

Предложение содержит ID, hashes документа/источников/snapshot, `operations`
с ID, `field`, `before`, `after`, `reason`, `source_refs`, `status`. Принимаются
только allowlist полей БТ; внешние DMB-поля, пользователи, команды и справочники
этим механизмом не изменяются. Источник содержит оригинальный `content`,
ID/версию, дату, fingerprint и `sections` с адресами вида
`src_…@1#section-2`, `start_line`/`end_line`.

AI-ревью и readiness не являются человеческим согласованием. Новый предмет
«редакция БТ» публикуется через DMB как отдельный immutable snapshot; сервис
агента не вызывает для этого старый `/send-for-review` и не блокирует рабочий
документ. Возвращённые человеком замечания можно добавить через `add_source`.


## Уточнения импорта и ручной правки — 09.10.2026

`POST /edit-draft-section` принимает `field="title"` наряду с разделами:
`{session_id, user_id, field, value, idempotency_key}`. Успешная правка создаёт
редакцию с новым fingerprint и сохраняет название при следующих изменениях разделов.
Блокировка отправленной редакции и проверка владельца действуют также для названия.

`POST /import-requirement-document` сохраняет первый Markdown H1 в `draft.title`.
В импортированном элементе `document_sources` поле `import_result` содержит
`recognized_fields` (ключи распознанных слотов) и `unmapped_sections` (исходные
неизвестные заголовки). Полный текст и адресуемые `sections` остаются в источнике.
Неизвестные заголовки по-прежнему доступны в совместимом `sources`.
«За границами» соответствует `scope_out`, «Основная роль» — `role`,
«Участники» — `actors`; поддержаны остальные заголовки текущего редактора.
Назначение неизвестного текста разделу в UI заполняет ручную форму: сохранение
происходит автоматически пакетом `save_sections`.

Автосохранение БТ (проверено 09.10.2026): `sections` принимает только поля
из `FIELD_SLOTS` и `title`; `business_requirements` через текстовый пакет
недоступно. Каждый текст — до 30 000 символов, название — 1–500. Пустой текст
очищает раздел, пустой список разделов недопустим. Проверяется весь пакет;
недопустимое поле возвращает 422 без частичного применения. Неизменённый пакет
не создаёт лишнюю редакцию. Исходный hash обязателен: конфликт даёт 409.
Происхождение изменённых вручную полей становится `human_decision`, остальные
поля, неизвестные расширения и стабильные BR-ID сохраняются. Последующая
проверка и предложения вычисляют устаревание по новой контрольной сумме.


Контракт содержательного ревью разделяет `reviewable_fields` и `editable_fields`.
В основной и связанной цитате разрешены существующие поля бизнес-контекста
(включая `priority`, `business_value`, роли и регуляторные условия), даже если
их изменение через документные предложения не разрешено. Каждая непустая цитата
по-прежнему должна буквально присутствовать в указанном поле. Замечание содержит
`can_propose`: для полей вне `editable_fields` интерфейс не предлагает AI-правку.
Версия инструкций документных действий — `document-actions.v3` плюс hash prompt.

## Полнота первого черновика — проверено 09.10.2026

`create_draft` использует отдельный контракт полного документа. Перед генерацией
сервер разбивает актуальную версию каждого текстового источника на фрагменты
с `id`, `source_ref`, `line`, `heading`, `field`, `quote`, `kind`. Известные разделы
переносятся дословно, затем модель дополняет производные разделы. Старые версии
источников сохраняются в истории, но не входят в набор проверяемых фрагментов.
Импорт и адресация источников распознают Markdown `#`, жирные заголовки и известные
обычные заголовки. Поддержаны «Бизнес-проблема», «Цель», «За рамками требования»,
«Открытые вопросы»; неизвестный жирный заголовок не присоединяется к предыдущему
разделу. `**Название:** …` распознаётся как название.

Контракт модели явно различает `array<string>` и `business_requirements` как
массив объектов. При первом черновике допустимо без потери содержания развернуть
объекты `{text, source_refs, status}` в строки, проверив ссылки; неизвестные поля
обёртки отклоняются. Ошибка формата использует единственную попытку исправления,
а при её неуспехе сохраняются только распознанные исходные разделы с ограничением.

Отдельная смысловая сверка возвращает покрытие каждого фрагмента, точную цитату
документа, неподтверждённые утверждения и решение по каждому вопросу. Сервер
проверяет полноту списка, уникальность ID, поля, наличие цитат и сохранение чисел
в цифровой записи. Смысл и числа словами проверяет модель; это не формальная
гарантия семантической эквивалентности. Допускается один проход исправления с
повторной сверкой. При неуспехе доступный черновик сохраняется с явным ограничением.

`draft.generation_report` — неизменяемый отчёт генерации в составе редакции.
`document_generation` — его копия с вычисленным `stale` при изменении редакции,
источников или snapshot. `status`: `complete`, `partial`, `unverified`.
Уточнение от 09.10.2026: `source_parsing` отдельно содержит статус разбора,
`nonempty_lines`, `accounted_lines`, `facts_total`, построчный `lines` и
`unresolved` с цитатами и адресами. Неизвестные Markdown/жирные заголовки и
обычные подписи с двоеточием прекращают предыдущий раздел и препятствуют
итоговому `complete`. Произвольный заголовок без разметки и двоеточия не всегда
отличим от содержания; смысл свободного текста по-прежнему проверяет модель.
Обычные `Название:` и `Бизнес-требование` распознаются без Markdown.
Факты имеют `evidence_ref` вида `src_id@version#L7`; адрес разрешён только для
существующей непустой строки. Явное бизнес-требование получает точное основание
из источника. Старые адреса источников/разделов сохраняют совместимость.
Счётчики подтверждают обработку переданного текста, а не полноту материалов,
которые автор намеревался передать. Отсутствующие части исходника не восстанавливаются.
Содержит `source_facts`, `coverage`, `issues`, `questions`, `section_states`,
число проверенных фрагментов и `repair_attempted`. Статусы разделов: `filled`,
`missing_data`, `not_applicable`, `conflict`, `unprocessed`. Содержание остаётся
неподтверждённым аналитиком. Авторские вопросы не удаляются; новые вопросы,
признанные отвеченными, дублирующими или вне объёма, исключаются при генерации
с сохранением причины в отчёте (`removed=true`).

`review` выполняет новую сверку и сохраняет её в `document_review.transfer_check`,
не меняя документ. Потери становятся критическими замечаниями существующего
процесса ревью. Ошибка сверки делает ревью `degraded`. Последующие изменения
существующего документа по-прежнему требуют выборочного принятия предложений.
