# Продуктовый контракт диалога AI Business Analyst

> AS-IS проверено по agentic runtime и API-тестам 08.09.2026.

## Цель

Помочь бизнес-заказчику с минимальными усилиями превратить свободное описание
проблемы или идеи в проверяемый черновик бизнес-требования для ревью BA/PO.
Агент не заменяет аналитика и не принимает решение о реализации.

## Основной принцип

Оркестрация разделена на два слоя:

1. **Жёсткие гарантии:** безопасность, принадлежность домену, сохранение истории,
   минимальное ядро требования, подтверждение пользователем, аудит и отправка.
2. **Адаптивная проработка:** порядок и глубина вопросов, промежуточные резюме,
   Q&A, исправления и ранний переход к черновику.

Основной runtime — `AgenticOrchestrator`: модель предлагает следующий шаг,
Python проверяет факты и выполняет явные операции с черновиком. Legacy state
machine не управляет основным диалогом.

## Минимальное ядро для полезного драфта

- суть потребности;
- основная роль;
- затронутый процесс;
- целевое состояние (To-Be).

После его заполнения пользователь может сформировать черновик сразу. Все
остальные незаполненные блоки маркируются как открытые вопросы для аналитика.

Явная команда «Подготовить черновик сейчас» создаёт артефакт без вызова LLM
и дополнительного подтверждения резюме. Подтверждение отправки остаётся в
существующей форме ревью. Значения «Не знаю» и «Не применимо» не заменяют
обязательные факты. Для инцидента сохраняется краткий путь с описанием проблемы.

Одна независимая проверка вычисляет блокеры при создании, восстановлении и
отправке черновика: отсутствующее минимальное ядро и критические противоречия.
Незаполненные ценность и критерии приёмки остаются рекомендациями. Формулировка
вопроса, в том числе префикс «Уточните:», не определяет запрет отправки.

## Режимы

- **guided:** подробная проработка для новичка, включая регуляторный вопрос;
- **hybrid:** стандартный баланс полноты и количества вопросов;
- **free_form:** опора на данные, извлечённые из развёрнутого сообщения, без
  прохождения необязательного чек-листа;
- **expert:** короткий путь — минимальное ядро и проверяемые критерии приёмки.

Режим не отменяет жёсткие гарантии и может изменяться по ходу разговора.

## Контракт UX

- Пользователь начинает со свободного рассказа, а не с классификатора.
- Агент задаёт один вопрос за раз.
- После минимального ядра каждый вопрос содержит вариант создать черновик сейчас.
- Прогресс означает качество проработки ключевых блоков, а не процент завершения
  внутренней анкеты.
- Готовый драфт можно редактировать в той же сессии: содержательная правка в
  чате применяется за один ход; при отказе LLM прежний драфт и текст правки
  сохраняются. Прямое редактирование полей не требует LLM.
- Основная роль, затронутые пользователи, процесс и приоритет редактируются
  независимо. Пересборка сохраняет идентификатор и автора драфта.
- Сигнал о необходимости аналитика не означает автоматическую передачу:
  интерфейс прямо сообщает, что отправка ещё не выполнена.
- Предположения и незаполненные блоки явно видны до отправки.
- UI получает фактический режим диалога, источники, происхождение и уверенность полей; технические уровни уверенности локализуются на клиенте.
- После отправки черновик доступен только для чтения до явного возврата request на уточнение.
- Корректный запрос на изменение не требует от пользователя знания инвестиционной
  терминологии: агент распознаёт комбинацию действия, системного объекта и
  бизнес-сущности.
- Пограничный запрос уточняется, а не отклоняется. Жёсткий отказ применяется
  только к явно посторонним или запрещённым запросам.

## Ключевые блоки качества

Потребность, To-Be, роль, процесс, продукт, критерии приёмки, модуль, ценность и
регуляторные аспекты. Они используются и для UI-прогресса, и для расчёта полноты.

## Профили качества по типам обращения

- **feature:** сценарии, целевое состояние, ценность и проверяемые критерии;
- **change:** обязательное различие As-Is/To-Be и анализ зависимостей;
- **problem:** наблюдаемая проблема, текущий процесс, эффект и критерии устранения;
- **incident:** краткий дефектный путь с последующей диагностикой;
- **clarification:** ответ из базы знаний и опциональный переход к запросу.

Техническая полнота и качество БТ являются разными показателями. Качество также
учитывает измеримость критериев и обнаруженные противоречия.

## Семантический анализ

Каждый содержательный ход проходит `decide_strict`. Модель возвращает кандидаты
с операцией add/replace/remove/confirm/defer и цитатой пользователя. Типы данных,
допустимые поля, опора значения на цитату и текущая реплика для исправлений
проверяются до изменения состояния. Неподтверждённые кандидаты сохраняются как
предположения, а противоречивые версии — как отдельные записи для уточнения.
Повтор прежнего предположения не превращает его в подтверждённый факт.

Ответ об обновлении полей строится с учётом результата применения фактов.
Неуспешное изменение не сопровождается обещанием «записал». Описание контрактов
состояния находится в [FACT_STATE.md](FACT_STATE.md).

«Да» подтверждает только непосредственно показанное резюме; «понял» и
«продолжай» не считаются подтверждением. «Нет» после содержательного вопроса
передаётся модели как ответ. Команды завершения сохраняют собранные сведения.
Сигнал о необходимости аналитика не блокирует последующую корректировку.

Модельные сигналы `summarize`, `draft` и `ready_for_draft` проходят общую проверку
готовности. После минимального ядра лимит вопросов и усталость завершают сбор
резюме с пробелами; один и тот же вопрос проверки качества не повторяется
бесконечно. Явный запрос раннего черновика сохраняет короткий путь. Резюме
показывает As-Is, регуляторные ограничения, предположения, конфликты и пробелы;
его подтверждение не подтверждает каждое поле отдельно.

## Метрики результата

Главные продуктовые метрики:

- доля драфтов, принятых BA без возврата заказчику;
- количество существенных правок аналитика;
- время пользователя до отправки;
- количество повторных уточнений после передачи;
- доля требований с проверяемыми критериями приёмки;
- abandonment rate и оценка удобства.

Completion rate и число заполненных полей являются только диагностическими
метриками и не доказывают качество БТ.

В активном runtime счётчики обновляются на каждом ответе, включая раннее
создание черновика; времена начала и создания берутся из сохранённой сессии.
Агрегатор остаётся в памяти процесса и не является полной историей продукта.
Перечисленные выше метрики экспертного принятия требуют отдельного сбора данных.
