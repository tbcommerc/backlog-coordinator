# Управляющий API запусков

Проверено 04.11.2026. Реализация миграции продолжается; полная приёмка L/C
ещё не завершена. Рабочая БД DMB этим изменением не мигрировалась.

V1/V2 добавляют `/internal/agent/v1` рядом с прежними предметными маршрутами.
V1 поддерживает `dialogue.message`; V2 — `dialogue.message`, `document.generate` и `document.review`. Сервис встреч использует
собственный фасад `meeting.extract`. Оценщик добавляет `value.estimate`/`priority.estimate`; ассистент по бэклогу —
`backlog.answer`. Их автономные проверки выполнены; сквозная приёмка gateway
и контейнерных профилей ещё продолжается.

Для V1/V2 обязательны `X-Agent-Secret`, `X-Agent-Caller: dmb`, числовой
`X-Actor-Ref` и `Idempotency-Key`. Необязательный `X-Agent-Context` — JSON
доверенного gateway: имя, email, роль, customer_access, team_name, department,
is_ba, operator_role. Идентификатор пользователя берётся только из заголовка
инициатора. Для диалога пользовательский `input` принимает `message`; документные операции V2 проходят собственную строгую валидацию входа.
Сервисный секрет остаётся на доверенной границе; заголовки не предназначены
для отправки из браузера пользователя.

`conversation_ref` и `source.ref` равны ID существующего диалога,
`source.kind=dialogue`, `source.revision` — его сохранённая версия.
`source.snapshot_hash` — `sha256:` и SHA256 UTF-8 JSON объекта `input`:
ключи сортированы, разделители `,`/`:`, `ensure_ascii=false`.
Перед выполнением сервис повторно проверяет владельца и ревизию диалога.

Технические таблицы `agent_runs`/`agent_run_events` создаются только явной
командой `python -m business_analyst.migrate` либо
`python -m business_analyst_experimental.migrate`. Расширение существующей БД
требует `--verified-backup-file`; импорт приложения не выполняет DDL.
Прежние записи диалогов и квитанции сообщений сохраняются.

Работник держит изменения диалога в той же транзакции, что финальный CAS запуска.
Отмена с отдельного соединения либо потеря версии запрещает публикацию и
откатывает состояние диалога и квитанцию сообщения. Повтор неизвестного исхода
создания можно оградить `POST /runs/cancellations`: поздний create вернёт тот же
отменённый запуск. Терминальные операции автоматически не повторяются.

Новый фасад ограничивает вход фактическим объёмом 1 MiB до разбора JSON.
События содержат только технический статус; модельный текст через SSE не идёт.
Результат читается отдельно, подтверждается `/acknowledgements` и очищается
по политике хранения. Старые API сохраняют прежний формат.

## Общий лимит

SDK 1.4.0 добавляет Redis-координатор логических операций: общий профиль — два
слота, самостоятельный сервис — один. Активная аренда не истекает по TTL.
Подготовка профиля выполняется штатным launcher до импорта приложения.
Режим без координатора допустим только в изолированных тестах.

Параметры запуска: `DMB_AGENT_LIMITER_MODE`, `DMB_AGENT_LIMITER_REDIS_URL`,
`DMB_AGENT_LIMITER_NAMESPACE`, `DMB_AGENT_LIMITER_STATE_DIR`; launcher получает
epoch и путь журнала через `python -m dmb_agent_contracts.limiter_cli`.
`DMB_AGENT_SERVICE_ID` задаёт сервис, `DMB_AGENT_REQUIRE_LIMITER=true` включает
обязательную проверку. Журнал должен быть доступен всем процессам одного общего
профиля по одному согласованному пути. Для разных Docker-хостов эта локальная
топология ещё не квалифицирована.

Потеря Redis, его поколения либо журнала закрывает допуск новых операций.
Восстановление `--reconcile-after-restart` допускается только после доказанной
очистки всех ранее активных ресурсов. Нельзя удалять epoch/журнал для обхода
занятых слотов. Транспорт Go ограничивает весь HTTP-обмен общим deadline;
слот сохраняется, пока реальный запрос или изолированная среда не закрыты.

Подтверждены синтетические межпроцессные проверки десяти операций пяти сервисов
(максимум два одновременно) и реальный перезапуск отдельного Redis с устаревшим
RDB. Эти проверки не являются живой предметной приёмкой Go или настоящего
серверного OpenCode.


Оценщик сохраняет собственный заголовок `X-Prioritiser-Secret`, а также требует
`X-Agent-Caller: dmb` и `X-Actor-Ref`. Его `input` — строгий `TaskAttributes`;
`source.kind=work_item`, `source.ref=task_id`. Снимок хешируется тем же способом,
что вход диалога. Полная история ответа и финальный CAS коммитятся вместе;
параллельные F5/F6 сохраняют только технический model cache независимыми сессиями.
Новый Alembic head — `20261104_03`, миграция только расширяет техническую схему.

Ассистент сохраняет mTLS и `X-Gateway-Attestation`, подписывающий метод, полный
путь, тело, ключ идемпотентности и одноразовый nonce. Новый фасад не принимает
обычный service secret вместо этой подписи. `input` соответствует `MessageCreate`,
`conversation_ref=source.ref` — существующая сессия ассистента,
`source.kind=assistant_context`, `source.revision=context_revision`.
Создание общего и прежнего запуска выполняется в одной транзакции с одним ID.
Проверенный ответ публикуется вместе со статусом общего запуска. Чтение результата
требует актуального `X-Read-Proof` и повторной проверки всех использованных источников.
Его явная миграция версии 3 требует проверенную резервную копию существующей схемы.

## Явная повторная попытка и профиль

Проверено 04.11.2026. Новый ключ идемпотентности может ссылаться на терминальный
запуск через `retry_of` (UUID) или `retry_of_key` (его ключ в том же caller/actor).
Оба поля, если переданы вместе, должны указывать на один запуск. Операция,
диалог и объект источника должны совпадать; чужой предшественник возвращает 404,
активный или несовместимый — 409. Автоматического повторного выполнения нет.
В статусе сохраняется канонический `retry_of`; capabilities объявляют
`explicit_retry_links` и `retry_by_key`. Старые тела без этих полей сохраняют хеш.

Расширение добавляет nullable `retry_of` в `agent_runs` и `meeting_runs`.
Для оценщика применяется Alembic `20261104_03`, для ассистента — техническая
версия 3; V1/V2 и встречи используют свои явные команды миграции. Изменение
существующей схемы требует проверенной резервной копии. Обычный start и doctor
ничего не мигрируют; doctor проверяет также колонки и актуальную версию.

Модельный профиль фиксируется при приёме запуска. Его смена до dispatch
завершает запуск с `runtime_profile_changed` до создания ресурса. Для внешней
фабрики ассистента обязательна стабильная `profile_ref`: 64 шестнадцатеричных
символа, совпадающая с `RuntimeSpec.profile_ref`. Смена endpoint, модели или
политики изоляции должна менять эту ссылку.

## Совместимые клиентские маршруты

Проверено 04.11.2026. В обычном режиме прежние chat/chat-stream V1/V2
создают долговечный run и ожидают его сохранённый результат. Единственный
исполнитель — service worker. `message_id` нужен для восстановления
запроса; DMB уже передаёт его. Legacy DTO без ID остаётся допустимым: сервер
назначает отдельную identity, но неизвестный повтор без клиентского ID
не может быть отождествлён с первым запросом. Переподключение с тем же ID читает тот же run
после изменения ревизии диалога; другое тело возвращает конфликт. Старые
квитанции сообщений, созданные до переключения, читаются без нового выполнения.
SSE сохраняет ready/status/delta/result; повторная генерация формулировки после
commit не выполняется. Обрыв HTTP не отменяет принятый run.

V2 также направляет `create_draft`, `draft`, `propose_change` и `review`
через очередь. Вход документного фасада принимает необязательные `action`
и `field`; action должен соответствовать generate/review. Ручные правки,
применение предложения и создание редакции остаются предметными транзакциями.

Прежние `/agent/value*` и `/agent/priority*` оценщика используют тот же worker
и сохраняют выходные DTO. DMB передаёт `X-Agent-Caller: dmb`, `X-Actor-Ref`,
`Idempotency-Key` и `X-Source-Revision`; все транспортные повторы одного запроса
сохраняют ключ. Аутентифицированные прежние операторские клиенты без actor
остаются отдельным service principal `legacy-coordinator/coordinator-service`,
а не подставным пользователем. Для восстановления неопределённого HTTP-исхода
они должны передавать собственный ключ либо использовать управляющий API.
Изолированный unit mode сохраняет синхронные handlers без фонового worker.


Проверено 04.11.2026: область ключа общего фасада — сервис, caller, actor,
operation и Idempotency-Key. Один ключ разных операций даёт независимые
квитанции; отмена неизвестного создания и retry_of_key используют ту же область.
Известная старая уникальность caller/actor/key заменяется явной миграцией
с подтверждённой резервной копией. Для SQLite миграция выполняется при
остановленных работниках; для PostgreSQL изменение ограничения транзакционно.
История, хеши, ID и события не переписываются. Откат на прежнюю уникальность
запрещён, если разные операции уже использовали одинаковые ключи.

Срок гарантии идемпотентности фиксируется на каждый ключ при создании.
Уменьшение текущей настройки его не сокращает; старые записи без сохранённого
срока удерживаются 90 дней. Приватная отметка срока не входит в ответ или
модельный профиль обработчика. Старый cleaner несовместим с этой гарантией
и требует обновления перед подключением к новой БД при откате.

Проверено 05.11.2026: legacy документные DTO V2 без idempotency_key также принимаются с назначенным ключом; для восстановления доставки клиент должен задать свой стабильный ключ. Обязательность ключа нового фасада не изменилась.
