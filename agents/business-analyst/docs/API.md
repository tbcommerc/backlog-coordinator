# AI Business Analyst Agent — API Reference

## Nullable-контекст — проверено 20.10.2026

При создании диалога отсутствующие и явно `null` строковые поля контекста
пользователя нормализуются в пустые строки перед созданием `UserContext`.
В частности, профиль без email может создать диалог без 502.
Реквизиты и сам профиль при этом не изменяются. Проверено unit-тестами
`test_nullable_context.py` и живым запросом заказчика №16.

## Извлечение поручений из встречи — проверено 17.10.2026

`POST /api/agent/meetings/extract`, обязательный `X-Agent-Secret`.
Вход: `transcript` (1–60 000 символов), необязательная `meeting_date`.
Выход: `items` (до 60), каждый содержит тип action/agreement, название,
описание, исполнителя текстом, исходную формулировку срока, точную цитату,
UUID, `origin=ai`, `selected=false`, пустые календарный срок и связь.
Строгая схема и проверка цитат; модель не имеет инструментов записи.
Ошибки: 502 при некорректном результате, 503 при недоступности провайдера
или mock-режиме. Черновики и подтверждение принадлежат backend.
Отказ авторизации провайдера (его HTTP 401/403) возвращается как HTTP 503 с
`detail={code: "meeting_ai_auth", message: <фиксированное безопасное пояснение>}`.
Ответ провайдера, его URL и реквизиты не возвращаются. Gateway сохраняет этот
код для отдельного состояния настройки AI на странице; при фоновом извлечении
backend сохраняет его в `analysis_error_code` принятого задания. 401 авторизации
пользователя приложения с этой ошибкой не смешивается.
Новые переменные окружения не нужны; используется действующий LLM.
[Полное описание](../../../docs/meeting-capture-agent.md).

> AS-IS проверено по `business_analyst/api/router.py`, `business_analyst/api/schemas.py`, session store
> и API-тестам 08.09.2026.

`GET /api/agent/health` сообщает liveness процесса. `GET /api/agent/ready`
возвращает 200 только при доступной БД сессий и допустимой конфигурации LLM;
при отказе зависимости возвращает 503 с безопасными типами ошибок.

## Назначение и адреса

Agent — внутренний FastAPI-сервис на `127.0.0.1:9000`. DMB Backend обращается к
нему по HTTP; браузер не должен вызывать Agent напрямую.

- Swagger UI: `/docs`;
- OpenAPI: `/openapi.json`;
- health: `GET /api/agent/health`;
- прикладной prefix: `/api/agent`.

Health не требует секрета. Все остальные прикладные endpoint требуют точное
значение `X-Agent-Secret`. В production endpoint Agent публикуется только во
внутреннюю сеть Compose/оркестратора.

Точный request/response контракт публикуется OpenAPI. Этот документ фиксирует
сквозные правила, которые нельзя надёжно вывести только из списка полей.

## Chat

Минимальный запрос:

```json
{
  "session_id": "session-123",
  "message_id": "client-message-001",
  "message": "Нужно автоматизировать сверку статусов расчётов",
  "context": {
    "user_id": 42
  }
}
```

`message` ограничен 4000 символами, `message_id` — 64. DMB Backend генерирует
стабильный `message_id`: повтор одного сообщения возвращает сохранённый ответ и
не добавляет вторую запись в историю.

Основные поля `AgentResponse`:

- `session_id`, `action`, `message`, `phase`;
- `blocks` — UI-блоки, включая preview и actions;
- `slots`, `progress`, `expected_slot`;
- `draft`, `quality`, `can_generate_draft`;
- `history`, `request_id`;
- `dialogue_mode`, `sources` — фактический режим диалога и использованные справочные материалы для прозрачности UI.

`action` описывает следующий шаг UI, а не HTTP-статус. Фактический набор
определяет orchestrator и покрывается API-тестами.

Новые записи assistant в `history` содержат `context.sources` и `context.mode`
на момент ответа. `sources` в ответе относятся к текущей реплике; у старой
истории контекст может отсутствовать. `progress[].status` различает `empty`,
`filled`, `skipped`, `unknown`, `not_applicable`. Неизвестное значение не
учитывается как заполненное обязательное поле.

`chat-stream` принимает тот же `ChatRequest`, но отвечает `text/event-stream`.
События идут в порядке `ready` → `status` → ноль или более `delta` →
необязательный `replace` → `result`. `delta` содержит только текст итоговой
пользовательской формулировки; внутренний structured-ответ модели в поток не
попадает. `replace` нужен, если уже показанный поток не прошёл финальную
проверку инвариантов, а `result` всегда содержит полный валидный `AgentResponse`
и завершает успешный поток. Повтор с тем же `message_id` возвращает сохранённый
`result` без повторного добавления истории.

При отключённом LLM или fallback-ответе итоговый текст может прийти одним
`delta`. Разрыв соединения прекращает доставку клиенту, но не отменяет уже
начатую серверную обработку: результат сохраняется и доступен при повторе того
же `message_id` или загрузке сессии.

`edit-draft-section` возвращает `action=sent_locked` и не изменяет данные, пока `review_status=needs_review`. Редактирование снова разрешается только после явного `reopen-review` в workflow возврата на уточнение.

## Сессии и конкурентность

Session store использует SQLAlchemy. Для production `SESSION_DATABASE_URL`
обязан указывать на PostgreSQL; SQLite допустим только в debug/изолированных
тестах.

- каждая строка имеет CAS-версию;
- mutation одной сессии сериализуется PostgreSQL advisory lock;
- повтор `message_id` идемпотентен;
- список сессий изолирован по `user_id`;
- archive не удаляет историю.

Элемент `GET /sessions` дополнительно содержит `has_draft`,
`last_message_role` и `needs_user_response`. Фаза списка восстанавливается из
авторитетных признаков draft/review/finished даже для старых строк со
сохранённым устаревшим `phase`. Поэтому готовый черновик не выдаётся интерфейсу
за диалог, ожидающий очередного текстового ответа пользователя.

Эти гарантии позволяют запускать две реплики Agent из
`compose.production.yaml` без process-local состояния диалога.

## Review workflow

`send-for-review` принимает `session_id`, числовой `task_id`, `title` и
необязательный `user_id`, а также `expected_draft_hash` просмотренного снимка.
Операция требует готового подтверждённого draft. Проверено 08.09.2026:
ожидаемый SHA-256 сравнивается до независимой проверки, внутри сериализации
сессии. При расхождении возвращается `action=revision_conflict`; при успехе
ответ содержит полный подтверждённый `draft` и его `draft_revision`.
Хеш вычисляется по полному canonical JSON: сортировка ключей, UTF-8,
разделители `,`/`:`, `ensure_ascii=False`, NaN запрещён. DMB сохраняет именно
подтверждённый снимок. GET состояния, обновление review findings и хеширование
выполняются в одной блокировке сессии, как ручная правка и отправка.

Для активного `AgenticOrchestrator` поток передаёт уже проверенный текст ответа
без повторной LLM-переформулировки: `delta` и `result.message` сохраняют факты,
ограничения и степень уверенности исходного ответа. Кэш и идемпотентность
`message_id` остаются общими для потока и обычного chat. Legacy runtime сохраняет
прежнюю переформулировку.

Draft содержит `primary_role`, `affected_users`, `process`; совместимый
`user_roles` объединяет основную роль и затронутых пользователей без дублей.
`edit-draft-section` поддерживает эти поля и `priority`; некорректное поле
возвращает `action=error`, а не подтверждение сохранения. Идентификатор драфта
и `created_by` сохраняются при редактировании.

`review_findings` с `severity=error` — источник блокеров UI и серверной
отправки. Проверка выполняется также при восстановлении старого черновика.
Она блокирует отсутствие минимального ядра (для incident — потребности) и
критические противоречия. `review_blocked` вычисляется по этим findings;
при отказе возвращаются `action=validation_error`, пояснение и актуальный draft.
Отправленный диалог отвечает `sent_locked` и на команду перезапуска в чате.

`reopen-review` принимает `session_id`, необязательный `user_id` и комментарий
до 5000 символов. Возврат снова делает диалог редактируемым; история и audit
сохраняются.

`cancel-review` принимает `session_id`, `task_id` и `user_id`. Backend вызывает
его только после rollback своей транзакции. Agent снимает маркер отправки лишь
когда текущий `review_task_id` совпадает, поэтому компенсация не отменяет более
новую или конкурентную отправку.

`edit-draft-section` принимает только разрешённое имя поля и значение до 5000
символов. После правки качество и presentation пересчитываются по текущему
draft.

## Context

`context` преобразуется в `UserContext`. Неизвестные или недоверенные поля не
должны использоваться для повышения прав. Авторизацию пользователя выполняет
DMB Backend; shared secret подтверждает сервисный вызов, а не роль человека.

## Ошибки

- `403` — отсутствующий или неверный `X-Agent-Secret`;
- `404` — сессия не найдена;
- `409` — конфликт версии/состояния, который нельзя безопасно повторить;
- `422` — ошибка Pydantic или нарушенное бизнес-условие endpoint;
- `500` — необработанная ошибка runtime.

DMB Backend преобразует недоступность/timeout Agent в контролируемый ответ proxy.
Секреты, системные промпты и сырые исключения не должны возвращаться клиенту.

## Наблюдаемость

При `OTEL_ENABLED=true` Agent инструментирует FastAPI, SQLAlchemy и urllib,
отправляет OTLP/HTTP traces и добавляет `X-Trace-ID`. Endpoint Prometheus у Agent
не реализован; HTTP-метрики proxy фиксирует DMB Backend. Health исключён из
трассировки по умолчанию.

Agent не настраивает CORS и rate limiting: он не является публичным browser API.
Сетевое ограничение, TLS и внешний rate limit обеспечиваются ingress/backend.
