# Контракт с Backlog coordinator

Дополнение 02.11.2026: [HTTP tools 1.0](REMOTE_TOOLS.md) — отдельный внутренний контракт scoped grants. Прежние `/agent/*` DTO сохранены; принятие factor tool не является разрешением записи в DMB.

> AS-IS сверено с `value_priority_assessor/api/contract.py`, `value_priority_assessor/service/scenarios.py` и FastAPI
> endpoint `/agent/*` 10.09.2026.

Агент-приоритизатор встраивается в Backlog coordinator как **вызываемый сервис
с долговечной очередью выполнения**. Backlog coordinator владеет базой и интерфейсом; агент считает.

Схемы — `value_priority_assessor/api/contract.py`. Транспорт (HTTP, очередь, вызов внутри процесса)
не зафиксирован; контракт от него не зависит.

## Два сценария

| Сценарий | Кнопка в интерфейсе | Что возвращает |
|---|---|---|
| `value` | «Рассчитай Value(internal)» | Финансовый эффект, диапазон, уверенность, обоснование |
| `priority` | «Определи приоритет» | P1–P5, вклад каждого фактора, обоснование |

Приоритет опирается на Value. Если Value не пришёл в атрибутах, агент сначала
считает его сам и возвращает вместе с приоритетом — отдельный вызов не нужен.

## Следствие отсутствия доступа к БД

Агент не читает базу Единого бэклога. Это касается и оценки по аналогии, которая
сейчас основной метод расчёта Value: на 192 задачах с известным ответом она
попадает в двукратную окрестность в **67%** случаев против **14%** у формулы.
Аналогия работает по задачам, где Value заполнил человек, а таких задач в
запросе нет — приходит одна задача.

Поэтому исторические оценки **зашиты в агента отдельным версионируемым
артефактом** — `data/value-snapshot/snapshot.json`: 192 задачи с человеческим
Value плюс `max_value_mln` для шкалы фактора F1. Обновляется не запросом в БД, а
выгрузкой из Backlog coordinator с согласованной периодичностью — тем же путём, что и
закрытый пакет знаний. Версия артефакта возвращается в каждом ответе
(`audit.snapshot_version`), чтобы можно было понять, на какой базе считалась
конкретная цифра.

**Шкала фактора F1 едет там же и по той же причине.** Value нормализуется
логарифмом относительно максимума по бэклогу, иначе задача получила бы балл в
другой шкале, чем соседи. Максимум привязан к версии слепка и не
пересчитывается от запроса к запросу: иначе приоритет задачи менялся бы без
изменения самой задачи.

Если слепка нет, расчёт не падает: он переходит на формулу и добавляет в
`warnings` предупреждение, что оценка заметно менее точна. Отсутствие слепка —
рабочее состояние новой установки, а не авария.

Плата за это — устаревание: Value, заполненные людьми между выгрузками, агент
не видит. Альтернатива — передавать аналоги в самом запросе, но тогда
Backlog coordinator должен уметь искать похожие задачи, то есть содержать половину
агента у себя.

## Вход

### Атрибуты задачи

| Поле | Тип | `value` | `priority` | Колонка бэклога |
|---|---|:--:|:--:|---|
| `task_id` | строка | обяз. | обяз. | ID задачи |
| `task_type` | строка | обяз. | обяз. | Тип задачи |
| `team` | строка | обяз. | обяз. | Ответственная команда |
| `title` | строка | обяз. | обяз. | Наименование задачи |
| `description` | строка | — | — | Описание задачи |
| `created_date` | дата | — | — | Дата поступления задачи |
| `customer_division` | строка | — | — | Подразделение бизнес-заказчика |
| `project` | строка | — | — | Проект |
| `deadline` | строка | — | обяз. | Срок выполнения |
| `involved_teams` | строка | — | — | Вовлечённые команды |
| `effort_man_days` | число | — | обяз. | Оценка трудозатрат, ч/д |
| `business_customer` | строка | — | обяз. | ФИО бизнес-заказчика |
| `value_internal_mln` | число | — | — | Value, если заполнен человеком |

`deadline` приходит в исходном виде: `3Q 2026`, `1Q 2026,2Q 2026`, `2026`,
`БЕЗ СРОКА`. Разбор — на стороне агента.

Незаполненное поле передаётся как `null` либо не передаётся вовсе. Пустая
строка и `null` для агента одно и то же.

### Почему трудозатраты и заказчик обязательны для приоритета

Вместе они несут **32% веса** модели: ресурсоёмкость — 0.17, уровень
заказчика — 0.15. Без них треть модели заменяется нейтральными значениями, и
приоритет перестаёт различать задачи. Первый прогон на 440 задачах это показал
буквально: 83% бэклога попало в P3.

Агент проверяет обязательные поля сам и при нехватке возвращает
`status: insufficient_data` со списком недостающих, а не считает «как получится».

### Value, заполненный человеком

Если `value_internal_mln` пришёл, он **истина**. Агент не пересчитывает его, не
корректирует и возвращает с `method: "manual"`, `confidence: "high"` и
диапазоном нулевой ширины. Обратное поведение обесценило бы работу команд,
которые эти поля заполняли.

## Период получения дохода

Три года, начиная с периода, следующего за сроком выполнения. Гранулярность
сдвига повторяет гранулярность срока:

| Срок | Доход считается с | по |
|---|---|---|
| `3Q 2026` | 2026-10-01 | 2029-09-30 |
| `1Q 2026,2Q 2026` | 2026-07-01 | 2029-06-30 |
| `2026` | 2027-01-01 | 2029-12-31 |
| `БЕЗ СРОКА` | следующий квартал | +3 года |

Из списка кварталов берётся последний — задача завершена, когда закрыт
последний из заявленных периодов. При отсутствии срока окно отсчитывается от
квартала, следующего за текущим, и в ответ добавляется предупреждение: это
допущение, а не расчёт.

Реализация — `value_priority_assessor/core/horizon.py`.

## Выход

Оба сценария возвращают один конверт:

```json
{
  "task_id": "TASK-300-014",
  "request_type": "value",
  "status": "ok",
  "value": { },
  "priority": null,
  "warnings": [],
  "audit": { }
}
```

### Сценарий `value`

```json
{
  "task_id": "TASK-300-014",
  "request_type": "value",
  "status": "ok",
  "value": {
    "internal_mln": 25.0,
    "low_mln": 4.2,
    "high_mln": 148.0,
    "coverage": 0.95,
    "confidence": "medium",
    "method": "analogy",
    "currency": "RUB",
    "horizon": {
      "start": "2026-10-01",
      "end": "2029-09-30",
      "years": 3,
      "derived_from": "3Q 2026"
    },
    "drivers": [],
    "analogues": [
      {"task_id": "TASK-300-002", "title": "…", "team": "IB",
       "project": "…", "value_mln": 30.0, "similarity": 0.971}
    ],
    "calculation": "медиана(30.0; 25.0; 18.0) = 25.0",
    "rationale": "Три задачи команды IB с человеческой оценкой…",
    "missing_inputs": ["Ожидаемое число сделок в год"],
    "zero_reason": null
  },
  "priority": null,
  "warnings": [],
  "audit": { }
}
```

**`method`** — каким путём получено число:

| Значение | Когда |
|---|---|
| `manual` | Value пришёл в атрибутах |
| `analogy` | Найдены похожие задачи с человеческой оценкой |
| `drivers` | Расчёт по формуле на драйверах из справочника |
| `zero` | Регуляторка, техдолг, исследование — эффекта по методике нет |

**`low_mln` / `high_mln`** — границы, в которые истинное значение попадает в 95%
случаев. Ширина и есть численное выражение уверенности. У `manual` и `zero`
диапазон вырожден: они точны по определению.

**`drivers`** — каждая величина, участвовавшая в расчёте, с указанием
происхождения:

| `origin` | Смысл |
|---|---|
| `attribute` | Из атрибутов самой задачи |
| `reference` | Из справочника `value_drivers.yaml` |
| `substitution` | Разрешённая замена отсутствующего драйвера |
| `assumption` | Числовая вводная, возвращённая моделью и требующая подтверждения |

Замена и предположение понижают уверенность — правила в шапке
`data/references/value_drivers.yaml`. Отсутствующий числовой драйвер не
заменяется типовым значением: без полного набора вводных формульный метод не
возвращает число и перечисляет `missing_inputs`.

**`missing_inputs`** — что спросить у автора задачи, чтобы оценка сузилась. Это
рабочий список для интерфейса, а не оправдание.

### Сценарий `priority`

```json
{
  "task_id": "TASK-300-014",
  "request_type": "priority",
  "status": "ok",
  "value": { },
  "priority": {
    "priority": "P2",
    "score": 0.647,
    "factors": [
      {"code": "F1", "title": "Value (внутренний)", "weight": 0.31,
       "score": 0.71, "contribution": 0.220,
       "explanation": "Value 25 млн ₽ при максимуме 3600 млн ₽ в бэклоге",
       "source": "computed"},
      {"code": "F5", "title": "Стратегическое соответствие", "weight": 0.10,
       "score": 0.80, "contribution": 0.080,
       "explanation": "Проект входит в стратегическую тему…",
       "source": "assessed"}
    ],
    "overrides": [],
    "rationale": "…",
    "cost_rub": 1920000.0,
    "cost_to_value": 0.077
  },
  "warnings": [],
  "audit": { }
}
```

`value` в этом ответе присутствует, только если агент считал его сам.

**Коды факторов.** Коды идут подряд, `F1`–`F7`, и совпадают с ключами
справочника весов. Отношения C/V среди них нет: `C/V = Cost / Value`, а `Cost`
это трудозатраты, умноженные на константу, то есть обе вводные уже учтены
факторами F1 (Value) и F4 (ресурсоёмкость). Сам показатель возвращается полями `cost_rub` и
`cost_to_value` как диагностика для карточки: он информативен для человека, но
в скор не входит. Разбор с измерениями — `docs/DEVIATIONS-FROM-TZ.md`, раздел 3.

**`source`** у фактора отвечает на вопрос «откуда балл»: `computed` — из
атрибутов, `assessed` — суждение субагента, `default` — нейтральное значение,
данных не было. Последнее должно быть видно в интерфейсе: балл 0.3 «потому что
нейтрально» и балл 0.3 «потому что посчитали» — разные утверждения.

**`overrides`** — сработавшие правила. Они только повышают приоритет и
действуют вне зависимости от скора; каждое возвращает приоритет до и после.

**`score`** нужен для сортировки внутри одного P: внутри P3 может лежать 85%
бэклога, и без сырого скора этот список не упорядочить.

### Субагенты

| Субагент | Когда вызывается | Что даёт |
|---|---|---|
| Оценка Value | `method` = `analogy` или `drivers` | Набор драйверов и метод расчёта |
| Уверенность | всегда в сценарии `value` | Уровень уверенности, диапазон, обоснование |
| Стратегия | сценарий `priority` | Балл F5; вес у поля `Проект` выше, чем у названия задачи |
| Зависимости | `priority`, **только** если `involved_teams` пусто | Балл F6 |

Если `involved_teams` заполнено, зависимости берутся оттуда: заполненное
человеком поле точнее любого вывода модели.

Арифметику субагенты не выполняют. Модель определяет **что** считать — метод и
набор драйверов; **как** считать выполняет Python. Иначе два прогона одного
бэклога дали бы разные приоритеты.

### Аудит

```json
{
  "request_id": "3f2b…",
  "cache_key": "9a71…",
  "cached": false,
  "reused_from_request_id": null,
  "reference_versions": {"value_drivers": 2, "factor_weights": 3, "overrides": 1},
  "snapshot_version": "2026-08-11",
  "llm_calls": 2,
  "model": "gigachat:GigaChat-Pro",
  "duration_ms": 3480,
  "phase_duration_ms": {
    "value_classification": 740,
    "analogy_index": 0,
    "value_calculation": 12,
    "factor_assessments": 2610,
    "priority_scoring": 2
  },
  "computed_at": "2026-08-13T10:24:11Z"
}
```

Версии справочников в ответе нужны, чтобы отличить «агент передумал» от
«методолог поменял веса». Без этого расхождение двух оценок одной задачи
необъяснимо.

`llm_calls` считает фактические обращения к модели, а не попадания в LLM-кэш.
`phase_duration_ms` — инженерная телеметрия для поиска задержек; эти значения
не участвуют в Value, факторах или выборе приоритета. Для ответа, целиком
восстановленного из истории, словарь содержит фазу `response_cache`.

## Повторяемость

Требование: одинаковые данные — одинаковая цифра; небольшое изменение —
небольшое изменение цифры.

**Полное совпадение.** Перед любым обращением к модели агент считает ключ по
нормализованным атрибутам (`cache_key` в `value_priority_assessor/api/contract.py`) и ищет его в
истории запросов. Нашёл — возвращает прежний ответ с `cached: true` и
`reused_from_request_id`. Модель не вызывается.

В ключ входят только атрибуты, влияющие на результат. Формулировка задания из
Backlog coordinator (`prompt`) в ключ не входит: переформулировка не должна менять
цифру. Тексты нормализуются — схлопывание пробелов, неразрывный пробел, регистр,
— иначе лишний пробел от копирования даст промах кэша.

Ключ включает версии справочников и версию слепка. Смена весов методологом
обязана давать новый расчёт, а не выдачу прежнего из истории.

**Частичное совпадение.** Устойчивость обеспечивается устройством расчёта, а не
кэшем: аналогия берёт медиану нескольких похожих задач, а медиана не прыгает от
правки формулировки; драйверы фиксированы в справочнике; арифметика
детерминирована. Модель влияет на выбор метода и набора драйверов — эти два
решения тоже сохраняются в истории и переиспользуются при близком совпадении,
поэтому одинаковый набор драйверов даёт одинаковую формулу.

## Отказ

```json
{
  "task_id": "TASK-300-014",
  "request_type": "priority",
  "status": "insufficient_data",
  "error": "Не заполнены обязательные атрибуты",
  "missing_attributes": ["effort_man_days", "business_customer"]
}
```

Агент отказывается считать приоритет без обязательных полей вместо того, чтобы
выдать правдоподобное число на нейтральных значениях. Для сценария `value`
обязательных полей меньше: тип, команда и название дают достаточно для поиска
аналогов.

## Как вызвать

**REST.** Сервис поднимается тем же приложением, что и остальное API:

Каждый REST-вызов Координатора передаёт `X-Prioritiser-Secret`. Этот capability
secret не даёт доступа к `/admin/*`, для которого используется отдельный
`X-Methodologist-Secret`.

| Метод | Путь | Сценарий |
|---|---|---|
| `POST` | `/agent/value` | Рассчитай Value(internal) |
| `POST` | `/agent/priority` | Определи приоритет |
| `GET` | `/agent/snapshot` | Версия и состав зашитого слепка |

Тело запроса — `{"task": {…атрибуты…}}`, ответ — конверт, описанный выше.

**Командная строка.** Тот же путь без поднятия сервиса:

```bash
python -m app.cli agent value --task-id NEW-001 --task-type "AD-HOC" --team Core --title "Автоматизация сверки лимитов" --deadline "3Q 2026"
```

```bash
python -m app.cli agent priority --json request.json
```

`--json -` читает атрибуты из stdin. Наличие обоих путей — не удобство: CLI
даёт способ проверить контракт на реальных данных до того, как Backlog coordinator
начнёт слать запросы, и остаётся точкой, к которой подключён opencode-агент.

## Обновление слепка

Слепок собирается вне агента и едет вместе с ним:

```bash
python scripts/value_snapshot_build.py --from-db
```

Результат — `data/value-snapshot/snapshot.json`: задачи с человеческим Value и
`max_value_mln` для шкалы фактора F1. Версия по умолчанию — дата сборки,
задаётся флагом `--version`.

Проверить, что стоит у агента:

```bash
python -m app.cli snapshot
```

Периодичность обновления определяет эксплуатация. Чем реже — тем сильнее
расходятся оценки агента с тем, что за это время заполнили люди; версия слепка
в каждом ответе позволяет это увидеть.

## Что ещё не зафиксировано

* **Транспорт.** Схемы готовы; способ вызова выбирается на стороне Backlog coordinator.
* **Периодичность обновления слепка** исторических Value и способ доставки.
* **Тип «техдолг»** упомянут в постановке, но в слепке отсутствует: там
  `МЕТРИЧЕСКИЕ KR` (114), `КВАРТАЛЬНАЯ/ГОДОВАЯ ЦЕЛЬ` (181), `AD-HOC` (130),
  `ИССЛЕДОВАНИЕ` (10). Нужна строка в `data/references/task_types.yaml` с
  решением, даёт ли техдолг нулевой Value.
* **Поле «Описание задачи»** в слепке отсутствует. Контракт его принимает;
  насколько оно улучшит оценку, можно будет измерить только на реальных
  заполненных описаниях.

## Выполнение и повторы — проверено 04.11.2026

Выходные DTO `/agent/*` сохранены. В обычном режиме выполнение принадлежит
долговечному worker; прежний HTTP endpoint ожидает сохранённый результат.
DMB передаёт доверенные `X-Agent-Caller: dmb`, `X-Actor-Ref`,
`Idempotency-Key`, `X-Source-Revision` вместе с прежним service secret.
Один ключ сохраняется во всех транспортных повторах. История и финальный
статус коммитятся вместе; источник и профиль фиксируются при приёме.
Клиенты без actor остаются аутентифицированным операторским service principal.
Они могут передать свой ключ для восстановления HTTP-исхода; автоматически
созданный ключ не является гарантией клиентского восстановления.
[Управляющий контракт](../../RUN_API.md) описывает очередь, ретенцию и явные retries.
