# Оценка факторов F5 и F6 субагентами

> AS-IS сверено с rubric, analysts, store и opencode tools 02.09.2026.

По ТЗ (Ф16, И3) стратегическое соответствие и зависимости между командами
приходят от внешнего агента Strategy Decomposer одним числом. Решением владельца
от 2026-08-11 оценка перенесена внутрь проекта и выполняется собственными
субагентами.

## Почему одного числа недостаточно

Внешний агент отдавал балл 1–10 и краткое обоснование. С таким ответом
методолог не может сделать ничего, кроме как принять его или отвергнуть целиком:
разложить число обратно на составляющие нельзя, а значит нельзя и оспорить
конкретное основание.

Отсюда устройство внутренней оценки: **субагент отвечает на критерии рубрики,
балл считает код**. Тот же принцип, что и во всей остальной методике, — модель
даёт входы, арифметику выполняет Python.

Это даёт три вещи, которых не даёт число:

* оценку можно оспорить по пункту: «связь с доходом здесь не прямая, а
  опосредованная» — предметный разговор, в отличие от «по-моему, не 8, а 6»;
* при изменении весов рубрики баллы пересчитываются без повторного обращения
  к модели;
* видно, на чём оценка стоит: ответы, обоснование и ссылки на фрагменты корпуса
  хранятся вместе с ней.

## F5. Стратегическое соответствие

Пять критериев с весами (`data/references/strategy_rubric.yaml`):

| Критерий | Вес | О чём |
|---|---:|---|
| `strategic_theme` | 0.30 | Привязка к направлениям развития трайба |
| `revenue_link` | 0.25 | Связь с доходом ДИД |
| `client_impact` | 0.20 | Влияние на путь корпоративного клиента |
| `platform_leverage` | 0.15 | Переиспользуемость результата |
| `mandate_fit` | 0.10 | Соответствие мандату команды |

Взвешенная сумма (0–1) переводится в шкалу ТЗ 1–10, дальше её нормализует
фактор F5 в 0.1–1.0.

**Уровень уверенности определяется числом источников**, а не самомнением модели:
два фрагмента корпуса и больше — высокий, один — средний, ни одного — низкий.
Оценка, ни на что не опирающаяся, не должна выглядеть уверенной.

## F6. Зависимость от команд

Субагент перечисляет команды и тип связи с каждой; штраф считает код.

| Тип | Штраф | Когда |
|---|---:|---|
| `blocking` | 0.25 | Работа не начнётся, пока команда не сделает своё |
| `coordination` | 0.12 | Можно вести параллельно, нужна синхронизация |
| `informational` | 0.04 | Достаточно уведомить |

Прежняя формула штрафовала за само число вовлечённых команд. Три команды,
которые достаточно уведомить, стоили дороже одной чужой поставки, без которой
работа не начнётся, — и это искажало ранжирование. Различие типов и есть главная
причина, по которой фактор перенесли внутрь.

Пустой список — валидный ответ. Самодостаточная задача не должна получать
выдуманные зависимости ради заполненности поля.

## Провайдеры

Оценка получается одним из трёх способов, с одинаковым контрактом:

| Провайдер | F5 | F6 | Когда применяется |
|---|:---:|:---:|---|
| `stub` / `declared` | ✓ | ✓ | Только явные тестовые прогоны (`declared` также читает переданный атрибут команд) |
| `agent` | ✓ | ✓ | Собственный оценщик на LLM-адаптере с опорой на корпус |
| `rest` | ✓ | — | Внешний Strategy Decomposer, как в исходном ТЗ |

```bash
PRIORITISER_STRATEGY_PROVIDER=agent     # agent | rest; stub только для тестов
PRIORITISER_DEPENDENCY_PROVIDER=declared # declared | agent
PRIORITISER_STRATEGY_USE_RAG=1
```

Рабочий default — `agent`: недоступность модели завершает расчёт ошибкой и не
включает эвристику. `stub` остаётся отдельной тестовой реализацией и должен
выбираться явно.

## Субагенты в opencode

| Субагент | Фактор | Пишет |
|---|---|---|
| `strategy-analyst` | F5 | `strategy-assess` |
| `dependency-analyst` | F6 | `dependency-assess` |

**Права разделены намеренно.** Ни оркестратор, ни другие субагенты не могут
записывать оценки; каждый аналитик пишет только свой фактор. Субагент, способный
двигать оба фактора одним суждением, легко подгонит их под желаемый приоритет —
разделение ролей этому мешает.

Порядок работы аналитика: прочитать рубрику (`rubric-read`), проверить, нет ли
уже оценки (`assessments-read`), прочитать задачу (`task-explain`), найти
основания в корпусе (`rag-search`), записать ответы (`*-assess`).

Инструмент возвращает ошибку с перечнем допустимых вариантов, если ответ не
соответствует рубрике: неполная оценка не записывается молча.

## Хранение

Таблица `factor_assessment`: ответы по критериям, вычисленный балл, обоснование,
идентификаторы фрагментов, провайдер, автор, модель, версия рубрики. Активная
оценка одна на пару «задача + фактор»; предыдущие сохраняются неактивными.

Баллы денормализованы в поля `Task` (`strategy_fit_raw`, `dependency_score`),
чтобы функции факторов оставались чистыми и не ходили в базу по каждой задаче —
именно это позволяет пересчитывать 440 задач за доли секунды.

**Оценки не пересчитываются на каждом прогоне.** Изменение весов факторов не
меняет сути суждения «насколько задача стратегична», а обращение к модели по 440
задачам не укладывается в норматив НФ8. Обновление — по явному требованию:

```bash
python -m app.cli recompute --all --refresh-strategy
```

## Что осталось нерешённым

Рубрика F5 написана на основе ТЗ и материалов трайба, но **не согласована с
методологом**. Веса критериев подобраны по здравому смыслу, а не выведены из
данных: калибровать их нужно на реальных решениях о приоритете, которых пока
нет. До этого F5 остаётся содержательнее прежней заглушки, но не является
выверенной методикой.
