## Пакет знаний K3

Пакет — age-зашифрованный tar, собранный в strategy-decomposer
(`package_version 2026.07.15.1`, `corpus_id k3-dmb-c2`). Внутри: корпус из девяти
источников, предсобранный FAISS-индекс, манифесты и набор из 25 размеченных
запросов.

**Правило обращения с ним, унаследованное от источника: в git попадает только
шифротекст.** Расшифрованный корпус, локальный векторный индекс и любые
извлечённые артефакты закрыты `.gitignore`. Тест
`test_decrypted_corpus_is_not_tracked_by_git` проверяет это на каждом прогоне.

В репозитории лежат:

```
data/rag-package/k3-rag-current.age      шифротекст, 3.2 МБ
data/rag-package/manifest.public.json    версия, sha256, счётчики
```

### Установка

```bash
python3 scripts/rag_package_install.py install
```

Расшифровать пакет может владелец приватного ключа, соответствующего одному из
получателей. По умолчанию берётся `~/.ssh/id_ed25519`, другой задаётся
`--identity`. Установщик сверяет sha256 шифротекста с публичным манифестом
**до** расшифровки, распаковывает архив с защитой от path traversal и заменяет
каталог целиком — полураспакованный корпус хуже отсутствующего.

```bash
python3 scripts/rag_package_install.py status
python3 scripts/rag_package_install.py remove
```

Без установленного пакета слой `k3` просто отсутствует: остальные три работают,
агент об этом честно сообщает через `rag-status`.

### Как отключить

```bash
PRIORITISER_RAG_ALLOW_K3=0
```

## Схема поиска

Два ретривера, объединение через Reciprocal Rank Fusion:

* **BM25** по токенам, усечённым до шести символов — грубая замена стеммера,
  которой хватает для русской морфологии бэклога («витрин-а/-ы/-ой»);
* **FAISS `IndexFlatIP`** по нормализованным эмбеддингам
  `intfloat/multilingual-e5-base` — та же модель, на которой собран пакет,
  поэтому семантика корпуса ведёт себя так же, как в исходном проекте.

RRF выбран не по вкусу: BM25-score и косинусная близость живут в разных шкалах и
разных диапазонах, складывать их напрямую нельзя, а ранги сопоставимы всегда.

Индекс сохраняется в `data/index/` и пересобирается только при изменении
отпечатка корпуса. Первая сборка занимает около минуты, последующие запуски
поднимают индекс с диска.

### Ограничение доли одного источника

Корпус K3 сильно перекошен: «Альбом продуктов» даёт около восьмидесяти процентов
всех фрагментов. Оба ретривера возвращали преимущественно его, а RRF перекос
усиливал — фрагменты, найденные обоими списками, получают удвоенный вклад.
Релевантный фрагмент небольшого документа не попадал в выдачу **вообще**: на
контрольном запросе Q08 ожидаемый источник отсутствовал даже в топ-20.

Поэтому на первом проходе одному источнику отводится не больше трети мест
выдачи, и только если мест не хватило — остаток добирается без ограничения. Это
исправило Q08 и подняло hit@k с 0.95 до 1.00.

## Проверка качества

Пакет несёт 25 размеченных запросов: для каждого указаны ожидаемые источники,
двенадцать требуют канонический источник `form-4441`, три помечены `no_answer` —
на них правильный ответ «в корпусе этого нет».

```bash
python3 scripts/rag_quality.py --top-k 8
```

Результат на текущем корпусе:

| Метрика | top-3 | top-5 | top-8 |
|---|---:|---:|---:|
| hit@k | 0.91 | 0.95 | **1.00** |
| Обязательный источник | 1.00 | 1.00 | **1.00** |
| Точность на no-answer | 1.00 | 1.00 | **1.00** |

Требования из README пакета (обязательный источник и no-answer равны единице)
выполняются на всех глубинах. Прогон закреплён тестом
`test_meets_package_quality_targets`.

Зачем это нужно: векторный поиск легко «работает» на глаз — он всегда что-то
возвращает, и выдача всегда выглядит правдоподобно. Отличить работающий поиск от
неработающего можно только на размеченном наборе, где заранее известно, какой
источник обязан оказаться в выдаче.

### Честная оговорка про плотный слой

На этом корпусе преимущество плотного слоя **не доказано**. После добавления
ограничения по источнику обе конфигурации дают одинаковый результат:

| Режим | hit@k | Обязательный источник | no-answer |
|---|---:|---:|---:|
| `dual_rrf` (BM25 + вектор) | 1.00 | 1.00 | 1.00 |
| `bm25` | 1.00 | 1.00 | 1.00 |

До ограничения различие было: BM25 давал 1.00 hit@k, но 0.92 по обязательному
источнику, а `dual_rrf` — наоборот, 0.95 и 1.00. То есть реальную проблему решило
разнообразие выдачи, а не плотный слой.

Плотный слой оставлен включённым по умолчанию: набор из 25 запросов слишком мал,
чтобы на нём отвергать семантический поиск, а корпус K3 написан продуктовым
языком, отличным от языка формулировок в бэклоге — именно там лексический поиск
и должен проваливаться. Но выдавать его за доказанное улучшение было бы
неправдой.

## Диагностика

```bash
python -m app.cli rag-status
```

Показывает состав слоёв, режим поиска, модель эмбеддингов и версию пакета.
То же доступно агенту инструментом `rag-status`, а preflight выводит это
отдельной проверкой `rag_corpus`.

```bash
python -m app.cli rag "критерии применимости мезонинного продукта" --layer k3 --top-k 5
```

В каждом результате возвращаются `bm25_rank` и `vector_rank` — видно, чем именно
найден фрагмент: лексическим совпадением, семантикой или обоими сразу.

## Что нужно знать при переносе в контур

1. **Шифротекст продублирован.** Пакет лежит и в strategy-decomposer, и здесь.
   Список получателей у копии зафиксирован на момент копирования: если владелец
   отзовёт получателя в исходном проекте, наша копия по-прежнему расшифруется
   старым ключом. При ротации получателей пакет нужно перекопировать.
2. **Модель эмбеддингов скачивается с Hugging Face** при первой сборке индекса.
   Во внутреннем контуре её нужно положить локально и указать путь через
   `PRIORITISER_RAG_EMBEDDING_MODEL`.
3. **Чанкование отличается от исходного.** Пакет собран с
   `chunking_version: 2-semantic-headings` и даёт 583 фрагмента; наш разбиватель
   режет длинные секции дополнительно и даёт 741. Поэтому пороги из
   `quality/retrieval-thresholds.json` напрямую не переносятся — мы меряем
   попадание в источник, а не абсолютный скор.
