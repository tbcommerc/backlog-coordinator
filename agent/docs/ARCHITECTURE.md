# Архитектура AI Business Analyst Agent

> AS-IS проверено по runtime, session store, KB adapters и тестам 08.09.2026.

Документ описывает фактически используемую архитектуру сервиса. Точка входа — `run.py`, приложение FastAPI — `agent/main.py`, основной диалоговый runtime — `AgenticOrchestrator`.

## Контекст системы

AI Business Analyst Agent — отдельный HTTP-сервис для сбора и оформления бизнес-требований. DMB Backend обращается к нему через `/api/agent/*` с заголовком `X-Agent-Secret`. Агент формирует черновик требования, но финальное решение остаётся за человеком.

```text
Пользователь
    ↓
DMB Backend / Frontend
    ↓ HTTP + X-Agent-Secret
FastAPI API (`agent/api/`)
    ↓
AgenticOrchestrator
    ├── guardrails
    ├── AgenticBA + LLM
    ├── session store и audit
    ├── composer + quality checks
    └── human-review workflow

SQLAlchemy session store → PostgreSQL (production)
OpenTelemetry → OTLP/HTTP collector
```

Исходники диаграмм находятся в `docs/diagrams/`.

## Основной runtime

Для каждого сообщения модель получает недавний диалог, карту уже собранных требований, фокус последнего вопроса и критические пробелы. Agentic runtime является единственным доступным режимом работы.

Модель возвращает структурированный `TurnDecision`, содержащий:

- извлечённые факты и исправления;
- предположения и противоречия;
- одно следующее действие;
- фокус следующего вопроса;
- естественный текст ответа.

`agent/dialogue/agentic.py` валидирует решение модели. Типы проверяются строго;
кандидаты сопоставляются с цитатами пользователя. Операции изменения, статусы
применимости, происхождение, предположения и конфликты сохраняются между ходами.
Контракт описан в [FACT_STATE.md](FACT_STATE.md).

`agent/agentic_orchestrator.py` применяет проверенное решение и формирует ответ API. Основной runtime не использует legacy state machine, фиксированный порядок слотов, эвристический Q&A router или старый question planner для управления обычным диалогом.

## Граница ответственности

Модель отвечает за семантическое понимание реплики, извлечение фактов и выбор следующего содержательного шага.

Python выполняет детерминированные обязанности:

- аутентификацию и guardrails;
- валидацию structured output;
- сохранение состояния и аудит;
- применение исправлений и сохранение конфликтов;
- построение схемы черновика;
- проверки качества;
- подтверждение, редактирование и отправку на human review.

Python не должен превращать основной agentic runtime в жёсткий опросник.

## Обработка сообщения

1. API проверяет `X-Agent-Secret` и входную схему.
2. Guardrails отклоняют конкретные нарушения безопасности или обработки данных.
3. `AgenticBA.decide_strict` выполняет один структурированный вызов LLM.
4. Результат валидируется и нормализуется.
5. `AgenticBA.apply` обновляет факты, исправления и противоречия сессии.
6. `AgenticOrchestrator` формирует следующий вопрос или другое разрешённое действие.
7. Composer и quality checks создают проверяемый черновик.
8. Независимый read-only validator проверяет черновик и блокирует отправку при
   структурной ошибке или критическом противоречии.
9. Терминальные операции выполняются детерминированно и записываются в аудит.

## Отказоустойчивость

Agentic runtime работает по принципу fail-closed. Если LLM недоступна или возвращает некорректный structured output:

- API возвращает действие `unavailable`;
- новые факты не извлекаются;
- fallback-диалог и эвристические догадки не запускаются;
- пользователь может повторить запрос после восстановления модели.

Если LLM недоступна, сервис не переключается на эвристический диалог: он возвращает `unavailable` и не изменяет карту требований.

## Данные и аудит

Состояние сессии хранит историю диалога, карту требований, исправления, противоречия, текущий фокус и состояние черновика. Изменения должны применяться через слой сессий, а значимые события — записываться через audit logger.

Полный сериализованный черновик имеет fingerprint `draft_revision`. При отправке
передаётся `expected_draft_hash`: расхождение с текущим snapshot отклоняется до
изменения статуса. DMB сохраняет snapshot, возвращённый подтверждением отправки.
Это отдельная проверка от CAS-версии сессии. История отправленных редакций и
комментариев хранится в обычной записи `RequirementRequest`.

SSE активного runtime передаёт уже проверенный текст без второго вызова LLM
на переформулировку. Счётчики диалога обновляются на каждом ответе; агрегированные
метрики остаются локальными для процесса и не заменяют продуктовую аналитику.

В production сессии находятся в PostgreSQL. CAS-version обнаруживает устаревшее
состояние, advisory lock сериализует mutation одной сессии между worker'ами, а
стабильный `message_id` делает повтор chat-вызова идемпотентным.

`kb_seed/` содержит исходные документы базы знаний. Правила её наполнения описаны в `KB_GUIDE.md`.

Retrieval policy учитывает минимальную релевантность, тип и статус источника,
а при наличии даты — допустимую давность. Приоритеты задаются независимо от
адаптера, поэтому локальная KB, история требований, БД и внешний RAG используют
единый воспроизводимый порядок.
