# Классификация домена и входных запросов

## Цель

Не отклонять корректные бизнес-запросы только потому, что пользователь не знает
терминологию платформы. Для intake-агента полнота распознавания важнее строгого
keyword matching, но security-проверки всегда имеют приоритет.

## Порядок решения

1. Prompt injection, запрещённые действия и чувствительные данные.
2. Сильные и слабые термины предметной области.
3. Форма запроса на изменение:
   - действие: добавить, изменить, вывести, автоматизировать и т. п.;
   - объект системы: поле, карточка, фильтр, реестр, отчёт, интеграция и т. п.;
   - бизнес-объект: клиент, сделка, контрагент, поручение и т. п.
4. Контекст активного диалога.

Обычная опечатка в длинном системном или бизнес-термине допускается через
ограниченное fuzzy-сопоставление. Короткие слова fuzzy-поиском не проверяются.

## Решения

| Решение | Поведение |
|---|---|
| `in_domain` | Сразу начать разбор потребности |
| `possibly_in_domain` | На первом ходе уточнить принадлежность платформе; внутри активного диалога принять как продолжение |
| `out_of_domain` | Вежливо вернуть пользователя в предметную область |
| `malicious_or_policy_violation` | Безопасный отказ |

Пример «добавить атрибут “Важный клиент” в карточку клиента» является уверенным
доменным запросом: действие + объект системы + бизнес-объект.

## Наблюдаемость

Для первого сообщения в audit log записываются verdict, причины, количество
доменных сигналов и признак `requirement_shaped`. Это позволяет анализировать
ложные отказы и расширять матрицу сценариев на основании реальных данных.

## Регрессионная матрица

Тесты покрывают:

- UI- и data-oriented доработки без инвестиционной терминологии;
- смешанный регистр и распространённые опечатки;
- короткие продолжения активного разговора;
- общие запросы на изменение, требующие уточнения;
- полностью посторонние темы;
- prompt injection, запрещённые действия и PII.
