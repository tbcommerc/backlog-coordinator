# AI Business Analyst Agent — Knowledge Base Guide

## Обзор

База знаний (KB) — это курируемый набор документов, которые агент использует для:
- Понимания предметной области (продукты, модули, процессы, роли)
- Ответов на вопросы пользователей (Q&A mode)
- Проверки дубликатов требований
- Grounded generation (ответы только на основе KB)

**ВАЖНО:** Агент использует ТОЛЬКО approved документы. Draft документы не searchable.

## Структура KB

```
kb_seed/
├── manifest.json              # Метаданные документов
├── business_context.md        # Бизнес-контекст подразделения
├── products.md                # Инвестиционные продукты
├── modules.md                 # Модули платформы
├── processes.md               # Бизнес-процессы
├── roles.md                   # Роли пользователей
├── regulations.md             # Регуляторные требования
├── architecture.md            # Системная архитектура
├── settlement_statuses.md     # Статусы расчётов
└── requirements_history.json  # История требований
```

## manifest.json

**Назначение:** Метаданные документов KB.

**Структура:**
```json
{
  "documents": [
    {
      "id": "products",
      "title": "Инвестиционные продукты",
      "domain": "products",
      "status": "approved",
      "priority": 100,
      "products": ["all"],
      "modules": [],
      "processes": []
    }
  ]
}
```

**Поля:**
- `id` (string) — уникальный идентификатор документа (совпадает с именем файла .md)
- `title` (string) — читаемое название
- `domain` (string) — домен (business, products, architecture, regulatory, history)
- `status` (string) — статус: `approved` (searchable) или `draft` (не searchable)
- `priority` (int) — приоритет при поиске (0-100, выше = важнее)
- `products` (array) — связанные продукты (или ["all"])
- `modules` (array) — связанные модули (или ["all"])
- `processes` (array) — связанные процессы (или ["all"])

**Рекомендации:**
- Все production документы должны иметь `status: "approved"`
- Priority 100 — критически важные документы (products, regulations)
- Priority 80-90 — важные документы (modules, processes, roles)
- Priority 70 — справочные документы (history)

## Markdown документы

### Формат

Каждый документ — markdown файл с секциями `## Header`.

**Структура:**
```markdown
# Заголовок документа

Описание документа (опционально).

## Entity Name (Aliases)

- **Описание:** ...
- **Жизненный цикл:** ...
- **Особенности сопровождения:** ...
- **Связанные модули:** ...
```

### Пример: products.md

```markdown
# Инвестиционные продукты платформы

Для каждого продукта указано: описание, жизненный цикл, тип клиента, особенности
сопровождения, учёт и отчётность, риски, комплаенс, связанные модули платформы.

## Акции

- **Описание:** долевые ценные бумаги, дающие право на долю в компании и дивиденды.
- **Жизненный цикл:** заключение сделки (trade) → подтверждение → расчёты (settlement) → зачисление/списание ценных бумаг в депозитарии → учёт позиций → дивидендные события (корпоративные действия).
- **Тип клиента:** корпоративные и институциональные клиенты, банки-контрагенты.
- **Особенности сопровождения:** контроль наличия бумаг, лимитов и денежных средств; обработка корпоративных действий; конвертация валют при расчётах.
- **Учёт и отчётность:** позиционный учёт по торговому и клиентскому портфелю; отчёт о сделках; отчёт по дивидендам.
- **Риски:** рыночный, операционный, расчётный (риск непередачи бумаг).
- **Комплаенс:** требования к лимитам, AML/KYC, запрет на инсайдерские сделки.
- **Связанные модули:** Сделки, Расчёты, Депозитарный учёт, Лимиты, Отчётность.

## Облигации

- **Описание:** долговые ценные бумаги, предполагающие выплату купонов и погашение номинала.
- **Жизненный цикл:** сделка → расчёты → купонные выплаты → погашение. Отдельная ветка — операции с частичным исполнением и несостоявшиеся расчёты (failed settlement).
- **Тип клиента:** корпоративные и институциональные клиенты, казначейство.
- **Особенности сопровождения:** накопленный купонный доход (НКД), даты фиксинга, ковенанты эмитента; повторные запросы на расчёты по несостоявшимся сделкам.
- **Учёт и отчётность:** учёт НКД, купонный график, отчёт по погашениям.
- **Риски:** кредитный, процентный, расчётный.
- **Комплаенс:** раскрытие информации, лимиты на эмитента.
- **Связанные модули:** Сделки, Расчёты, Отчётность, Мастер-данные.
```

### Пример: modules.md

```markdown
# Модули платформы сопровождения сделок

## Сделки

- **Описание:** учёт и сопровождение торговых сделок (заключение, подтверждение, исполнение).
- **Функции:** регистрация сделок, проверка лимитов, генерация подтверждений, статусная модель.
- **Интеграции:** торговые системы, риск-система, комплаенс.

## Расчёты

- **Описание:** расчёты по сделкам (settlement), включая повторные запросы и обработку failed settlement.
- **Функции:** генерация расчётных инструкций, контроль исполнения, повторные запросы, статусы расчётов.
- **Интеграции:** депозитарий, платёжная система, SWIFT.

## Депозитарный учёт

- **Описание:** учёт ценных бумаг в депозитарии (зачисление, списание, корпоративные действия).
- **Функции:** учёт позиций, обработка корпоративных действий, сверка с депозитарием.
- **Интеграции:** депозитарий, НКР.
```

### Пример: roles.md

```markdown
# Роли пользователей платформы

## Бэк-офицер

- **Описание:** операционный сотрудник, обрабатывающий расчёты и пост-трейд операции.
- **Задачи:** контроль расчётов, обработка failed settlement, подготовка отчётности.
- **Модули:** Расчёты, Депозитарный учёт, Отчётность.

## Фронт-офицер (Трейдёр)

- **Описание:** сотрудник, заключающий сделки с клиентами.
- **Задачи:** заключение сделок, контроль лимитов, работа с клиентами.
- **Модули:** Сделки, Лимиты.

## Риск-менеджер

- **Описание:** сотрудник, контролирующий риски (рыночные, кредитные, операционные).
- **Задачи:** контроль лимитов, маржирование, стресс-тестирование.
- **Модули:** Лимиты, Риски, Отчётность.
```

## requirements_history.json

**Назначение:** История требований для duplicate detection.

**Структура:**
```json
[
  {
    "id": "REQ-4521",
    "title": "Экран списка несостоявшихся расчётов по облигациям с повторным запросом",
    "intent": "feature",
    "product": "Облигации",
    "module": "Расчёты",
    "process": "Расчёты по сделкам",
    "role": "Бэк-офицер",
    "status": "approved",
    "decision": "Принято в бэклог. Реализация запланирована.",
    "reason": "Высокая ценность для бэк-офиса, повторяющийся ручной процесс.",
    "summary": "Отдельный экран со списком сделок, по которым не прошли расчёты, и кнопка повторного запроса инструкции."
  }
]
```

**Поля:**
- `id` (string) — ID требования (из Jira/Backlog)
- `title` (string) — заголовок требования
- `intent` (string) — тип обращения (feature, change, problem, clarification, incident)
- `product` (string) — продукт
- `module` (string) — модуль
- `process` (string) — процесс
- `role` (string) — роль пользователя
- `status` (string) — статус (approved, rejected, draft)
- `decision` (string) — решение (принято/отклонено)
- `reason` (string) — обоснование решения
- `summary` (string) — краткое описание

**Рекомендации:**
- Загружать из Jira/Backlog экспортом
- Включать только approved и rejected требования (для обучения)
- Обновлять периодически (раз в неделю/месяц)

## Как добавить новый документ

### Шаг 1: Создайте markdown файл

Создайте файл в `kb_seed/`:
```bash
touch kb_seed/new_document.md
```

### Шаг 2: Наполните документ

Используйте формат:
```markdown
# Заголовок документа

Описание.

## Entity Name (Aliases)

- **Описание:** ...
- **Детали:** ...
```

### Шаг 3: Добавьте в manifest.json

```json
{
  "documents": [
    ...
    {
      "id": "new_document",
      "title": "Новый документ",
      "domain": "business",
      "status": "approved",
      "priority": 80,
      "products": [],
      "modules": [],
      "processes": []
    }
  ]
}
```

### Шаг 4: Проверьте загрузку

```bash
python -c "from agent.kb.loader import kb; print(kb.stats())"
```

**Ожидаемый вывод:**
```
{'documents': 10, 'chunks': 50, 'approved': 50}
```

## Как обновить существующий документ

### Шаг 1: Отредактируйте markdown файл

```bash
nano kb_seed/products.md
```

### Шаг 2: Перезапустите агент

```bash
# Если агент запущен — перезапустите
python run.py
```

KB загружается при старте агента.

---

## Как изменить статус документа

### Временно отключить документ (draft)

Измените в `manifest.json`:
```json
{
  "id": "products",
  "status": "draft"  // было "approved"
}
```

Документ не будет searchable, но останется в KB.

### Вернуть документ (approved)

```json
{
  "id": "products",
  "status": "approved"
}
```

---

## Как изменить приоритет документа

Измените `priority` в `manifest.json`:

```json
{
  "id": "regulations",
  "priority": 100  // было 95
}
```

Выше приоритет = выше в результатах поиска.

## Best Practices

### 1. Структурируйте документы

Каждый документ должен иметь чёткую структуру:
- Заголовок `# Document Title`
- Секции `## Entity Name`
- Буллеты с ключевой информацией

### 2. Используйте aliases

Добавляйте aliases в скобках для улучшения matching:
```markdown
## Расчёты (Settlement, Settlements)
```

### 3. Включайте ключевые слова

Используйте термины, которые пользователи могут использовать:
- "failed settlement" → "несостоявшиеся расчёты"
- "back office" → "бэк-офис"
- "trade" → "сделка"

### 4. Поддерживайте актуальность

- Обновляйте KB при изменениях в платформе
- Удаляйте устаревшие документы
- Добавляйте новые продукты/модули/процессы

### 5. Проверяйте качество

Периодически проверяйте:
- Все ли документы имеют `status: "approved"`
- Нет ли дубликатов
- Актуальны ли данные

## Troubleshooting

### Проблема: Документ не загружается

**Симптомы:** `kb_stats.documents` не увеличивается

**Решение:**
1. Проверьте имя файла (должно совпадать с `id` в manifest)
2. Проверьте валидность JSON в manifest.json:
   ```bash
   python -m json.tool kb_seed/manifest.json
   ```
3. Проверьте логи загрузки

---

### Проблема: Поиск не находит документы

**Симптомы:** Поиск возвращает пустые результаты

**Решение:**
1. Проверьте, что документы имеют `status: "approved"`
2. Проверьте, что запрос содержит ключевые слова из документов
3. Проверьте ontology matching:
   ```bash
   python -c "
   from agent.kb.ontology import ontology
   print(ontology.match_product('облигации'))
   "
   ```

---

### Проблема: Дубликаты не находятся

**Симптомы:** Агент не обнаруживает похожие требования

**Решение:**
1. Проверьте, что `requirements_history.json` загружен
2. Проверьте формат записей (должны иметь title, summary, product, module)
3. Увеличьте лимит поиска в `requirements_history.py`

## Автоматизация обновления KB

### Скрипт экспорта из Jira

```python
import requests
import json

def export_requirements_from_jira():
    response = requests.get(
        "https://jira.bank.internal/rest/api/2/search",
        auth=("user", "api-token"),
        params={
            "jql": "project = DMB AND type = Requirement",
            "fields": "summary,description,status"
        }
    )
    
    requirements = []
    for issue in response.json()["issues"]:
        requirements.append({
            "id": issue["key"],
            "title": issue["fields"]["summary"],
            "status": "approved" if issue["fields"]["status"]["name"] == "Done" else "draft",
            # ... другие поля
        })
    
    with open("kb_seed/requirements_history.json", "w") as f:
        json.dump(requirements, f, ensure_ascii=False, indent=2)

export_requirements_from_jira()
```

### Cron job для периодического обновления

```bash
# Обновлять requirements_history.json каждый понедельник в 3:00
0 3 * * 1 cd /opt/agent && python scripts/export_requirements.py
```
